## 논문 선정 배경

- HyDE를 보면서 "효과는 좋은데 **쿼리마다 LLM을 한 번씩 호출**한다"는 비용이 답변 지연에 영향을 준다고 생각했어요. 짧고 모호한 질문과 긴 근거 문서 사이의 **임베딩 공간 비대칭**은 똑같이 풀고 싶은데, 그 비용을 **사용자가 기다리지 않는 곳**으로 옮길 수 없을까 하는 문제의식이 있었어요.
- HyDE가 **쿼리를 문서로** 바꿨다면, HyPE는 **문서를 질문으로** 미리 바꿔 둬요. 가설 생성을 인덱싱 시점으로 옮겨 **쿼리타임 추가 지연 0**을 달성하면서 검색 품질도 올리는지 확인하려고 정리했어요.

## 문제 정의: HyDE의 비용을 어디로 옮길까

dense retrieval의 근본 문제는 HyDE와 같아요. **짧은 질문과 긴 문서는 어휘·문체가 달라서 같은 임베딩 공간에서 잘 맞지 않아요** (question-answer gap).

HyDE는 이를 "쿼리 → 가설 문서 → 검색"으로 풀지만, **질문이 들어올 때마다 LLM을 호출**해야 해요.

| HyDE의 런타임 비용 | 영향 |
|---|---|
| 매 쿼리 LLM 호출 | latency 증가 |
| 토큰 비용 | 쿼리량에 비례해 누적 |
| 비결정성 | 같은 질문도 매번 다른 가설 문서 → 결과 불안정 |

HyPE의 출발점은 이거예요. **"비대칭은 풀되, 비용은 사용자가 기다리지 않는 시점(인덱싱)으로 옮기자."**

## 핵심 아이디어: 가설 질문을 거쳐 검색

검색이 "질문 ↔ 문서"(모양이 다름)가 아니라 **"질문 ↔ 질문"(모양이 같음)**이 되도록, 문서 쪽에 예상 질문을 미리 붙여 둬요.

| 단계 | 시점 | 구성요소 | 역할 |
|---|---|---|---|
| 1. Generate | **인덱싱 (오프라인, 1회)** | LLM | 청크마다 "이 청크가 답이 될 가설 질문" N개 생성 |
| 2. Encode & Store | 인덱싱 | 임베딩 인코더 | 가설 질문들을 벡터화해 원본 청크에 연결해 저장 |
| 3. Embed query | **쿼리타임 (실시간)** | 임베딩 인코더 | 사용자 질문만 벡터화 (LLM 호출 없음) |
| 4. Search | 쿼리타임 | vector similarity | 저장된 가설 질문과 비교 → 가장 닮은 질문에 연결된 청크 반환 |

- **Relevance 모델링**은 LLM이 맡지만 **인덱싱 때 한 번만** 해요. 라벨도 필요 없어요.
- **Grounding**: 가설 질문이 실제 청크에 직접 연결돼 있어서, 검색 결과는 항상 실제 코퍼스에 묶여 있어요.

## 인덱싱 파이프라인

HyDE가 task별로 "답변 문서를 써라"라고 지시했다면, HyPE는 인덱싱 때 **"이 청크가 답할 질문을 만들어라"**라고 지시해요.

```text
📖 청크: "1545년 4월 28일, 한 사내아이가 서울 건천동에서 태어났다…"
        │
        ▼  LLM: "이 글이 답이 될 수 있는 질문을 여러 개 생성하라"
        ├─ "이순신은 언제 태어났는가?"
        ├─ "이순신의 출생지는 어디인가?"
        └─ "이순신은 몇 년도에 태어났나?"
        │
        ▼  각 질문을 임베딩 → 원본 청크에 연결해 저장 💾
```

결과적으로 벡터 스토어는 **"질문 → 청크" 매핑의 모음**이 돼요. 한 청크에 여러 질문이 연결되므로, 다양한 표현의 사용자 질문을 폭넓게 받아낼 수 있어요 (멀티벡터 성격).

## 실험 결과

6개 공개 데이터셋에서 RAG 검색 품질 지표(context precision, claim recall)로 평가했어요.

| 지표 | 표준 방식 대비 |
|---|---|
| Context precision | **최대 +42%p** |
| Claim recall | **최대 +45%p** |
| 쿼리타임 추가 지연 | **없음** |

re-ranking, multi-vector retrieval 같은 다른 RAG 기법과 함께 쓸 수 있어요.

## 핵심 통찰

- 한 줄로 요약하면 **"비대칭 해소 비용을 쿼리타임에서 인덱스타임으로 옮긴다"**예요. HyDE와 같은 통찰(가설 콘텐츠로 분포를 맞춘다)을 **비용 구조만 바꿔** 재배치한 거예요.
- 검색을 **question-to-question 매칭**으로 바꿨다는 점이 중요해요. 같은 종류(질문)끼리 비교하니 임베딩 공간 정렬이 자연스럽고, 한 청크에 여러 질문이 붙어 질문 표현의 다양성도 흡수해요.
- 가설을 미리 고정해 저장하므로, HyDE의 비결정성 문제도 사라지고 **결과가 일관돼요.**

## 시사점

**① 지연 부담 없이 적용 가능**: 가설 질문 생성을 문서 파싱 → 검색 인덱스 적재 경로에 넣으면, 쿼리타임은 그대로 두고 검색 정확도를 올릴 수 있어요.

**② 트레이드오프**

- **인덱싱 비용·시간 증가**: 청크 수 × 질문 N개만큼 LLM 호출이 생겨요. 단, 1회성·오프라인이에요.
- **저장 공간 증가**: 청크마다 질문 벡터가 여러 개라 인덱스가 커져요.
- **문서 변경 시 재생성**: 문서가 바뀌면 그 청크의 가설 질문도 다시 만들어야 해요.
- **한국어 도메인 실측 필요**: 논문은 주로 영어 데이터셋 기준이라, 한국어 문서에서는 별도 실험이 필요해요.

**③ HyDE와의 선택 기준**: 쿼리량이 많고 지연에 민감하면 HyPE, 코퍼스가 자주 바뀌고 인덱싱 비용을 줄이고 싶으면 HyDE가 유리해요.

## 정리

- HyPE는 HyDE의 쿼리타임 LLM 호출을 **인덱스타임 가설 질문 생성**으로 뒤집어, **추가 지연 없이** question-answer gap을 줄여요.
- LLM은 인덱싱 때 relevance를 모델링하고, 저장된 질문-청크 매핑이 grounding을 맡아요. 검색은 질문 ↔ 질문 매칭으로 단순해져요.
- 6개 데이터셋에서 context precision 최대 **+42%p**, claim recall 최대 **+45%p**.
- 한계는 인덱싱 비용·저장 공간 증가, 문서 갱신 시 재생성, 한국어 실측 필요예요.
- HyDE ↔ HyPE는 **같은 통찰, 다른 비용 시점**이에요. 지연에 민감한 환경이라면 HyPE가 잘 맞아요.
