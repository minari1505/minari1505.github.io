### 논문 선정 배경

- HyDE를 살펴보면서 "효과는 좋은데 *쿼리마다 LLM 호출 1회*"라는 비용이 채팅 답변을 뱉는 시간 지연에 영향을 미친다고 생각했습니다. 짧고 모호한 사용자 질문과 긴 근거 문서 사이의 *임베딩 공간 비대칭*은 똑같이 풀고 싶은데, 그 비용을 *사용자 대기시간이 아닌 곳*으로 옮길 수 없을까 하는 문제의식이 있었습니다.
- HyDE가 *쿼리를 문서로* 바꿨다면, HyPE는 *문서를 질문으로* 미리 바꿔 둡니다. 가설 생성을 인덱싱 시점으로 밀어 넣어 **쿼리타임 추가 지연 0**을 달성하는지, 그러면서도 retrieval 품질을 끌어올리는지 확인하고자 정리했습니다.

### 한 눈에 보기

- **저자/소속:** Domen Vake, Jernej Vičič, Aleksandar Tošić (InnoRenew CoE / University of Primorska)
- **출처:** IEEE Access (2025), SSRN 5139335
- **핵심 주장:** 가설 콘텐츠 생성을 인덱싱 시점으로 옮기면, 쿼리타임 LLM 호출 없이도(=지연 추가 없이) retrieval의 context precision·recall을 크게 끌어올릴 수 있음
- **핵심 개념:** Hypothetical Prompt Embeddings (HyPE), question-to-question matching, index-time generation
- **방법론:** 인덱싱 시 각 청크마다 *그 청크가 답이 될 가설 질문* 다수 생성 → 질문들을 임베딩해 청크에 연결 저장. 쿼리 시엔 실제 질문만 임베딩해 *질문↔질문* 검색
- **포지션:** HyDE의 *런타임 query rewriting*을 *인덱스타임 document-to-question rewriting*으로 뒤집어, 비용을 사용자 대기시간 밖으로 이동

### 문제 정의 - HyDE의 비용을 어디로 옮길 것인가

Dense retrieval의 근본 문제는 HyDE와 동일: *짧은 질문과 긴 문서는 어휘·문체가 달라 같은 임베딩 공간에서 잘 안 맞는다(question-answer gap).*

HyDE는 이를 *쿼리 → 가설 문서 → 검색*으로 풀지만, **질문이 들어올 때마다 LLM을 호출**해야함. 이건 세 가지 비용을 만듦.

| **HyDE의 런타임 비용** | **영향** |
| --- | --- |
| 매 쿼리 LLM 호출 | latency 증가 |
| 토큰 비용 | 쿼리량에 비례해 누적 |
| 비결정성 | 같은 질문도 매번 다른 가설 문서 → 결과 불안정 |

HyPE의 출발점: *"비대칭은 풀되, 그 비용을 사용자가 기다리지 않는 시점(인덱싱)으로 옮기자."*

### HyPE 핵심 아이디어 - Pivot through Hypothetical Questions

검색이 *질문↔문서*(모양 다름)가 아니라 **질문↔질문**(모양 같음)이 되도록, 문서 쪽에 "예상 질문"을 미리 붙여 둔다.

두 단계로 책임이 분리됩니다.

| **단계** | **시점** | **구성요소** | **역할** |
| --- | --- | --- | --- |
| 1. Generate | **인덱싱 (오프라인, 1회)** | LLM | 각 청크마다 *그 청크가 답이 될 가설 질문* N개 생성 |
| 2. Encode & Store | 인덱싱 | 임베딩 인코더 | 가설 질문들을 벡터화해 *원본 청크에 연결*하여 저장 (벡터 스토어가 Q–청크 매핑이 됨) |
| 3. Embed query | **쿼리타임 (실시간)** | 임베딩 인코더 | 사용자의 실제 질문만 벡터화 (LLM 호출 없음) |
| 4. Search | 쿼리타임 | vector similarity | 저장된 *가설 질문*들과 비교 → 가장 닮은 질문에 연결된 청크 retrieval |

핵심 디커플링은 HyDE와 같지만 *시점*이 다릅니다.

1. **Relevance 모델링** — LLM이 담당하되 **인덱싱 시점에 한 번**만 (라벨 불요)
2. **Grounding** — 가설 질문을 *실제 청크에 직접 연결*해 저장하므로, 검색 결과는 항상 실재 코퍼스에 묶임

이 "시점 이동" 덕분에 *쿼리타임 추가 비용 0*이면서 비대칭을 해소합니다.

### 인덱싱 파이프라인 / prompt

HyDE가 *task별로 "답변 문서를 써라"* 지시를 줬다면, HyPE는 *인덱싱 시점에 "이 청크가 답할 질문을 만들어라"* 지시를 전달.

```py
📖 청크: "1545년 4월 28일, 한 사내아이가 서울 건천동에서 태어났다…"
        │
        ▼  LLM: "이 글이 답이 될 수 있는 질문을 여러 개 생성하라"
        ├─ "이순신은 언제 태어났는가?"
        ├─ "이순신의 출생지는 어디인가?"
        └─ "이순신은 몇 년도에 태어났나?"
        │
        ▼  각 질문을 임베딩 → 원본 청크에 연결해 저장 💾
```

> 결과적으로 벡터 스토어는 *"질문 → 청크"* 매핑들의 모음이 됨. 한 청크가 여러 질문과 연결되어 *다양한 표현의 사용자 질문*을 폭넓게 커버(멀티벡터 성격).

### 실험 결과

**평가 규모:** 6개 공통 데이터셋

- **평가 지표:** retrieval context precision, claim recall (RAG 검색 품질 평가 지표)

| **지표** | **표준 방식 대비 향상** |
| --- | --- |
| Context precision | **최대 +42%포인트** |
| Claim recall | **최대 +45%포인트** |
| 쿼리타임 추가 지연 | **없음 (0)** |

- **호환성:** re-ranking, multi-vector retrieval 등 다른 RAG 기법과 함께 사용 가능 (배타적이지 않음)

### 핵심 통찰

HyPE의 효과 한 줄 요약 : *"비대칭 해소 비용을 쿼리타임에서 인덱스타임으로 이전한다".*<br>
HyDE가 *런타임 query→document rewriting*이라면,<br>
HyPE는 *인덱스타임 document→question rewriting*으로, 같은 통찰(가설 콘텐츠로 분포를 맞춘다)을 **비용 구조만 바꿔** 재배치한 것.

주목할 점은 **검색을 question-to-question 매칭으로 환원**했다는 것.<br>
사용자 질문과 **같은 종류(질문)**끼리 비교하므로 임베딩 공간 정렬이 자연스럽고, 한 청크에 여러 가설 질문이 달려 *질문 표현의 다양성*까지 흡수할 수 있음.<br>
HyDE의 비결정성(매번 다른 가설 문서) 문제도, 가설을 미리 고정 저장하므로 **결과 일관성**이 확보됨.

### 시사점

**① RAG에 지연 부담 없이 적용 가능**

가설 생성을 문서 파서 → 검색 인덱스 적재 경로(인덱싱)에 넣으면, **쿼리타임은 그대로 두면서** 검색 정확도를 올릴 수 있음

② **trade-off 명확화 필요**

- (a) **인덱싱 비용·시간 증가**: 청크 수 × 질문 N개만큼 LLM 호출이 인덱싱 때 발생 (단, 1회성·오프라인).
- (b) **저장 공간 증가**: 청크당 여러 질문 벡터 저장 → 인덱스 크기 확대.
- (c) **콘텐츠 변경 시 재생성**: 문서가 갱신되면 해당 청크의 가설 질문도 다시 생성해야 함.
- (d) **국문 도메인 실측 필요**: 논문은 6개 데이터셋(주로 영어권 추정) 기준 — 우리 한국어 문서에서 별도 ablation 권장.

③ **HyDE와의 선택 기준**

*쿼리량 많고 지연 민감 시* HyPE, *코퍼스가 자주 바뀌고 인덱싱 비용을 줄이고 싶으면* HyDE가 유리

### 정리

- HyPE는 HyDE의 *쿼리타임 LLM 호출*을 *인덱스타임 가설 질문 생성*으로 뒤집어, **쿼리타임 추가 지연 0**으로 question-answer gap을 해소
- LLM은 *인덱싱 시 relevance 모델링*, 저장된 질문-청크 매핑이 *grounding* 담당 → 검색이 **질문↔질문 매칭**으로 단순화
- 6개 데이터셋에서 context precision 최대 **+42%p**, claim recall 최대 **+45%p**, **지연 추가 없음**
- 한계: 인덱싱 비용·저장공간 증가, 문서 갱신 시 재생성, 국문 도메인 실측 필요
- HyDE ↔ HyPE는 *같은 통찰, 다른 비용 시점* — 우리처럼 지연 민감한 환경엔 HyPE가 적합
