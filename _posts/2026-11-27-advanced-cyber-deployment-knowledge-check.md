OpenAI PartnerU의 **Advanced Cyber Deployment: Orientation, Use Cases and Deployment Readiness** 과정에서 제출한 지식 점검 5문항을 정리했다. 각 문항은 Sana에 제출한 뒤 표시된 정답 및 공식 피드백을 확인했다.

## 1. Daybreak 보안 스택의 세 계층과 역할 연결

**문제 번역**  
Daybreak 스택의 각 계층을 주된 역할과 연결하라.

**정답**

| 계층 | 역할 |
|---|---|
| The model (모델) | 복잡한 사이버·소프트웨어 보안 작업에 고도화된 추론 제공 |
| Codex | 추론을 코드, 도구, 테스트 및 사람의 검토와 연결 |
| Codex Security | 전문적인 조사, 검증, 수정 및 보고 워크플로 구성 |

**정답과 오답의 이유**

- 모델은 추론 계층이다. 코드 저장소에 직접 연결하거나 보안 업무 절차를 관리하는 역할과 혼동하면 안 된다.
- Codex는 모델의 추론을 코드·도구·테스트·사람의 검토가 있는 실행 환경에 연결한다. 그 자체가 전문 보안 조사 워크플로를 뜻하지는 않는다.
- Codex Security는 보안 조사와 검증, 수정 준비, 결과 보고를 조직하는 전문 에이전트 계층이다. 일반 추론 모델이나 범용 실행 하네스와 역할이 다르다.
- 따라서 계층을 서로 바꾸어 연결하면 추론, 실행, 보안 업무 오케스트레이션의 책임 경계가 흐려진다.

**공식 해설 번역**  
세 쌍을 모두 올바르게 연결했다.

**핵심 암기 포인트**  
**모델은 추론, Codex는 코드·도구 실행과 사람 검토 연결, Codex Security는 보안 업무 워크플로 구성.**

**AI 개발 실무 추가 설명**  
에이전트형 시스템을 설계할 때 모델, 실행 하네스, 업무별 에이전트를 분리하면 권한과 책임을 명확히 할 수 있다. 모델의 출력이 곧 실행 승인이나 보안 검증 완료를 의미하지 않는다.

## 2. AppSec 저장소 분석에 적합한 경로

**문제 번역**  
AppSec 팀이 소유한 저장소의 취약점을 찾아 분류하고, 영향받은 코드를 검토한 뒤 방어적 패치를 검증하려 한다. 어느 경로가 가장 적절한 시작점인가?

1. 전문 사이버 작업이므로 저장소 분석도 항상 Daybreak Red로 시작한다.
2. 저장소에서 공격 체인 검증을 시작한 뒤 경로를 결정한다.
3. 탐지·분류·검토·패치 검증을 포괄하는 방어 작업이므로 Daybreak Blue로 시작한다. ✅
4. 작업자가 현재 사용할 수 있는 경로를 기준으로 둘 중 하나를 선택한다.

**정답과 오답의 이유**

- **1번 ❌** 모든 보안 작업이 Red 대상은 아니다. 소유 저장소에서 취약점을 찾아 방어적으로 수정하는 일반적인 AppSec 흐름은 Blue에 맞는다.
- **2번 ❌** 경로 선택과 승인 확인을 미룬 채 검증부터 시작하면 안 된다. 작업의 성격과 허용 범위를 먼저 판단해야 한다.
- **3번 ✅** 발견부터 분류, 코드 검토, 방어적 수정 검증까지 이어지는 광범위한 방어 업무에 적합하다.
- **4번 ❌** 도구를 쓸 수 있는지 여부만으로 경로를 고르면 업무 목적과 승인 범위를 놓친다.

**공식 해설 번역**  
요구되는 작업은 Daybreak Blue에 배정되는 광범위한 방어 워크플로와 일치한다. Daybreak Red는 모든 사이버 작업의 기본 경로가 아니라 승인된 전문 워크플로에 사용한다.

**핵심 암기 포인트**  
**일반적인 방어형 AppSec는 Blue, 승인된 전문 공격 테스트는 Red.**

**AI 개발 실무 추가 설명**  
도구 선택은 모델 성능만의 문제가 아니다. 대상의 소유권, 작업 목적, 허용된 행위, 검토 책임을 먼저 확인하고 그에 맞는 실행 경로를 선택해야 한다.

## 3. 모니터링 중단 후의 대응

**문제 번역**  
지원되는 GPT-6 Astra API 워크플로가 일부 출력을 만든 뒤 misalignment monitoring에 의해 중단됐다. 동료가 작업은 승인됐으니 자동 재시도하자고 제안한다. 어떻게 해야 하는가?

1. 모니터링 플래그만으로 운영자 의도가 입증됐다고 보고 정책 위반으로 확정한다.
2. 원래 요청은 괜찮았다는 증거로 일부 출력을 보존하고, 세부 정보를 줄여 같은 대화를 재시도한다.
3. 이후 작업이 안전하게 되돌려졌다는 증거로 중단 알림을 남기고 부분 출력으로 검토를 완료한다.
4. 추가 작업을 중단하고 기록을 보존한 뒤, 담당 운영자가 이미 완료된 작업과 의도한 작업을 검토하게 한다. ✅

**정답과 오답의 이유**

- **1번 ❌** 모니터링 중단은 그 자체로 운영자의 의도나 정책 위반을 입증하지 않는다.
- **2번 ❌** 승인됐다는 사실만으로 중단된 대화를 자동 재개할 수 없다. 표현을 바꾸어 재시도하는 것도 적절하지 않다.
- **3번 ❌** 부분 출력은 검토 완료의 근거가 아니며, 중단이 이미 수행된 작업을 되돌렸다는 뜻도 아니다.
- **4번 ✅** 추가 실행을 멈추고 기록과 완료된 작업을 검토해 상황을 판단한다.

**공식 해설 번역**  
승인이 있었다고 해서 모니터링으로 중단된 대화를 다시 진행할 수 있는 것은 아니다. 이미 완료된 작업을 검토해야 한다. 중단은 이전 작업을 롤백하지 않으며, 위반이나 보안 검토 완료를 입증하지도 않는다.

**핵심 암기 포인트**  
**중단은 자동 롤백도, 위반 확정도, 검토 완료도 아니다. 멈추고 기록과 완료된 작업을 사람이 확인한다.**

**AI 개발 실무 추가 설명**  
에이전트의 부분 실행을 고려해 도구 호출 로그, 변경 파일, 외부 시스템 영향, 생성된 산출물을 확인해야 한다. 재시도는 부작용을 중복 발생시킬 수 있으므로 멱등성, 실행 이력, 승인 상태를 확인하기 전에 자동화하지 않는다.

## 4. 외부 대상 레드팀 테스트의 준비 조건

**문제 번역**  
고객이 외부 시스템을 대상으로 레드팀 테스트를 원한다. 기술적으로는 Daybreak Red가 적합하지만 고객은 대상의 소유권이나 테스트 권한을 확인하지 않았다. 어떻게 해야 하는가?

1. 승인이 확인될 때까지 Daybreak Blue로 시작한다.
2. 레드팀은 전문 작업이므로 Daybreak Red로 보낸다.
3. 정찰만 하면 되므로 테스트를 진행한다.
4. 경로를 선택하거나 실행하기 전에 소유권, 승인, 범위, 사람의 검토 경로를 확인한다. ✅

**정답과 오답의 이유**

- **1번 ❌** Blue로 바꾼다고 승인·소유권 문제가 해결되지는 않는다. 먼저 대상과 허용 범위를 확인해야 한다.
- **2번 ❌** 기술적 적합성만으로 실행 권한이 생기지 않는다.
- **3번 ❌** 정찰도 대상에 대한 행위이므로 승인과 범위가 필요하다.
- **4번 ✅** 경로 선택 전에 권한과 범위, 책임자 및 검토 절차를 확인하는 것이 준비 조건이다.

**공식 해설 번역**  
기술적 작업은 Daybreak Red에 해당할 수 있지만, 현재 워크플로는 진행 준비가 되지 않았다. 실행 전에 승인, 범위, 소유권, 사람의 검토 경로가 명확해야 한다.

**핵심 암기 포인트**  
**기술적 적합성보다 먼저 권한·범위·소유권·검토 책임을 확인한다.**

**AI 개발 실무 추가 설명**  
보안 자동화에서는 허용된 대상의 식별자와 범위를 실행 설정에 고정하고, 외부 쓰기·네트워크 접근을 제한해야 한다. 요청자의 말만으로 권한을 추정하지 말고, 증빙과 승인 경로를 확인한다.

## 5. 고객 생애주기 순서

**문제 번역**  
Daybreak 고객의 예상 생애주기를 올바른 순서로 고르라.

1. SDLC에 통합 → 의존성 감사 → 취약점 패치 → 중요 저장소 스캔
2. 취약점 패치 → 중요 저장소 스캔 → SDLC 통합 → 의존성 감사
3. 의존성 감사 → SDLC 통합 → 중요 저장소 스캔 → 취약점 패치
4. 중요 저장소 실행/스캔 → 취약점 패치 → 의존성 감사 → SDLC에 통합 ✅

**정답과 오답의 이유**

- **1번 ❌** 예방 단계인 통합을 시작점으로 놓고 발견·수정 순서를 뒤집었다.
- **2번 ❌** 취약점 발견 전 패치를 시작하며, 이후 단계도 올바른 순서가 아니다.
- **3번 ❌** 의존성 감사와 SDLC 통합이 저장소의 초기 발견·수정보다 앞서 있다.
- **4번 ✅** 저장소를 스캔해 문제를 발견하고, 수정한 뒤, 의존성을 감사하고, 마지막으로 PR 흐름에 통합해 재발을 예방한다.

**공식 해설 번역**  
생애주기는 저장소 분석으로 발견하는 단계에서 시작해 수정으로 이어지고, 그다음 의존성 검토를 거쳐 마지막으로 PR 통합을 통한 예방 단계로 진행한다.

**핵심 암기 포인트**  
**Run → Patch → Audit → Embed**  
실행/발견 → 패치 → 의존성 감사 → SDLC 통합·예방.

**AI 개발 실무 추가 설명**  
초기에는 핵심 저장소에서 실제 취약점과 검토 과정을 파악하고, 수정 및 의존성 관리 역량을 갖춘 뒤 CI/PR에 통합하는 점진적 도입이 적절하다. PR 체크는 증거와 상태를 제공하지만, 소유자 승인 및 병합 정책을 대신하지 않는다.
