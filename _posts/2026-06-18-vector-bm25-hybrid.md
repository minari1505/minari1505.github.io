#### **참고 자료**

- 단일 논문이 아닌 **정보검색(IR)의 정석 기법 조합**
  - **BM25**: Robertson & Zaragoza, *The Probabilistic Relevance Framework: BM25 and Beyond* (Foundations and Trends in IR, 2009) — 원형은 1994년 Okapi BM25
  - **순위 융합(RRF)**: Cormack, Clarke, Büttcher, *Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods* (SIGIR 2009)
  - **RAG에서의 현대적 재조명**: Sawarkar et al., *Blended RAG* (IBM, arXiv 2404.07220, 2024) — Dense + Sparse(BM25/SPLADE) 하이브리드가 검색 정확도 최상위
  - 엔지니어링 레퍼런스: OpenSearch Hybrid Search, Anthropic Contextual Retrieval(여기서도 BM25 레이어가 핵심)

### **선정 배경**

- 벡터(dense) 검색은 "의미가 비슷한" 문서는 잘 찾지만, **정확히 같은 토큰**(회사명 `SKT`, 지표명 `영업이익`, 숫자 `4,095`, 코드 `326030`)을 놓치는 약점이 있습니다. 임베딩은 의미를 *압축*하느라 희귀 고유명사·숫자의 정확매칭이 흐려지기 때문입니다.
- 우리 도메인은 **한국어 문서**라 정확매칭이 답의 정확도를 좌우합니다("SKT" vs "SK스퀘어", "연결" vs "별도", 특정 분기 숫자). 의미 검색의 약점을 *어휘 검색*으로 메우되, **재임베딩 없이 + 지연 없이** 적용할 수 있는지 확인하고자 정리했습니다.

### **한 눈에 보기**

- **출처:** BM25(2009/1994), RRF(SIGIR 2009), Blended RAG(2024) 등 — 표준 IR 기법
- **핵심 주장:** 의미(dense)와 어휘(sparse/BM25) 검색은 **서로 다른 실패를 한다.** 두 결과를 합치면 각자의 약점을 메워 검색 정확도가 오른다
- **핵심 개념:** BM25(확률적 어휘 매칭), dense vector(의미 매칭), score/rank fusion(RRF 등)
- **방법론:** 같은 질의를 ① 벡터 검색 ② BM25 검색으로 각각 돌린 뒤, 두 점수/순위를 융합해 최종 top-K를 만든다
- **포지션:** 새 모델·새 임베딩이 아니라, **이미 있는 인덱스 위에 어휘 검색 한 갈래를 더해 합치는** 검색 단계 보강

### **문제 정의 — 벡터 검색은 무엇을 놓치는가**

Dense 검색의 강점(의미 유사)이 그대로 약점이 됨. 의미로 뭉뚱그리느라 **정확한 토큰**을 흘리는 문제 발생

| **벡터 단독의 약점** | **증상** |
| --- | --- |
| 희귀 고유명사 | "SKT"를 "통신사 일반"으로 흐릿하게 매핑 |
| 숫자·코드 정확매칭 | "4,095", "326030"을 식별 못 함 |
| 동음이의·표기 차이 | "연결/별도", "영업이익/영업손익" 혼동 |

BM25는 정반대 성격. 의미는 모르지만 **토큰이 정확히 겹치면** 강하게 매칭 → 둘은 *상보적*

### **핵심 아이디어 — 의미와 어휘를 둘 다 쓰고, 합친다**

BM25: 점수를 매기는 확률적 어휘 검색. **"질의 단어가 문서에 얼마나·얼마나 희귀하게 나오는가"**

| **BM25 요소** | **의미** |
| --- | --- |
| TF(빈도) 포화 | 단어가 많이 나올수록 점수↑, 단 **포화**(과다 반복은 가중 제한) |
| IDF(희귀도) | 흔한 단어는 낮게, "엑스코프리"처럼 희귀한 단어는 높게 |
| 길이 정규화 | 긴 문서가 단지 길어서 유리해지지 않게 보정 |

하이브리드는 같은 질의를 두 갈래로 돌려 융합함

```json
🙋 질의: "SKT 1분기 영업이익"
   │
   ├─▶ ① Dense(벡터) 검색 → 의미 유사 청크 순위
   │
   └─▶ ② BM25(어휘) 검색 → "SKT","영업이익" 토큰 정확매칭 순위
   │
   ▼  ③ Fusion (RRF 또는 가중합)
      RRF: score = Σ 1/(k + rank_i)  ← 각 검색의 순위를 합산
   │
   ▼  최종 top-K (의미+어휘 모두 반영)
```

> RRF는 **점수 스케일이 다른 두 검색을 순위로 통일**해 합치기 때문에 튜닝이 단순<br>
> (OpenSearch는 가중 점수 결합·RRF 둘 다 지원)

### **효과 (검색 정확도)**

- **Anthropic Contextual Retrieval**: 임베딩 단독 검색 실패율 3.7% → **BM25 결합 시 2.9%** (전체 기준 -35% → **49%**). 즉 **BM25 레이어 추가만으로 실패가 추가로 크게 감소**
- **Blended RAG(IBM, 2024)**: Dense + Sparse(BM25/SPLADE) 하이브리드가 단일 검색 대비 retrieval 정확도 최상위. 정확매칭이 중요한 질의에서 특히 이득
- **지연**: BM25는 OpenSearch 내장 역색인이라 쿼리 1회로 처리 → **추가 지연 사실상 0**, **추가 LLM 호출 0**

### **핵심 통찰**

하이브리드의 효과 한 줄 요약: *"의미 검색과 어휘 검색은 서로 다른 실패를 하므로, 합치면 실패가 겹치지 않고 메워진다."*

HyPE/Contextual Retrieval이 *인덱싱 시점에 콘텐츠를 가공*해 품질을 올렸다면, 하이브리드는 **콘텐츠를 안 건드리고 검색 단계에서 두 신호를 합치는** 직교적(orthogonal) 보강.<br>
그래서 다른 기법들과 배타적이지 않고 **함께 쌓을 수 있음.** 또한 임베딩(비싼 자산)을 그대로 둔 채 어휘 검색만 얹으므로, **투입 대비 효과(특히 정확매칭)와 비용 구조가 가장 유리함**.

### **시사점**

**① 재임베딩 0, 지연 ≈0으로 적용 가능**

우리 매핑은 `"text": {"type":"text"}`라 BM25 색인이 이미 잡혀 있을 가능성이 높음. 그렇다면 검색 모듈의 `function_score`에 BM25 `match` 항을 더해 융합하기만 하면 됨(analyzer만 먼저 확인 — 경우 B면 벡터는 재사용하고 BM25 색인만 재빌드)

② **우리 도메인에 직접적**

회사 코드/지표명/분기 숫자의 정확매칭이 강해져, "SKT 영업이익"에서 엉뚱한 회사·기간 청크가 끌려오는 문제를 검색 단에서 줄임. 구조화 근거 전달(작업 ①)과 **상보적** — 검색이 맞는 청크를 데려오고, 구조화 근거가 청크 안에서 맞는 값을 고르게 함

③ **주의/튜닝 포인트**

- (a) **한국어 형태소 분석기**: BM25 품질은 analyzer(예: Nori)에 좌우됨 → 토크나이저 확인·실측 필요.
- (b) **융합 방식·가중치**: RRF(견고, 기본 추천) vs 가중 점수합(미세조정 가능). dense:sparse 비중은 우리 데이터로 ablation.
- (c) **순수 BM25 하이브리드**이지 Contextual BM25(맥락 주입=재색인)는 아님 — 범위 혼동 주의.

### **정리**

- Vector + BM25 하이브리드는 **의미 검색(dense)과 어휘 검색(BM25)을 각각 돌려 융합(RRF/가중합)** 하는 표준 IR 기법
- 효과: 정확매칭(회사·지표·숫자) 보강으로 검색 실패↓ (Anthropic: BM25 결합 시 -35%→-49%), **재임베딩·추가 LLM 호출·지연 없음**
- 한계: 한국어 analyzer 의존, 융합 가중치 튜닝 필요
- 우리 환경 적용: 매핑상 text가 이미 색인돼 있어 **재임베딩 없이 검색 쿼리만 하이브리드로** 전환 가능 → 구조화 근거 전달과 함께 "재임베딩 0·지연 0" 묶음의 양대 축
- HyPE/Contextual Retrieval ↔ 하이브리드: 앞은 *콘텐츠를 인덱스 시점에 가공*, 하이브리드는 *검색 시점에 신호를 융합* — 직교적이라 **함께 쌓을 수 있음**
