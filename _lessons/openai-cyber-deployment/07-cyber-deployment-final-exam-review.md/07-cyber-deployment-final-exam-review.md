# OpenAI Cyber Practitioner 기말 퀴즈 해설 (2/2)

브라우저에서 문항별 답안을 제출한 뒤 공개된 정답과 공식 해설을 확인해 정리했어요. 총 **20문항 중 20문항 정답(100%)**입니다. 각 문항의 선택지는 의미를 한국어로 옮겼고, 정답뿐 아니라 오답이 놓치는 경계도 함께 설명합니다.

> 공식 해설은 원문의 뜻을 유지해 한국어로 번역·요약했어요. 정답 번호는 이 퀴즈 화면에 표시된 선택지 순서 기준입니다.

## 1번. 같은 승인 범위를 더 깊게 검토하려면?

**문제:** 고객이 소유한 중요 저장소에서 Codex Security 플러그인으로 표준 스캔을 마쳤고, 추가 검토 여력도 있다. 승인된 동일 범위를 더 철저히 살펴보려면 어떤 워크플로우가 적절할까?

**정답: 4번 ✅ 심층 보안 스캔을 실행한다.**

**선택지 분석**

- 1번 ❌ 표준 스캔을 다시 실행해 두 번의 결과를 비교한다 — 검토 깊이를 높여 달라는 요구에 같은 깊이의 반복은 맞지 않는다.
- 2번 ❌ 코드 변경 보안 리뷰를 한다 — 특정 변경(diff)이 제시된 것이 아니라 동일 저장소 범위의 더 포괄적인 분석을 원한다.
- 3번 ❌ 발견 항목을 수정·검증한다 — 아직 수정이 승인된 단계가 아니다. 우선 검토 깊이를 늘리는 상황이다.
- 4번 ✅ 동일한 승인 범위에서 더 포괄적인 분석을 수행한다. 리뷰어 여력과 증거 기대치도 충족된다.

**공식 해설 번역:** 동일한 승인 범위를 더 포괄적으로 분석해야 하고 고객이 리뷰어 여력과 증거 기대치를 갖췄다면 심층 보안 스캔이 적절하다.

**핵심 암기 포인트:** 같은 범위에서 분석 깊이를 높이는 요구는 심층 스캔으로 대응한다.

**AI 개발 실무 추가 설명:** 분석 강도를 바꾸더라도 저장소·브랜치·리비전 등 승인 범위가 그대로인지 확인하고, 더 많은 결과를 검토할 사람과 시간을 확보한다.

**공식 해설 출처:** Codex Security Workflow Patterns · **누적 정답률:** 1/20 · 100%

## 2번. 소스 근거와 런타임 증명을 구분하기

**문제:** PR이 인가 로직을 바꿨다. 리뷰어는 diff와 관련 소스 파일을 봤지만 런타임 테스트는 승인되지 않았다. 증거를 어떻게 기술해야 할까?

**정답: 4번 ✅ 소스에서 확인한 사실과 뒷받침되는 추론을 기록하고, 런타임 동작은 아직 증명되지 않은 공백으로 명시한다.**

**선택지 분석**

- 1번 ❌ 승인된 런타임 재현이 없으니 오탐이라고 한다 — 테스트를 하지 않았다는 사실은 오탐이라는 증거가 아니다.
- 2번 ❌ 소스가 동작을 강하게 예측하므로 런타임 증명이라고 한다 — 코드 맥락의 추론은 실제 실행 관찰과 다르다.
- 3번 ❌ 보안 민감 변경이므로 검증 완료로 본다 — 변경의 민감도만으로 취약점이 입증되지는 않는다.
- 4번 ✅ 확인된 소스 사실·합리적 추론과 미검증 런타임 동작을 분리한다.

**공식 해설 번역:** 소스 증거는 사실과 합리적 추론을 뒷받침할 수 있지만, 런타임 증명에는 승인된 실행과 관찰이 필요하다. 시험하지 않은 부분은 증명 공백으로 기록한다.

**핵심 암기 포인트:** 소스 근거 ≠ 런타임 증명. 테스트 미수행 ≠ 오탐.

**AI 개발 실무 추가 설명:** 보안 리뷰 기록에는 코드 위치, 관찰된 사실, 추론, 재현 여부, 미확인 조건을 별도 필드로 남긴다. 권한 없는 테스트로 증거 공백을 메우지 않는다.

**공식 해설 출처:** Codex Security Workflow Patterns · **누적 정답률:** 2/20 · 100%

## 3번. 수정이 승인된 finding의 다음 단계

**문제:** AppSec이 finding을 수정 대상으로 수용했다. 고객은 최소 패치, 집중 테스트, 재검증 증거와 엔지니어링 리뷰 자료를 원한다. 어떤 워크플로우가 맞을까?

**정답: 3번 ✅ 범위가 제한된 패치·집중 테스트·재검증 자료를 준비해 수정 내용을 검증한다.**

**선택지 분석**

- 1번 ❌ 심층 스캔부터 다시 수행한다 — 이미 수정 대상으로 수용된 finding을 처리하려는 단계와 다르다.
- 2번 ❌ 저장소를 다시 스캔한다 — 재검색은 수정·집중 테스트·재검증 요청을 해결하지 않는다.
- 3번 ✅ 제한된 수정과 검증, 리뷰 인계를 준비하는 Fix and Verify 패턴이다.
- 4번 ❌ 수용된 finding을 새 diff 리뷰로 되돌린다 — 목적은 변경 검토 자체가 아니라 승인된 수정과 검증이다.

**공식 해설 번역:** 수정 대상이 수용된 뒤에는 Fix and Verify가 적절하다. 범위가 제한된 패치, 집중 테스트, 재검증, 리뷰어 인계를 지원하면서 수용·병합·출시·종결 결정은 고객에게 남긴다.

**핵심 암기 포인트:** finding 수용 후 수정·검증은 Fix and Verify. 병합과 출시는 여전히 사람의 결정이다.

**AI 개발 실무 추가 설명:** 변경 diff, 회귀 테스트, 재검증 결과, 잔여 위험을 묶어 리뷰 가능하게 제공하되 자동 병합이나 릴리스 결정을 시스템이 대신하지 않게 한다.

**공식 해설 출처:** Codex Security Workflow Patterns · **누적 정답률:** 3/20 · 100%

## 4번. 고객이 소유해야 하는 책임

**문제:** Codex Security 워크플로우에서 고객 측에 남아야 하는 책임의 조합은 무엇일까?

**정답: 3번 ✅ 심각도 판단, 수정 수용, 변경 병합·출시 여부의 승인.**

**선택지 분석**

- 1번 ❌ 증거 정리·보고서 작성·잔여 위험 요약 — 유용한 지원 업무지만 최종 책임의 핵심은 아니다.
- 2번 ❌ finding 구조화·수정 제안·증거 패키지 준비 — 도구나 파트너가 지원할 수 있는 작업이다.
- 3번 ✅ 위험 심각도와 수정 수용, 병합·출시 같은 결과 결정은 고객의 보안·엔지니어링 책임이다.
- 4번 ❌ 범위 내 자료 리뷰와 승인된 점검, 제안 변경 준비 — 작업 수행은 지원 가능하지만 승인권을 넘기지 않는다.

**공식 해설 번역:** Codex Security는 분석·증거·점검·수정 준비를 지원할 수 있다. 심각도, 수정 수용, 중요한 출시 결정에 대한 책임은 사람인 보안·엔지니어링 팀에 남는다.

**핵심 암기 포인트:** AI는 증거와 제안을 돕고, 위험 수용·병합·출시는 사람이 결정한다.

**AI 개발 실무 추가 설명:** 제품 설계에서 생성 제안과 실제 실행 권한을 분리한다. 승인자와 감사 기록을 명시하고, 모델 출력만으로 고영향 결정을 확정하지 않는다.

**공식 해설 출처:** Codex Security Workflow Patterns · **누적 정답률:** 4/20 · 100%

## 5번. 시끄러운 백로그를 평가할 첫 대상

**문제:** 고객 소유 저장소 하나에 스캐너 백로그가 많다. AppSec과 엔지니어링 리뷰어가 있고, 주된 문제는 어떤 finding이 실제로 조치할 만한지 가리는 일이다. 가장 적합한 첫 평가 대상은?

**정답: 2번 ✅ 소유 저장소의 정의된 백로그 일부를 정해진 리뷰어와 의사결정 품질 지표로 평가한다.**

**선택지 분석**

- 1번 ❌ 상위 finding부터 자동 수정한다 — 실제성 확인이 병목인데 수정부터 시작하면 잘못된 결과와 권한 위험이 커진다.
- 2번 ✅ 소유·승인된 저장소에서 범위를 제한하고, 이름이 정해진 리뷰어와 품질 측정을 둔다.
- 3번 ❌ 모든 엔지니어링 저장소를 리뷰한다 — 첫 평가 범위를 과도하게 넓힌다.
- 4번 ❌ 운영 앱에서 악용 가능성을 시험한다 — 승인된 범위를 넘는 런타임 테스트를 전제한다.

**공식 해설 번역:** 강한 첫 대상은 소유되고 승인됐으며, 범위가 제한되고 관련성·리뷰 가능성·측정 가능성·맥락·안전성을 갖춰야 한다. 정의된 백로그 일부가 실제 검증 문제에 맞는다.

**핵심 암기 포인트:** 넓은 자동화보다 실제 병목을 겨냥한 작고 리뷰 가능한 평가부터 시작한다.

**AI 개발 실무 추가 설명:** 평가 전에 저장소 소유자, 샘플 범위, 리뷰 담당자, 라벨 기준, 측정 지표를 정한다. 사람의 판정 없이 생성 결과 개수만으로 도입 효과를 주장하지 않는다.

**공식 해설 출처:** Bounded Evaluation and Pilot Design · **누적 정답률:** 5/20 · 100%

## 6번. 스캔 시작 전 준비 조건

**문제:** 승인된 저장소의 Security Cloud 스캔을 계획 중이다. 리뷰어는 정해졌지만 증거 한도, 중단 조건, 접근, 저장소 연결과 비용은 확인되지 않았다. 시작 전에 무엇을 해야 할까?

**정답: 1번 ✅ 파일럿 경계를 완성하고 접근·연결·허용 작업·비용을 확인한다.**

**선택지 분석**

- 1번 ✅ 증거 기대치와 중단 시점, 접근·연결·활동 범위와 비용을 실행 전에 확인한다.
- 2번 ❌ 추가 맥락을 얻도록 저장소 접근을 넓힌다 — 필요성·승인 없이 권한을 확대한다.
- 3번 ❌ 공식 리뷰나 에스컬레이션 조건 없는 기능 데모로 바꾼다 — 평가 준비의 미비를 해소하지 않는다.
- 4번 ❌ 일단 소스 리뷰를 시작하고 증거 패키지 후 나머지를 정한다 — 경계와 권한은 작업 전 확정해야 한다.

**공식 해설 번역:** 저장소와 리뷰어가 정해졌다고 실행 준비가 끝난 것은 아니다. 스캔이 제공할 증거와 중단 조건을 정하고, 접근·연결·허용 활동·비용을 실행 전에 확인한다.

**핵심 암기 포인트:** 승인 범위, 접근, 행동, 중단 조건, 비용은 작업 시작 전에 합의한다.

**AI 개발 실무 추가 설명:** 클라우드 연결 계정의 권한 범위, 데이터 보관, 예상 사용량·비용 상한, 담당자와 중단 절차를 체크리스트화한다.

**공식 해설 출처:** Bounded Evaluation and Pilot Design · **누적 정답률:** 6/20 · 100%

## 7번. 평가가 실제 병목을 개선했는지 측정하기

**문제:** 고객의 병목은 finding 검증 지연과 부실한 엔지니어링 인계다. 평가가 워크플로우를 개선했는지 가장 잘 보여 주는 점수표는?

**정답: 3번 ✅ finding 유효성, 증거 유용성, 오탐 감소, 리뷰 부담, 검토 결정까지 걸린 시간.**

**선택지 분석**

- 1번 ❌ 워크플로우 실행 횟수·도구 호출·모델 사용량·알림 수 — 활동량은 의사결정 품질을 보여 주지 않는다.
- 2번 ❌ 제안 패치·병합·티켓 종료·배포와 릴리스 빈도 — 고객이 정하지 않은 실행 결과까지 성공으로 잡는다.
- 3번 ✅ 검증 품질과 증거 가치, 리뷰 부담과 신뢰 가능한 결정 속도를 직접 측정한다.
- 4번 ❌ 전체 finding 수·고위험 수·스캔 저장소 수·보고서 길이 — 산출량은 실제 병목 개선을 보장하지 않는다.

**공식 해설 번역:** 지표는 고객의 실제 병목을 측정해야 한다. 여기서는 더 나은 증거, 낮은 잡음, 줄어든 리뷰 부담, 더 빠르고 신뢰할 수 있는 결정이 raw 활동량보다 중요하다.

**핵심 암기 포인트:** 성공 지표는 사용량이 아니라 고객의 결정 품질과 업무 흐름에 연결한다.

**AI 개발 실무 추가 설명:** 파일럿 전 기준선과 비교 기간을 정하고, 리뷰어가 유효·오탐·미해결로 판정한 비율 및 검토 시간을 수집한다. 작은 표본의 개선을 전체 조직 효과로 일반화하지 않는다.

**공식 해설 출처:** Bounded Evaluation and Pilot Design · **누적 정답률:** 7/20 · 100%

## 8번. 성공적인 첫 평가 뒤의 확장

**문제:** 첫 평가에서 유용한 증거와 감당 가능한 리뷰 부담, 수용된 수정 경로를 확인했다. 고객은 이제 모든 저장소에 CI/CD 통합을 원한다. 가장 적절한 다음 단계는?

**정답: 2번 ✅ 사전 합의 기준 충족 여부와 증명 공백을 검토하고, 같은 리뷰 게이트 아래 인접한 제한 범위 하나에 대해 별도 승인을 구한다.**

**선택지 분석**

- 1번 ❌ 기존 리뷰 게이트만 유지하며 여러 저장소로 바로 넓힌 뒤 CI/CD를 검토한다 — 확대 대상이 이미 여러 저장소로 늘어난다.
- 2번 ✅ 미리 정한 기준을 평가하고 공백을 점검한 뒤 인접한 한 범위만 별도로 승인받는다.

## 16번. finding 통계의 정확한 분모와 상태

**문제:** 제한된 저장소 리뷰에서 finding 레코드 30개가 나왔고 그중 중복이 6개다. 고유 finding 24개 중 4개는 조치 가능, 10개는 억제, 10개는 미해결이다. 수정 제안 하나가 엔지니어링에 전달됐지만 런타임 테스트는 없었다. 가장 정확한 요약은?

**정답: 2번 ✅ 고유 finding 24개 중 4개가 조치 가능하고 10개는 미해결이다. 수정 인계는 완료된 수정이 아니며 런타임도 시험되지 않았다.**

**선택지 분석**

- 1번 ❌ 표시 레코드 30개 중 4개가 조치 가능 — 중복 6개를 분모에 넣으면 고유 finding 기준 비율이 왜곡된다.
- 2번 ✅ 중복을 제거한 24개를 기준으로 결과와 미해결 상태, 수정 인계, 런타임 공백을 함께 보고한다.
- 3번 ❌ 중복 6개가 20% 오탐률이고 인계가 완료 수정 하나다 — 중복과 오탐은 다르고 인계와 수정 완료도 다르다.
- 4번 ❌ 결정된 14개만 분모로 삼고 미해결 10개를 제외한다 — 미해결을 빼면 조치 가능 비율이 과대 표시된다.

**공식 해설 번역:** 조치 가능 비율의 분모는 미해결을 포함한 고유 finding 24개다. 중복 6개는 오탐의 증거가 아니다. 수정 인계는 완료된 수정이 아니고 런타임 동작도 시험되지 않았다.

**핵심 암기 포인트:** 중복 제거·고유 분모·미해결 상태를 모두 보존한다. 인계 ≠ 수정 완료.

**AI 개발 실무 추가 설명:** 데이터 파이프라인에서 중복 키, 고유 건수, 상태별 분모를 명시한다. 미확정 항목을 제외해 성공률을 부풀리지 않고 표본 수와 상태 정의를 함께 공개한다.

**공식 해설 출처:** Cyber Value Story & Executive Readout · **누적 정답률:** 16/20 · 100%

## 17번. 릴리스 전 특정 PR 검토

**문제:** AppSec 백로그가 시끄럽지만 당면 과제는 릴리스 전 인가 관련 PR 하나를 평가하는 것이다. AppSec과 엔지니어링 리뷰어도 정해졌다. 어떤 워크플로우가 가장 적합할까?

**정답: 1번 ✅ 특정 PR 변경과 보안 영향을 검토한다.**

**선택지 분석**

- 1번 ✅ 즉각적인 결정 대상이 구체적인 pull request와 그 변경이다.
- 2번 ❌ 개별 PR 전에 백로그 전체를 스캔한다 — 실제 의사결정을 지연시키고 범위를 넓힌다.
- 3번 ❌ 릴리스 민감 PR이므로 바로 수정·검증한다 — 아직 finding이 수용되거나 수정 대상으로 결정되지 않았다.
- 4번 ❌ 인가 변경이므로 저장소 심층 스캔을 한다 — 특정 변경 리뷰보다 넓은 분석을 자동 선택할 이유는 없다.

**공식 해설 번역:** 제한된 요구가 릴리스 전 특정 코드 변경 평가라면 코드 변경 보안 리뷰가 가장 적절하다. 더 넓은 백로그는 나중에 다룰 수 있지만 당장의 PR 검토를 대체하지 않는다.

**핵심 암기 포인트:** 구체적인 변경을 판단해야 할 때는 코드 변경 리뷰를 선택한다.

**AI 개발 실무 추가 설명:** PR 번호·커밋·관련 파일을 범위로 지정하고, 승인되지 않은 저장소 전체 스캔이나 릴리스 자동 승인을 섞지 않는다.

**공식 해설 출처:** Cyber Application Practice · **누적 정답률:** 17/20 · 100%

## 18번. 런타임 미검증 인가 우려의 분류

**문제:** 소스 리뷰에서 한 경로가 역할 검사 로직으로 도달하는 방식이 바뀐 것을 확인했다. 런타임 테스트는 없고 다른 통제가 인가를 강제할 수도 있다. 어떻게 분류해야 할까?

**정답: 2번 ✅ 소스 근거가 뒷받침하는 후보 finding이며 런타임 통제는 명시적인 증명 공백이다.**

**선택지 분석**

- 1번 ❌ 인가 로직이 바뀌었으므로 검증된 finding이다 — 런타임 영향과 다른 통제를 확인하지 않았다.
- 2번 ✅ 가능한 우려는 기록하되 실제 실행 결과와 남은 공백을 분리한다.
- 3번 ❌ 무단 사용자가 경로를 실행한 런타임 테스트가 없으니 오탐이다 — 미시험은 오탐 근거가 아니다.
- 4번 ❌ 인가 민감 변경은 입증 전까지 확정 릴리스 차단이다 — 위험 가능성을 확정 사실처럼 단정한다.

**공식 해설 번역:** 소스 증거는 타당한 우려를 뒷받침하지만 런타임 동작을 확정하지 않는다. 따라서 증명 공백을 명확히 표시한 후보 finding이 적절하다.

**핵심 암기 포인트:** 후보 finding은 검토 가치가 있다는 뜻이지, 취약점 확정이나 오탐 판정이 아니다.

**AI 개발 실무 추가 설명:** 위험 등급·상태·근거 수준을 분리 저장한다. 권한 경계가 여러 계층에 걸치면 상위 미들웨어, 정책 엔진, 실제 요청 경로를 확인하기 전 확정하지 않는다.

**공식 해설 출처:** Cyber Application Practice · **누적 정답률:** 18/20 · 100%

## 19번. PR 리뷰 평가의 성공 기준

**문제:** 인가 관련 PR을 제한적으로 검토한다. 평가 성공을 가장 잘 보여 주는 지표는?

**정답: 3번 ✅ AppSec과 엔지니어링이 간결하고 검토 가능한 증거 기록으로 수용·거절·추가 증거 요청을 결정할 수 있다.**

**선택지 분석**

- 1번 ❌ 전체 애플리케이션 포트폴리오 확대 여부를 판단할 만큼 finding을 많이 만든다 — 특정 PR 검토의 성공 목표를 넘는다.
- 2번 ❌ 예정된 릴리스 전에 수정안을 만들어 엔지니어링이 병합하게 한다 — AI가 수정·병합 시한을 보장하는 목표는 아니다.
- 3번 ✅ 리뷰어가 근거를 바탕으로 다음 결정을 내릴 수 있는지가 핵심이다.
- 4번 ❌ 기존 도구보다 더 많은 finding을 정해진 릴리스 시간 내 생성한다 — 수량과 속도가 결정의 타당성을 보장하지 않는다.

**공식 해설 번역:** 성공 기준은 finding 수나 자동 수정이 아니라 의사결정 품질이다. 리뷰어가 PR에 대해 방어 가능한 결정을 내릴 충분한 증거를 받으면 평가가 성공한 것이다.

**핵심 암기 포인트:** 성공 = 리뷰어가 수용·거절·추가 증거 요청 중 근거 있는 결정을 할 수 있음.

**AI 개발 실무 추가 설명:** 정답 근거의 추적성, 리뷰어 판정 일치도, 추가 증거 요청의 적절성, 결정까지 걸린 시간을 본다. 단순 생성량은 보조 지표로 둔다.

**공식 해설 출처:** Cyber Application Practice · **누적 정답률:** 19/20 · 100%

## 20번. PR 승인에서 저장소 스캔으로 범위 확대하기

**문제:** 승인된 PR 리뷰에서 인가 문제 가능성이 나왔지만 런타임은 시험되지 않았다. 고객이 저장소 전체 스캔을 요청한다. 파트너가 권고할 다음 행동은?

**정답: 1번 ✅ 현재 증거와 증명 공백을 바탕으로 AppSec·엔지니어링이 결정하도록 하고, 저장소 스캔은 범위·접근을 별도로 승인받는다.**

**선택지 분석**

- 1번 ✅ 기존 PR 증거에 대한 사람의 판단과 새 저장소 스캔의 승인 절차를 분리한다.
- 2번 ❌ PR 리뷰를 소스 증거만으로 닫고 기존 승인으로 저장소 전체 스캔을 한다 — PR 승인을 저장소 전체 승인으로 확대한다.
- 3번 ❌ 저장소 나머지로 스캔을 확장한 뒤 결과를 리뷰한다 — 사전 범위·접근·승인 확인이 빠졌다.
- 4번 ❌ 인가 우려를 확정 릴리스 차단으로 분류한다 — 런타임 미검증 우려를 확정 사실로 과장한다.

**공식 해설 번역:** 한 PR을 리뷰할 권한은 저장소 전체 스캔 권한이 아니다. AppSec과 엔지니어링은 현재 증거와 미입증 부분을 바탕으로 다음 행동을 결정해야 한다. 더 넓은 스캔에는 별도 범위·접근·승인 확인이 필요하다.

**핵심 암기 포인트:** 승인 범위는 자동 확장되지 않는다. 다음 범위는 새로 정의하고 승인받는다.

**AI 개발 실무 추가 설명:** 승인 문서에 저장소·브랜치·커밋·도구 접근·읽기/쓰기·스캔 동작을 명시한다. 변경된 대상과 권한을 기록한 뒤 새 워크플로우를 실행한다.

**공식 해설 출처:** Cyber Application Practice · **누적 정답률:** 20/20 · 100%

- **권한과 거버넌스:** 질문에 답할 최소 권한부터 시작하고, 테스트·저장소 확대는 별도 승인한다.
- **운영 준비:** 접근·비용·리뷰 용량·소유자·중단 조건·임시 데이터 규칙을 실행 전에 정한다.

- **사람의 책임:** 심각도·수정 수용·병합·출시는 고객의 보안·엔지니어링 팀이 결정한다.
