## 학습 목표

- Codex 보조 엔지니어링 워크플로우의 **운영·거버넌스 위험**을 찾아내기
- 워크플로우를 **위험 사다리(저·중·고)**로 분류하고 어디에 안전장치가 필요한지 정하기
- **승인 · 리뷰 · 검증 · 에스컬레이션** 체크포인트를 구분해 설계하기
- 권한, 금지 작업, 샌드박스, 접근 경계, 감사 가능성, 관리자 통제가 **언제** 필요한지 판단하기
- 속도와 신뢰를 함께 잡는 **거버넌스 인식 워크플로우 추천서** 만들기

## 예제 상황 — Bridgeford Trent와 Arfon Digital

가상의 파트너 **Bridgeford Trent**가 고객 **Arfon Digital**을 도와요. Arfon은 PR 준비, CI 조사, 문서 업데이트, 일부 구현에 Codex를 쓰고 싶어 해요. 그런데 이해관계자마다 걱정이 달라요.

| 누가 | 하는 말 | → 필요한 통제 |
|---|---|---|
| 개발자 | "내가 승인 안 한 변경에 놀라고 싶지 않아요" | 승인 경계, 금지 작업 |
| 리뷰어 | "어떤 파일을 봤고 어떤 검증 증거를 찾았는지 알아야 해요" | 검증 증거, 리뷰 가능성 |
| 플랫폼 담당 | "어떤 팀·워크스페이스가 범위인지 알아야 해요" | 저장소·워크스페이스·환경·도구 경계 |
| 보안 담당 | "민감 파일·자격 증명·프로덕션 작업엔 분명한 제한이 필요해요" | 데이터 민감도, 접근 제한, 감사 가능성, 에스컬레이션 |
| 엔지니어링 리더 | "팀 전체에 믿고 쓸 롤아웃 패턴이 필요해요" | 반복 가능한 패턴, 확장을 뒷받침하는 증거 |

### 이 코스의 4가지 거버넌스 도구

| 도구 | 하는 일 |
|---|---|
| 1. 위험 사다리 | 저위험 보조 / 중위험 위임 / 고위험 엔지니어링 작업으로 분류 → 모든 일에 같은 통제를 거는 실수 방지 |
| 2. 체크포인트 지도 | 승인 · 리뷰 · 검증 · 에스컬레이션을 구분 |
| 3. 운영 경계 체크리스트 | 승인된 경계, 금지 작업, 승인 필요 작업, 검증 증거, 리뷰어, 에스컬레이션, 가시성 |
| 4. 통제 선택 입력값 | 워크플로우 위험 · 데이터 민감도 · 개발자 권한 · 도구/환경 접근 · 고객 거버넌스 기대 |

## 1단계 — 운영 위험 찾기와 위험 사다리

<div class="oa-eli">
  <span class="oa-eli__head">🔪 쉽게 말하면</span>
  <p>요리 수업에서 <b>레시피 읽어주기</b>(저위험)는 아무나 해도 되고, <b>채소 썰기</b>(중위험)는 선생님이 칼 쓰는 범위를 정해주고 결과를 확인하고, <b>가스불·튀김기</b>(고위험)는 선생님이 직접 하거나 꼭 옆에서 허락을 받아야 하죠. 모든 활동에 "튀김기 수준 안전 규칙"을 걸면 수업이 안 굴러가고, 튀김기에 "레시피 읽기 수준 규칙"을 걸면 사고가 나요.</p>
</div>

위험은 **워크플로우가 그 주변 운영 모델보다 빨리 움직일 때** 생겨요. 저장소 접근, 명령 실행, 배포, 도구·인터넷 접근, 민감 파일, 무제한 실행, 부족한 리뷰, 불분명한 소유권, 약한 검증, 에스컬레이션 경로 부재, 낮은 가시성이 위험 신호예요.

### 통제 선택 입력값 5가지

| 입력값 | 질문 |
|---|---|
| 워크플로우 위험 | 코드 품질·일정·프로덕션 준비·인프라·고객 대면 시스템에 영향을 주나? |
| 데이터 민감도 | 비밀·자격 증명·기밀 코드·민감 로그·고객 데이터를 마주칠 수 있나? |
| 개발자 권한 | 개발자·리뷰어·플랫폼 담당·관리자 중 누구 수준의 권한으로 동작하나? |
| 도구 접근 | 어떤 저장소·CI·이슈 트래커·로그·패키지 매니저·배포 도구·MCP 연결 시스템이 범위인가? |
| 고객 거버넌스 기대 | 승인·증거·감사·관리자 감독·에스컬레이션·예외 처리에 무엇을 요구하나? |

> 위험은 꼭 "Codex가 틀린 답을 낸다"가 아니에요. **무슨 일이 있었는지, 누가 검토했는지, 어떤 증거가 있었는지, 경계 안에 있었는지 팀이 모르는 것**도 위험이에요.

중위험에선 런타임의 **샌드박스·승인 설정**을 꼭 확인해요. 허용된 로컬 수정·명령은 네이티브 승인 프롬프트가 안 뜰 수도 있지만, **고객이 요구한 승인은 그래도 받아야** 해요. CLI 예시라면 클라이언트 버전·실제 모델·권한을 기록해 기본값에 기대지 않게 해요. 고위험의 목표는 **영원히 막는 게 아니라, 고위험 일에 저위험 안전장치를 주지 않는 것**이에요.

### 위험 경계를 넘는 신호

| 위험 신호 | 거버넌스 질문 |
|---|---|
| 추가 저장소·도구·로그·시스템 접근 | 어떤 접근 경계가 적용되나? |
| 파일 수정·명령 실행·원래 작업 너머로 계속 | 설정된 승인 정책·샌드박스·고객 게이트가 멈춤을 요구하나? |
| 민감 파일·인프라·프로덕션·배포 준비 | 사람 주도로 남길까, 더 강한 리뷰가 필요한가? |
| 엔지니어링 결정에 영향을 주는 출력 | 어떤 검증 증거와 리뷰어가 필요한가? |
| 검증 실패·소유권 불명·범위 확대 | 어떤 에스컬레이션 경로? |
| 나중에 무슨 일이 있었는지 봐야 함 | 어떤 가시성·감사가 필요한가? |
| 규제·내부 승인 정책 | 고객이 기대하는 관리자 가시성·승인 기록·예외 절차는? |

### 같은 작업, 다른 산업 (강의 예시)

같은 "제한된 CI 조사"라도 데이터가 다르면 통제가 달라져요.

> **샌드박스·네트워크·승인 설정은 "기술적으로 무엇이 가능한가"를 통제할 뿐, "고객이 그 데이터를 쓰거나 그 행동을 할 권한이 있는가"를 결정하지 않아요.** 제품·설정, 계약 조건, 데이터 보존·위치 요건, 고객 승인 절차는 담당 전문가와 확인할 질문이지 법적 충족의 증거가 아니에요. 산업 라벨이 아니라 **실제 데이터와 허용된 행동**으로 판단해요.

### 방어적 보안 작업도 권한이 필요해요 (강의 기준)

Arfon이 **Codex Security Cloud**로 저장소 하나의 취약점을 스캔하고 싶다면: 어떤 저장소·데이터를 쓸지 합의하고, 위협 모델의 범위·가정을 검토하고, 발견 사항을 검증할 보안 담당자를 지정해요. 일회성인지 지속 스캔인지, 누가 멈출 수 있는지도 정해요. **방어 목적이라고 불분명한 접근이 허용되진 않아요.**

- 제품 접근과 준비도는 따로 확인: Codex Security는 research preview — 플랜 자격, 워크스페이스 Cloud·Security 권한, 저장소 접근, Cloud 과금 경로와 예산 확인
- Security Cloud에 Daybreak Blue가 포함돼도 로컬 플러그인 접근이 보장되진 않음
- **발견 사항과 제안 패치는 리뷰용 증거일 뿐 적용 승인이 아님.** 보안 담당이 발견을 평가하고, 권한 있는 엔지니어가 패치·검증 증거·남은 위험을 리뷰. 적용·merge·릴리스는 각각 별도의 고객 결정

## 2단계 — 승인·리뷰 워크플로우 설계 (체크포인트 지도)

<div class="oa-eli">
  <span class="oa-eli__head">✈️ 쉽게 말하면</span>
  <p>공항을 떠올려 봐요. <b>승인</b>은 "탑승해도 되나요?"(게이트에서 멈춤), <b>검증</b>은 "여권·항공권 증거가 맞나?", <b>리뷰</b>는 "직원이 보고 통과시킬지 판단", <b>에스컬레이션</b>은 "이상한 게 있으면 보안팀으로 넘김"이에요. 네 개는 비슷해 보여도 <b>서로 대체할 수 없어요.</b></p>
</div>

| 체크포인트 | 핵심 질문 | 예시 |
|---|---|---|
| ✋ 승인 | 설정된 정책이나 고객 절차가 Codex를 **멈추게** 하나? | 이 파일 수정·명령·저장소 접근 전에 멈춰야 하나? |
| 👀 리뷰 | 이 산출물을 **수용**할까? | 리뷰어가 수용·수정·거절·에스컬레이션 |
| 🧪 검증 | 어떤 **증거**가 뒷받침하나? | 어떤 테스트를 돌렸고, 뭐가 바뀌었고, 어떤 가정이 남았고, 무엇을 확인 못 했나 |
| 🚨 에스컬레이션 | 언제 **멈추거나 다른 담당자**에게 넘기나? | 민감 데이터, 프로덕션 설정, 검증 실패, 소유권 불명 |

모든 워크플로우에 똑같이 걸지 않아요. 문서 요약은 리뷰만, CI 조사는 검증 증거 + 특정 수정 전 고객 게이트, 프로덕션 인접 작업은 명시적 승인 + 금지 작업 + 감사 + 플랫폼·보안 에스컬레이션.

리뷰 경로(로컬 / 앱 내 PR / 저장소 트리거 cloud)에도 같은 체크포인트를 적용해요. 자동 GitHub 리뷰엔 연결·저장소 접근·리뷰 설정이 필요하지만 새 cloud 작업 환경은 필요 없어요. **발견 사항을 준비·검사하는 것은 피드백 게시·변경 승인·merge 권한이 아니며**, 설정된 자동 리뷰 자체도 승인된 워크플로우여야 해요.

### 승인 체크포인트가 필요한 순간

<div class="oa-cards">
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🔁</span><span class="oa-card__title">분석 → 행동</span>조사에서 구현으로 넘어감, 정책·고객이 승인을 요구하는 코드 변경 적용</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">💻</span><span class="oa-card__title">영향 큰 명령</span>의존성·빌드·테스트 상태·인프라·환경에 영향, 실패를 숨길 수 있는 테스트 동작 변경</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🔓</span><span class="oa-card__title">범위 확장</span>추가 저장소·로그·외부 도구·MCP 연결, 민감 파일·자격 증명</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">⚠️</span><span class="oa-card__title">이상 상황</span>검증 실패 후 계속, 소유권 모호, 릴리스·배포 준비, 인프라 설정 수정</div>
</div>

승인 체크포인트는 세 질문에 답해요: **Codex가 무슨 행동을 하려 하나? 누가 승인 권한이 있나? 승인자는 결정 전에 무엇을 봐야 하나?**(수정할 파일, 이유, 돌릴 검증, 범위 밖 항목)

설정은 런타임마다 확인해요. 설정이 로컬 수정을 프롬프트 없이 허용해도 **고객의 "수정 금지" 지시를 덮어쓰지 않아요.** "제안만 하는 리뷰(proposal-only)"는 Codex의 네이티브 모드가 아니라 **고객이 정의한 프로세스**예요.

### 워크플로우별로 보여야 할 증거

| 워크플로우 | 돌려받을 증거 |
|---|---|
| PR 준비 | 살펴본 파일, 변경 요약, 테스트 증거, 빠진 증거, 위험, 리뷰어 질문 |
| CI 조사 | 본 로그, 원인 후보, 살펴본 파일, 다음 단계, 추천·실행한 명령, **프로덕션 영향 작업이 없었다는 증거**, 불확실성 |
| 문서 업데이트 | 사용한 소스, 초안, 미해결 질문, 정확성 리뷰 담당자, 게시 승인 상태 |
| 보안 발견 | 해당 코드·리비전과 관련 위협 모델 가정, 수행한 검증·결과·미검증 항목(발견 ≠ 확정 취약점), 제안 패치의 검증 증거·남은 위험·별도 사람 결정 |

### 4가지 가시성 = 운영 신뢰

<ol class="oa-flow">
  <li><strong>작업 가시성</strong>무엇을 하라고 했나?</li>
  <li><strong>Context 가시성</strong>작업·저장소·리비전, 쓴 파일·로그·도구, cloud 환경 소유자</li>
  <li><strong>증거 가시성</strong>검증 증거·위험·가정·빠진 것·질문</li>
  <li><strong>결정 가시성</strong>누가 검토해 수용·거절·에스컬레이션? 게시·승인·merge는 누가? 인계 후 누가 이어받나?</li>
</ol>

**리뷰 가능성 실패 사례**: Codex가 그럴듯한 PR 요약을 냈는데 리뷰어가 "어떤 파일을 봤지? 업데이트된 테스트를 확인했나, diff만 요약했나? 빠진 증거는? 불확실한 걸 확실한 듯 썼나?"를 물어야 한다면 실패예요. 더 강한 출력은 구현 의도, 살펴본 파일, 검증 증거, 빠진 증거, 위험·가정, 열린 질문, **리뷰어가 집중할 곳**을 포함해요. 사람 리뷰를 없애는 게 아니라 **더 효과적으로** 만드는 거예요.

## 3단계 — 운영 안전장치 고르기

무제한 실행의 위험은 Codex가 **의도한 경계 너머로** 행동할 때 생겨요. 승인 안 된 저장소 읽기, 워크스페이스 밖 쓰기, 의존성·인프라에 영향 주는 명령, 리뷰 없는 도구·인터넷 사용, 검증 실패 후 계속, 프로덕션 인접 변경, 민감 파일, 소유권 없는 광범위 수정, 모호해진 작업 계속하기 등이요.

> 핵심 질문: **"데이터 민감도·권한·도구 접근·거버넌스 기대를 고려할 때, 이 워크플로우가 여전히 쓸모 있는 가장 작은 안전 경계는 무엇인가?"**

### 운영 경계 체크리스트 (9항목)

| # | 항목 | 정할 것 |
|---|---|---|
| 1 | 워크플로우 위험 | 저 / 중 / 고 중 어디? |
| 2 | 데이터 민감도 | 마주칠 수 있는 데이터, 범위 밖으로 둘 것 |
| 3 | 개발자 권한 경계 | 어떤 역할의 권한을 가정? 높은 권한 포함? |
| 4 | 도구·환경 접근 | 승인된 저장소·브랜치·CI·로그·MCP·서비스. cloud면 환경 소유자, 네트워크뿐 아니라 서비스 권한도. **환경 공유 ≠ 더 넓은 작업 승인** |
| 5 | 런타임 통제 vs 고객 게이트 | 실제 샌드박스·네트워크·승인 설정(CLI면 버전·모델·권한) **따로**, 고객 프로세스 게이트(제안 전용 리뷰, 특정 행동 전 승인) **따로** |
| 6 | 금지 작업 | PR 승인, merge, 프로덕션 배포, 인프라 수정, 무관한 저장소, 민감 파일, 미승인 도구, 파괴적 명령, 범위 밖 리팩터 |
| 7 | 승인 필요 작업 | 특정 파일 변경 적용, 고위험 명령, 저장소 범위 확장, 외부 시스템, 조사→구현 전환, 추가 로그 접근, 검증 실패 후 계속 |
| 8 | 가시성·감사·관리자 통제 | 나중에 관리자·플랫폼·보안·리뷰어가 볼 활동·출력·승인·예외 기록 |
| 9 | 에스컬레이션 경로 | 언제 멈추고 누구를 부르나 |

**비례적으로** 적용해요. 저위험 문서 워크플로우에 프로덕션 인접 작업만큼의 안전장치는 필요 없어요.

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">🚫 금지 작업 (restricted)</span>
    <p>파일럿 중 <b>아예 하면 안 되는 것</b>. 승인을 받아도 이 파일럿 범위에선 안 함. 예: merge, 프로덕션 배포, 인프라 수정</p>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✋ 승인 필요 작업 (approval-gated)</span>
    <p>할 수는 있지만 <b>멈추고 허락을 받은 뒤</b>에. 설정된 승인 정책·샌드박스 또는 고객 프로세스 게이트가 요구. 예: 특정 파일 변경 적용, 범위 확장</p>
  </div>
</div>

### 안전장치 선택 매트릭스 (결정 보조 도구, 설정 가이드 아님)

| 워크플로우 유형 | 예시 | 확인할 입력값 | 추천 안전장치 |
|---|---|---|---|
| 저위험 보조 | 모듈 설명, 승인된 context로 문서 초안 | 낮은 민감도, 제한된 권한, 프로덕션·도구 접근 없음 | 승인된 context, 사람 리뷰, 민감 데이터 제한, 출력 기대치 |
| 리뷰 체크포인트 | 리뷰어용 PR 요약 | 저장소 범위, 살펴본 파일, 검증 증거, **merge 권한 없음** | 파일·증거·공백·질문 검사. 게시·승인·merge는 사람 결정 |
| 중위험 위임 | CI 실패 조사, 선택된 저장소의 테스트 업데이트 | 저장소 경계, 권한 가정, CI/로그 접근, 특정 수정 전 승인 필요 여부 | 저장소 경계, 작업 범위, 검증 증거, 리뷰어, 경계 넘을 때 승인, 고객 게이트, 에스컬레이션 |
| 도구 연결 워크플로우 | 승인된 도구·MCP로 context 수집·행동 | 도구 허용 목록, 자격 증명 경계, 행동 권한, 감사 기대 | 도구 허용 목록, 자격 증명 경계, 행동 제한, 승인 요건, 활동 가시성 |
| 고위험 작업 | 인프라·배포·민감 저장소·프로덕션 인접 | 민감 데이터, 높은 권한, 프로덕션 접근, 강한 거버넌스 | 사람 주도, 보안·플랫폼 리뷰, 명시적 승인 경로, 금지 작업, 환경 분리, 감사 |

피해야 할 두 실수: **고위험을 과소 통제**하기, **저위험을 과잉 통제**해서 못 쓰게 만들기.

진단 질문: **"이 워크플로우에서 가장 일어날 법한 실수는 무엇이고, 어떤 안전장치가 그걸 막나?"**

## 4단계 — 거버넌스 인식 추천서 만들기

### 거버넌스 = 가속의 조건

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">❌ 이렇게 말하지 않기</span>
    <p>"거버넌스는 Codex를 느리게 합니다."</p>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✅ 이렇게 말하기</span>
    <p>"거버넌스는 Codex 보조 워크플로우가 <b>안전하게 가속</b>할 수 있는 조건을 정의합니다." — 경계가 분명하면 팀이 워크플로우마다 처음부터 협상할 필요가 없어서 오히려 빨라져요.</p>
  </div>
</div>

**반복 가능성 ≠ 모든 워크플로우에 같은 통제.** 반복돼야 하는 건 **결정 패턴**이에요: 위험 분류 → 경계 정의 → 승인 지점 → 필요한 증거 → 리뷰어 → 에스컬레이션. 확장성 테스트 질문: **"다른 팀이 새 위험 없이 같은 패턴을 이해하고 따라 할 수 있나?"**

주의: 요약 초안 파일럿의 성공이 **cloud 위임·자동 리뷰·보안 스캔의 준비를 증명하지 않아요.** 새 경로마다 접근·소유권·증거·행동 경계를 다시 확인해요.

### 5부 추천서 프레임

| 섹션 | 담을 내용 |
|---|---|
| 1. 워크플로우·위험 context | 워크플로우 이름, 해결할 문제, 저/중/고 위험과 그 주된 이유 |
| 2. 경계·운영 자세 | 범위 안/밖. **네이티브 런타임 통제**(읽기 전용·워크스페이스 쓰기 샌드박스, 네트워크, 승인 정책)와 **고객 프로세스 게이트**를 구분 |
| 3. 사람 체크포인트 | 어디서 멈추고, 누가 리뷰하고, 언제 에스컬레이션 |
| 4. 증거·가시성 | 돌려받을 검증 증거, 추적 가능하게 남길 활동 |
| 5. 확장 조건 | 다른 팀·저장소·용도로 넓히려면 어떤 증거가 필요한가 |

두 함정: **너무 모호**("거버넌스와 함께 Codex 쓰기") vs **너무 상세**(필요 없는 통제까지 전부 나열 → 일반 체크리스트처럼 보임).

## 정리

- 거버넌스는 **통제 목록이 아니라 고객 워크플로우**에서 시작한다. 입력값 5개: 위험·데이터 민감도·개발자 권한·도구 접근·고객 거버넌스 기대.
- **위험 사다리**(저·중·고)로 분류해, 저위험을 과잉 통제하지도 고위험을 과소 통제하지도 않는다.
- **승인·리뷰·검증·에스컬레이션**은 서로 대체되지 않는다. 런타임 설정이 허용해도 고객의 승인 요구·수정 금지 지시는 그대로 유효하다.
- 샌드박스·네트워크·승인 설정은 기술적 가능성만 통제할 뿐, **데이터 사용·행동의 권한**은 고객과 전문가가 정한다. 보안 발견·패치도 리뷰용 증거이지 적용 승인이 아니다.
- 운영 경계 체크리스트 9항목과 선택 매트릭스로 **가장 작은 안전 경계**를 정하고, 작업·context·증거·결정 가시성을 확보한다.
- 거버넌스는 브레이크가 아니라 **안전한 가속의 조건**. 추천서는 위험 context → 경계 → 체크포인트 → 증거 → 확장 조건 5부로.
