## 학습 목표

- 작업에 맞는 단일 호출, loop, graph 구조를 선택하기
- 안전한 loop의 목표·상태·검증·종료 조건을 설계하기
- graph의 node·edge·router·reducer·checkpoint·contract를 실전에 적용하기
- Claude Code와 Codex에 구조가 드러나는 자연어 지시를 작성하기

## 시작은 구조가 아니라 문제다

“이번 작업에 graph를 써야지”라고 먼저 결정하면 일을 구조에 억지로 끼워 맞추게 됩니다. 먼저 다음 세 질문을 던지는 편이 낫습니다.

1. 한 번의 요청으로 충분히 좋은 결과를 만들 수 있는가?
2. 결과를 객관적으로 검사하고 다시 고칠 필요가 있는가?
3. 서로 독립적인 작업, 분기 또는 부분 실패 복구가 필요한가?

| 대답 | 먼저 시도할 구조 |
|---|---|
| 한 번에 끝낼 수 있다 | 단일 호출 |
| 검사와 수정이 반복된다 | Loop |
| 독립 작업·분기·합류가 있다 | Graph |

복잡도는 필요할 때만 올립니다. Anthropic의 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)도 단순한 해결책부터 시작하고, 측정 가능한 개선이 있을 때 복잡한 에이전트 구조를 추가하라고 권합니다.

## 실전 Loop 설계

안전한 loop에는 여섯 가지가 필요합니다.

| 요소 | 질문 | 코드 수정 예시 |
|---|---|---|
| 목표(Goal) | 무엇을 달성해야 하는가? | 로그인 실패 버그 수정 |
| 상태(State) | 다음 시도까지 무엇을 기억하는가? | 변경 파일, 이전 오류, 시도 횟수 |
| 행동(Action) | 무엇을 바꿀 수 있는가? | 코드 편집, 테스트 실행 |
| 검증(Verification) | 성공을 누가 어떻게 판정하는가? | 재현 테스트와 관련 테스트 통과 |
| 종료 조건(Stop) | 언제 멈추는가? | 테스트 통과, 3회 실패, 시간 초과 |
| 예산(Budget) | 얼마까지 사용할 수 있는가? | 20분, 최대 3회, 변경 파일 5개 |

### 예시: 테스트 실패 수정 Loop

```text
실패 재현
   ↓
원인 가설 세우기
   ↓
가장 작은 수정
   ↓
관련 테스트 실행
   ├─ 통과 → 회귀 테스트 → 종료
   └─ 실패 → 새 정보가 생겼는가?
                ├─ 예 → 상태 기록 후 다음 시도
                └─ 아니요 → 중단하고 사람에게 보고
```

여기서 핵심은 **모델이 “좋아 보인다”고 판단하는 것과 성공 판정을 분리하는 것**입니다. 컴파일, 테스트, 스키마 검사, 링크 확인처럼 코드로 판단할 수 있는 것은 코드가 결정하게 합니다.

### Claude Code·Codex에 요청하는 방법

제품별 마법 키워드를 외우기보다 목표, 문맥, 제약, 완료 조건을 적습니다. Codex 공식 prompting 문서도 원하는 동작, 관련 코드나 재현 단계, 중요한 제약, 검증 방법을 포함하라고 권합니다.

```text
목표: 결제 완료 후 주문 상태가 갱신되지 않는 버그를 수정해줘.

문맥:
- 재현 테스트는 tests/orders/test_payment.py에 있어.
- 주문 상태 전이는 src/orders/state.py에서 관리해.

제약:
- 공개 API는 바꾸지 마.
- 매 시도마다 관련 테스트를 실행해.
- 같은 오류가 두 번 반복되면 더 수정하지 말고 원인과 막힌 지점을 알려줘.
- 최대 3회까지만 수정해.

완료 조건:
- 재현 테스트와 orders 테스트 전체가 통과해야 해.
- 마지막에 변경 파일과 검증 명령을 요약해.
```

이 요청은 에이전트가 스스로 loop를 돌 수 있게 하면서도, 반복 범위와 성공 판정은 사람이 통제합니다. 자세한 기본 원칙은 [OpenAI의 Codex Prompting 문서](https://developers.openai.com/codex/prompting/)에서 확인할 수 있습니다.

## Loop가 실패하는 방식

### 종료 조건이 “만족할 때까지”뿐이다

만족의 뜻이 모호하면 loop가 불필요하게 오래 돌거나, 모델이 스스로 성공했다고 선언합니다. 반드시 기계적 검사와 상한을 함께 둡니다.

```text
종료 = 테스트 통과
    또는 시도 3회 도달
    또는 20분 초과
    또는 같은 실패 2회 반복
```

### 상태가 매번 초기화된다

이전 오류와 시도한 해결책을 기록하지 않으면 같은 수정을 반복합니다. 최소한 아래 상태는 다음 시도에 전달합니다.

- 이전 시도에서 바꾼 것
- 실행한 검증과 결과
- 실패 원인의 현재 가설
- 남은 시간·token·시도 횟수

### 검증자가 작업자의 설명만 읽는다

작업자가 “수정 완료”라고 쓴 문장은 증거가 아닙니다. 검증자는 실제 diff, 테스트 출력, 산출물과 외부 출처를 확인해야 합니다.

## 실전 Graph 설계

Graph는 작업을 많이 만드는 기술이 아닙니다. **필요한 의존성만 남기는 기술**입니다.

### 여섯 가지 기본 부품

| 용어 | 쉬운 뜻 | 설계 질문 |
|---|---|---|
| Node | 하나의 작업 단위 | 입력 하나를 받아 어떤 출력을 만드는가? |
| Edge | 작업 사이의 연결 | 다음 작업이 앞 결과를 정말 필요로 하는가? |
| Router | 경로 선택기 | 어떤 조건에서 어느 경로로 보내는가? |
| Reducer | 여러 결과의 통합기 | 누락·중복·충돌을 어떻게 처리하는가? |
| Checkpoint | 다시 시작할 저장 지점 | 실패 후 어디부터 재개할 수 있는가? |
| Contract | 노드의 입출력 약속 | 형식, 필수 필드, 실패 상태는 무엇인가? |

### Fake-edge test: 가짜 의존성 지우기

두 작업이 선으로 연결되어 있다면 물어봅니다.

> 뒤 작업을 시작하려면 앞 작업의 출력이 반드시 필요한가?

필요하지 않다면 그 edge는 가짜일 가능성이 큽니다. 예를 들어 세 제품의 공식 문서를 조사하는 작업은 서로의 결과가 없어도 시작할 수 있습니다. 반면 조사 결과를 비교하는 작업은 세 결과가 필요하므로 뒤에 와야 합니다.

```text
                 ┌→ 제품 A 공식 문서 조사 ─┐
질문 → 계획·분배 ├→ 제품 B 공식 문서 조사 ─┼→ 입력 수 확인 → 비교 → 결론
                 └→ 제품 C 공식 문서 조사 ─┘
```

LangGraph의 [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)는 이런 구조를 state, node, edge와 병렬 superstep으로 표현합니다. 특정 프레임워크를 쓰지 않아도 같은 설계 원리는 적용됩니다.

### Contract: 결과를 합칠 수 있게 만드는 약속

세 조사 노드가 제각각 결과를 쓰면 reducer가 내용을 안정적으로 합치기 어렵습니다. 시작 전에 공통 형식을 정합니다.

```yaml
topic: "조사 대상"
claim: "확인한 핵심 주장"
evidence:
  - url: "공식 출처 URL"
    summary: "주장을 뒷받침하는 내용"
limitations:
  - "확인하지 못한 점 또는 적용 조건"
status: "complete | partial | failed"
```

좋은 contract는 성공 결과만 정의하지 않습니다. `partial`, `failed`, `not_applicable` 같은 상태도 표현해야 silent failure를 막을 수 있습니다.

### Router: 반드시 거절 경로를 둔다

라우터가 모든 입력을 기존 범주 중 하나로 억지 분류하면 조용히 잘못된 경로로 보낼 수 있습니다.

```text
요청 분류 ┬→ 문서 작업
          ├→ 코드 작업
          ├→ 데이터 분석
          └→ unknown → 추가 질문 또는 사람 검토
```

결정적 규칙은 코드에 둡니다. 예를 들어 파일 확장자가 `.csv`인지는 코드가 판단할 수 있습니다. 요청의 의도가 애매한지는 모델이 판단하되, 낮은 확신을 표현할 방법을 줍니다.

### Reducer: 병렬 처리의 진짜 병목

fan-out은 시작일 뿐입니다. 결과를 합치는 fan-in이 느리거나 부정확하면 전체 graph의 이점이 사라집니다.

Reducer는 최소한 다음을 확인해야 합니다.

- 예상한 결과 수와 실제 도착한 결과 수가 같은가?
- 실패하거나 부분 완료된 노드가 있는가?
- 같은 주장을 중복 보고했는가?
- 서로 모순되는 결과는 무엇인가?
- 최종 결론이 어떤 출처에서 왔는가?

## Claude Code·Codex용 Graph 요청 예시

다음 예시는 특정 명령어 없이도 작업 구조를 전달합니다.

```text
이 저장소의 인증 구조를 조사하고 개선안을 제안해줘.

1. 먼저 조사 항목과 실제 의존성을 정리해.
2. 서로의 결과가 필요 없는 아래 작업만 독립적으로 조사해.
   - 인증 관련 코드 경로
   - 테스트와 실패 사례
   - 보안 설정과 문서
3. 각 결과는 '발견, 근거 파일, 위험, 확신도, 미확인 사항' 형식으로 반환해.
4. 읽기 작업은 병렬로 해도 되지만 같은 파일을 동시에 수정하지 마.
5. 모든 결과가 도착했는지 확인한 뒤 하나의 개선안으로 통합해.
6. 근거가 충돌하거나 부족하면 추측하지 말고 별도로 표시해.
7. 지금은 조사와 제안만 하고 코드는 수정하지 마.
```

Codex에서 독립적인 작업을 실제 하위 에이전트에 맡기고 싶다면 “독립적인 조사 작업을 subagent에 위임해”처럼 직접 요청할 수 있습니다. 다만 여러 에이전트가 각각 모델과 도구를 사용하므로 token 소비가 늘고, 동시에 같은 파일을 수정하면 충돌 위험이 커집니다. 공식 [Codex Subagents 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)도 읽기 중심의 탐색·테스트·요약부터 병렬화하고, 쓰기 중심 작업은 더 조심하라고 설명합니다.

Claude Code의 동적 workflow도 스크립트가 여러 Claude 실행을 조정하고 중간 결과를 변수로 보관하는 방식입니다. 기능과 버전 조건은 바뀔 수 있으므로 실제 사용 전 [Claude Code Workflows 공식 문서](https://code.claude.com/docs/en/workflows)를 확인합니다.

## 작업 공간과 상태를 분리하라

병렬 작업이 실패하는 흔한 이유는 모델의 능력보다 공유 자원의 충돌입니다.

- 같은 파일을 여러 작업자가 동시에 수정함
- 공용 임시 파일을 덮어씀
- 하나의 API rate limit을 모두 사용함
- 전역 상태를 누가 갱신하는지 불분명함

읽기 작업은 비교적 안전하게 병렬화할 수 있습니다. 쓰기 작업은 파일 소유권을 나누거나 Git worktree처럼 격리된 공간을 사용합니다. 최종 통합은 한 주체가 담당하도록 정하는 편이 단순합니다.

## 실전 선택표

| 상황 | 권장 구조 | 이유 |
|---|---|---|
| 짧은 코드 설명 | 단일 호출 | 반복·분기가 필요 없음 |
| 테스트가 통과할 때까지 작은 버그 수정 | Loop | 외부 검증 기준이 명확함 |
| 여러 제품의 공식 문서 비교 | Fan-out/Fan-in graph | 독립 조사 후 통합 가능 |
| 요구사항이 계속 바뀌는 초기 탐색 | 사람과 짧은 loop | graph를 미리 고정하면 재작업이 큼 |
| 입력 유형에 따라 도구가 달라짐 | Router graph | 경로와 거절 조건을 명시할 수 있음 |
| 하나의 파일을 순서대로 크게 리팩터링 | Chain 또는 단일 작업자 loop | 병렬 쓰기 충돌 가능성이 큼 |

## 실행 전 체크리스트

### Loop

- [ ] 성공을 외부에서 검사할 수 있는가?
- [ ] 이전 시도와 실패 원인을 상태로 남기는가?
- [ ] 최대 반복 횟수, 시간, 비용이 정해졌는가?
- [ ] 진전이 없을 때 중단하거나 사람에게 넘기는가?

### Graph

- [ ] 각 edge는 실제 데이터 의존성을 나타내는가?
- [ ] 병렬 노드가 같은 파일이나 자원을 건드리지 않는가?
- [ ] 노드의 입력·출력·실패 contract가 정해졌는가?
- [ ] router에 `unknown` 또는 거절 경로가 있는가?
- [ ] reducer가 누락·중복·충돌을 검사하는가?
- [ ] 실패 후 재개할 checkpoint와 상태 소유자가 명확한가?

## 핵심 정리

Claude Code와 Codex에 graph를 “켜는” 것보다 중요한 것은 작업의 실제 구조를 말해주는 것입니다. 독립적인 것만 병렬화하고, 결과 형식을 통일하고, 모두 도착했는지 확인하고, 실패와 종료 조건을 코드나 명시적 규칙으로 통제해야 합니다.
