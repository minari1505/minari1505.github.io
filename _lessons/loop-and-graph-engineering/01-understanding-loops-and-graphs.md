- 단일 호출, loop, graph 중 어느 수준이 필요한지 판단하기

## 먼저 한 문장으로

**Loop engineering은 한 작업이 잘 끝날 때까지 반복하는 방법을 설계하는 일이고, graph engineering은 여러 작업이 어떤 순서와 관계로 움직일지 설계하는 일입니다.**

조금 더 쉽게 풀어보겠습니다.

## Loop: 한 사람이 확인하면서 고쳐 나가는 방식

학교에 제출할 글을 쓴다고 해봅시다. 처음 쓴 글이 바로 완벽할 가능성은 낮습니다.

1. 글을 쓴다.
2. 맞춤법과 논리를 확인한다.
3. 문제가 있으면 고친다.
4. 다시 확인한다.
5. 기준을 만족하면 제출한다.

이것이 loop입니다.

```text
목표 → 실행 → 결과 확인 → 수정 필요? ── 아니요 ─→ 종료
         ↑                       │
         └──────── 예 ───────────┘
```

AI 에이전트도 비슷하게 움직일 수 있습니다. 코드를 작성한 뒤 테스트를 실행하고, 실패 메시지를 읽고, 코드를 수정하고, 다시 테스트합니다.

여기서 중요한 것은 단순히 “계속 시도하라”가 아닙니다. 다음과 같은 반복 규칙을 함께 정해야 합니다.

- 무엇을 성공으로 볼 것인가?
- 이전 시도에서 무엇이 달라졌는가?
- 같은 실패가 반복되면 어떻게 할 것인가?
- 몇 번 또는 얼마의 비용까지 허용할 것인가?
- 언제 사람에게 도움을 요청할 것인가?

이런 규칙을 설계하는 일이 **loop engineering**입니다.

## Graph: 여러 작업의 관계를 그리는 방식

이번에는 혼자 쓰는 글이 아니라 팀 보고서를 만든다고 해봅시다.

- 한 사람은 시장 자료를 조사합니다.
- 한 사람은 경쟁 제품을 조사합니다.
- 한 사람은 기술 위험을 검토합니다.
- 세 결과가 모두 모이면 편집자가 하나의 보고서로 합칩니다.
- 마지막 검토에서 문제가 발견되면 해당 부분만 다시 조사합니다.

이 경우에는 반복 하나만 잘 설계해서는 전체 흐름을 설명하기 어렵습니다. 어떤 작업이 먼저이고, 무엇을 동시에 할 수 있으며, 결과를 어디에서 합칠지 정해야 합니다.

```text
                         ┌→ 시장 조사 ───┐
요청 → 작업 계획 → 분배 ─┼→ 경쟁사 조사 ─┼→ 결과 통합 → 검토 → 종료
                         └→ 기술 검토 ───┘              │
                                  ↑                    │
                                  └── 필요한 부분 재작업 ┘
```

이 작업 지도에서 각 작업은 **노드(node)**, 작업 사이의 연결은 **엣지(edge)**라고 부릅니다. 어떤 길로 보낼지 정하는 지점은 **라우터(router)**, 여러 결과를 합치는 지점은 **리듀서(reducer)** 또는 집계 단계라고 부를 수 있습니다.

이처럼 작업 사이의 의존성, 분기, 병렬 실행, 합류와 실패 경로를 설계하는 일이 **graph engineering**입니다.

## 둘은 교체 관계가 아니다

“loop 다음 시대가 graph”라는 표현만 보면 graph가 loop를 없애는 것처럼 들립니다. 실제 관계는 다릅니다.

- loop는 다시 앞 단계로 돌아가는 **순환 그래프**로 표현할 수 있습니다.
- graph의 각 노드 안에는 자체 loop가 들어갈 수 있습니다.
- graph는 반복이 전혀 없는 DAG(Directed Acyclic Graph)일 수도 있습니다.
- 하나의 에이전트가 graph의 여러 노드를 차례로 수행할 수도 있습니다.

즉, loop는 **반복의 품질**에 초점을 두고 graph는 **작업 사이의 관계**에 초점을 둡니다.

```text
Graph
├─ 조사 노드
│  └─ 검색 → 검증 → 부족하면 재검색하는 loop
├─ 작성 노드
│  └─ 초안 → 평가 → 수정하는 loop
└─ 통합 노드
   └─ 형식 검사 → 수정하는 loop
```

## 자주 만나는 네 가지 모양

### 1. Chain: 앞 결과가 다음 작업에 꼭 필요할 때

```text
요구사항 분석 → 구현 → 테스트 → 배포 검토
```

앞 단계의 출력이 다음 단계의 입력이라면 순차 실행이 맞습니다. 단지 보기 좋게 병렬화하면 오히려 틀린 결과를 빨리 만들 뿐입니다.

### 2. Loop: 같은 결과를 기준에 맞을 때까지 개선할 때

```text
초안 → 평가 → 수정 ─┐
       ↑             │
       └─────────────┘
```

명확한 평가 기준과 종료 조건이 있을 때 효과적입니다.

### 3. Router: 입력에 따라 전문 경로가 달라질 때

```text
요청 분류 ┬→ 결제 문제 처리
          ├→ 기술 문제 처리
          └→ 분류 불가 → 사람에게 전달
```

분류 결과가 애매할 수 있으므로 반드시 `분류 불가` 경로를 두는 편이 안전합니다.

### 4. Fan-out/Fan-in: 독립 작업을 나누고 다시 합칠 때

```text
          ┌→ 자료 A 조사 ─┐
요청 → 분배├→ 자료 B 조사 ─┼→ 누락 확인 → 통합
          └→ 자료 C 조사 ─┘
```

병렬 작업이 정말 독립적이어야 합니다. 같은 파일을 동시에 수정하거나, 서로의 결과가 필요한 작업이라면 충돌과 재작업이 늘어납니다.

이 네 가지는 자주 쓰는 예시이지 가능한 graph의 전부는 아닙니다. 실제 시스템은 여러 모양을 섞어 사용합니다.

## 단일 호출, Loop, Graph 비교

| 구분 | 단일 호출 | Loop | Graph |
|---|---|---|---|
| 핵심 질문 | 한 번에 끝낼 수 있는가? | 언제 다시 시도하고 멈출 것인가? | 어떤 작업이 연결되고 갈라지는가? |
| 잘 맞는 일 | 요약, 짧은 변환, 단순 생성 | 코드 수정, 글 개선, 반복 탐색 | 복합 조사, 전문 역할 분리, 승인·복구 흐름 |
| 주요 위험 | 조건 누락 | 무한 반복, 비용 증가 | 조정 비용, 상태 충돌, 통합 병목 |
| 필요한 장치 | 명확한 입력·출력 | 검증 기준, 종료 조건, 예산 | 노드 계약, 라우팅, 상태 소유권, 관찰 가능성 |

## 흔한 오해

### “Graph를 쓰면 무조건 더 빠르다”

독립적인 작업을 병렬로 실행하면 대기 시간을 줄일 수 있습니다. 하지만 마지막 통합이 느리거나 작업들이 서로 의존한다면 이점이 사라집니다. 여러 에이전트가 더 많은 token을 사용했기 때문에 품질이 좋아진 것을 graph 자체의 효과로 착각할 수도 있습니다.

### “Graph는 반드시 여러 에이전트를 사용한다”

아닙니다. graph는 제어 흐름을 표현하는 구조입니다. 하나의 모델이 모든 노드를 수행해도 graph이고, 여러 모델이 한 loop에 참여할 수도 있습니다.

### “Loop는 오래된 방식이라 이제 필요 없다”

graph의 각 노드도 결과를 검증하고 수정해야 합니다. 안정적인 loop가 없는 graph는 실패를 더 넓게 퍼뜨릴 수 있습니다.

## 무엇부터 사용해야 할까?

다음 순서로 복잡도를 올리는 것이 안전합니다.

```text
단일 호출 → 검증 가능한 loop → 필요한 부분만 graph로 분리
```

먼저 한 번의 요청으로 충분한지 확인합니다. 품질을 객관적으로 검사하고 다시 고칠 필요가 있을 때 loop를 추가합니다. 실제 분기, 독립적인 병렬 작업, 부분 실패 복구가 필요할 때 graph를 고려합니다.

좋은 설계는 가장 복잡한 구조가 아니라 **문제를 해결하는 가장 단순한 구조**입니다. Anthropic도 에이전트 시스템을 설계할 때 단순한 구성에서 시작하고, 측정 가능한 이득이 있을 때만 복잡도를 높일 것을 권합니다.

## 세 문장 요약

1. **Loop engineering**은 실행·검증·수정·종료의 반복 규칙을 설계합니다.
2. **Graph engineering**은 여러 작업의 순서·분기·병렬화·합류·복구 경로를 설계합니다.
3. 둘은 경쟁하지 않습니다. 안정적인 graph는 잘 설계된 loop를 포함할 수 있습니다.
