## 1. 핵심 AI 용어의 관계

AI, 머신러닝, 딥러닝, 신경망, LLM은 **서로 관련 있지만 바꿔 쓸 수 있는 말은 아니에요.** 외우기 시험이 아니라, 누가 "AI"를 느슨하게 쓸 때 **무슨 뜻인지 되물을 수 있을 만큼** 이해하는 게 목표예요.

| **머신러닝 (ML)** | 고정된 규칙에만 의존하지 않고 **데이터에서 패턴을 배우는** 시스템 | AI의 부분집합 |

| **신경망** | 연결된 층으로 이뤄진 **모델 구조**. 작동 원리까지 알 필요는 없음 | 딥러닝이 흔히 쓰는 구조 |

### 왜 이 계층이 대화에서 중요할까

고객이 **"우리 이미 사기 탐지에 AI 써요"** 라고 하면, 그건 고정된 비즈니스 규칙일 수도, ML 분류기일 수도, 생성형 AI 워크플로일 수도, 이것들의 조합일 수도 있어요.

### LLM은 어디에 있을까

- **LLM(대규모 언어 모델)** = 언어를 처리하고 생성하도록 학습된 **딥러닝 모델의 한 종류**.
- 채팅·초안·요약·추론 지원·콘텐츠 생성 같은 익숙한 생성형 AI 경험 뒤에 있어요.
- 일부 최신 LLM은 **멀티모달**이라 텍스트·이미지·오디오 등 여러 종류의 입력을 다룰 수 있어요 (모델·제품에 따라 다름).
- 하지만 **LLM이 AI의 전부는 아니에요.** 거래 분류, 패턴 탐지, 추천, 이미지 분석, 오디오 처리, 의사결정 지원처럼 언어 생성이 중심이 아닌 AI도 많고, 여러 역량을 조합한 시스템도 있어요.

> 고객에게(의역): "LLM은 특히 언어 기반 작업에서 중요한 AI 모델의 한 종류예요. 하지만 AI 분야 전체는 아니에요."

**핵심 습관: 되묻기.** 누가 "AI"라고 하면, 어떤 기술이나 경로인지 가정하기 전에 실제로 뭘 뜻하는지 들어요.

## 2. "모델"이란 무엇인가

"모델"은 AI 대화에서 가장 중요한 단어이면서 **가장 오해하기 쉬운** 단어예요. 사람마다 다른 뜻으로 쓰거든요.

### 한 단어, 두 가지 흔한 의미

| 의미 | 설명 | 예 |
|---|---|---|
| **일반적 의미** | 학습한 패턴을 바탕으로 **입력을 출력으로 바꾸는 학습된 시스템** | 글 → 요약 / 이미지 → 내용 식별 / 정형 데이터 → 분류 |
| **제품·플랫폼에서의 의미** | 제품·인터페이스·**API**(소프트웨어끼리 소통하는 방식) 설정에서 고르는 **이름 붙은 모델 옵션** | 개발자가 설정에서 고르는 특정 모델 |

<div class="oa-eli">
  <span class="oa-eli__head">🚗 쉽게 말하면</span>
  <p>"무슨 <b>차</b> 타?"라고 물으면 "자동차요"(일반적인 탈것)일 수도, "OO사 2026년형 하이브리드요"(구체적인 차종)일 수도 있어요. "모델"도 똑같아요. 그냥 <b>AI 시스템</b>을 말하는 건지, <b>특정 이름의 옵션</b>을 말하는 건지 먼저 알아야 대답이 엇나가지 않아요.</p>
</div>

고객이 **"어떤 모델을 써야 해요?"** 라고 물을 때 가능한 뜻:

1. 어떤 **종류의 AI 시스템**이 필요한가?
2. 개발자가 **어떤 이름의 모델 옵션**을 설정해야 하나?
3. 제품 경험 안에서 **어떤 모델을 쓸 수 있나**?
4. 비용·**지연 시간(latency, 응답 받기까지 걸리는 시간)**·추론·멀티모달 요건에 **가장 맞는 모델**은?

> 되묻기(의역): "모델이라고 하신 게 AI 시스템 전반인가요, 아니면 쓰고 계신 특정 모델 옵션인가요?"

### 모델 vs 제품 · 플랫폼 · API

| 구분 | 의미 |
|---|---|
| **모델** | 입력을 처리해 출력을 만드는 학습된 시스템 |
| **제품·워크스페이스** | 사람이 AI와 상호작용하는 **사용자용 경험** (예: ChatGPT) |
| **API 표면(API surface)** | AI를 제품·워크플로에 넣을 때 쓰는 **개발자용 인터페이스** |

<div class="oa-eli">
  <span class="oa-eli__head">🎮 쉽게 말하면</span>
  <p>게임 <b>엔진</b>(모델)과 그 엔진으로 만든 <b>게임</b>(제품), 그리고 개발자가 엔진을 다루는 <b>도구 상자</b>(API)는 다른 거예요. 같은 게임이 엔진을 바꿀 수도 있고, 같은 엔진이 여러 게임에 쓰일 수도 있죠.</p>
</div>

- 같은 제품·API가 **여러 모델**을 지원할 수 있어요.
- 같은 모델이 제품·요금제·설정·가용성에 따라 **여러 경험**에서 쓰일 수 있어요.
- ChatGPT, Codex, API로 만든 앱은 모델을 서로 다르게 노출·사용할 수 있고, **에이전트 기능**과 **오픈 웨이트(open-weight) 모델 배포 결정**은 워크플로와 운영 환경에 따른 별개의 고려 사항이에요 (강의 기준).
- 이 코스에선 API 설정이나 엔드포인트 선택은 몰라도 돼요. 핵심은 **모델을 그 모델이 쓰이는 경험·인터페이스와 헷갈리지 않는 것.**

## 3. 파트너가 듣게 될 모델 어휘

**트랜스포머 · 파운데이션 모델 · 프런티어 모델**은 기술적으로 들리지만 **알아보는 수준**이면 충분해요. 이 셋은 모델의 **서로 다른 측면**을 설명하는 말이라 **동의어가 아니에요.**

<div class="oa-eli">
  <span class="oa-eli__head">🏠 쉽게 말하면 — 집으로 비유</span>
  <p><b>트랜스포머</b> = "철근 콘크리트 구조예요"(어떻게 지었나). <b>파운데이션 모델</b> = "주거·사무실·가게 어디로든 쓸 수 있는 다용도 건물이에요"(얼마나 넓게 쓰나). <b>프런티어 모델</b> = "지금 이 동네에서 가장 최신 건물이에요"(지금 얼마나 앞서 있나 — 내년엔 바뀔 수 있음). 한 건물이 셋 다일 수도 있지만, 각각 다른 질문에 대한 답이에요.</p>
</div>

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">🏗️</span><span class="oa-card__title">트랜스포머 (Transformer)</span><b>모델을 어떻게 만들었나</b> (아키텍처). 제품도, 특정 모델 이름도 아님. 언어·코드·멀티모달 AI의 큰 발전을 이끌었고 많은 최신 시스템이 이 방식이나 그 발전형을 씀. 단, <b>고객 유스케이스에 맞는지는 알려 주지 않음</b></div>
  <div class="oa-card"><span class="oa-card__icon">🧱</span><span class="oa-card__title">파운데이션 모델 (Foundation model)</span><b>얼마나 넓게 쓰이고 적응하나</b>. 텍스트 생성·요약·분석·질의응답·코딩 등 여러 작업을 지원하는 범용 모델. 프롬프트·도구·검색·파인튜닝·제품 워크플로로 방향을 잡음. <b>"OpenAI 것"이란 뜻도, 그 자체로 완성된 솔루션이란 뜻도 아님</b></div>
  <div class="oa-card oa-card--hl"><span class="oa-card__icon">🏔️</span><span class="oa-card__title">프런티어 모델 (Frontier model)</span><b>그 시점에 얼마나 앞서 있나</b>. 비교 시점에 가장 유능한 축에 드는 모델에 붙는 <b>움직이는 라벨</b>. 새 모델이 나오면 바뀜 → 고객에게 특정 모델을 약속하기 전에 <b>최신 공식 출처로 확인</b></div>
</div>

고객이 이 용어를 쓰면 **어떤 측면을 묻는지** 먼저 정리해요.

| 고객이 묻는 건… | 관련 용어 |
|---|---|
| 아키텍처(어떻게 만들었나)? | 트랜스포머 |
| 활용 범위(얼마나 넓게)? | 파운데이션 모델 |
| 현재 역량(얼마나 앞섰나)? | 프런티어 모델 |
| 특정 제품·기술 설정에서 어떤 옵션을 쓰나? | 이름 붙은 모델 옵션 → 확인 필요 |

## 4. 역량을 먼저, 이름은 필요할 때 확인 ⭐

모델 이름, 모델 계열, 추천 선택지, 가격, 가용성, 제품 지원은 **시간이 지나며 바뀌어요.** 모델 이름부터 꺼내면 말이 금방 **낡거나 틀릴** 수 있고, 필요한 **역량**부터 설명하면 더 오래 맞고 고객의 실제 문제와 이어져요.

<div class="oa-eli">
  <span class="oa-eli__head">📱 쉽게 말하면</span>
  <p>친구가 "폰 추천해 줘" 하면 바로 "OO 15 사!"라고 하기보다 "<b>사진을 많이 찍어? 게임해? 예산은?</b>"을 먼저 묻죠. "사진 잘 나오고 배터리 오래 가는 폰이 필요하네"(역량)를 정한 뒤, 매장 가기 직전에 <b>지금 나와 있는 최신 기종</b>(이름)을 확인하는 게 맞아요. 몇 달 지나면 추천 기종이 바뀌니까요.</p>
</div>

고객은 모델 **이름**보다 AI가 **해야 할 일**에 더 관심이 있어요: 대량의 고객 피드백 요약, 여러 단계 분석을 위한 더 강한 추론, 대량 처리용 비용 최적화 옵션, 텍스트+이미지 같은 멀티모달 처리 — 이게 모두 **역량 요구**예요.

> 파트너 기준: **구체성이 필요할 땐 구체적으로. 정확한 이름이 핵심이 아닐 땐 역량 중심으로.**

### 역량 먼저 말하기 예시

| ❌ 대신에 | ✅ 이렇게 (의역) |
|---|---|
| "고객 피드백 요약은 무조건 이 모델로 해요." | "대량의 고객 피드백 요약에 맞는 모델이 필요해요. 추천 전에 정확한 모델 옵션을 확인하죠." |
| "이 모델이 추론엔 항상 최고예요." | "이 워크플로는 여러 단계 분석에 더 강한 추론이 필요할 수 있어요. 그 요건에 맞는 최신 옵션을 확인해요." |
| "제일 싼 모델 쓰세요." | "이 워크플로는 **처리량(throughput, 정해진 시간에 많은 요청 처리)** 이 중요해서 비용과 응답 시간이 관건이에요. 품질 요건은 지키는 비용 최적화 모델을 찾아봐요." |
| "이 모델이면 다 돼요." | "텍스트와 이미지를 함께 처리하는 멀티모달 역량이 필요할 수 있어요. 어떤 최신 옵션이 지원하는지 확인하죠." |

역량 중심 언어는 대화를 **흐리게 만드는 게 아니라 더 정확하게** 만들어요.

### 정확한 모델 이름이 필요한 순간

<div class="oa-vs">
  <div class="oa-vs__good">
    <span class="oa-vs__label">💬 역량 중심이면 충분</span>
    <ul>
      <li>디스커버리(고객 요구 파악)</li>
      <li>초기 설명</li>
    </ul>
  </div>
  <div class="oa-vs__bad">
    <span class="oa-vs__label">🔍 정확한 이름 + 공식 출처 확인 필수</span>
    <ul>
      <li>코드·설정 (개발자가 구현할 때)</li>
      <li>가격·비용·처리량·지연·가용성 논의</li>
      <li>요금제·가용성 안내</li>
      <li>고객에게 하는 구체적 약속</li>
      <li>오래 정확해야 하는 구현 문서</li>
      <li>공식 솔루션 추천</li>
    </ul>
  </div>
</div>

<div class="oa-eli">
  <span class="oa-eli__head">✍️ 연습 — 모델 이름 중심 문장 고쳐 쓰기</span>
  <p>원문: "모든 고객 지원 워크플로엔 최신 모델을 써야 해요." / "이 모델이 모든 요약에 최고예요." / "문서가 길어서 꼭 이 모델이어야 해요." / "그냥 제일 싼 모델이면 돼요."</p>
  <p>모범 예(의역): "고객 지원 워크플로는 고객 대화를 정확히 요약하고 예상 처리량을 감당할 모델이 필요할 수 있어요. 구현이나 가격 추천 전에 정확한 모델 옵션을 확인하죠." → 각 문장마다 <b>언제 이름을 확인할지</b> 한 줄씩 덧붙이기.</p>
</div>

## 5. 시스템은 어떻게 배우나

세 가지 용어를 **알아보는 수준**으로만 익혀요. 학습 파이프라인 설계나 세부 원리는 몰라도 돼요.

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">📝</span><span class="oa-card__title">지도 학습 (Supervised)</span><b>정답이 있는 예시</b>로 배움. 입력-출력 쌍을 보고 패턴을 익혀 새 사례를 분류·예측<br><small>"예시와 기대 출력을 분명히 정할 수 있을 때 유용"</small></div>
  <div class="oa-card"><span class="oa-card__icon">🗺️</span><span class="oa-card__title">비지도 학습 (Unsupervised)</span><b>정답 없이</b> 데이터 속 구조를 찾음. 묶기·군집화·구조 발견<br><small>"정답 예측이 아니라 구조·패턴 발견이 목표일 때 유용"</small></div>
  <div class="oa-card"><span class="oa-card__icon">🎮</span><span class="oa-card__title">강화 학습 (Reinforcement)</span>연속된 <b>행동과 피드백</b>으로 개선. 어떤 행동이 더 나은 결과로 이어지는지 시행착오로 배움<br><small>"고정된 데이터셋이 아니라 피드백으로 행동을 개선"</small></div>
</div>

<div class="oa-eli">
  <span class="oa-eli__head">🎒 쉽게 말하면</span>
  <p><b>지도 학습</b>: 답지가 있는 문제집으로 공부해요. 문제 풀고 → 답 맞춰 보고 → 패턴을 익혀요.<br><b>비지도 학습</b>: 지도 없이 처음 간 도시를 걸어 다니다 "여긴 식당 골목, 저긴 학원가"처럼 동네를 스스로 알아채요.<br><b>강화 학습</b>: 자전거 타기. 넘어지면(나쁜 피드백) 자세를 고치고, 잘 가면(좋은 피드백) 그 방법을 계속 써요.</p>
</div>

| | 지도 학습 | 비지도 학습 | 강화 학습 |
|---|---|---|---|
| 배우는 재료 | 정답 라벨이 붙은 예시 | 라벨 없는 데이터 | 행동과 결과에 대한 피드백 |
| 목표 | 새 사례 분류·예측 | 구조·묶음 발견 | 더 나은 결과로 가는 행동 |
| 흔한 연관 | 과거 기록 기반 예측 | 비슷한 항목 묶기 | 제어 문제, 순차적 의사결정, 행동이 미래 상태에 영향을 주는 시스템 |

### 섞인 시스템 알아보기

실제 AI 시스템은 **여러 방식을 섞어요.** 개발 단계엔 한 방식, 다듬는 단계엔 다른 방식, 평가·안전·제품 동작엔 또 다른 과정을 쓸 수 있죠. 그러니 고객 대화에서 모든 시스템을 **한 칸에 억지로 넣지 말고**, 지금 이야기하는 **주된 학습 아이디어**에 집중해요.

> 되묻기(의역): "이 시스템은 정답 있는 예시로 배우나요, 정답 없이 패턴을 찾나요, 아니면 시간에 걸친 피드백으로 개선되나요?"

실제 고객 솔루션은 여러 기법이나 포트폴리오 구성요소를 섞을 수 있으니, 다음 단계는 **빠른 라벨 붙이기가 아니라 되묻기**인 경우가 많아요.

## 정리

- **AI ⊃ 머신러닝 ⊃ 딥러닝**, 신경망은 딥러닝이 흔히 쓰는 구조. **LLM**은 언어용 딥러닝 모델의 한 종류로 중요하지만 AI의 전부는 아니다.
- 고객이 "AI"라고 하면 **고치지 말고 되묻는다** — 고정 규칙? 데이터로 배우는 모델? 생성형 AI 워크플로?
- **"모델"은 두 뜻**: 입력을 출력으로 바꾸는 학습된 시스템 / 제품·API에서 고르는 이름 붙은 옵션. 그리고 **모델 ≠ 제품 ≠ API**.
- 모델은 고객 정보를 **자동으로 알지 못한다.** 알맞은 설정·승인된 연결로 제공된 **컨텍스트**를 쓴다.
- **트랜스포머(어떻게 만들었나) · 파운데이션(얼마나 넓게) · 프런티어(지금 얼마나 앞섰나)** 는 서로 다른 질문에 답한다.
- **역량을 먼저 말하고**, 코드·가격·가용성·약속·공식 추천처럼 이름이 중요할 땐 **최신 공식 출처로 확인**한다.
- **지도(정답 있는 예시) · 비지도(정답 없이 구조 발견) · 강화(피드백으로 개선)** — 실제 시스템은 섞여 있으니 라벨보다 되묻기.
