고객은 AI가 별도 작업 공간이 아니라 **이미 쓰는 제품 · 시스템 · 워크플로 안**에 나타나길 원할 때가 많아요. 지원 포털, 내부 도구, 고객용 앱, 반복 업무 프로세스처럼요. OpenAI API는 그런 필요를 위한 **빌드·통합 경로**예요. **개발자가 아니어도 돼요** — 목표는 API가 무엇을 하는지, 언제 API 경로를 탐색할 만한지 **알아보는 것**이에요. 제품·모델 이름은 모두 **(강의 기준)** 이에요.

## 1. API란 무엇이고 왜 중요한가

### 왜 API가 AI 도입에 중요한가

API가 없으면 AI는 **별도 제품·화면**에서만 쓸 수 있어요. 하지만 많은 조직은 AI가 **기존 경험의 일부**(지원 포털 · 내부 앱 · 고객 여정 · 업무 프로세스 · 소프트웨어 제품)가 되길 원해요.

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">🔗</span><span class="oa-card__title">통합 단순화</span>시스템이 연결되고 정보를 주고받게</div>
  <div class="oa-card"><span class="oa-card__icon">⚡</span><span class="oa-card__title">개발 가속</span>AI를 처음부터 만들지 않고 기존 역량 활용</div>
  <div class="oa-card"><span class="oa-card__icon">📏</span><span class="oa-card__title">생산성·품질</span>반복 빌드 노력 감소, 시스템 상호작용 표준화</div>
  <div class="oa-card oa-card--hl"><span class="oa-card__icon">✨</span><span class="oa-card__title">새 제품·서비스</span>사람들이 이미 쓰는 소프트웨어에 AI를 직접 내장</div>
</div>

AI는 고객 질문에 답하고, 문서를 요약하고, 지원 티켓을 분류하고, 구조화된 기록을 만들고, 워크플로 안에서 승인된 도구를 쓸 수 있어요. **API는 AI 역량을 소프트웨어 안에서 작동하는 것으로 바꿔 줘요.**

> 예: 고객이 로그인해 계정을 관리하고 문의를 여는 지원 포털이 있어요. 회사는 고객이 **포털을 떠나지 않고** 승인된 지원 콘텐츠 기반 답과 다음 단계 안내를 받길 원해요. 바로 쓰는 AI 작업 공간으론 부족해요 — 경험이 **회사 제품 안**에 있어야 하니까요. 앱이 사용자 요청과 승인된 시스템의 맥락을 API로 보내고 응답을 포털 안에 보여 줘요. **경험은 회사 것, AI는 뒤에서 일해요.**

## 2. OpenAI API란

OpenAI 개발자 플랫폼은 모델 · API · 도구 · 문서를 제공해요. OpenAI API는 **AI 기반 소프트웨어를 만드는 빌드 경로**예요.

### 누가 에이전트 작업을 조율하나 — 두 가지 실행 방식 (강의 기준)

<div class="oa-eli">
  <span class="oa-eli__head">🎪 쉽게 말하면 — 직접 진행 vs 행사 대행사</span>
  <p>학교 축제를 <b>학생회가 직접 진행</b>(Responses API, 앱 소유 흐름)하면 순서 짜기, 장비 대여, 기록까지 다 챙겨야 해요. <b>행사 대행사</b>(Agents API, 관리형 실행)를 부르면 진행은 대행사가 맡아요. 하지만 <b>어떤 공연을 허용할지, 예산이 얼마인지, 끝나고 잘됐는지 평가하는 건 여전히 학생회</b>예요. 대행사를 불렀다고 학교 강당 열쇠가 자동으로 생기지도 않죠.</p>
</div>

| | 앱 소유 흐름 | 관리형 에이전트 실행 |
|---|---|---|
| 대표 API | **Responses API** | **Agents API** (Codex 하네스 제공) |
| 누가 루프를 돌리나 | 개발자가 워크플로 조율 · 맞춤 함수 실행 · 상태·통제 관리 | OpenAI가 하네스(맥락 · 도구 실행 · 서브에이전트 조율)를 유지 |
| 개발자가 고르는 것 | 전부 | 모델 · 도구 · 실행 환경 |
| 고객 책임 | 권한 · 평가 · 승인 | **똑같이 권한 · 평가 · 승인** — 관리형 실행이 고객 시스템 접근을 주거나 책임을 없애지 않음 |

둘 다 **맞춤 사용자 경험**을 지원할 수 있어요. GPT-6 Astra(강의 기준) 같은 모델을 API로 쓸 수 있고, **도구 · 권한 · 승인 통제**는 그 모델을 둘러싼 **애플리케이션**이 정해요.

핵심 질문은 "AI가 도울 수 있나?"만이 아니라 **"고객이 자기가 통제하는 소프트웨어 안에 사는, 만들어진 경험이 필요한가?"** 예요. 예: 고객 지원 포털 · 직원 헬프데스크 · 제품 온보딩 흐름 · 문서 처리 워크플로 · 내부 운영 도구 · 고객용 모바일 앱.

### 개발자가 만들 수 있는 것 — 빌딩 블록

| 역량 영역 | 무엇을 하나 |
|---|---|
| 텍스트 생성·요약 | 생성 · 재작성 · 요약 · 변환 |
| 추론·여러 단계 문제 해결 | 정보 해석 · 옵션 비교 · 여러 단계 요청 처리 |
| 이미지 이해·생성 | 시각 입력 다루기 · 이미지 생성 |
| 오디오·음성·실시간 | 새 **대화형 음성 앱은 GPT-Live**가 권장 출발점, 실시간 음성 세션을 직접 통제하려면 **Realtime API**, 대화 없는 전사·음성 합성은 **전용 오디오 API** (강의 기준) |
| 임베딩·검색 | 키워드가 아니라 **의미**로 관련 정보 찾기, 승인된 콘텐츠에 답을 근거시키기 |
| 도구 사용·함수 호출 | 승인된 도구·함수·외부 시스템에 연결해 조회하거나 통제된 행동 실행 |
| 모더레이션·안전장치 | 안전 검사 등 책임 있는 동작 지원 |

이 코스에선 **구현 방법을 알 필요는 없어요.** API가 **소프트웨어에 AI를 넣는 빌딩 블록**을 준다는 게 핵심이에요.

### 왜 API로 만드나

API 기반 솔루션은 **AI가 어디에 나타나고, 어떻게 동작하고, 시스템과 어떻게 연결되는지를 더 통제**하고 싶을 때 유용해요: 기존 제품에 내장 · 맞춤 UX · 고객 데이터·워크플로 연결 · 많은 사용자·거래로 확장 · 앱 안 AI 동작 통제 · 비즈니스 맥락이 필요한 반복 워크플로에 지능 내장.

### API · ChatGPT · Codex 비교

| 경로 | 가장 잘 맞을 때 | 기억법 |
|---|---|---|
| **ChatGPT** | 바로 쓰는 작업 환경이 맞을 때. Chat 협업, Work 위임, **dot**(개인 지속 책임), **Team Task**(팀 소유 예약·이벤트 프로세스) | 사람들이 AI와 협업하거나 개인·팀 업무를 위임 |
| **OpenAI API** | AI가 기존 제품 · 앱 · 포털 · 내부 도구 · 워크플로 안에 **만들어져야** 할 때 | 개발자가 제품·시스템에 AI를 만들어 넣음 |
| **Codex** | 소프트웨어 전달(계획 · 작성 · 리뷰 · 테스트 · 디버깅 · 문서화 · 유지보수) | 엔지니어링팀의 소프트웨어 전달 지원 |

**반복 업무라고 자동으로 맞춤 API 앱이 필요한 건 아니에요.** (→ 4장에서 다시)

## 3. 대표 API 사용 사례와 통합 패턴 ⭐

고객은 "Responses API 주세요"라고 하지 않아요. "제품에 AI 어시스턴트를 넣고 싶어요", "직원이 정보를 찾게 돕고 싶어요", "문서에서 정보를 뽑고 싶어요", "음성 경험을 만들고 싶어요", "AI를 업무 시스템에 연결하고 싶어요"라고 하죠. 패턴을 알아보는 기준: **AI가 무엇을 해야 하나 · 경험은 어디 사나 · 제품·시스템·워크플로에 만들어 넣어야 하나.**

**패턴은 섞여요.** 포털 속 지원 어시스턴트가 승인된 도움말을 검색하고(②), 답을 요약하고, 후속 질문을 하고, 승인된 시스템을 불러 주문 상태를 확인(④)할 수 있어요.

### ① 내장 어시스턴트 — 그리고 ChatGPT Site와의 차이

API로 만든 어시스턴트는 경험을 **고객 제품 안**에 두지만, 그렇다고 고객이 **모든 단계를 직접 호스팅·조율해야 하는 건 아니에요** — 실행 환경과 런타임은 별도 선택이에요. 한편 **ChatGPT Site**(강의 기준)는 가벼운 웹 경험이에요. 방문자가 자기 연결 앱에 **읽기 전용** 접근을 허락할 수 있지만 만든 사람의 자격 증명이 넘어가진 않아요. 웹 기반 AI 필요가 **모두 같은 API 빌드를 요구한다고 가정하지 마세요.**

### ② 검색·지식 접근

<div class="oa-eli">
  <span class="oa-eli__head">📚 쉽게 말하면 — 도서관 사서</span>
  <p>"우주에 관한 쉬운 책"을 찾으면 사서는 먼저 관련 책을 <b>여러 권 뽑아 오고</b>(검색, retrieval), 그중 <b>가장 맞는 순서로 정리</b>해서(랭킹·재랭킹) 건네줘요. 제목에 '우주'가 없어도 '별과 행성' 책을 찾아 주는 건 <b>뜻으로 찾기</b> 때문이에요(임베딩). 그리고 사서는 <b>열람 권한이 있는 서가</b>에서만 책을 꺼내요.</p>
</div>

검색은 쿼리와 관련된 후보를 돌려주고, **랭킹·재랭킹**이 관련도 순으로 정렬한 뒤 선택된 정보가 답을 뒷받침해요. 모델이 원래 아는 것에만 기대지 않고 **승인된 콘텐츠에 근거**하게 돕죠. 단, 내부 원천 데이터는 **적절한 시스템 · 권한 · 접근 통제 · 거버넌스**로 다뤄야 해요. API는 경험을 만들 뿐, **어떤 정보를 누구에게 보여 줄지는 조직이 관리**해요.

### ③ 구조화 정보 — 형식이 맞다고 내용이 맞는 건 아니다

- **JSON**: 앱 사이에 구조화 데이터를 주고받는 표준 형식. **JSON Schema**: 그 데이터의 모양(필수 필드 · 값 타입 · 허용 값)을 정의.
- **Structured Outputs**(강의 기준): 모델 응답이 정의된 구조를 따르게 해서 다른 시스템이 일관되게 처리하게 함.

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">⛔ 착각</span>
    <ul>
      <li>JSON 형식이 맞으니 내용도 정확하다</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✅ 실제</span>
    <ul>
      <li><b>올바른 형식 ≠ 올바른 답</b></li>
      <li>모델이 요청한 출력을 못 줄 때 처리 · 빠진 정보 확인 · 중요한 세부 검증이 여전히 필요</li>
    </ul>
  </div>
</div>

> 예: 고객 운영팀이 주문 변경 이메일 수백 통을 받아요. API 워크플로가 **주문 번호 · 요청 변경 · 고객 이름 · 긴급도**를 리뷰용 구조화 기록으로 뽑아요. 가치는 AI가 이메일을 "읽는 것"이 아니라 **지저분한 정보를 업무 프로세스가 쓸 수 있는 형태로 바꾸는 것**이에요.

### ④ 도구 사용과 행동 워크플로

지원 어시스턴트가 배송 지연을 설명하려면 **주문 상태**와 **서비스 정책**이 둘 다 필요해요. 앱 소유 함수 호출 흐름에선: 모델이 조회를 **요청** → 앱이 승인된 함수를 **실행** → 결과가 모델로 **돌아가요.**

| 개념 (강의 기준) | 뜻 | 주의 |
|---|---|---|
| **비동기 도구 호출** | 서로 독립적인 조회면, 결과를 기다리는 동안 다른 유용한 작업 계속 | 그 결과에 **의존하는 답은 기다려야** 함 (추측 금지). 모델 응답을 백그라운드로 돌리는 것과도 다름 |
| **중간 방향 조정 (mid-turn steering)** | 지원되는 응답 도중 사용자가 방향을 바꾸거나 추가 | **이미 시작된 행동·도구 호출을 취소하거나 되돌리지 않음** |
| **Agents API** | 관리형 런타임이 도구와 맥락을 조율 | 허용 접근·행동 정의와 결과 확인은 **고객 몫** |
| **MCP Events** | 구독한 이벤트가 생기면 에이전트에 알림 → 작업 시작 가능 | **데이터 접근이나 행동 권한을 주지 않음** |

행동 워크플로엔 **경계**가 필요해요: 접근 가능한 도구 · 할 수 있는 행동 · **승인이 필요한 행동** · 쓸 수 있는 데이터 · 활동 리뷰 방법. 여기서 **맥락 · 런타임 · 관측 가능성**이 중요해지기 시작해요.

### ⑤ 멀티모달·실시간 경험

예: 손 안 쓰고 작업을 끝내는 음성 어시스턴트 · 말을 글로 바꾸는 전사 · 시각 정보를 해석하는 이미지 이해 · 창작·제품용 이미지 생성 · 질문하면 바로 말로 답하는 실시간 튜터링.

## 4. API 솔루션이 필요한 상황 알아보기

### 작업에 맞는 역량 고르기 — 초기 인식 질문

- AI가 어떤 작업을 해야 하나?
- 텍스트 · 이미지 · 오디오 · 실시간 중 무엇이 필요한가?
- 비공개·공개 정보를 **검색**해야 하나?
- 모델이 **도구를 부르거나 행동**해야 하나?
- 출력이 **구조화**되거나 **리뷰**돼야 하나?
- 조직은 시간이 지나며 어떻게 **모니터링 · 리뷰 · 개선**하나?

깊은 기술 설계 질문이 아니라 **초기 인식 질문**이에요. 그리고 **모델 선택은 별개 결정**이에요.

### 비용은 "요청 1건"이 아니라 "리뷰를 통과한 기록 1건"으로

<div class="oa-eli">
  <span class="oa-eli__head">🧮 쉽게 말하면 — 싼 문제집의 함정</span>
  <p>싼 문제집을 샀는데 오답이 많아서 정답지를 다시 찾고 선생님께 물어보느라 시간이 두 배로 들었다면, 정말 싼 걸까요? 모델도 마찬가지예요. <b>요청 1건 가격</b>이 아니라 <b>리뷰를 통과한 기록 1건을 만드는 데 드는 비용</b>(실패한 결과 · 응답 시간 · 사람이 고친 횟수까지 포함)으로 비교해요.</p>
</div>

- 주문 이메일 워크플로라면 **같은 대표 메시지**로 후보 모델을 시험해요. 저렴한 모델은 **리뷰 과정에 충분할 만큼 정확할 때만** 좋은 선택이에요.
- 텍스트 모델 사용량은 **토큰**(입력·출력 텍스트의 작은 단위)으로 측정. 일부 도구는 **별도 사용 비용**을 더할 수 있어요. 대표 요청과 예상 볼륨으로 추정하고, 운영 중엔 실제 사용량·지출을 모니터링해요.
- **지출 알림(spend alert)** 은 정해진 수준에 도달하면 알려 줄 뿐이고, **설정된 지출 한도(spend limit)** 는 해당 트래픽을 멈출 수 있어요. 예산 임계값을 **보장된 상한으로 믿기 전에** 실제로 어떤 통제가 있고 설정됐는지 확인해요.
- 약속 전에 기술팀에 **모델 접근 · 필요한 기능 지원 · 필요한 도구 사용 권한**을 확인해 달라고 해요.

### 무엇이 API 사용 사례를 만드나

| API 신호 | 예 |
|---|---|
| AI 경험이 기존 제품 · 앱 · 포털 · 내부 도구 **안에** 있어야 함 | 포털 속 정책 Q&A |
| 업무 시스템 · DB · 워크플로 도구와 **연결** | 주문 시스템 조회 |
| 출력이 다른 시스템용 **구조화 형식** | 리뷰용 레코드 |
| 특정 사용자 여정·제품 흐름에 **맞춤** | 제품 온보딩 안내 |
| 고객이 통제하는 맞춤 제품·통합 안에서 **반복 실행** | 수백 건 이메일 처리 |

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">⛔ API 신호가 아님</span>
    <ul>
      <li>"매주 반복되는 일이니 API 앱을 만들자" — <b>반복 자체는 API 신호가 아님</b></li>
      <li>자격 있는 워크스페이스면 <b>Team Task</b>가 맞춤 앱 없이 팀 반복 프로세스를, <b>dot</b>이 개인 지속 책임을 지원할 수 있음</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✅ 가장 강한 단서</span>
    <ul>
      <li><b>"AI가 쓸모 있으려고 사용자가 제품 · 시스템 · 프로세스를 떠나면 안 된다."</b></li>
      <li>먼저 <b>누가 그 일을 소유하는지</b>, 사용자에게 <b>맞춤 제품 경험</b>이 필요한지 묻기</li>
    </ul>
  </div>
</div>

> 대비: 직원이 ChatGPT로 사내 메모 초안을 쓰는 건 **바로 쓰는 작업 공간**. HR 포털이 포털 안에서 승인된 문서로 정책 질문에 답하고, 접근 규칙을 따르고, 형식 있는 답을 돌려준다면 **API 기반**일 가능성이 커요. 차이는 **AI 경험이 어디에 살고 무엇과 연결되느냐**예요.

### 안전 · 신뢰성 · 사람 검토

API 시스템은 고객 · 데이터 · 업무 프로세스에 영향을 주니 안전장치가 필요해요. 전체를 설계할 필요는 없지만 **범주를 알아보고 기술·보안·거버넌스 지원이 필요한 곳**을 짚을 수 있어야 해요.

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">🛡️</span><span class="oa-card__title">모더레이션·안전 검사</span>잠재적으로 위험·부적절한 콘텐츠 식별</div>
  <div class="oa-card"><span class="oa-card__icon">📐</span><span class="oa-card__title">Structured Outputs</span>신뢰할 구조 계약이 필요하면 JSON Schema로 응답 모양 정의</div>
  <div class="oa-card"><span class="oa-card__icon">🔧</span><span class="oa-card__title">도구 범위·승인</span>허용 도구 · 허용 행동 · 승인 지점 정의</div>
  <div class="oa-card"><span class="oa-card__icon">🚧</span><span class="oa-card__title">권한·접근 경계</span>사용자와 워크플로에 맞는 데이터·도구·시스템만</div>

  <div class="oa-card"><span class="oa-card__icon">🔭</span><span class="oa-card__title">로깅·모니터링·리뷰</span>디버그 · 감사 · 리뷰 · 개선</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🧑‍⚖️</span><span class="oa-card__title">고영향 결정의 사람 감독</span>Usage Policies가 자격 있는 사람 검토를 요구하는 고영향 결정이면, 행동·의존 전에 <b>필수</b></div>
</div>

역할에 따라 쓰임이 달라요: **영업·사업개발**은 기술 검증이 필요한 기회를 알아보는 데, **기술·배포** 역할은 접근 · 도구 사용 · 모니터링 · 리뷰에 더 깊은 설계가 필요한 곳을 찾는 데 써요.

**관리형 실행은 누가 에이전트 루프를 돌리는지를 바꿀 뿐, 누가 책임지는지는 바꾸지 않아요.** 고객은 여전히 접근·승인 경계를 정하고, 결과를 평가하고, **중단된 작업이 어떻게 복구되는지** 확인해요. **설정된 런타임 ≠ 운영 준비 완료**예요.

### 종합 예시 — HR 포털에서 API 적합성 알아보기

<ol class="oa-flow">
  <li><strong>위치</strong>기존 HR 포털 안에서 경험</li>
  <li><strong>맥락</strong>승인된 정책 문서</li>
  <li><strong>권한</strong>직원마다 자격이 다름</li>
  <li><strong>형식</strong>포털이 보여 줄 일관된 형식 + 출처 표시</li>
  <li><strong>사람 검토</strong>해결 안 된·민감한 질문은 HR로</li>
  <li><strong>개선</strong>모니터링하며 계속 개선</li>
</ol>

이 단계에서 기술 솔루션을 정의할 필요는 없어요. **기존 시스템에 내장 · 특정 워크플로 맞춤 · 올바른 비즈니스 맥락 · 필요한 곳의 리뷰**라는 신호를 알아보는 게 중요해요.

## 정리

- **API = 정해진 규칙으로 시스템끼리 소통하는 방법.** 요청 → 처리 → 응답 → 사용. AI에선 모델 역량을 **이미 쓰는 제품 · 시스템 · 워크플로 안으로** 가져오는 길이다.
- **OpenAI API = AI 기반 소프트웨어의 빌드·통합 경로.** **Responses API**는 앱 소유 흐름, **Agents API**는 관리형 에이전트 실행 (강의 기준). **UX · 모델 · 런타임 · 실행 환경은 각각 별도 선택.**
- 빌딩 블록: 텍스트 · 추론 · 이미지 · 오디오·실시간(GPT-Live / Realtime API / 전용 오디오 API) · 임베딩·검색 · 도구·함수 호출 · 구조화 출력 · 안전장치.
- 다섯 패턴: **내장 어시스턴트 · 검색·지식 접근 · 구조화 추출 · 도구 사용 · 실시간·멀티모달.** 서로 섞인다. **형식이 맞다고 내용이 맞는 건 아니다.**
- **인터페이스 · 작업을 시작시키는 이벤트 · 행동 권한은 서로 다르다.** 중간 방향 조정은 이미 시작된 행동을 취소하지 않는다.
- API의 가장 강한 단서: **사용자가 제품·시스템을 떠나지 않아야 AI가 쓸모 있다.** **반복만으론 API 신호가 아니다** — Team Task나 dot이 맞을 수 있다.
- 비용은 **리뷰를 통과한 결과 1건**으로 비교하고, **알림 ≠ 한도**임을 확인한다.
- 안전장치: 모더레이션 · 구조화 출력 · 도구 범위·승인 · 권한 경계 · **키는 비밀** · 속도 제한 · 보존 · 로깅·모니터링 · 고영향 결정의 사람 검토. **관리형 실행도 책임은 고객에게.**
