## 학습 목표

- 서로 독립적인 **세 가지 포트폴리오 결정 레이어**(사용자·제품 표면 / 역량·아키텍처 / 배포·운영) 설명하기
- 표면 레이어에서 **ChatGPT Chat · ChatGPT Work · Codex · API로 만든 앱·프로세스**가 어디에 맞는지 설명하기
- 표면을 넓혀 주는 **역량·인터페이스**(Apps · Workspace Agents · 음성 · 이미지 생성 · 딥 리서치 등) 알아보기
- 간단한 **포트폴리오 매핑 프레임워크**로 고객 워크플로를 표면 · 역량 · 배포 결정에 연결하기
- 여전히 **제품·기술·보안·거버넌스·배포 검증**이 필요한 질문 찾기

<ol class="oa-flow">

  <li><strong>다섯 패턴</strong>직원 생산성 · 고객 경험 · 소프트웨어 · 자동화 · 배포</li>
  <li><strong>워크플로 우선 매핑</strong>문제 → 표면 → 역량 → 배포·운영</li>

조직은 AI를 다양하게 써요. 직원이 일을 더 잘하게 돕거나, 제품·서비스에 AI를 넣거나, 소프트웨어 개발을 지원하거나, 워크플로를 자동화하거나, 특정 배포 요건을 맞추거나. 이 코스는 **바로 제품을 추천하지 않고** 고객의 필요를 가능한 OpenAI 경로에 연결하는 **실용적인 지도**를 줘요. 제품명·모델명은 모두 **(강의 기준)** 이고 바뀔 수 있어요.

## 1. OpenAI 포트폴리오 이해하기

### 왜 기술이 여러 가지인가

조직마다 **푸는 문제가 다르기** 때문이에요. 어떤 곳은 직원의 리서치·초안·분석이 먼저고, 어떤 곳은 제품 안에 AI를 넣는 게 먼저예요. 엔지니어링팀은 소프트웨어 수명주기 전반의 도움이, 운영팀은 도구·시스템을 넘나드는 단계 조율이 필요하죠. 배포 요건이 AI가 **어디서 어떻게** 돌 수 있는지를 정하기도 해요.

AI 도입이 성숙할수록 가치는 개인 생산성 도구를 넘어 **워크플로 · 시스템 · 팀 · 거버넌스 · 운영 모델에 지능을 심는 것**으로 옮겨 가요.

<ol class="oa-flow">
  <li><strong>워크플로·결과</strong>무엇을 개선하려 하나?</li>
  <li><strong>어디서</strong>사람·워크플로는 주로 어디서 일하나?</li>
  <li><strong>무엇이 필요</strong>어떤 역량·아키텍처?</li>
  <li><strong>일의 모양</strong>협업 · 위임된 여러 단계 · 도구 · 승인?</li>
  <li><strong>어떻게 운영</strong>어디서 돌고, 어떻게 통제·모니터링?</li>
</ol>

이 질문들은 대화를 **"어떤 제품 써야 해요?"** 에서 **워크플로 · 표면 · 역량 · 운영 요건의 지도**로 옮겨 줘요.

- **에이전트형 동작**은 ChatGPT Work, API 프로세스, 다른 적절한 표면 안에서 나타나는 **역량**이지 별도 제품 경로가 아니에요.
- **오픈 웨이트 모델**은 검증할 **배포 옵션 하나**이지, 모든 통제·프라이버시·데이터 레지던시 요건의 기본 답이 아니에요.

### 모델 선택은 별개의 결정

<div class="oa-eli">
  <span class="oa-eli__head">🚗 쉽게 말하면 — 자동차와 엔진</span>
  <p>ChatGPT Work · Codex · API 앱은 <b>자동차 종류</b>(승용차 · 트럭 · 버스)예요. Astra · Sol · Luna는 그 안에 들어가는 <b>엔진</b>이에요. 같은 차에도 다른 엔진을 고를 수 있고, 동네 마트 갈 때 경주용 엔진이 필요하진 않죠. 그리고 내가 <b>어떤 엔진을 쓸 수 있는지</b>(접근 권한)는 차 모델 · 요금제 · 설정에 따라 또 달라요.</p>
</div>

| 모델 (강의 기준) | 설계 의도 | 메모 |
|---|---|---|
| **GPT-6 Astra** | 까다로운 **여러 단계 작업** | — |
| **GPT-6.1 Sol** | 복잡한 전문 업무와 **에이전트형 작업** | Work · Codex · API에서 제공, 일반 Chat에는 아직 없음 |
| **GPT-6 Luna** | **효율적인 대량 작업**에 평가해 볼 옵션 | 작업 품질 기준을 충족하는지 확인하고 **검토·재작업까지 포함한 총비용**으로 비교 |

이건 **순위가 아니라 출발점**이에요. 예를 들어 일상 지원 요청 분류엔 복잡한 조사 브리프만큼의 추론이 필요 없을 수 있어요. **대표적인 실제 작업**으로 적합한 모델들을 비교해 필요한 품질을 맞추는 걸 고르세요. 그리고 **제품 경험 · 모델 · 접근 요건**은 각각 따로 생각해요.

### 지능이 포트폴리오 전반에서 작동하는 방식

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">📚</span><span class="oa-card__title">맥락 (Context)</span>AI가 비즈니스에 대해 <b>아는 것</b>: 회사 지식, 파일, 데이터, 정책, 워크플로, 시스템, 권한</div>
  <div class="oa-card"><span class="oa-card__icon">⚙️</span><span class="oa-card__title">런타임 (Runtime)</span>워크플로가 <b>어디서 어떻게 실행되나</b>: ChatGPT, 앱, 엔지니어링 환경, 도구, 시스템, 고객 운영 환경. 표면·역량과는 구분</div>
  <div class="oa-card"><span class="oa-card__icon">🔭</span><span class="oa-card__title">관측 가능성 (Observability)</span>AI 활동을 <b>모니터링·추적</b>: 무엇을 하는지, 무엇에 접근하는지, 성능, 결과와 오류</div>
  <div class="oa-card oa-card--hl"><span class="oa-card__icon">⚖️</span><span class="oa-card__title">거버넌스 (Governance)</span>AI 사용을 정하는 <b>정책 · 역할 · 권한 · 승인 경계 · 검토 요건 · 책임</b></div>
</div>

맥락과 런타임은 **일이 수행되는 방식**, 관측 가능성은 **가시성**, 거버넌스는 **규칙과 책임**이에요. 특히 **모니터링(관측)과 정책·통제(거버넌스)를 섞지 마세요.**

> 예: 지역 보험사가 "AI를 쓰고 싶어요"라고 해요. 고객 서비스팀은 정책 정보에 빠르게 접근하길(→ **ChatGPT** Chat/Work + Apps·검색·Workspace Agents), 엔지니어링팀은 레거시 앱 유지보수 도움을(→ **Codex**), 제품팀은 디지털 채널 속 AI 경험을(→ **API로 만든 앱**) 원해요. 조직 전체에 범주 하나를 고르는 게 아니라 **워크플로마다** 세 레이어로 매핑하고, 운영·거버넌스 요건은 일관되게 적용해요.

## 2. 고객 워크플로에서 단서 찾기

고객 요청은 늘 정확하지 않아요. "생산성 개선", "AI 기능 만들기", "개발자 지원", "프로세스 자동화"처럼 말하죠. **누가 관여하는지, 경험이 어디에 속하는지, 시스템이 무엇을 해야 하는지, 어떤 운영 요건이 있는지** 단서를 찾아요.

| 단서 묶음 | 전형적인 신호 | 가장 관련 있는 레이어·선택 |
|---|---|---|
| **사람·팀을 위한 AI** | 직원이 주 사용자 · 리서치·분석·글쓰기·소통·의사결정 지원 · 생산성이 목표 · 직원이 AI로 직접 일함 | 표면: **ChatGPT** |
| **제품·앱 안의 AI** | 소프트웨어에 내장 · 기존 제품·포털·서비스로 상호작용 · 맞춤 UX · 제품 여정의 일부 | 표면: **API로 만든 앱·프로세스** |
| **소프트웨어 전달용 AI** | 개발자가 주 사용자 · 코딩·테스트·디버깅·리뷰·문서화·유지보수·현대화 · 엔지니어링 생산성 | 표면: **Codex** |
| **일을 수행하는 AI** | 여러 곳에서 정보 수집 · 여러 단계 · 행동 조율 · 도구·승인·인수인계 · 사람 감독 | 레이어: **역량**(에이전트형) — 표면·배포는 따로 |
| **배포 유연성이 필요한 AI** | 인프라·운영 소유·프라이버시·지연 시간·신원·보존·로깅·데이터 이동 요건이 결정을 좌우 | 레이어: **배포·운영** |

### ChatGPT 안에서: 일하는 관계와 공유 결과물

<div class="oa-eli">
  <span class="oa-eli__head">📒 쉽게 말하면 — 모둠 과제</span>
  <p>친구와 함께 아이디어를 내는 건 <b>Chat</b>, "이 부분 보고서 완성해 줘"라고 맡기는 건 <b>Work</b>, "내 마감일을 계속 챙겨 줘"는 개인 비서 <b>dot</b>, "매주 모둠 회의록을 정리해 줘"는 모둠 전체의 당번 일인 <b>Team Task</b>예요. 그리고 완성된 보고서를 올려 두는 <b>공유 문서(Page)</b>는 결과물일 뿐, <b>그 문서를 누가 계속 고칠지</b>는 따로 정해야 해요.</p>

| 일하는 관계 (강의 기준) | 무엇을 지원 | 핵심 |
|---|---|---|
| **ChatGPT Chat** | 함께 생각하고 창작 | 협업 |
| **ChatGPT Work** | 경계가 있는 **위임된 결과** 하나 | 결과로 끝남 |
| **dot** | 한 사람의 **지속적인 책임** | 유지된 맥락 · 연결된 앱 · 클라우드 컴퓨터 |
| **Team Task** | **팀 소유** 프로세스, 일정·이벤트로 실행 | 팀 **서비스 계정**과 설정된 연결 사용. 만든 사람의 개인 기록·메모리를 상속하지 않음 |
| **Workspace Agents** | 설정·게시된 **재사용** 워크플로 | 자격 있는 워크스페이스에서. 위 옵션의 다른 이름이 아님 |

| 공유 결과물 (강의 기준) | 뜻 |
|---|---|
| **Space** | Page와 관련 작업을 모아 두는 곳. 계정 수준 워크스페이스가 **아님** |
| **Page** | 공유·편집 가능한 문서. 공유해도 개인 채팅·메모리가 자동 공유되진 않지만, **Page에 복사한 정보는 대상에게 보임.** Page는 결과물이지 그것을 최신으로 유지하는 프로세스가 아님 |

> 예: 마케팅 매니저가 메모 다듬기엔 **Chat**, 캠페인 브리프 하나엔 **Work**, 허용된 캠페인 정보를 계속 지켜보는 덴 **dot**. 매주 팀 브리프라면 **Team Task** + 검토된 **Page**를 공유 결과물로. 고르기 전에 **담당자 · 연결 신원(어느 계정으로 접근하나) · 대상 · 가용 접근**을 확인해요.

### 제품 안의 AI: 실행 관리 방식은 별개

- 앱이 에이전트 단계를 **직접 조율**할 수 있어요 — Responses API(강의 기준)를 통해서도.
- **Agents API**(강의 기준)는 OpenAI가 **에이전트 루프를 실행**하는 관리형 실행 옵션을 더해요. 모든 Responses 워크플로를 대체하라는 요구가 아니에요.
- UX와 실행 환경은 **따로** 결정해요. 고객은 여전히 허용 도구 · 데이터 · 승인 · 모니터링을 정의하고, 관리형 실행이 모든 행동을 허락하거나 모든 맞춤 도구를 자동 실행하지 **않아요.**

### 소프트웨어 전달: Codex Cloud

Codex Cloud(강의 기준)는 저장소 · 의존성 · 승인된 접근을 갖춘 **재사용 가능한 개발 환경**에서 일해요. 작업마다 자기 작업 공간이 있고, 지원 기기 간에 이어서 할 수 있어요. 하지만 인수인계 땐 **변경된 파일과 테스트 근거를 검토**해야 하고, **클라우드에서 돌았다고 승인·병합·운영 준비가 된 건 아니에요.**

### 배포 유연성: 하나의 요건 ≠ 최종 추천

고객이 "AI가 우리가 직접 통제하는 환경에서 돌아야 해요"라고 하면 중요한 운영 요건이지만 **최종 추천을 하기엔 부족해요.** 앱은 어디서 도는지, 모델 추론은 어디서 일어나는지, 누가 각 구성요소를 운영하는지, 데이터는 어떻게 움직이는지(레슨 7의 네 가지 배포 질문)를 먼저 밝혀요. 고객 실행 오픈 웨이트 모델이 옵션일 수 있지만 **호스팅·내장 방식도 요건을 충족할 수 있어요.**

> 작은 차이가 표면을 바꿔요. "고객이 포털을 떠나지 않고 질문하고 도움받길 원해요" → 사용자는 **고객**, 경험은 **기존 제품 안** → **API로 만든 앱**. "고객 성공 매니저가 계정을 조사하고 후속 노트를 준비하는 걸 돕고 싶어요" → 사용자는 **직원** → **ChatGPT**(협업이면 Chat, 위임이면 Work). 역량과 배포는 여전히 따로 결정해요.

패턴별 주의점:

- **④ 자동화**: 운영팀이 정기 공급업체 검토 브리프를 원하면, 먼저 ChatGPT의 팀 소유 **Team Task**인지 기존 시스템 안 **API 프로세스**인지 정하고, 출처·연결 신원·트리거·허용 행동·검토 지점·대상을 정해요. **반복 일정이 표면을 정하거나 공급업체에 대한 결정을 허락하지 않아요.** 에이전트형 동작은 역량이지 별도 제품 경로가 아니에요.
- **⑤ 배포**: 규제 대상 조직이 내부 분석용 AI를 탐색할 때, 호스팅·내장·고객 실행 중 무엇이 맞을지 정하기 전에 **앱 위치 · 추론 위치 · 운영 주체 · 데이터 이동**을 먼저 나눠요. 이 패턴은 **어떻게 돌고 운영되는지**를 정하지, UX나 역량을 정하지 않아요.

> 예: 금융 서비스 조직 — 관계 매니저의 빠른 계정·정책 정보 접근(**①**), 디지털 포털 안 고객 지원(**②**), 검토 프로세스의 수작업 인수인계 감소(**④**), 배포 요건이 경로에 영향을 주는지(**⑤**). 하나의 단서가 아니라 **패턴의 묶음**이에요. 패턴을 알아본 뒤 각각을 세 레이어로 매핑해요.

## 5. 워크플로 우선으로 포트폴리오 매핑하기

### 고객 문제에서 시작하라

기술 대화는 제품에서 시작하기 쉽지만, 더 효과적인 대화는 **고객이 풀려는 문제**에서 시작해요.

| 비즈니스 질문 | 워크플로 질문 |
|---|---|
| 어떤 문제를 풀려 하나? | 어떤 일이 일어나야 하나? |
| 어떤 비즈니스 결과를 추구하나? | 어떤 결과를 추구하나? |
| 왜 지금 중요한가? | 지금 **마찰**은 어디에 있나? |

비슷한 제품 요청도 **전혀 다른 문제**에서 나올 수 있고, 같은 문제도 여러 표면·역량·운영 모델을 지원할 수 있어요.

### 누가 일하나 — 사용자와 책임자를 구분

관여자: 직원 · 고객 · 엔지니어링팀 · 운영팀 · 관리자·검토자 · 리더·의사결정자. 관여하는 사람이 표면에 영향을 줘요(직원 → ChatGPT Chat/Work, 제품 속 고객 → API 앱, 엔지니어 → Codex, 여러 단계 운영팀 → 에이전트형 역량, 단 표면은 따로).

**사용자와 책임 있는 소유자를 구분하세요.** 경계 있는 위임 작업인지, 한 사람의 지속 책임인지, 팀 소유 프로세스인지? 일을 유용하게 유지하고, 결과를 검토하고, 멈추거나 에스컬레이션할 **사람·팀의 이름**을 정해요. **공유 결과를 받는 사람이 자동으로 그 일의 소유자가 되진 않아요.**

### 경험은 어디에 사나

ChatGPT Chat/Work · API로 만든 앱·프로세스 · Codex와 지원 엔지니어링 표면 · 그 경로 안의 웹·모바일·데스크톱·내장 표면. 도구·시스템을 넘나들어야 하면 표면을 고른 **뒤에** 필요한 에이전트형 역량을 더하고, 환경 통제가 주요 요건이면 배포·운영 옵션을 **따로** 평가해요.

결과를 **어디서 검토하고 누가 볼 수 있는지**도 정해요. Page로 공유해도 유지 담당자가 정해지거나 자동 업데이트되진 않아요. **대상(audience)** 은 원본 파일 접근 권한, 워크플로 실행 위치와 **별개**예요.

### 매핑 프레임워크

<ol class="oa-flow">
  <li><strong>① 고객 문제·워크플로</strong>무엇을 개선? 어떤 결과가 중요?</li>
  <li><strong>② 사용자·제품 표면</strong>사람·워크플로는 주로 어디서?</li>
  <li><strong>③ 역량·아키텍처</strong>무엇을 하고·접근하고·조율?</li>
  <li><strong>④ 배포·운영</strong>어디서 어떻게 돌고, 통제·모니터링?</li>
</ol>

그다음 네 가지 운영 개념을 확인해요.

| 개념 | 질문 |
|---|---|
| **맥락** | AI에 필요한 정보와 비즈니스 지식은? |
| **런타임** | 워크플로는 어디서 어떻게 실행? |
| **관측 가능성** | 활동·성능·결과를 어떻게 모니터링·추적? |
| **거버넌스** | 어떤 정책·권한·승인·검토 지점·책임이 적용? |

계속되거나 공유되는 일이라면: **누가 소유 · 허용된 출처와 도구 · 어느 계정이 접근을 제공 · 누가 결과를 보나 · 무엇을 만들고 누가 검토 · 어떤 행동에 승인 필요.** 반복 업무라면 **무엇이 시작시키고 · 언제 검토하고 · 언제 멈추거나 사람에게 묻는지**까지.

> 예: 의료 기관이 환자 지원 문서 작성 개선을 원해요. 처음엔 "AI 쓰기"로 시작했지만, 제품 요청이 **워크플로 평가**로 바뀌어요. 직원 표면은 ChatGPT Chat/Work, 승인된 맥락과 여러 단계 지원은 Apps·검색·에이전트형 역량, 배포·권한·관측·거버넌스·사람 검토는 **별도 검증**. 최종 추천이 아니라 **첫 번째 지도**와 검증 목록을 만드는 거예요.

### 연습 — 워크플로를 포트폴리오에 매핑하기

  <span class="oa-eli__head">✍️ 네 가지 워크플로로 스냅샷 써 보기 (실제 제품 접근 불필요)</span>
  <p>예시: ① 내부 보고서를 조사·준비하는 직원 ② 소프트웨어 제품 안에서 AI 도움을 받는 고객 ③ 레거시 앱을 현대화하는 엔지니어 ④ 여러 단계 운영 프로세스를 자동화하는 팀</p>

## 정리

- 포트폴리오는 **세 개의 독립 레이어**: **사용자·제품 표면**(어디서) · **역량·아키텍처**(무엇을) · **배포·운영**(어떻게 돌고 통제). 같은 급의 경로가 아니다.
- 표면: **ChatGPT Chat**(협업) · **ChatGPT Work**(위임) · **Codex**(소프트웨어) · **API로 만든 앱·프로세스**(내장). 에이전트형 동작은 **역량**, 오픈 웨이트 모델은 검증할 **배포 옵션** (강의 기준).
- 음성 · 이미지 생성 · 딥 리서치 · Apps · Workspace Agents · Intelligent UI는 표면을 **넓히는** 역량·인터페이스. **모델 선택**(Astra · Sol · Luna, 강의 기준)과 **접근 요건**은 또 별개 — 대표 작업으로 품질·속도·총비용을 비교한다.
- ChatGPT 안에선 **Work(한정 위임) · dot(개인 지속) · Team Task(팀 반복, 서비스 계정) · Workspace Agents(재사용)**, 공유 결과물은 **Space의 Page**. 결과물 공유 ≠ 유지 프로세스 ≠ 권한.
- **트리거·인터페이스·관리형 실행·클라우드 실행은 행동 권한이나 승인이 아니다.** 결과는 따로 검토·검증한다.
- 다섯 패턴: **직원 생산성 · 고객 경험 · 소프트웨어 전달 · 워크플로 자동화 · 유연한 배포**. 한 조직에 여러 패턴이 섞이면 **워크플로별로** 매핑한다.
- 매핑 순서: **고객 문제·워크플로 → 표면 → 역량 → 배포·운영**, 그리고 **맥락 · 런타임 · 관측 가능성 · 거버넌스** 점검. 소유자 · 허용 접근 · 검토 가능한 결과 · 대상을 분명히 하고, 모르는 건 **열린 질문**으로 남긴다. 목표는 최종 추천이 아니라 **첫 번째 지도**다.
