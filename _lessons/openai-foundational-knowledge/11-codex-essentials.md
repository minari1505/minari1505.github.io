소프트웨어 개발은 코드 작성만이 아니에요. 문제를 조사하고, 변경을 테스트하고, 리뷰하고, 문서화하고, 기존 앱을 유지보수하죠. **개발자가 아니어도** 이 코스를 들을 수 있어요 — 목표는 Codex가 **어디에 맞고 왜 중요한지** 기본 감각을 갖는 거예요. 제품·모델 이름은 모두 **(강의 기준)** 이에요.

## 1. Codex란 무엇이고 왜 중요한가

<div class="oa-eli">
  <span class="oa-eli__head">🔧 쉽게 말하면 — 공구 vs 수리 기사님</span>
  <p>전통적인 코딩 도우미는 <b>좋은 공구</b>예요. "드라이버 줘" 하면 드라이버를 주지만, 나사를 어디에 박을지·잘 박혔는지는 내가 다 해야 하죠. Codex는 <b>수리 기사님</b>에 가까워요. "세탁기에서 물이 새요"라고 하면 원인을 찾고, 부품을 고치고, 물을 틀어 다시 확인한 뒤 "이렇게 고쳤고 이건 확인했어요"라고 <b>보고</b>해요. 그래도 <b>수리비를 내고 "됐어요"라고 승인하는 건 집주인(엔지니어)</b>이에요.</p>
</div>

Codex는 **소프트웨어 개발을 위한 OpenAI의 코딩 에이전트**예요. 프롬프트에 코드 조각 하나 돌려주는 게 아니라, 코드 이해 · 이슈 조사 · 변경 구현 · 테스트·리뷰 지원 · 문서 유지까지 **소프트웨어 전달 워크플로 전반**을 도와요.

### 어디서 쓰나 (강의 기준)

| 사용 경로 | 뜻 |
|---|---|
| **ChatGPT 데스크톱 앱** | 데스크톱에서 Codex에 지시 |
| **Codex CLI** | CLI = 명령줄 인터페이스, 터미널에서 글자로 작업 |
| **IDE 확장** | IDE = 통합 개발 환경(코드 편집기 + 도구). 코드 옆에서 AI와 작업 |
| **Codex Cloud** | 코드 · 도구 · 접근 권한을 갖춘 클라우드 환경에서 작업 실행 |
| **GitHub 워크플로** | 지원되는 GitHub 흐름 안에서 |

**지시를 내리는 곳이 작업이 실행되는 곳과 늘 같진 않아요.** 쓸 수 있는 기능과 허용 범위는 선택한 경험과 설정에 따라 달라요.

### 왜 Codex가 있나 — 많은 엔지니어링 문제는 "워크플로 문제"

엔지니어링팀이 매일 쓰는 시간: 시스템·요구사항 이해 · 이슈·결함 조사 · 구현·개선 · 테스트·검증 · 리뷰·품질 유지 · 문서화·지식 공유 · 기존 시스템 유지보수. 코드베이스가 커지고 의존성이 늘고 레거시가 쌓일수록 조율이 어려워져요.

전통 도구는 이 중 **코드 생산 한 부분**만 도와요. 팀에 필요한 건 **무엇을 바꿀지 이해하고, 안전하게 적용하고, 동작을 검증하고, 결과를 리뷰하고, 시스템 지식을 유지하는 것**까지예요.

### ChatGPT · API · Codex 비교

| 경로 | 누가 | 무엇을 |
|---|---|---|
| **ChatGPT** | 사람들 | 작업 공간에서 지식 업무를 **협업(Chat) 또는 위임(Work)** |
| **OpenAI API** | 빌더 | 제품 · 앱 · 워크플로에 AI **내장** |
| **Codex** | 엔지니어링팀 | **소프트웨어 전달** 작업 지원 |

이 경로들은 **함께 쓰일 수 있어요.** 예를 들어 API 기반 솔루션을 만들고 유지하는 엔지니어링 작업을 Codex가 도울 수 있어요. 엔지니어링 필요를 **기본값처럼** 일반 직원 생산성이나 API 빌드로 취급하지 말고, 먼저 **정말 소프트웨어 전달 문제인지** 확인해요.

> 예: 백로그가 쌓이는 엔지니어링팀. 리더는 처음에 "개발자가 코드를 더 빨리 쓰게 하려면?"을 물어요. 들여다보니 개발자는 시스템 이해 · 결함 조사 · 구현 · 테스트 작성 · 리뷰 · 문서 유지에 시간을 나눠 쓰고 있어요. 질문이 **"엔지니어가 소프트웨어 전달 작업을 더 효과적으로 끝내게 하려면?"** 으로 바뀌는 순간 Codex가 관련돼요.

### 산출물(Output) vs 성과(Outcome) ⭐

<div class="oa-eli">
  <span class="oa-eli__head">🍳 쉽게 말하면 — 레시피 한 장 vs 차려진 저녁</span>
  <p>"계란말이 레시피 알려 줘"로 받는 건 <b>산출물</b>(레시피 한 장)이에요. "가족 저녁 식사 준비"는 <b>성과</b>예요 — 장보기, 요리, 맛보기, 상 차리기까지 이어져야 이뤄지죠. 레시피는 쓸모 있지만 그 자체로 저녁이 되진 않아요.</p>
</div>

| 산출물 (Output) | 성과 (Outcome) |
|---|---|
| 코드 조각 | 버그가 조사되고 수정안이 제안됨 |
| 설명 | 기능이 프로젝트 기대에 맞게 구현됨 |
| 구현 제안 | 기대 동작을 검증하는 테스트가 추가·갱신됨 |
| 가능한 원인 목록 | 코드 변경의 위험이 리뷰됨 |
| 테스트 케이스 초안 | 미래 엔지니어를 위해 문서가 갱신됨 |

유용한 질문: **"우리는 산출물 한 조각을 요청하는가, 아니면 Codex에게 소프트웨어 작업을 완료 쪽으로 밀어 달라고 하는가?"** 이게 Codex 대화를 **리뷰 가능한 엔지니어링 성과**에 묶어 줘요. 성과 중심이라고 사람이 빠지는 건 아니에요.

### 프롬프팅 vs 위임(Delegation)

| | 프롬프팅 | 위임 |
|---|---|---|
| 요청 | AI에게 응답을 요구 | 목표 + 충분한 맥락을 주고 목표를 향해 일하게 함 |
| 예 | "리스트를 정렬하는 Python 함수 써 줘" | 아래 Blossom 예시 |
| 결과 | 산출물 | 리뷰 가능한 엔지니어링 성과 + 근거 |

위임에 들어가는 것: **목표 정의 · 관련 맥락 · 필요한 정보·시스템·요구사항·제약에 대한 접근 · 바꾸면 안 되는 것 · 결과 확인 방법 · 진행·결과 검토.**

> 위임 예시 (강의의 가상 샘플 앱): "Blossom Airlines 예약 앱에서 좌석 선택 후 발생하는 예약 실패를 **재현**해 줘. 선택한 좌석 · 부가 서비스 · 마일리지 · 총액을 잃지 않고 예약이 확정되도록 **가장 작은 승인된 수정**을 해. 관련 검사를 돌리고 변경 · 결과 · 남은 한계를 **리뷰용으로** 돌려줘. **병합하거나 배포하지 마.**"

### 사람과 에이전트의 협업

사람은 여전히 **방향 · 맥락 · 판단 · 승인 · 책임**을 제공해요. 감독 방식은 표면과 설정에 따라 달라요 — Codex는 정해진 작업 공간 안의 허용된 일을 끝낼 수 있지만, **설정된 경계를 넘거나 · 네트워크를 쓰거나 · 높은 권한이 필요한 행동**은 승인 단계를 부를 수 있어요.

  <div class="oa-card"><span class="oa-card__icon">⚖️</span><span class="oa-card__title">② 다른 맥락이 필요한 결정</span>제품 · 보안 · 법무 · 고객 맥락이 필요한 결정이 있음</div>
  <div class="oa-card"><span class="oa-card__icon">💥</span><span class="oa-card__title">③ 영향 범위</span>변경은 사용자 · 시스템 · 성능 · 안정성에 영향을 줌</div>

### 코드 리뷰: 살펴보기 ≠ 피드백 게시 ≠ 승인 ≠ 병합

<div class="oa-eli">
  <span class="oa-eli__head">📝 쉽게 말하면 — 친구 숙제 봐 주기</span>
  <p>친구 숙제를 <b>읽어 보는 것</b>, 빨간 펜으로 <b>코멘트를 써서 돌려주는 것</b>, 선생님이 <b>"통과" 도장을 찍는 것</b>, 그 숙제를 <b>제출함에 넣는 것</b>은 다 다른 행동이에요. 코드 리뷰(PR)도 마찬가지: 변경을 <b>살펴보거나 Codex에게 조사를 시키는 것</b>은 피드백 게시 · 승인 · 병합이 <b>아니에요.</b> 코멘트는 <b>즉시 전송될 수 있으니</b> 게시 전에 검토하고, 승인·병합은 최신 변경과 근거를 보고 따로 결정해요.</p>
</div>

### 검증 근거 읽는 법 — Blossom Airlines 사례 (강의 기준)

<ol class="oa-flow">
  <li><strong>재현</strong>좌석 선택 후 결제 실패 재현</li>
  <li><strong>수정</strong>가장 작은 승인된 수정</li>
  <li><strong>자동 검사</strong>예약 로직 자동 테스트</li>
  <li><strong>재빌드·재시도</strong>실패하던 예약 여정 반복 → 확정, 좌석·부가·마일·총액 유지</li>
  <li><strong>사람 판단</strong>근거가 충분한가?</li>
</ol>

**유용한 근거지만 모든 시나리오를 증명하진 않아요.** 자동 검사는 **UI가 아니라 예약 로직**을 다뤘고, 앱 재시험은 모든 요금이 아니라 **Blossom One 요금만** 다뤘어요. 엔지니어가 **근거가 충분한지** 판단해야 해요.

> 짧은 예시들: 신입 개발자가 알림 서비스를 이해(Codex가 관련 파일 요약·흐름 설명 → 개발자가 코드베이스와 대조) · 오류 처리 소폭 변경(Codex가 제어 위치를 찾고 수정 제안 → 엔지니어 리뷰) · 버그 수정에 테스트 추가(Codex가 재현 테스트 초안 → 엔지니어가 돌려 보고 의미 있는지 확인) · 워크플로 변경 후 기술 노트 초안 → 팀이 리뷰 후 저장소에 추가.

병목이 늘 **코드 작성**은 아니에요. 시스템 이해 · 변경 검증 · 리뷰 · 품질 유지 · 지식 갱신도 병목이죠. Codex는 AI를 **코드 생성기가 아니라 소프트웨어 전달 작업의 지원**으로 보게 해요.

### 에이전트형 위임의 다섯 요소 ⭐

레슨 8(에이전트와 에이전트형 워크플로)의 **소프트웨어 전달 버전**이에요: 맥락 · 경계 · 도구 · 사람 검토를 갖춘 목표 지향 작업.

| 요소 | 질문 |
|---|---|
| **목표 (Objective)** | 일이 끝나면 무엇이 참이어야 하나? |
| **맥락 (Context)** | Codex에 필요한 정보는? 클라우드 작업이면 **어떤 준비된 환경**이 저장소 · 의존성 · 도구 · 승인된 접근을 주나? 빠진 건 시작 전에 확인 |
| **제약 (Constraints)** | 바꾸면 안 되는 것? 지켜야 할 규칙·요구사항·경계? |
| **기대 결과 (Expected outcome)** | 리뷰용으로 무엇을 만들거나 준비하나? |
| **검토 기대 (Review expectations)** | 사람은 결과를 어떻게 평가하나? |

> 예: "CSV에 중복 이메일이 있을 때 고객 가져오기가 실패하는 이유를 조사해 줘. **가져오기 검증이 어디서 일어나는지부터** 찾아. **DB 스키마는 바꾸지 마.** 가장 작고 안전한 수정을 추천하고 돌려야 할 테스트를 요약해." → 코드만 요구하지 않고 목표 · 맥락 · 경계 · 검토 경로를 담고 있어요.

### 오래 걸리는 비동기 작업

<ol class="oa-flow">
  <li><strong>환경 준비</strong>저장소 · 의존성 · 도구 · 승인된 서비스 접근. 설정·검사 리뷰 후 재사용용으로 게시</li>
  <li><strong>작업 실행</strong>작업마다 자기 작업 공간. 경계 있는 목표, 빠진 의존성·권한 먼저 확인</li>
  <li><strong>검토하고 이어가기</strong>변경 파일 · 테스트 근거 · 남은 한계 → 다듬기 · 재검사 · 커밋/PR 결정</li>
</ol>

헷갈리기 쉬운 포인트 (강의 기준):

- **환경 게시 ≠ 미래 코드 변경 승인.**
- **자동 GitHub 리뷰**는 저장소 · 연결 · 리뷰 정책을 **따로** 설정해야 해요. 클라우드 코딩용 환경 게시와 별개예요.
- 긴 작업 · 자동화 · 병렬 작업에도 범위를 벗어나면 **방향을 바꾸거나 멈출 담당자**가 필요해요.
- 좋은 습관: **"이 작업이 계속되기 전에 사람 판단이 필요한 결정 지점은 어디인가?"** Codex가 추가 지시 없이 해도 되는 구현·검증 단계를 미리 합의하고, 최종 보고엔 **변경 · 실제로 돌린 검사 · 결과 · 남은 한계**를 요구해요. **병합·배포 결정은 사람 리뷰어에게.**
- GPT-6 Astra(강의 기준)에선 변경에 맞는 **의미 있는 검사**를 쓰고, 실패 · 새 변경 · 해결 안 된 우려가 있으면 테스트를 넓히거나 반복해요.

### 왜 중요한가

잠재적 이점: 효율 · 반복 노력 감소 · 복잡한 워크플로 지원 · 더 가치 있는 엔지니어링에 집중 · **이슈 → 리뷰된 결과**로 더 빠르게. 잘 정의된 일을 위임하면 엔지니어는 **아키텍처 · 제품 판단 · 복잡한 문제 해결 · 리뷰** 같은 사람 전문성이 필요한 일에 더 시간을 쓸 수 있어요. 그래도 **무엇이 출시되는지에 대한 책임은 팀**에 있어요.

## 5. 왜 조직이 Codex에 관심을 갖나

### 소프트웨어 전달 = 비즈니스 역량

소프트웨어는 제품 · 서비스 · 고객 경험 · 내부 운영 · 혁신을 받쳐요. 전달이 느려지면 **제품 출시가 밀리고, 고객 경험 개선이 늦어지고, 내부 시스템이 비효율적으로 남고, 유지보수가 혁신을 밀어내요.** 기초 단계에선 비즈니스 케이스를 숫자로 만들 필요는 없지만, **왜 조직이 신경 쓰는지**는 알아야 해요. 기술직이 아니어도 **엔지니어링 워크플로를 설계하는 척하지 않고** 비즈니스 영향에 집중하면 신뢰 있게 대화할 수 있어요.

### 흔한 엔지니어링 압박

| 압박 | 뜻 |
|---|---|
| 복잡도 증가 | 시스템이 커지고 얽혀 이해하기 어려워짐 |
| 기술 부채 | 예전 결정·지름길·낡은 시스템이 변경을 느리고 위험하게 |
| 유지보수 책임 | 새 기능을 만들면서 기존 시스템도 안정적으로 |
| 전달 압박 | 더 빠른 출시 · 더 많은 기능 · 빠른 고객 대응 |
| 품질 기대 | 안정성 · 보안 · 유지보수성 · UX를 희생하지 않기 |

이 압박들은 **서로 얽혀 있어요.** Codex는 **마법 해결책이 아니라** 워크플로 일부를 지원해 팀이 더 효과적으로 일하게 돕는 방법이에요.

## 정리

- **Codex = 소프트웨어 개발용 OpenAI 코딩 에이전트.** 코드 이해 · 이슈 조사 · 구현 · 테스트·리뷰 · 문서·유지보수까지 **전달 워크플로 전반**을 지원한다 (강의 기준).
- ChatGPT는 지식 업무(협업·위임), API는 제품에 AI 내장, Codex는 소프트웨어 전달. **함께 쓰일 수 있다** — Codex가 API 솔루션을 만드는 엔지니어링을 도울 수 있다.
- 핵심 전환: **코딩 도우미 → 코딩 에이전트**, **산출물 → 성과**, **프롬프팅 → 위임**.
- 위임의 다섯 요소: **목표 · 맥락(준비된 환경 포함) · 제약 · 기대 결과 · 검토 기대.**
- 클라우드 작업은 작업마다 자기 작업 공간에서 기기를 넘어 이어지지만, **완료된 실행 ≠ 수용된 변경**. 진행 메시지·소요 시간은 완료 증거가 아니다. **변경 · 실제 검사 · 결과 · 한계**를 확인한다.
- 리뷰에서 **살펴보기 · 피드백 게시 · 승인 · 병합 · 배포는 각각 별개의 결정**이다. 검사 통과도 모든 시나리오를 증명하지 않는다.
- 소프트웨어 전달은 **비즈니스 역량**. 가치는 메시지 수나 생성 속도가 아니라 **비교 가능한 수용된 결과 + 리뷰·재작업량**으로 판단한다. 사람은 **무엇이 출시되는지에 책임**진다.
