## 학습 목표

- 산업·운영 맥락이 AI 기회에 **왜** 영향을 주는지 설명하기
- 추천을 바꿀 수 있는 **워크플로·이해관계자·데이터·거버넌스·위험** 요소 찾기
- **워크플로 패턴**과 그 주변의 **산업별 맥락**을 구분하기
- 추천 전에 **추가 검증**이 필요한 순간 알아차리기
- 일반적인 산업 가정이 아니라 **고객의 운영 환경**에 맞춰 추천 조정하기
- 가진 증거에 맞는 **다음 단계** 추천하기

고객은 "헬스케어에 AI", "금융 서비스용 AI", "규제 업무용 AI", "문서 검토 도와줘"처럼 넓게 말해요. 같은 워크플로라도 **주변 맥락**(이해관계자, 데이터 요건, 거버넌스 기대, 성공 지표, 승인 경로)이 다음에 무엇을 할지를 바꿔요. 산업 전문가가 될 필요는 없고, **믿을 만한 추천을 하고 검증할 것을 짚을 만큼만** 이해하면 돼요.

## 1. 버티컬 맥락 읽기

<div class="oa-eli">
  <span class="oa-eli__head">🍜 쉽게 말하면</span>
  <p>"라면 끓이기"는 어디서나 비슷한 패턴이에요. 그런데 <b>집에서 혼자</b> 끓이는 것, <b>학교 급식실</b>에서 300인분 끓이는 것, <b>캠핑장</b>에서 끓이는 것은 필요한 도구, 지켜야 할 위생 규칙, 누가 맛을 보고 허락하는지, "잘 됐다"의 기준이 전부 달라요. 이 "주변 조건"이 바로 <b>버티컬 맥락</b>이에요.</p>
</div>

- **버티컬 솔루션 적용** = 추천을 고객의 **실제 운영 환경**에 맞게 조정하는 과정
- **버티컬 맥락** = AI 기회를 형성하는 산업별 현실 (워크플로, 이해관계자, 위험, 거버넌스 기대, 성공 지표). discovery에서 무엇을 물을지, 준비도를 어떻게 판단할지, 어떤 가치 스토리가 통할지, 어떤 솔루션 방향이 그럴듯한지에 영향을 줘요.

### 다섯 가지 증거 영역

| 증거 영역 | 의미 | 왜 신경 쓰나 |
|---|---|---|
| **워크플로** | 프로세스, 인수인계, 시스템, 결과물 | 추천을 실제 업무에 붙여 둠 |
| **이해관계자** | 후원·사용·승인·관리·운영하는 사람들 | 누가 관심 있고, 누가 결정하고, 누가 검증해야 하는지 |
| **위험** | 비즈니스·운영·법률·규제·데이터·평판 우려 | **가정하면 안 되는 것**을 찾음 |
| **거버넌스** | 승인 단계, 감독, 권한, 감사 가능성, 운영 통제 | 핸드오프 전 검증할 것을 정함 |
| **성공 지표** | 개선 여부를 판단할 고객의 결과 기준 | 기회를 비즈니스 가치에 연결 |

"문서 검토용 AI"도 **어떤 문서를, 누가 검토하고, 어떤 결정을 지원하며, 어떤 데이터·시스템·통제가 있고, 무엇을 개선하려는지**에 따라 전혀 달라져요.

### 같은 패턴, 다른 환경

세 고객(금융·헬스케어·생명과학)이 모두 "여러 소스를 검토·종합해 의사결정용 자료를 준비"한다고 말해요. 겉보기엔 똑같이 "문서 검토용 AI"지만…

| 버티컬 맥락 | 워크플로 모습 | 추천에서 달라지는 것 |
|---|---|---|
| **금융 서비스 리스크 검토** | 고객 문서·내부 정책·이전 메모·시장 맥락·위원회 요건으로 리스크 검토 패킷 준비 | 민감 금융 데이터 경계, 감사 가능성, 정책 일관성, 기록 시스템, 위원회 검토 단계, 리스크 오너 승인, 성공 지표 |
| **헬스케어 행정 접수** | 요청 검토·요약·문서 준비 후 운영 담당자에게 라우팅 | 승인된 데이터 경계, 민감 건강정보 여부, **행정·운영·임상** 중 무엇인지, 사람 검토 지점, 사용 승인자 |
| **생명과학 지식 종합** | 과학·규제·연구·내부 문서를 브리핑·검토용 결과물로 종합 | 증거 기준, 출처 추적, 검토 주기, 도메인 오너 검증, 데이터 민감도, 접근 통제, 명시적 배포·인프라 요건 (오픈 웨이트·자체 관리는 **기본 결론이 아니라 검증 항목**) |

<div class="oa-eli">
  <span class="oa-eli__head">🏥 같은 "헬스케어 요약"인데…</span>
  <p>한 팀은 <b>예약 행정 요청</b>을 라우팅하고, 다른 팀은 <b>임상 검토용 요약</b>을 준비해요. 둘 다 요약하지만 결과물의 쓰임이 달라서 검증할 사람과 "괜찮은 결과"의 기준이 달라져요. 행정팀은 운영 오너에게 <b>정확한 라우팅·처리 시간</b>을, 임상팀은 임상 오너에게 <b>결정에 쓰이기 전 필요한 검토·승인</b>을 물어요. "헬스케어"라는 단어에서 조건을 추론하지 말고, 실제 작업 대상·결과물이 지원하는 결정·오너·성공 지표를 기록해요.</p>

**핵심:** 워크플로에서 시작하되 거기서 멈추지 마세요. 공통 워크플로 패턴, 산업별 맥락, 검증 요건, 결정 오너, 추천을 바꿀 요인(감사 가능성, 개인정보 요건, 증거 기준, 배포 제약)을 찾아요.

## 2. 솔루션 패턴을 버티컬 워크플로에 맞추기

### 워크플로 결과물부터

**솔루션 패턴** = AI가 워크플로의 결과를 돕는 **반복 가능한 방식**. 답할 질문은 하나예요: **"이 워크플로에서 AI가 해야 할 일은 무엇인가?"**

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">🔎</span><span class="oa-card__title">검색·종합</span>지식을 찾아 종합</div>
  <div class="oa-card"><span class="oa-card__icon">🗃️</span><span class="oa-card__title">추출·구조화</span>정보를 뽑아 구조화</div>
  <div class="oa-card"><span class="oa-card__icon">✍️</span><span class="oa-card__title">초안·요약·변환</span>콘텐츠 작성·요약·변환</div>
  <div class="oa-card"><span class="oa-card__icon">🏷️</span><span class="oa-card__title">분류·라우팅·우선순위</span>일을 분류하고 보내고 순서 매김</div>
  <div class="oa-card"><span class="oa-card__icon">✅</span><span class="oa-card__title">검토·평가</span>결과물 점검</div>
  <div class="oa-card"><span class="oa-card__icon">🧭</span><span class="oa-card__title">다음 행동 추천</span>무엇을 할지 제안</div>
  <div class="oa-card"><span class="oa-card__icon">🔗</span><span class="oa-card__title">다단계 조율</span>도구·승인을 넘나드는 작업 조율</div>
  <div class="oa-card"><span class="oa-card__icon">🧑‍💻</span><span class="oa-card__title">소프트웨어 제공</span>계획·구축·테스트·리뷰·문서·유지보수</div>
</div>

이건 기술 분류표나 제품 목록이 아니라 **비즈니스 결과물에 대화를 고정하는 실용 도구**예요. "접수용 AI 어시스턴트"를 원한다면 "접수 단계에서 워크플로가 **어떤 결과물**을 만들어야 하나요?"라고 물어요. 구조화된 요약, 우선순위 라벨, 라우팅된 요청, 응답 초안, 예외 플래그 — 결과물마다 추천과 검증 필요가 달라요.

> **Decisions API**(공개 베타, 강의 기준)는 요청 카테고리 **라벨**을 줄 수 있지만, 요청을 라우팅하거나 응답을 준비하지는 않아요. 필요한 결과물, 허용 오류, 사람 검토, 통합 필요를 기술 검증용으로 기록해요.

### 버티컬 증거로 패턴 조정하기

결과물이 명확해지면 이렇게 물어요: 어떤 데이터·시스템·지식이 필요한가 / 누가 검토·승인하나 / 결과가 불완전·부정확·감사 불가능하면 무엇이 잘못되나 / 어떤 가치가 개선되나 / 어떤 표면이 가장 그럴듯한가 / 어떤 역량·운영 요건을 검증해야 하나 / 증거가 지지하는 다음 단계는?

같은 패턴도 **서로 독립적인 세 축**에서 다른 선택으로 이어질 수 있어요 (레슨 5의 솔루션 맵과 같은 구조).

| 축 | 선택지 (강의 기준) |
|---|---|
| **사용자·제품 표면** | Chat(협업), Work(위임·완성 결과물), Codex(소프트웨어), API 앱·프로세스(내장) |
| **역량·아키텍처** | 검색, 구조화 출력, 앱·도구, 코드 실행, 자동화, 승인 기반 다단계 실행 |
| **배포·운영** | 실행 ID, 권한, 승인, 보존, 로깅, 사람 검토. 반복 업무면 결과 열람 범위, 연결 유지, 소스 최신성, 오너 연속성 |

- 축들은 **조합**될 수 있어요. 에이전트·다단계 실행은 **역량**이지 동급의 제품 경로가 아니에요.
- **오픈 웨이트·자체 관리**는 현재 호스팅 통제를 평가한 뒤에도 명시적 요건이 남을 때만 배포·운영 선택지로 다뤄요. 데이터 민감도나 레지던시만으로 경로를 추론하지 마세요.

### 사례 — 헬스케어 행정 접수

> 고객: "행정 요청을 처리하고 요약해서 담당자에게 보내는데, 너무 오래 걸리고 라우팅이 일관되지 않아요."

<ol class="oa-flow">
  <li><strong>요청 접수</strong></li>
  <li><strong>정보 검토</strong></li>
  <li><strong>필요 요약</strong></li>
  <li><strong>담당자 식별</strong></li>
  <li><strong>라우팅</strong></li>
  <li><strong>응답·다음 행동 준비</strong></li>
</ol>

| 항목 | 셀러 수준 분석 |
|---|---|
| 워크플로 결과물 | 올바른 운영 담당자에게 라우팅된 요약된 요청 |
| 유력 패턴 | 요약 + 분류 + 라우팅 |
| 표면 | 협업 준비면 Chat, 위임 준비면 Work, 내장 접수면 API 프로세스 |
| 역량 | 요약·분류와 **라우팅 행동을 분리**. Decisions는 한정된 카테고리 출력에만, 접수 전체엔 아님 |
| 배포·운영 | ID, 권한, 검토, 로깅, 시스템 오너십, 실제 데이터에 대한 **각 기능의 적격성** 검증 |
| 가치 결과 | 빠른 접수, 수동 인수인계 감소, 일관된 라우팅, 행정 부담 감소 |
| 검증할 요건 | 데이터 경계, 승인 오너, 시스템, 사람 검토, 성공 지표, 실제 조직·제품·기능의 커버리지 |
| 다음 단계 | 위 항목 확인 후 배포 핸드오프 또는 추가 qualification |

셀러는 "헬스케어엔 이 제품이 필요해요"가 아니라 **"이 워크플로엔 이런 AI 지원 결과물이 필요하고, 이 버티컬 맥락이 무엇을 검증해야 하는지를 정해요"**라고 말해요.

### 사례 — 생명과학 지식 종합

> 고객: "연구·규제 브리핑 준비에 시간이 너무 들어요. 정보는 있는데 흩어져 있고, 검토자는 결과 뒤의 **증거를 믿을 수 있어야** 해요."

| 이해관계자 | 가치 |
|---|---|
| 연구 리더 | 빠른 종합, 이전 작업 재활용 |

| 기술·거버넌스 | 승인된 소스 접근, 데이터 통제, 검토 워크플로, 결과 생성 과정의 가시성 |

### 3축을 분리하는 신호 (강의 기준)

- **표면:** Chat = 함께 생각·탐색·초안·비평·다듬기 / Work = 결과·맥락·경계·검토 기준을 주고 복잡한 지식 업무 위임 / Codex = 소프트웨어 엔지니어링 전용 / API = 제품·시스템·운영 워크플로에 내장
- **역량:** 검색, 구조화 출력, 앱·도구, 코드 실행, 자동화, 승인 기반 다단계 작업. **에이전트 행동은 여기에 속하며**, 적절한 표면으로 제공되는 역량이에요.
- **배포·운영:** ID, 권한, 승인, 보존, 로깅, 사람 검토, 운영 오너십. 역량이 "있다"고 보기 전에 현재 플랜·워크스페이스·앱·권한 가용성 확인.
- **조합:** 직원 업무엔 ChatGPT, 내장 실행엔 API처럼 여러 표면이 필요하면, 전체를 "하이브리드"라고 부르지 말고 **각 축을 따로** 말해요.

추천을 바꾸거나 확장할 수 있는 요건 — **자체 관리·오픈 모델**(런타임 통제, 사설 배포, 레지던시, 온프레미스), **거버넌스**(민감 데이터, 사람 검토, 감사, 권한, 모니터링), **기술 타당성**(시스템 통합, 데이터 접근, 저장소, 도구 접근, 시스템 간 자동화), **다단계 워크플로**(생성에서 멈추지 않고 도구·승인·결과물을 넘나듦) — 은 셀러의 기술 설계가 아니라 **검증 필요**가 돼요.

### 다음 단계 논리

| 상황 | 다음 단계 |
|---|---|
| 워크플로·오너·데이터 경계·가치·준비도·라우팅을 아직 자신 있게 설명 못 함 | **추가 qualification** |
| 라우팅 판단은 믿을 만하지만 기술·보안·법률·컴플라이언스·마이그레이션·오픈 웨이트·자체 관리·운영 질문이 남음 | **핸드오프 전 검증** |
| 워크플로·오너·가치·데이터 경계·준비도·라우팅이 충분히 명확 | **기술·배포 핸드오프** |
| 기존 AI 솔루션·모델·자동화·코딩 어시스턴트·벤더 구현을 교체 | **마이그레이션 discovery** |

> 핸드오프는 **모호함에서 도망치는 수단이 아니에요.** 증거가 약하면 증거부터 강화하고, 증거는 강한데 제약이 남았으면 제약을 검증하고, 모두 명확하면 핸드오프를 준비해요.

| 버티컬 | 피치 요지 (강의 예시 요약) |

## 정리

- 버티컬 솔루션 적용은 **제품·산업 라벨이 아니라 고객 워크플로**에서 시작해요.
- 버티컬 맥락은 **워크플로·이해관계자·위험·거버넌스·성공 지표** 다섯 영역으로 읽고, 작업 대상·마찰·데이터 경계·오너·검토 요구·반복 조건을 기록해요.
- 같은 워크플로 패턴도 산업과 결과물의 쓰임(행정 vs 임상)에 따라 **검증자와 "괜찮은 결과"의 기준**이 달라져요.
- 솔루션 패턴은 **"AI가 이 워크플로에서 할 일"**로 정하고, 표면·역량·배포/운영 **세 축을 분리**해 라우팅해요. 분류 출력과 워크플로 행동은 분리해요.
- 가치는 **이해관계자별로** 다르고, 신뢰·준비도는 **구체적으로** 적어요. 법률·규제·보안·아키텍처 결정은 셀러가 아니라 자격 있는 검증자의 몫이에요 (예: PHI에 대한 BAA 커버리지 확인).
- 반복 업무는 같은 필요에 대해 **개인·팀 소유·내장 운영을 비교**하고, 피치는 짧고 증거 기반이며 **아직 확인할 것에 솔직하게** 해요.
