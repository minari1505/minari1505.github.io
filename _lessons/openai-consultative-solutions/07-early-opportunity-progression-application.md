- 막연한 "AI 관심"을 **증거 기반의 Stage 1 준비도 추천**으로 바꾸기
- 워크플로를 명확히 하고, 비즈니스 문제를 검증하고, **결과 오너**를 찾기
- **다섯 가지 qualification 신호**를 강함·발전 중·없음으로 평가해 준비도 판단하기

- 파트너 팀·OpenAI 담당자가 바로 쓸 수 있는 **Stage 1 추천 스냅샷** 쓰기

### Leon이 신경 쓰는 것

- 청구 급증 시 **백로그 감소**
- 초기 분류의 **일관성**
- 조정사가 **더 나은 청구 맥락**으로 시작하기
- 최종 보장·책임·지급·예외 같은 **고위험 보험 결정에 대한 자격 있는 사람 검토와 책임** 유지 — OpenAI 사용 정책은 사람 검토 없는 고위험 보험 결정 자동화를 금지해요 (강의 기준)
- 청구 워크플로에서 검토·통제·승인 지점이 **보이게** 유지
- **현실적인 첫 파일럿**의 모습

Leon은 **최종 기술 결정권자가 아니에요.** 기회가 진전되면 청구 시스템·데이터·보안·법무 이해관계자를 불러야 해요.

## 2. 롤플레이 1 — discovery와 qualification

"AI가 유용해 보여요"만으로는 부족해요. 빠른 제품 라우팅이 아니라 **discovery·qualification 대화**로 다뤄요.

### 대화에서 명확히 할 것

| 질문 | 왜 |
|---|---|
| 청구 워크플로에서 지금 무슨 일이 일어나나? | 문제를 실제 업무에 고정 |
| 누가 영향을 받나? | 사용자·오너 파악 |
| 문제가 시간·품질·속도·위험·고객 경험에서 얼마나 비싼가? | 가치 가설의 재료 |
| "나아진 모습"은? | 성공 기준 |
| 검증할 만큼 **좁은** 첫 유스케이스는? | 거대한 변혁 대신 파일럿 |
| 진전되면 누가 더 참여해야 하나? | 시스템·데이터·보안·법무 |
| Leon이 약속할 다음 단계는? | 고객 참여 신호 |

반복되는 일이라면 **얼마나 자주, 누가 결과를 쓰고 검토하는지, 개인·팀·기존 비즈니스 프로세스 중 무엇을 주로 지원하는지**도 물어요. 전체 솔루션을 설계하려 하지 마세요.

### 점수가 아니라 판단

<div class="oa-eli">
  <span class="oa-eli__head">🧩 쉽게 말하면</span>
  <p>퍼즐에서 빠진 조각이 <b>하늘 한 귀퉁이</b>인지 <b>그림의 한가운데</b>인지에 따라 의미가 달라요. 귀퉁이가 빠져도 무슨 그림인지는 알 수 있지만, 한가운데가 빠지면 뭘 맞추는지조차 몰라요. 신호도 마찬가지로 <b>"기회를 알아볼 수 없게 만드는 공백"</b>인지 <b>"후속 미팅에서 확인하면 되는 공백"</b>인지 구분해요.</p>
</div>

| 증거 상태 | 판단 |
|---|---|
| 이름 붙은 워크플로 문제 + 책임 있는 오너 + 약속된 검증 세션 (기준 수치는 아직 확인 필요) | **조건부 준비됨(conditionally ready)** 가능 |
| 관심은 있지만 명확한 워크플로나 합의된 다음 단계가 없음 | **추가 discovery** |

Leon이 **실제로 한 말**을 Evidence notes에 적고, 내 **가정과 분리**하고, 다음 검증 행동을 정해요. 빈칸을 그럴듯한 답으로 채우지 마세요.

### Leon에게 돌아가기 전 준비할 관점

1. 이 기회가 Stage 1로 진전해야 하나?
2. 첫 파일럿은 무엇에 집중해야 하나?
3. 왜 그게 올바른 첫 단계인가?
4. 증거로 정당화할 수 있는 표면·역량·배포/운영은?
5. 무엇을 아직 검증해야 하나?
6. Leon은 다음에 무엇에 동의해야 하나?

## 4. 롤플레이 2 — Stage 1 추천 전달

### 추천 구조

| 항목 | 담을 것 |
|---|---|
| **추천** | Stage 1로 진전해야 하나? |
| **증거** | 어떤 qualification 신호가 뒷받침하나? |
| **셀러 수준 경로** | 먼저 탐색할 표면, 필요할 수 있는 역량·아키텍처, 검증할 배포·운영 요건 |
| **이 경로인 이유** | 더 넓거나 더 위험한 대안보다 문제·증거·가치·위험에 잘 맞는 이유 |
| **가치** | 잘 되면 어떤 청구 결과가 나아지나 |
| **검증** | 깊은 솔루션 설계 전에 확인할 것 |
| **다음 단계** | Leon, 파트너 팀, OpenAI가 각각 할 일 |

강한 추천은 **먼저 추구할 것과 아직 추구하지 않을 것**을 함께 말해요. 예를 들어 조정사가 청구 맥락을 모으는 데 시간을 많이 쓰고 지역별 분류가 일관되지 않다는 증거가 있다면, **청구 접수·분류 지원(intake & triage assist) 워크플로**가 믿을 만한 첫 초점일 수 있어요. 단, 증거가 뒷받침하기 전에 제품 경로를 가정하지 마세요.

- **API 앱·프로세스**: 청구 시스템·앱·운영 워크플로에 지능을 넣어야 할 때. 시스템 오너십·통합·데이터 접근·출력 요건·평가를 검증한 뒤 확정.
- **Codex**: 소프트웨어 제공·SDLC 전환 문제일 때만.

진행 중인 워크플로라면 **개인·팀·기존 비즈니스 프로세스** 중 무엇을 지원하는지, 어떤 오너십·검토 방식이 검증 필요한지도 짚어요. 아키텍처·구현 세부를 확정하지 않아요.

## 정리

- **초기 기회는 핸드오프가 아니라 결정 지점이에요.** 열정이 아니라 증거로 판단해요.
- 롤플레이 1에선 워크플로·영향·오너·좁은 첫 유스케이스·다음 단계 약속을 찾고, 설계·ROI 보장·법률 조언으로 넘어가지 않아요.
- 다섯 신호를 **강함·발전 중·없음**으로 평가하되 **점수가 아니라 판단**으로 써요. 들은 것과 가정을 분리해요.
- 추천은 **준비됨·조건부 준비됨·아직 아님** 중 하나로 말하고, 근거 증거·검증할 것·먼저 할 것과 **아직 하지 않을 것**을 함께 밝혀요.
- 경로는 **표면 → 역량 → 배포/운영** 순으로 분리하고, 불명확하면 진행 동작(discovery·검증·핸드오프)으로 답해요.
- 레슨 1–6의 기술(기회 인식 → discovery → 유스케이스 → 가치 → 솔루션 매핑 → 버티컬 적용)이 모두 하나의 **Stage 1 추천 스냅샷**으로 모여요.
