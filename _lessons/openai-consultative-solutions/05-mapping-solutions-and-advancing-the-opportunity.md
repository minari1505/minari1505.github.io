## 학습 목표

- **솔루션 매핑**이 컨설팅형 기회 개발에서 어떤 역할을 하는지 설명하기
- 셀러용 솔루션 맵으로 **사용자·제품 표면 / 역량·아키텍처 / 배포·운영 모델 / 진행 동작** 네 가지를 구분하기
- 검증된 고객 워크플로를 ChatGPT Chat, ChatGPT Work, Codex, API 기반 애플리케이션 중 **가장 그럴듯한 표면**에 연결하기 (제품명은 강의 기준)
- 준비도·트레이드오프·제약·검증 증거로 **경로 후보를 비교**하기
- 믿을 만한 **다음 단계**를 추천하고, 기술·배포 팀이 바로 쓸 수 있는 **간결한 핸드오프**를 준비하기

이 코스의 출발점은 막연한 AI 관심이 아니라 **이미 검증된 고객 문제·유스케이스**예요. 목표는 제품 이름을 빨리 말하는 게 아니라, **워크플로 증거에 근거하고 아직 검증할 것을 솔직히 밝힌 셀러 수준의 추천**이에요. 기술 설계까지 들어가지는 않아요.

## 1. 솔루션을 말하기 전에 간단한 라우팅 맵부터

<div class="oa-eli">
  <span class="oa-eli__head">🍽️ 쉽게 말하면</span>
  <p>친구가 "배고파, 맛있는 거!"라고 하면 바로 식당 이름을 대기 전에 물어봐야 해요. <b>어디서</b> 먹을래(집 배달? 식당?), <b>뭘</b> 먹고 싶어(국물? 고기?), <b>어떻게</b> 할래(예산, 알레르기, 시간), 그리고 <b>다음에 뭘 할지</b>(지금 주문? 먼저 메뉴판 보기?). 고객의 "에이전트가 필요해요"도 똑같이 쪼개서 들어야 해요.</p>
</div>

고객은 "에이전트", "챗봇", "코파일럿", "자동화", "API", "마이그레이션" 같은 넓은 라벨로 원하는 걸 말해요. 라벨은 **단서**이지 **결론**이 아니에요.

> **라우팅(routing)** = 일이 어디서 일어나는지, 어떤 역량이 필요한지, 어떻게 실행·통제되는지, 다음에 무엇을 할지를 **분리해서** 가장 적절한 OpenAI 솔루션 경로를 찾는 과정.

"에이전트가 필요해요"는 이런 뜻일 수 있어요.

### 버티컬 맥락(vertical context)

**버티컬 맥락**은 산업별 조건(워크플로, 이해관계자, 데이터 환경, 거버넌스, 위험 허용도, 도입 필요, 성공 지표, 운영 모델)이에요. 금융·헬스케어·생명과학 전문가가 될 필요는 없지만, **맥락이 질문·위험·검증·핸드오프를 어떻게 바꾸는지**는 알아야 해요.

### 예시 — "티켓 해결 시간을 줄일 AI 에이전트가 필요해요"

바로 "에이전트"로 라우팅하지 말고 워크플로를 명확히 해요.

| 워크플로 증거 | 가리키는 것 |
|---|---|
| 상담원이 정책을 탐색하고 답변 초안을 대화하듯 다듬음 | 표면: **ChatGPT Chat** |
| 맥락을 모아 검토 가능한 응답 패키지를 만드는 긴 과정을 위임 | 표면: **ChatGPT Work** |
| 티켓 시스템 안에 지능이 들어가야 함 | 표면: **API 앱** |
| 분류 → 계정 맥락 검색 → 초안 → 예외 에스컬레이션 → 승인 요청 | **역량·아키텍처** 요건 (Work, Workspace Agent, API, 조합 중 검증) |
| 기존 지원 자동화 도구를 교체 중 | 진행 동작: **마이그레이션 discovery** |

반복 업무라면 **무엇이 각 사이클을 시작하는지, 허용된 일, 수용 기준 결과, 예외 검토자**까지 확인해요. 쓸 만한 응답 패키지 한 번은 "매주 안정적으로 돌아간다"는 증거가 아니에요. 가치 대화는 계속 **워크플로 결과**(빠른 해결, 일관된 응답, 에스컬레이션 부담 감소, 고객 경험)에 고정해요.

> 더 강한 신호는 "에이전트"라는 **단어**가 아니라, 그 뒤에 있는 **워크플로 증거**예요.

## 2. 워크플로를 사용자·제품 표면에 매핑하기

### 워크플로 증거부터

표면을 추천하기 전에 이걸 알아야 해요: **누가 지금 일하나 / 어떤 워크플로가 느리고·비싸고·위험하고·일관되지 않고·확장 어려운가 / 어떤 결과물이 나아져야 하나 / AI가 사람·시스템·도구·데이터와 어디서 만나나 / 개선되면 어떤 가치를 기대하나.**

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">🌫️ 라우팅하기 어려움</span>
    <ul>
      <li>"법무용 AI"</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">🎯 라우팅하기 쉬움</span>
    <ul>
      <li>"법무 운영팀이 일상적 계약 변경을 요약하고, 빠진 조항을 검토용으로 표시하고, 현업이 읽기 쉬운 요약을 초안"</li>
    </ul>
  </div>
</div>

같은 "문서 검토"라도 은행·병원·제조사에서는 이해관계자, 데이터 경계, 승인 단계, 성공 지표가 달라요. 그 요건을 **과장하지 말고**, 중요할 수 있는 것을 짚은 뒤 고객과 검증해요.

### 표면별 적합 신호

<div class="oa-eli">
  <span class="oa-eli__head">🍳 쉽게 말하면</span>
  <p>요리로 치면 <b>Chat</b>은 엄마랑 같이 레시피를 보며 한 단계씩 요리하는 것, <b>Work</b>는 "저녁 준비해 줘, 다 되면 맛볼게"라고 맡기는 것, <b>API 앱</b>은 식당 주방 시스템 자체에 자동 조리 기능을 넣는 것, <b>Codex</b>는 주방 기계를 고치고 업그레이드하는 엔지니어링 일이에요.</p>
</div>

| 표면 (강의 기준) | 강한 적합 신호 | 약한 적합 신호 |
|---|---|---|
| **ChatGPT Chat** | 직원이 대화하며 탐색·질문·초안·비평·다듬기, 각 단계에 사람 판단이 핵심, 커스텀 앱 없이 익숙한 업무 공간 | 내장 커스텀 경험이나 대량 시스템 간 실행이 주된 필요 |
| **ChatGPT Work** | 위임된 다단계 지식 업무, 조직 맥락·도구, 명확한 결과물, 작업 중 사용자 조정·승인 (예: 검토용 운영 보고서, 여러 소스로 발표 자료 만들기) | 위와 같음 / 소프트웨어 엔지니어링 문제면 Codex |
| **API 앱·프로세스** | 기존 제품·시스템·워크플로 안에 들어가야 함, 커스텀 로직·오케스트레이션·구조화 출력·검색·도구 사용·앱 수준 통제, 고객·내부 시스템·대량 운영 처리 | 통합·평가·거버넌스·제품 오너십을 감당할 준비가 안 됨 → 기회가 약한 게 아니라 **아키텍처·운영 모델 검증이 먼저** |
| **Codex** | 계획·코딩·테스트·리뷰·문서·유지보수·현대화 개선, SDLC 전체 흐름, 가치가 더 빠르고 안전한 소프트웨어 제공에 달림 | 소프트웨어 제공·엔지니어링 운영과 무관한 워크플로 |

몇 가지 주의점 (강의 기준):

- **Intelligent UI**는 Chat 답변을 상호작용형으로 만들 수 있지만, 상호작용형 응답이 **위임된 프로세스는 아니에요.** Intelligent UI는 Chat에서만 쓸 수 있고 Work에서는 아니에요.
- **API를 "더 기술적인 ChatGPT"로 보지 마세요.** 핵심 판단은 **경험이 어디에 살아야 하느냐**예요.
- API 표면을 골라도 단계별 필요를 확인해요. 예: **Decisions API**(공개 베타)는 한정된 분류를 지원하지만, 주변 워크플로 실행·도구 호출·서면 설명은 하지 않아요.
- Codex는 "범용 생산성"이 아니라 **소프트웨어 제공 일**로 프레이밍해요. 셀러는 엔지니어링 워크플로를 설계할 필요 없이, 문제가 SDLC에 뿌리를 두었다는 **증거를 포착**하면 돼요.

> **더 믿을 만한 말:** "사용자가 함께 생각하고 만들어야 하면 Chat이, 결과·맥락·제약을 정해 주고 완성된 결과를 검토할 수 있으면 Work가 맞을 수 있어요. 어느 쪽이든 확정 전에 사용자 그룹, 데이터 접근, 사용 가능한 도구, 승인 경계, 도입 경로를 검증해야 해요."

### 사례로 보기

**재무 보고 (예시)** — 재무팀이 승인된 자료를 모아 주간 성과 업데이트를 며칠씩 준비하고, 재무 리드가 배포 전 검토해요.

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">💬</span><span class="oa-card__title">Chat</span>분석가가 정보를 탐색하며 스토리를 대화로 다듬을 때</div>
  <div class="oa-card"><span class="oa-card__icon">👤</span><span class="oa-card__title">Work + 개인 dot</span>한 분석가가 준비 작업과 접근 권한을 소유, 재무 리드가 배포 전 검토</div>
  <div class="oa-card"><span class="oa-card__icon">👥</span><span class="oa-card__title">Work + Team Task</span>한 분석가와 무관하게 계속 돌아야 할 때. 실행 계정·연결, 유지 담당, 결과 검토자·열람자 검증</div>
  <div class="oa-card"><span class="oa-card__icon">🧱</span><span class="oa-card__title">API 프로세스</span>내장 데이터 추출·구조화 출력·내부 보고 시스템 통합이 필요할 때. ChatGPT의 자동 업그레이드가 아니라 통합·앱 오너십 책임이 추가됨</div>
</div>

**Space 페이지**(강의 기준)는 공유 업데이트를 담을 수 있지만, **결과물을 공유한다고 반복 프로세스가 생기진 않아요.** 열람 대상과 복사된 소스 내용을 확인하고, 자동 업데이트나 연속성을 가정하지 마세요.

**고객 온보딩** — SaaS 기업이 제품 안에서 온보딩 여정을 개인화하고 싶어 해요 → 고객 대면 경험에 내장되어야 하니 **API 앱**이 유력. 내부 팀이 리서치·계정 준비에 Chat/Work를 쓸 수는 있지만, 그게 주된 표면이 되지는 않아요.

**레거시 현대화** — 오래된 코드, 불안정한 테스트, 리뷰 병목 → **Codex**가 유력. 수명주기 중 **어느 단계**(계획·코딩·테스트·리뷰·문서·유지보수·현대화)가 제약인지 포착해서 Codex 담당자에게 넘겨요.

## 3. 역량·아키텍처·운영 요건 찾기

유력한 표면이 답의 전부는 아니에요. 워크플로가 요구하는 역량·아키텍처·운영 통제가 솔루션을 만들고·돌리고·관리하는 방식을 바꿔요.

### 앱·도구·다단계 행동이 필요할 때

이런 말을 들으면 **역량·아키텍처 신호**예요.

- "질문에 답만 하는 게 아니라 **행동**을 해야 해요."
- "여러 시스템·도구를 넘나들어야 해요."
- "상태 확인, 레코드 업데이트, 티켓 생성, 후속 조치 트리거가 필요해요."
- "특정 단계 전에 **승인**을 요청해야 해요."
- "예외를 처리하거나 사람에게 에스컬레이션해야 해요."

필요할 수 있는 것: 앱·도구, 검색, 다단계 계획, 행동, 스케줄링, 승인, 예외 처리, Workspace Agent. **시스템이 해야 할 일을 먼저 밝힌 뒤** Work, Workspace Agent, API 솔루션, 조합 중 무엇이 맞는지 판단해요. 가용성과 권한은 고객의 플랜·워크스페이스 기준으로 검증해요.

<div class="oa-eli">
  <span class="oa-eli__head">🔑 Team Task를 검토한다면 (강의 기준)</span>
  <p>반 공용 노트북을 생각해 보세요. 누구 개인 계정이 아니라 <b>반 계정</b>으로 로그인되어 있고, 저장한 내용은 지금 반 친구와 <b>내년 반 친구</b>도 볼 수 있어요. Team Task도 비슷해요: 실행은 개개인의 맥락이 아니라 <b>서비스 계정과 그 연결 앱</b>을 쓰고, 결과는 현재·미래 팀원에게 보여요. 그래서 담당자가 떠나면 누가 연결과 작업을 유지하는지, 누가 결과를 검토하는지, 열람 대상이 적절한지, 그리고 <b>워크스페이스 크레딧</b>을 쓰니 사용량 담당자는 누구인지 확인해요.</p>
</div>

### 배포 통제·자체 관리 인프라가 중요할 수 있을 때

"우리 환경에서 돌려야 해요", "데이터가 통제된 인프라 밖으로 나가면 안 돼요", "데이터 레지던시·주권 요건", "오프라인·사설·에어갭 운영", "모델 운영을 직접 관리할 준비가 됐어요" → **배포·운영 모델 신호**예요.

<ol class="oa-flow">
  <li><strong>요건 포착</strong>왜 자체 관리가 필요한가</li>
  <li><strong>호스팅 먼저</strong>OpenAI 호스팅 제품·엔터프라이즈 통제로 충족되나</li>
  <li><strong>전문가 참여</strong>기술·보안·컴플라이언스</li>
  <li><strong>그래도 필요하면</strong>고객 관리 오픈 웨이트 고려</li>

**민감 데이터나 데이터 레지던시만으로 오픈 웨이트가 필요하다고 결론 내리지 마세요.** 자체 관리 오픈 웨이트 배포는 모델 호스팅·모니터링·거버넌스·유지보수·지원 책임이 따라오니, 고객이 그 책임을 질 준비가 됐는지도 포착해요.

### 기존 AI 환경에서 옮겨 올 때

"기존 AI 도구가 확장이 안 돼요", "AI 지출·벤더를 통합하고 싶어요", "여러 팀 파일럿을 더 통제된 방식으로", "중단·연속성·평가·변화 관리가 걱정돼요" → **마이그레이션은 제품도 역량도 아닌 진행·구현 동작**이에요. 목표 표면을 검증하기 전에 **현재 상태 discovery**가 먼저일 수 있어요. 무엇에서 옮기는지, 왜 바꾸는지, 무엇이 계속 돌아가야 하는지, 어떤 위험을 검증할지를 포착해 마이그레이션·기술·배포 담당자에게 연결해요.

### 사례 — 헬스케어 운영

헬스케어 운영팀이 더 빠른 내부 정책 지원을 원해요. Chat(대화형 지식 접근·종합·초안) 또는 Work(긴 준비 워크플로 위임 후 검토)가 맞을 수 있어요.

| ❌ 일반론 | ✅ 워크플로 기반 판단 |
|---|---|
| "헬스케어는 거버넌스가 더 필요해요." | "이 워크플로는 민감한 정책·데이터 고려가 있을 수 있으니, 진행 전에 접근·검토·감사 기대치를 검증해야 해요." |

요건은 고객이 적절한 컴플라이언스·법무·보안·기술 이해관계자와 확인하기 전까지 **확정된 것으로 취급하지 않아요.**

## 4. 경로가 믿을 만한지 테스트하기

### 적합성과 준비도를 분리

<div class="oa-eli">
  <span class="oa-eli__head">🚲 쉽게 말하면</span>
  <p>자전거가 학원 가는 데 딱 맞는 교통수단(<b>적합성</b>)이어도, 아직 자전거를 못 타거나 헬멧이 없거나 부모님 허락을 안 받았다면(<b>준비도</b>) 내일부터 타고 가자고 할 순 없어요. 먼저 연습하고 허락받는 게 다음 단계죠.</p>
</div>

- **적합성:** 이 방향이 워크플로·유스케이스·가치 가설에 맞나?
- **준비도:** 고객이 이 방향을 진전시킬 준비가 됐나?

예: 운영 시스템에 지능을 넣고 싶으니 API가 맞아 보여도, 제품 오너·데이터 소스·통합 경로·평가 방식·거버넌스 검토가 없다면 아직 기술 핸드오프 단계가 아니에요. **검증 세션**이 다음일 수 있어요.

### 준비도 점검

| 점검 항목 | 확인할 것 |
|---|---|
| 문제·우선 워크플로 | 비즈니스 문제, 우선 워크플로, 팀, 사용자 그룹을 설명할 수 있나 |
| 이해관계자 오너십 | 결과에 관심 있고 다음 단계를 이끌 비즈니스 오너가 있나 |
| AI 성숙도·다음 단계 | 탐색 너머로 갈 경험·긴급성·운영 역량이 있고, 구체적 다음 행동에 합의했나 |
| 거버넌스·승인 | AI 사용을 누가 검토·승인하는지 아나 |
| 데이터·통합 준비 | 필요한 데이터·지식·시스템을 알고, 기존 시스템 연결이 필요한가 |
| 도입·성공 지표 | 누가 쓰고, 어떤 행동이 바뀌어야 하고, 무엇이 가치를 증명하나 |
| 가치 가설 명시 | "AI가 어떻게든 좋게 해 주겠지"뿐이라면 아직 이름 |
| 검증 지원 가능 | 검증 세션에 참여하고 워크플로 정보를 공유할 오너가 있나 |

### 복잡한 워크플로라면 세 가지 질문

외울 프레임워크가 아니라 쉬운 말로 먼저: **"일은 어디서 일어나고, 시스템은 무엇을 해야 하고, 어떻게 실행·통제되나요?"**

1. **어디서 일하나?** → 표면 (Chat, Work, Codex, API 앱)
2. **어떤 역량·아키텍처가 필요하나?** → 비즈니스 맥락, 앱·도구, 검색, 구조화 출력, 코드 실행, 다단계 행동, 스케줄링, 승인, 커스텀 오케스트레이션
3. **어디서 어떻게 실행·통제되나?** → 배포·운영 모델. **런타임**은 실행 위치·방식, **모니터링·트레이싱**은 관측성, **권한·승인·보존·로깅·사람 검토**는 거버넌스·운영 통제예요.

셀러의 일은 운영 모델을 설계하는 게 아니라 **답과 열린 질문을 기록**하는 거예요.

### 경로를 바꿀 수 있는 트레이드오프

| 트레이드오프 | 셀러 질문 | 영향받을 수 있는 것 |
|---|---|---|
| **비용** | 구축·반복 실행·검토·유지 비용은? 사용료는 누가 내나? | 가치 케이스가 이 경로를 정당화하나 |
| **지연 시간** | 수용 가능한 결과가 얼마나 빨리 나와야 하나? 생성 속도가 그걸 바꾸나? | 라우팅 전 기술 검증 필요 여부 |
| **통합** | 앱·도구·시스템 통합·내장 경험이 필요한가? | API 앱, Workspace Agent, 앱 액션, 조합, 기술 핸드오프 검증 |
| **데이터** | 어떤 데이터가 어디 있고 얼마나 민감한가? | 접근·거버넌스·보안·호스팅 통제·오픈 웨이트 요건 검증 |
| **거버넌스** | 어떤 승인·정책·감사·감독 요건? | 검증 세션 또는 배포 핸드오프 필요 |
| **도입** | 누가 쓰고 어떤 행동이 바뀌어야 하나? | 실제로 가치를 낼 준비가 됐나 |
| **복잡도** | 경로가 성숙도·긴급성·기대 가치에 비례하나? | 단순화하거나 단계적으로 나눌지 |
| **사람 역할·되돌림 가능성** | 사람이 검토·승인·무효화·감독해야 하나? 실수를 쉽게 고칠 수 있나? | 승인·감사·에스컬레이션·검토 통제 검증 |

#### 경로 안의 모델 선택은 따로 (강의 기준)

- **모델 선택은 제품 표면과 분리**해요. Work·Codex·API의 복잡한 전문 업무엔 GPT-6.1 Sol과 GPT-6 Astra를 고객 과제로 비교해요. GPT-6.1 Sol은 일반 Chat 옵션이 아니에요. GPT-6 Sol과 GPT-6 Luna는 집중적·대량 작업을 포함한 별개의 API 후보예요. 이건 **평가 후보이지 라우팅 규칙이 아니에요.**
- 기술 오너에게 **대표 입력**으로 후보 모델·추론 설정을 고객의 **품질 기준**(결과가 쓸 만하려면 충족해야 할 조건)에 비춰 비교하게 하고, 기준을 넘는 옵션 중에서 **수용된 결과 하나당 완료 시간·비용**(검토·재작업 포함)을 비교해요.
- 티켓 분류는 Decisions를 다른 적합한 API와 대표 티켓으로 비교해요. **라벨은 계정 맥락을 찾거나 답장하거나 해결하지 않아요.** 오분류와 검토 노력을 검증하고, 속도가 절감을 보장하지 않아요.
- **속도·접근:** 기술 오너가 모델·모드·플랜·처리 지역·사용 조건을 검증해요. Standard·Fast와 (자격 있는) Ultrafast를 구분하고 모델 지원을 확인해요.
- **사용료 자금:** 참여 앱의 개인 ChatGPT 허용량은 로그인 ID·앱 요금과 별개, Team Task는 워크스페이스 크레딧, API 과금은 별도예요. 마켓플레이스 자격은 고객·제품·구매에 따라 다르고, 고객은 파트너와 직접 계약·지불하며 자격 있는 구매는 OpenAI 약정에 반영돼요. **확정된 사항과 열린 상업 질문을 기록**해요.

> 트레이드오프는 기회를 멈출 이유가 아니라 **책임 있게 라우팅할 이유**예요. 비즈니스 트레이드오프면 가치·이해관계자 정렬을 계속하고, 기술·데이터·보안·거버넌스·통합 트레이드오프면 검증이나 핸드오프로 넘겨요.

## 5. 다음 단계 추천과 핸드오프 준비

### 강한 추천이 답하는 6가지

1. 어떤 고객 문제와 워크플로를 개선하려 하나?
2. 어떤 **가치 가설**이 추진할 이유가 되나?
3. 어떤 사용자·제품 표면이 가장 믿을 만한가?
4. 어떤 역량·아키텍처 요건을 검증해야 하나?
5. 어떤 배포·운영 가정·위험·통제를 검증해야 하나?
6. 다음에 무엇을 하고, **누가 소유**하나?

선택한 표면이 왜 그럴듯하고 **대안은 왜 가능성이 낮거나·이르거나·추가 검증에 달려 있는지**도 설명해요. 최종 아키텍처를 내놓는 게 아니에요.

## 정리

- 고객의 "에이전트·코파일럿·자동화"는 **단서이지 결론이 아니에요.** 표면 / 역량·아키텍처 / 배포·운영 모델 / 진행 동작으로 쪼개서 들어요.
- **Chat = 협업, Work = 위임, API = 내장, Codex = 소프트웨어 제공** (강의 기준). "이건 API예요"가 아니라 그 뒤의 워크플로 증거를 말해요.
- 에이전트적 요구는 **역량**, 오픈 웨이트는 호스팅 통제 평가 후의 **배포** 고려, 하이브리드는 **이유 있는 조합**, 마이그레이션은 **진행 동작**이에요.
- 경로는 **적합성 + 준비도**로 테스트하고, 비용·지연·통합·데이터·거버넌스·도입·복잡도·사람 역할 트레이드오프를 확인해요. 모델 선택·사용료 자금은 표면 선택과 분리해요.
- 다음 단계는 증거 상태에 맞춰 고르고, 핸드오프엔 **아는 것 / 가정 / 검증할 것 / 다음 오너 / 가능하게 할 결정**을 담아 discovery를 다시 하지 않게 해요.
- 가장 강한 추천은 가장 기술적인 추천이 아니라, **명확하고 구체적이며 고객 맥락에 근거하고 아직 검증할 것을 솔직히 밝힌** 추천이에요.
