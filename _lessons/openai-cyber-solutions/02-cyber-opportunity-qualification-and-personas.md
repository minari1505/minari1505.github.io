## 학습 목표

- **워크플로우 우선 검증 렌즈**로 사이버 적합(cyber-fit) 기회를 알아보기
- **CISO · AppSec · DevSecOps · 보안 엔지니어링 · 엔지니어링 리더십**의 우선순위와 필요한 증거 구분하기
- 현재 **보안 입력·도구·기록 시스템·인계 지점**을 지도로 그리기
- **find → validate → test → remediate → prove**로 병목 찾기
- 개선을 보여줄 **증명 지점(proof point)** 정의하기
- 레드팀·공격 중심·승인 불명확 맥락을 알아보고 **신중하게 라우팅·에스컬레이션**하기

> **"AI를 보안에 쓰고 싶어요"는 기회의 시작 신호일 뿐, 검증된 기회가 아니다.** 검증된 기회 = 실제 방어 워크플로우 + 알려진 이해관계자 + 현재 보안 입력 + 병목 + 개선을 보여줄 증명 지점.

## 1단계 — cyber-fit이란 무엇인가

<div class="oa-eli">
  <span class="oa-eli__head">🩺 쉽게 말하면</span>
  <p>환자가 "몸이 안 좋아요"라고만 하면 의사는 약을 바로 처방하지 않아요. <b>어디가(신호), 언제부터 어떻게(병목), 나으면 뭐가 달라지는지(증명)</b>를 먼저 물어요. 고객의 "AI 보안 하고 싶어요"도 똑같이 진찰부터 해야 해요.</p>
</div>

**cyber-fit 기회** = 승인된 방어자가 범위가 정해진 방어 보안 워크플로우를 개선해야 하는 고객 문제.

| 용어 | 뜻 |
|---|---|
| 승인된 방어자 (approved defender) | 소유·운영하거나 테스트·분석을 명시적으로 허가받은 시스템·앱·저장소·데이터를 보호할 권한이 있는 고객 팀(또는 그 팀을 위한 작업) |
| 범위가 정해진 워크플로우 (bounded) | 저장소 1개, 앱 1개, 백로그 조각 1개, 취약점 유형 1개, PR 패턴 1개, 하위 환경 1개, 보안 리뷰 프로세스 1개처럼 구체적 |

적합 신호 예: 노이즈 많은 취약점 백로그 · 보안 리뷰가 필요한 저장소 · 검증이 어려운 SAST/SCA finding · 엔지니어가 안 믿는 보안 티켓 · 감사용 증거 준비가 힘듦 · AppSec↔엔지니어링 인계 문제 반복.

첫 질문: **"가장 먼저 개선하고 싶은 방어 보안 워크플로우가 무엇인가요?"**

### 3가지 진단 질문

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">📡</span><span class="oa-card__title">① 보안 신호는 어디서 오나?</span>스캐너, 코드 변경, 버그 보고, 감사, 의존성 경고, 사고 교훈, 위협 모델, 수동 코드 리뷰 → <b>일의 출처</b></div>
  <div class="oa-card"><span class="oa-card__icon">🐢</span><span class="oa-card__title">② 어디서 느려지나?</span>찾기는 잘하는데 검증·우선순위·인계·수정 테스트·증거에서 막힐 수 있음 → <b>병목 위치</b></div>
  <div class="oa-card oa-card--hl"><span class="oa-card__icon">📏</span><span class="oa-card__title">③ 무엇이 개선의 증거인가?</span>더 빠른 검증, 오탐 감소, 더 나은 증거, 수용된 수정, 명확한 인계, 감사 준비 → <b>추진할 가치</b></div>
</div>

이 질문은 고정 대본이 아니라 **검증 가설(qualification hypothesis)**로 가는 안내예요. 가설 = 고객 문제가 무엇으로 보이고, 무엇이 기회를 확인해 줄지에 대한 짧은 문장.

> 예: "SAST·의존성 스캔에서 finding이 오지만, 엔지니어링이 움직이기 전에 AppSec이 진짜를 가리는 데 시간이 너무 걸리는 **검증 병목**으로 보인다. 백로그 한 조각에서 검증이 빨라지고 반려 티켓이 줄면 유용한 증명이 된다."

### 3가지 분류

| 분류 | 조건 | 예시 |
|---|---|---|
| 🟢 강한 적합 | 승인된 워크플로우, 범위 있는 자산, 이름 있는 소유자, 보이는 병목, 개선 증거를 말할 수 있음 | "고객 포털 저장소 1개의 SAST 백로그. 엔지니어링이 증거 없는 티켓을 반려해 검증에서 지연. AppSec 리드가 리뷰, 성공 = 분쟁 finding 감소 + 빠른 리뷰된 수정" |
| 🟡 확인 필요 | 관심은 있으나 자산·소유자·신호원·병목·증명 중 빠진 것이 있음 | "AI를 보안에 쓰고 싶은데 어디서 시작할지 몰라요" → 제품 추천이 아니라 첫 워크플로우 질문 |
| 🔴 에스컬레이션·신중한 라우팅 | 공격 테스트, 실서비스 대상, 승인 불명확, 핵심 인프라, 운영 테스트, 특별 모델 접근, 특별 데이터 조건 | 역량 주장으로 넘어가지 않고 워크플로우·소유·리뷰 확인 후 OpenAI·기술 SME 참여 |

**예시 — 막연한 관심이 가설이 되는 과정**: "AI 보안 하고 싶은데요" → "신호는 어디서?" (SAST·의존성) → "어디서 느려지나요?" (AppSec이 진짜를 가리는 데 며칠) → "무엇이 개선 증거?" (분쟁 finding 감소, 티켓 속 명확한 증거, 빠른 결정) → 이제 **기존 방어 워크플로우의 검증·우선순위 병목**이라는 구체적 기회가 됐어요. 바로 Daybreak 포지셔닝이나 "전부 스캔"을 제안하지 않은 게 핵심이에요.

## 2단계 — 페르소나와 이해관계자 우선순위

<div class="oa-eli">
  <span class="oa-eli__head">🏫 쉽게 말하면</span>
  <p>학교 축제 하나를 두고도 교장선생님은 "안전하고 학교 평판에 좋은가", 학생회는 "재밌고 참여가 많은가", 시설 담당은 "전기·청소는 누가 하나"를 물어요. <b>같은 행사, 다른 안경.</b> 보안 워크플로우도 누가 보느냐에 따라 필요한 증거가 달라요.</p>
</div>

페르소나는 직함이 아니라 **결정 렌즈 · 성공 척도 · 리뷰 책임**이에요.

| 페르소나 | 관심사 | 이런 질문을 함 | 필요한 증거 |
|---|---|---|---|
| CISO·보안 리더십 | 위험 감소, 노출, 거버넌스, 감사, 경영진 신뢰, 고급 AI의 통제된 사용 | "어떤 중대 위험이 줄었나?" "거버넌스되는지 어떻게 아나?" | **결정 등급 증거** — 승인·감시·리뷰·위험 감소 연결 |
| AppSec | finding 유효성, 오탐, 악용 가능성, 심각도, 공격 경로 맥락 | "어떤 게 진짜인가?" "우리 환경에서 도달 가능한가?" | **실무·기술 증거** — 수용·거절·억제·에스컬레이션할 만큼의 맥락 |
| DevSecOps | 확장 가능한 SDLC 자동화, PR 시점 검사, CI/CD 통합, 개발자 친화 수정 | "기존 SDLC에 맞나?" "PR 검사·티켓·파이프라인과 어떻게 연결?" | **워크플로우 호환성** — 어디서 돌고 어떻게 리뷰·연결되나 |
| 보안 엔지니어링 | 도구, harness, 통합, 텔레메트리, 기록 시스템, 권한, 운영 통제 | "로그·결정은 어디 기록?" "어떤 권한이 필요?" | **운영 증거** — 통제·감사·책임 있는 통합 |
| 엔지니어링 리더십 | 개발 생산성, 릴리스 속도, 패치 품질, 변경 위험, 스프린트 영향 | "엔지니어 일이 늘어나나?" "패치가 의도된 동작을 지키나?" | **전달 중심 증거** — 유용하고 리뷰 가능하며 엔지니어링 흐름에 맞나 |

### 언어로 렌즈 알아듣기

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">🏛️</span><span class="oa-card__title">이사회·노출·감사·통제</span>→ CISO 렌즈</div>
  <div class="oa-card"><span class="oa-card__icon">🎯</span><span class="oa-card__title">오탐·악용 가능성·심각도</span>→ AppSec 렌즈</div>
  <div class="oa-card"><span class="oa-card__icon">🔁</span><span class="oa-card__title">CI/CD·PR 검사·자동화</span>→ DevSecOps 렌즈</div>
  <div class="oa-card"><span class="oa-card__icon">🛠️</span><span class="oa-card__title">도구·로그·권한·기록 시스템</span>→ 보안 엔지니어링 렌즈</div>
  <div class="oa-card"><span class="oa-card__icon">🚀</span><span class="oa-card__title">릴리스 위험·개발자 부담·속도</span>→ 엔지니어링 리더십 렌즈</div>
</div>

CISO에게 저장소 스캔 기능 투어를 하거나, 엔지니어링 리더에게 경영 거버넌스 연설을 하면 **잘못된 사람에게 잘못된 메시지**예요. 그리고 보안 워크플로우 문제는 보통 여러 페르소나에 걸쳐 있으니, 한 명만 있다면 **누가 더 참여해야 하는지** 파악해요.

### 흔한 함정과 더 나은 질문

| 함정 | 더 나은 질문 |
|---|---|
| CISO의 관심 = 워크플로우 준비 완료로 착각 | "현재 신호는 어디서 오고, 어느 팀이 검증하고, 무엇이 노출 우려에 대한 진전의 증거일까요?" |
| finding을 누가 리뷰할지 확인 없이 Codex Security 가능성 논의 | "finding 유효성과 제안 수정의 수용 여부는 누가 판단하나요?" |
| AppSec의 고통이 엔지니어링 채택으로 이어질 거라 가정 | "엔지니어링이 보안 티켓을 '실행 가능'하다고 보려면 무엇이 필요하나요?" |
| 통합 관심 = 완성된 기회로 착각 | "첫 워크플로우가 리뷰어의 어떤 결정을 도와야 하고, 그 결정은 어디에 기록되나요?" |

**예시 — CISO는 급한데 병목은 AppSec에**: 감사 전 노출을 줄이고 싶은 CISO. 알고 보니 AppSec이 스캐너 finding 검증에 허덕이고, 엔지니어링은 재현 노트·코드 맥락·수정 가이드 없는 티켓을 반려. ❌ "Daybreak가 보안 프로그램 전반의 노출을 줄여줍니다." ✅ "노출 우려가 AppSec 워크플로우의 검증·증거 병목과 연결돼 보입니다. 어떤 finding이 백로그에 들어오고, AppSec이 어떻게 검증하고, 엔지니어링이 신뢰하는 리뷰어는 누구이며, 감사 전 무엇이 진전의 증거일지 확인하죠."

## 3단계 — 현재 보안 입력과 시스템 지도

<div class="oa-eli">
  <span class="oa-eli__head">🗺️ 쉽게 말하면</span>
  <p>이사 온 집에 새 가구를 들이기 전에 먼저 <b>방 배치도</b>를 그리죠. 문은 어디고, 콘센트는 어디고, 이미 있는 가구는 뭔지. 고객도 빈 집이 아니에요. 이미 스캐너·티켓·대시보드·감사 저장소가 있어요.</p>
</div>

### 보안 신호를 만드는 것들

| 입력 | 설명 |
|---|---|
| SAST | 소스 코드의 잠재 약점 스캔 |
| DAST | 실행 중인 앱의 불안전한 동작 테스트 |
| SCA | 의존성·오픈소스 구성요소의 취약점 식별 |
| 시크릿 스캔 | 노출된 자격 증명·토큰 식별 |
| 컨테이너·클라우드 설정·IaC 검사 | 인프라 측 설정 점검 |
| 그 외 | 의존성 알림, PR·diff 리뷰, 위협 모델, 버그바운티, 감사 finding, 사고 교훈 |

질문은 "신호가 충분한가?"가 아니라 **"신호를 검증·우선순위화·리뷰 가능한 행동으로 바꿀 수 있는가?"**예요. 큰 백로그는 스캔 문제일 수도 있지만 검증 지연·소유권 불명확·약한 인계·증거 부족일 수도 있어요. 모의해킹·레드팀·공격 중심 보고서·악성코드 관련·운영 활동·외부 대상은 승인과 용도에 따라 **신중한 라우팅**이 필요해요.

### 기록 시스템 vs 실행 surface

<div class="oa-vs">
  <div class="oa-vs__good">
    <span class="oa-vs__label">📒 기록 시스템 (system of record)</span>
    <p>소유권·상태·증거·결정을 추적하는 곳. 예: Jira(수정 담당), GRC 플랫폼(감사 증거), ServiceNow, 취약점 관리 플랫폼</p>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">🔧 실행 surface (execution surface)</span>
    <p>일이 조사·변경·테스트·리뷰되는 곳. 예: 저장소, PR, 로컬 개발 환경, 테스트 환경, 보안 리뷰 도구</p>
  </div>
</div>

도구 선택 메모 (강의 기준):

- **로컬 Codex Security 플러그인** — 로컬 환경 보안 작업
- **Codex Security Cloud** — 연결된 **GitHub** 저장소 스캔 + 새 커밋 감시. GitLab·Bitbucket도 지원한다고 **가정하지 않기**
- **Code Review** — 제안된 코드 변경에 집중, 저장소 전체 스캔을 보완
- 어떤 경우든 고객이 finding과 제안 수정을 리뷰해야 함. **제안 패치 ≠ 취약점 수정 완료**

기존 도구를 버리거나 평행한 프로세스를 만들라고 암시하지 않아요. 발견 질문: finding은 어디로 들어오나? 수정 결정은 어디 기록되나? 엔지니어링은 어디서 리뷰하나? 감사 증거는 어디 가야 하나? 어떤 도구가 진실의 원천인가?

### 안전한 첫 단계 — 4가지 확인

"코드 전부 스캔"이나 "운영 전반 보안 자동화"는 너무 넓어요. **작고 승인된 조각**(저장소 1개, 핵심 앱 1개, 백로그 조각 1개, 취약점 유형 1개, PR 패턴 1개, 승인된 하위 환경 1개)에서 시작해요.

<ol class="oa-flow">
  <li><strong>소유</strong>고객이 소유·운영 또는 명시적 허가</li>
  <li><strong>승인</strong>보안·엔지니어링이 방어 목적으로 승인</li>
  <li><strong>리뷰어</strong>이름 있는 사람이 finding·수정 평가</li>
  <li><strong>증거 기대</strong>어디에 무엇을 남기면 개선인지</li>
</ol>

승인이 특정 변경인지, 백로그 조각인지, 저장소 전체인지 합의해요. **한 번의 리뷰 허가가 모든 자산·미래 리뷰를 허가하지 않아요.** 접근과 운영 준비는 따로 확인해요.

**예시 — 여러 도구에 흩어진 finding**: SAST·의존성·클라우드 설정 도구 → Jira에서 수정 추적 → GRC에 감사 증거. AppSec은 검증이 어렵고, 엔지니어링은 맥락 부족, 경영진은 보고가 수작업. ❌ "Daybreak가 보안 워크플로우를 자동화해 드려요." ✅ 신호원·기록 시스템·리뷰 위치·증거 목적지를 먼저 지도로 그리고, 이름 있는 AppSec 리뷰어가 있는 **저장소 1개 또는 백로그 조각 1개**를 안전한 첫 단계로.

## 4단계 — 5단계 워크플로우로 병목 진단

<div class="oa-eli">
  <span class="oa-eli__head">🚗 쉽게 말하면</span>
  <p>출근길이 막힐 때 "차가 많다"가 답은 아니에요. 진짜 원인은 <b>특정 교차로의 신호 대기</b>일 수 있죠. 고객이 "finding이 너무 많아요"라고 해도 실제 막힌 곳은 검증·테스트·수정·증거·인계 중 하나일 수 있어요.</p>
</div>

| 단계 | 발견 질문 | 병목 징후 |
|---|---|---|
| Find | 무엇이 finding을 만드나? 양은? 어떤 자산? 그룹화·중복 제거되나? | 출처 과다, 중복, 약한 우선순위, 접수 시 소유권 불명확 |
| Validate | 누가 검증? 어떤 증거로? 오탐은 어떻게 가리나? | AppSec 맥락 부족, 노이즈, 무엇이 중요한지 결정 못 함 |
| Test | 테스트가 승인됐나? 어떤 환경? 무엇이 미검증? | 안전한 환경 없음, 승인 불명확, 커버리지 부족 |
| Remediate | 누가 수정 소유? 엔지니어링은 무엇이 필요? | 티켓 반려, 패치 불명확, 소유권 분쟁, 전달 우선순위와 충돌 |
| Prove | 증거는 어디? 누가 종결 수용? 감사에 뭐가 필요? | 증거 분산, 리뷰어 결정 미기록, 경영진이 진전을 못 봄 |

## 5단계 — 증명 지점과 기회 준비도

<div class="oa-eli">
  <span class="oa-eli__head">🏃 쉽게 말하면</span>
  <p>"운동 열심히 할게요"보다 "한 달 뒤 1km를 30초 더 빨리 뛰겠다"가 확인하기 쉬워요. 증명 지점은 <b>무엇이, 누구에게, 어느 범위에서 좋아지는지</b> 관찰 가능한 목표예요. 거창한 ROI 모델일 필요는 없어요.</p>
</div>

증명은 **병목에 맞춰야** 해요:

| 병목 | 어울리는 증명 지점 |
|---|---|
| 검증 | 검증된 finding까지의 시간 단축, 오탐 감소 |
| 개발자 인계 | 반려 티켓 감소, 수용된 수정 경로 증가 |
| 감사 증거 | 더 명확한 증거 패킷, 종결 문서화 수작업 감소 |

쓸 만한 증명 지표: finding 유효성 · 노이즈 감소 · 증거 유용성 · 검증까지 시간 · 리뷰된 수정까지 시간 · 패치 수용 · 회귀 신뢰도 · 리뷰어 신뢰도 · 감사 준비도. **미승인 ROI·벤치마크·경쟁 비교·모델 성능 약속은 피해요.**

      <li>"소유 저장소 1개에서 결과가 finding 유효성·증거 품질·리뷰어 신뢰를 개선하는지 판단할 수 있다."</li>

### 기회 준비도 체크리스트

**적합한 사용 사례 ≠ 시작할 접근·승인이 있음.** 준비도는 열정이 아니라 **증거의 질**이에요.

| 영역 | 확인 항목 |
|---|---|
| 문제 | 명확한 방어 워크플로우 문제 · 이름 있는 이해관계자/소유자 · 알려진 신호원 · 보이는 병목 |
| 범위 | 범위 있는 자산과 리뷰 범위 + **저장소 제공자**와 **소유자 승인 기록** |
| 사람 | 시간 여유가 있는 이름 있는 리뷰어 · 수정 수용 소유자 |
| 기록·증명 | 기록 시스템/증거 위치 · 개선을 보여줄 증명 지점 |
| 미결 사항 | 열린 질문·가정·에스컬레이션 필요, **각각 담당자와 다음 행동** |
| 접근 (강의 기준) | 선택된 surface와 모델, 의도한 사용자·워크스페이스/API 프로젝트의 접근 증거 · 적격 ChatGPT 플랜(Codex Security는 Pro·Business·Enterprise·Edu research preview) · Enterprise/Edu는 Codex Cloud + Codex Security **둘 다** 활성화 |
| Cloud 운영 (강의 기준) | 저장소 연결, Security **사용 권한**과 스캔 설정 **관리 권한**(별개) · 스캔 예산과 그 소유자 · 합의된 중단 조건 시 지속 작업을 멈출 사람 |

접근 메모 (강의 기준): Cloud에는 별도 신청 없이 **Daybreak Blue**가 포함되지만 API·다른 surface 접근은 주지 않아요. Red는 고급 승인 작업용 별도 승인. **어느 등급도 자산 리뷰에 대한 고객의 허가를 대신하지 않아요.** Cloud 스캔은 토큰 과금이라 기존 고객은 유료 사용 전 opt-in, 예산이 없으면 스캔 일시중지 → 구독이 커버한다고 가정하지 말고 관리자·예산 소유자에게 확인해요.

"취약점이 수천 개예요"는 아직 준비 안 됨. 출처, 먼저 다룰 부분집합, 검증자, 결정 기록 위치, 증명 지점이 필요해요.

### 검증 스냅샷 작성

**검증 스냅샷** = 아는 것 / 가정하는 것 / 확인이 필요한 것을 담은 간결한 기록. 원래 대화에 없던 OpenAI·파트너 동료도 이해할 수 있어야 해요.

<div class="oa-cards">
  <div class="oa-card oa-card--hl"><span class="oa-card__icon">✅</span><span class="oa-card__title">알려진 사실</span>"SCA finding은 Jira에서 추적되고 AppSec이 리뷰한다고 고객이 말했다."</div>
  <div class="oa-card"><span class="oa-card__icon">🤔</span><span class="oa-card__title">가정</span>"범위 있는 첫 단계에 맞는 저장소가 하나 있을 수 있으나 미확인."</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🕳️</span><span class="oa-card__title">증명 공백</span>"엔지니어링이 수정을 수용하기 전 어떤 증거가 필요한지 아직 정의 안 됨."</div>
</div>

| 스냅샷 항목 | 예시 (고객 포털 사례 요약) |
|---|---|
| 고객 문제 | AppSec 백로그 증가, 엔지니어링이 맥락 부족으로 티켓 반려 |
| 이해관계자 | AppSec 리드 = 검증, 엔지니어링 매니저 = 수정 수용, CISO = 감사용 증거 |
| 신호원 / 기록 시스템 | SCA·SAST / Jira(수정), GRC(종결 증거) |
| 병목 | 검증 + 개발자 인계 |
| 범위 있는 출발점 | 소유 고객 포털 저장소 1개 또는 백로그 조각 1개 (확인 대기) |
| surface·모델 | 미선택. Cloud 고려 전 저장소 제공자 확인, 모델·교차 surface 접근 가정 금지 |
| 접근·연결 | 증거 없음. 워크스페이스 관리자가 사용자/프로젝트 범위·활성화·연결·사용/관리 권한 확인 |
| 운영 준비 | AppSec이 리뷰어·여력 확인, 저장소 소유자가 허용 행동 합의, 스폰서가 예산·중단 담당자 지정 |
| 증명 지점 | 반려 티켓 감소, 리뷰어 결정 가속 |
| 다음 안전한 단계 | 범위 있는 리뷰 1건과 공백을 실행 전에 명확히. 승인·접근·예산·리뷰 여력이 없으면 멈춤. 제안 패치 ≠ 수용된 수정 |

**연습 포인트 (강의 예시)**: 스폰서가 포털의 향후 변경 감시 + **다른 저장소 제공자에 있는 두 번째 서비스**까지 바로 넣자고 할 때 → 포털은 유망한 기회로 기록하고, 승인 안 된 두 번째 서비스는 **별도로 보류**해요. 초기 리뷰 승인 ≠ 지속 작업 허가·여력.

## 6단계 — 민감한 맥락 알아보고 라우팅하기

  <span class="oa-eli__head">🧯 쉽게 말하면</span>
  <p>동네 약국 약사도 "이 약 얼마나 먹어도 되나요?"엔 답하지만, 특수한 상황이면 "의사 선생님과 먼저 상의하세요"라고 해요. 그게 실패가 아니라 <b>환자를 지키는 일</b>이죠. 민감한 사이버 요청을 전문가에게 넘기는 것도 똑같아요.</p>

**잠시 멈춰야 하는 맥락**: 레드팀 요청 · 보안 연구 요청 · 공격 중심 작업 · 공격 테스트 · 악성코드 분석·생성 · 실서비스 대상 테스트 · 승인 불명확 · 가드레일 없는 운영 테스트 · 핵심 인프라·고위험 환경 · 맞춤 harness·API 게이트웨이·고급 자동화 · 사이버 특화 모델 접근 요청 · 특별 데이터 처리·가격·가용성·내부 접근 등급 질문.

이런 맥락이 항상 부당한 건 아니에요. 많은 정당한 방어자가 승인된 환경에서 고급 작업을 해요. 다만 진행 전에 **승인됐는지 · 방어 목적인지 · 고객 소유 또는 명시적 허가인지 · 범위가 있는지 · 사람이 리뷰하는지 · 증거 기대가 명확한지**를 확인해요.

> **역량을 논하기 전에 워크플로우를 명확히 하라.**

**에스컬레이션은 실패한 대화가 아니에요.** 고객 신뢰와 플랫폼 무결성을 지키고, 접근·가용성·배포·데이터 처리에 대해 말하기 전에 전문가가 검토하게 해요.

접근 메모 (강의 기준): 고객이 쓰려는 **모델과 제품**을 항상 확인 (하나의 승인이 다른 것을 보장하지 않음). Blue에서 GPT-6 Astra는 표준 안전장치 유지, 거절 감소는 Red 승인 + 활성화, GPT-5.6-Cyber는 모델별 추가 승인·접근 설정. 일상적 Cloud 설정 질문은 고객 관리자에게, 불확실한 자격·민감 작업은 OpenAI에. 일반 Trusted Access는 승인된 내부 작업용이고, 고객에게 Daybreak 기반 보안 서비스를 제공하려면 **Daybreak Cyber Partner Program** 별도 승인이 필요해요.

### 3가지 라우팅 분류

| 분류 | 조건 | 다음 행동 |
|---|---|---|
| 🟢 더 검증할 준비됨 | 승인된 워크플로우, 이름 있는 이해관계자, 명확한 신호, 보이는 병목, 범위, 리뷰어, 증명 지점 | **스캔 시작이 아니라 추가 검증.** 미확인 접근·예산·리뷰 여력은 담당자와 함께 넘기고 증거가 갖춰질 때까지 실행 보류 |
| 🟡 확인 필요 | 잠재 문제는 있으나 소유·범위·신호원·증명·리뷰 절차 불명확 | 첫 워크플로우를 묻는 질문 |
| 🔴 진행 전 에스컬레이션 | 민감 맥락, 승인 불명확, 공격 중심, 운영·핵심 인프라, 특별 접근, 미지원 제품 주장 | 전술·모델 역량·고급 워크플로우 논의 금지. 승인 확인 후 OpenAI·기술 SME 참여 |

분류에는 항상 **이유**를 함께 적어요. 이유 없는 분류는 책임 있는 후속 조치에 충분하지 않아요.

**예시 — 외부 대상 레드팀 자동화 요청**: ❌ "네, 고급 사이버 역량이 있어서 도와드릴 수 있어요." (승인·범위·소유·리뷰어·방어 목적 확인 전 역량 주장) / ✅ "고급 워크플로우를 논의하기 전에 승인된 방어 맥락을 확인하죠. 어떤 대상이 소유 또는 명시적 승인 대상인가요? 승인된 환경은? 누가 결과를 리뷰하나요? 경로를 추천하기 전에 OpenAI SME 리뷰가 필요할 수 있어요." → 전술 논의로 들어가지 않고, 표준 AppSec 검증 경로로 취급하지 않아요.

## 정리

- 막연한 관심은 **3가지 진단 질문**(신호원 · 병목 · 증명)으로 **검증 가설**이 된다. 분류는 강한 적합 / 확인 필요 / 에스컬레이션, 항상 이유와 함께.
- 페르소나는 직함이 아니라 **결정 렌즈**다. CISO는 결정 등급 증거, AppSec은 기술 증거, DevSecOps는 호환성, 보안 엔지니어링은 운영 통제, 엔지니어링 리더는 전달 영향.
- **신호원 · 기록 시스템 · 실행 surface · 인계 · 증거 공백**을 지도로 그리고, 소유·승인·리뷰어·증거 기대가 확인된 **작은 조각**에서 시작한다.
- 증명 지점은 **병목에 맞춰** 관찰 가능하게. 준비도는 열정이 아니라 증거의 질이며, 각 공백에는 **담당자와 다음 행동**이 붙는다.
- 민감 맥락에선 **역량보다 워크플로우를 먼저** 확인하고, 에스컬레이션은 실패가 아니라 신뢰를 지키는 일이다.
