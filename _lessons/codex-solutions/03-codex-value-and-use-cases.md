## 학습 목표

- Codex의 가치를 **기능이 아니라 결과(outcome) 중심 영업 언어**로 설명하기
- "개발 생산성"을 코딩 속도가 아니라 **일이 시스템을 통과하는 방식**으로 풀고, 고객 우선순위와 연결하기
- 리뷰·검증 / 저장소 이해·온보딩 / 현대화·유지보수 / 트러블슈팅·사후 대응 중 **앞세울 고가치 SDLC 사용 사례** 고르기
- 같은 사용 사례를 **이해관계자와 산업·운영 맥락**에 맞춰 다르게 이야기하기
- 모델·처리 등급 비교를 **품질 · 시간 · 수용된 결과당 총비용**으로 판단하고, 과금 가정을 분리하기

## 한눈에 보는 코스 흐름

<ol class="oa-flow">
  <li><strong>비즈니스 가치 번역</strong>무엇을 하나 → 왜 중요한가</li>
  <li><strong>개발 생산성 결과</strong>코딩 속도가 아닌 흐름 개선</li>
  <li><strong>고가치 SDLC 사용 사례</strong>무엇을 앞세울까</li>
  <li><strong>이해관계자별 가치</strong>같은 사실, 다른 강조점</li>
  <li><strong>산업·운영 맥락</strong>워크플로는 어디, 맥락은 어떻게</li>
</ol>

이 코스를 관통하는 한 문장: **고객 압박에서 시작해 → 마찰을 만드는 SDLC 워크플로를 찾고 → 그 워크플로를 지원하는 Codex를 과장 없이 결과 언어로 말한다.**

## 1. Codex 비즈니스 가치 — 셀러의 번역 작업

<div class="oa-eli">
  <span class="oa-eli__head">🚲 쉽게 말하면</span>
  <p>자전거 가게에서 "이 기어는 21단이에요"(기능)라고 하면 시큰둥하지만, "언덕 많은 등굣길에서 덜 지치게 해 줘요"(결과)라고 하면 귀가 열려요. Codex도 "PR 리뷰를 도와요"보다 "<b>리뷰 대기 때문에 릴리스가 늦어지는 문제</b>를 줄이는 데 도움"이라고 말해야 해요.</p>
</div>

### 가치 대화의 3가지 질문

| 질문 | 예시 |
|---|---|
| ① 어떤 고객 결과가 압박받나? | 로드맵 실행, 릴리스 예측성, 현대화 진척, 엔지니어링 대응력 |
| ② 어떤 개발 워크플로가 원인인가? | 리뷰, 테스트, 디버깅, 문서화, 유지보수, 온보딩 |
| ③ 왜 비즈니스에 중요한가? | 제품 출시 지연, 엔지니어링 부담 증가, 현대화 지연, 시장 대응 저하 |

| 고객의 말 | 가능한 원인 | 더 강한 가치 방향 |
|---|---|---|
| "릴리스가 계속 밀려요" | 리뷰·테스트·디버깅·릴리스 준비 마찰 | 반복적 딜리버리 마찰 감소, 릴리스 예측성 |
| "시니어가 계속 방해받아요" | 지식 전달·온보딩·리뷰 병목 | 반복 맥락 전달 감소, 시니어 역량 보존 |
| "현대화가 계속 밀려요" | 레거시 이해·유지보수·기술 부채 | 현대화 워크플로 지원, 운영 부담 감소 |
| "리뷰 후 재작업이 많아요" | 리뷰 불일치·검증 기준 불명확 | 리뷰·검증 워크플로 지원 (개발 속도 일반론 ✗) |

|---|---|
| "PR 리뷰를 도와요" | "리뷰 대기가 릴리스 준비를 늦출 때, 리뷰 워크플로 지원으로 반복 리뷰 부담을 줄이고 릴리스 예측성을 높여요" |
| "코드를 설명해 줘요" | "지식 전달이 온보딩·현대화를 늦출 때, 저장소 이해 지원으로 반복 맥락 전달을 줄여요" |
| "버그를 고쳐요" | "반복 이슈가 계획된 개발을 방해할 때, 범위 정해진 트러블슈팅·사후 작업으로 반복 조사 부담을 줄여요 — 장애 복구·리뷰·승인 책임은 사람에게" |

### 6단계 가치 내러티브 패턴

<ol class="oa-flow">
  <li><strong>고객 우선순위</strong>릴리스 예측성이 압박받음</li>
  <li><strong>워크플로 압박</strong>리뷰 조율·반복 CI 실패</li>
  <li><strong>SDLC 사용 사례</strong>테스트·디버깅·리뷰 지원</li>
  <li><strong>이해관계자 영향</strong>엔지니어링=처리량, 제품=로드맵</li>
  <li><strong>Codex 가치</strong>해당 워크플로 지원으로 프레이밍</li>
  <li><strong>결과 언어</strong>반복 조사 부담 감소, 흐름 개선</li>
</ol>

```text
이 고객은 [워크플로 압박]을 겪고 있고, 이것이 [비즈니스·운영 결과]에 영향을 준다.
Codex 가치는 [이해관계자]를 위한 [SDLC 사용 사례]로 프레이밍하고, [결과]를 강조한다.
```

### 비용 이야기 전에: 과금 구조를 섞지 않기 (강의 기준)

구독이나 Marketplace 등록만으로 **권한·무제한 사용·비용 절감**이 생기지 않아요. 비용·절감 이야기 전에 **사용·구매 방식, 예산 책임자, 구매 후속 절차**를 확인하세요.

### 환경마다 다른 생산성 이야기

| 고객 환경 | 주로 원하는 가치 | 핵심 과제 |
|---|---|---|
| **빠르게 성장하는 팀** | 온보딩 연속성, 일관성, 시니어 방해 감소 | 새 팀이 소수 시니어 없이도 일하는 법을 이해 |
| **성숙한 플랫폼 팀** | 표준화, 워크플로 일관성, 조율 부담 감소 | 복잡한 환경 전반의 예측 가능한 흐름 |
| **현대화 중심 팀** | 저장소 이해, 유지보수 부담, 기술 부채 탐색 | 무엇이 있고 위험이 어디 있는지 파악 |

맥락은 트레이드오프도 바꿔요. 현대화 작업은 품질 체크를 맞추려 **더 많은 리뷰·추론**이 정당할 수 있고, 반복적인 일상 작업은 통과만 한다면 **저비용 옵션**이 나을 수 있어요.

### 모델·처리 등급 비교: 토큰 가격 ≠ 결과 비용

<div class="oa-eli">
  <span class="oa-eli__head">🛒 쉽게 말하면</span>
  <p>싼 우산을 샀는데 세 번 고장 나서 네 개를 샀다면, 비싼 우산 하나보다 더 쓴 거예요. 모델도 <b>토큰당 가격</b>이 아니라 <b>"합격한 결과물 하나를 얻는 데 든 총비용"</b>으로 비교해요.</p>
</div>

강의 예시(강의 기준): GPT-6.1 Sol은 GPT-6 Astra보다 표준 API 토큰 가격이 낮지만, 그게 수용된 결과의 비용이 낮다는 뜻은 아니에요. Ultrafast는 별도 모델이 아니라 **처리 등급**이고, GPT-6.1 Sol Ultrafast는 아직 제공되지 않아요. Codex Cloud는 현재 기본 모델 변경을 지원하지 않아요. 표면이 비교하려는 모델·처리 옵션을 지원하는지, 접근·권한·처리 지역 요구사항은 기술 전문가와 확인해요.

| 측정 | 무엇을 보나 |
|---|---|
| **품질** | 어떤 결과가 합격 체크를 통과했나, 시도가 얼마나 자주 실패했나 |
| **시간** | 작업 시작 → 수용까지 (도구 대기·재시도·리뷰 포함). 리뷰어 노력은 따로 기록 |
| **비용** | 수용된 결과당 총비용 = 시험 총비용 ÷ 수용된 결과 수 (실패·재시도·도구·사람 리뷰 포함) |

- 수용된 결과가 0이면 "비용 0의 성공"이 아니라 **시험 비용과 수용 0건**으로 보고해요.
- API 평가는 최신·날짜가 표시된 요율과 실측 사용량(입출력 토큰, 캐시 읽기·쓰기, 장문·지역 요금)을 써요. **프롬프트 캐싱은 일치하는 입력을 재사용**하는 것이지 완성된 답을 재사용하는 게 아니니, 실제 관측된 캐시 재사용만 계산해요.
- 리뷰가 주 병목이면 더 빠른 처리 등급이 딜리버리를 줄여 주지 않을 수 있어요.

## 3. 고가치 SDLC 사용 사례 고르기

### SDLC 가치 경로 (5단계 대화 보조)

| 고객 신호 | discovery 질문 | 워크플로 고통 | 압박받는 결과 | 다음 이해관계자 행동 |
|---|---|---|---|---|
| 릴리스 지연 | 어디서 일이 느려지나? | PR 리뷰 병목 | 더 빠른 딜리버리 | 탐색할 사용 사례 합의 |
| 개발 생산성 | 엔지니어링 시간이 어디로 새나? | 반복 CI 조사·디버깅 | 역량 개선·재작업 감소 | 사용 사례 확정 |
| 현대화 | 어떤 레거시 작업이 진척을 막나? | 코드 이해·문서 공백 | 현대화 진척 | 워크플로 담당자 확인 |
| 품질 통제 우려 | 체크·리뷰·승인이 어디서 들쭉날쭉한가? | 리뷰·릴리스 준비 관행 불일치 | 품질·거버넌스 강화 | 개선 목표·성공 신호 명확화 |

배포 준비와 장애 복구는 사람·프로세스가 걸린 더 넓은 결과예요. 이 맥락에서는 맥락·도구·권한·환경·리뷰 게이트가 갖춰졌을 때 **변경·테스트·문서·수정 작업 준비 같은 범위 정해진 작업**으로만 Codex를 위치시켜요.

### 4가지 사용 사례 패턴

| 패턴 | 이럴 때 앞세우기 | 셀러 프레이밍 |
|---|---|---|
| **리뷰·검증 병목** | PR 대기열, 시니어 리뷰 과부하, 수동 검증 의존, 반복 CI 실패 | "개발 효율 문제가 아니라 **릴리스 준비 워크플로** 문제예요" |
| **저장소 이해·온보딩** | 신입 적응이 느림, 같은 질문 반복, 낡은 문서, 거대한 저장소 | "더 빠른 온보딩만이 아니라 **조직 전반의 반복 지식 전달 부담** 감소" |
| **현대화·유지보수** | 레거시가 로드맵을 늦춤, 기술 부채, 범위 잡기 어려운 마이그레이션 | "현대화 작업을 **덜 마찰스럽게 이해·계획·진행**" (자동 변환 약속 ✗) |
| **트러블슈팅·사후 엔지니어링** | 반복 디버깅, 잦은 CI 실패, 이슈 후 맥락 재구성 | "**반복 조사 부담**을 줄이고 더 효율적으로 대응" (복구·리뷰·승인은 사람) |

리뷰·검증은 완성된 작업과 릴리스 준비 **사이**에 있어서, 고객이 어디서 일이 기다리는지 직접 볼 수 있다는 점에서 특히 상업적으로 구체적이에요. 트러블슈팅은 일회성 버그가 아니라 **반복 조사 노력**을 짚을 수 있을 때 가장 강해요.

### 고객 사례를 쓰는 법

<ol class="oa-flow">
  <li><strong>문제부터</strong>줄이려던 병목·마찰</li>
  <li><strong>워크플로에서 어떻게 썼나</strong>구현 세부보다 바뀐 일</li>
  <li><strong>사람·비즈니스로 연결</strong>대기·리뷰·반복 감소 → 역량·속도</li>
  <li><strong>고객에게 되묻기</strong>비슷한 병목·기준선·성공 지표는?</li>
</ol>

다른 고객의 결과를 **약속하지 마세요.** 사례는 가능한 가치의 종류를 보여 주는 도구예요.

## 4. 이해관계자별 가치 이야기

| 이해관계자 | 리뷰 병목이 의미하는 것 | 가치 내러티브 |
|---|---|---|
| **VP Engineering** | 딜리버리 처리량·팀 역량 | "리뷰·테스트·유지보수의 반복 운영 마찰을 줄여 SDLC 효율 지원" |
| **플랫폼·개발 생산성 리더** | 워크플로 일관성·개발자 경험 | "팀 전반의 일관성 개선, 반복 맥락 전달 감소" |
| **제품·딜리버리 리더** | 로드맵 예측성·릴리스 일정 | "로드맵 실행·릴리스 대응력에 영향 주는 병목 해결" |
| **거버넌스 민감 이해관계자** | 리뷰 책임·통제된 변경 | "기존 리뷰·승인·감독·운영 가시성 프로세스 **안에서** 가치 프레이밍" |

거버넌스 메시지는 이 코스에선 **가치 내러티브 수준**에 머물러요. 보안 아키텍처·권한·관리자 설정·배포 거버넌스 통제는 설명하지 않아요.

## 5. 산업·운영 맥락에 맞추기

> **워크플로는 고통이 어디 있는지 알려 주고, 맥락은 가치를 어떻게 말할지 알려 준다.**

| 고객 맥락 | 앞세울 것 | 주의 |
|---|---|---|
| **소프트웨어 중심·디지털 네이티브** | 릴리스 속도, 디버깅 처리량, 분산 팀 조율 | 개인 코딩 속도로 축소하지 않기 |
| **규제 환경** | 통제된 워크플로 개선, 리뷰 일관성, 운영 책임, 작업·리뷰 가시성 | 승인된 자료로 검증되지 않은 컴플라이언스·보안 통제 주장 금지 |
| **현대화 중심 기업** | 레거시 이해, 유지보수 부담, 마이그레이션 지원 | 자동 변환 약속 금지 |
| **개발 생산성 성숙도 낮음** | 워크플로 일관성, 온보딩 | 반복 습관·공통 방식부터 |
| **성숙도 높음** | SDLC 처리량, 확장 패턴, 엔지니어링 레버리지 | 팀 전반으로 일관된 워크플로 확장 |

같은 "개발 생산성"이라도 빠르게 성장하는 SaaS 회사엔 **릴리스 이동·확장 조율**, 규제된 공공 현대화 프로그램엔 **통제된 진척·리뷰 일관성·장기 유지보수성**이 강조점이 돼요.

## 정리

- 가치 대화는 **압박받는 결과 → 원인 워크플로 → 비즈니스 의미** 순. 기능 목록·보장 수치·"개발자 대체"는 피한다.
- 개발 생산성은 **코딩 속도가 아니라 일이 시스템을 통과하는 방식**. 환경(성장·플랫폼·현대화)에 따라 이야기가 달라진다.
- 앞세울 사용 사례는 **반복·교차 기능·결과 연결·단순 도구로 안 풀림·거버넌스 가능**한 것: 리뷰·검증, 저장소 이해·온보딩, 현대화·유지보수, 트러블슈팅·사후 작업.
- 이해관계자와 산업 맥락에 맞춰 **같은 사실, 다른 강조점**.
- 모델·등급은 **품질 · 시작→수용 시간 · 수용된 결과당 총비용**으로 비교하고, 로그인·플랜 사용량·API 과금·Marketplace 구매를 **섞지 않는다**.
