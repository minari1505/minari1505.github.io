## 1. Codex Opportunity Fit Lens의 다섯 점검 항목

**문제:** Codex Opportunity Fit Lens의 다섯 항목을 모두 포함하는 조합은?

**정답: 2번 ✅ 반복되는 고충, 사업 영향, 이해관계자 소유권, 준비도, 반복 가능한 워크플로우**

**선택지 분석:** 1번 예산·선호도·조달은 구매 정보라 기회 적합성 전체를 설명하지 못합니다. 2번은 고충의 반복성과 사업 맥락, 책임자, 평가 준비, 업무 반복성까지 확인합니다. 3번 코딩 속도·모델·저장소 규모는 기술 인벤토리이며 고객 가치와 소유권을 놓칩니다. 4번 보안 승인·배포·ROI 전망은 일부 준비 요소지만 고충과 반복성을 확인하지 않습니다.

**공식 해설 번역:** 이 렌즈는 고통이 반복되는지, 사업 결과에 영향을 주는지, 믿을 만한 소유자가 있는지, 현실적으로 평가할 준비가 되었는지, 반복 가능한 소프트웨어 제공 워크플로우와 연결되는지를 확인합니다. 제품 소개나 배포 체크리스트가 아니라 영업 기회 적격성을 판단하는 기준입니다.

**핵심 암기 포인트:** 반복성·사업 영향·소유권·준비도·반복 워크플로우.

**AI 개발 실무 추가 설명:** PoC 전에 문제 빈도와 영향, 업무 책임자, 테스트 가능한 사례, 배포 전제조건을 분리해 적으면 과장된 ROI와 준비도 오판을 줄일 수 있습니다.

**누적 정답률:** 1/1 · 100%

## 2. 모호한 고객 불만에 대한 다음 질문

**문제:** 고객은 “테스트가 너무 오래 걸린다”고 하지만 어떤 워크플로우가 지연되는지, 사업 결과가 무엇인지 설명하지 못합니다. 영업 담당자의 최선 판단은?

**정답: 1번 ✅ 워크플로우, 제공 지연의 결과, 지금 중요한 이유를 더 탐색한다.**

**선택지 분석:** 1번 불만을 구체적인 업무와 영향으로 확인합니다. 2번 테스트가 늘 Codex의 강한 활용 사례라고 가정해 너무 일찍 진행합니다. 3번 일반 데모로 긴급성을 만들려 해 실제 원인을 놓칩니다. 4번 정량 ROI가 없다는 이유만으로 영구 중단하는 것도 성급합니다.

**공식 해설 번역:** 넓은 엔지니어링 불만은 적격성을 보여주는 증거가 아니라 탐색의 시작점입니다. 워크플로우, 영향을 받는 제공 결과, 현재 중요한 이유가 불명확하면 기회가 있을 수는 있지만 추가 발견이 필요합니다.

**핵심 암기 포인트:** 불만을 곧바로 솔루션 수요로 간주하지 말고 구체적인 증거를 탐색한다.

**AI 개발 실무 추가 설명:** 기준선·실제 지연 구간·오류 유형·책임자를 확인한 뒤 자동화 가능성과 성공 지표를 정의합니다.

**누적 정답률:** 2/2 · 100%

## 3. 실제 업무 흐름을 파악하는 질문

**문제:** 테스트가 느려 릴리스가 늦어진다는 고객에게 솔루션 논의 전에 물을 가장 좋은 질문은?

**정답: 2번 ✅ “최근 이런 일이 있었던 상황을 처음부터 설명해 주시겠어요?”**

**선택지 분석:** 1번 경쟁사 기능 비교는 실제 업무를 보여주지 않습니다. 2번 최근 사례를 따라가면 참여자·단계·지연 위치·맥락·검토 과정을 찾을 수 있습니다. 3번 조달 일정은 업무 탐색보다 구매 절차에 앞서갑니다. 4번 선호하는 Codex 경험부터 고르면 제품 중심 대화가 됩니다.

**공식 해설 번역:** 실제 발생 사례를 따라가면 무엇을 하던 중이었는지, 지연이 어디서 생겼는지, 누가 참여했는지, 어떤 맥락이 필요했는지, 결과를 어떻게 검토했는지 드러납니다. 이를 통해 병목이 테스트인지, 요구사항·커버리지·소유권·리뷰·릴리스 조율인지 판단할 수 있습니다.

**핵심 암기 포인트:** 구체적인 최근 사례를 단계별로 재구성한다.

**AI 개발 실무 추가 설명:** 인터뷰 때 입력, 도구, 단계별 소요시간, 실패·재작업, 승인 조건을 기록하면 자동화 대상과 사람 검토 지점을 구분하기 쉽습니다.

**누적 정답률:** 3/3 · 100%

## 4. 제품 요구가 소프트웨어 전달 문제가 아닐 때

**문제:** 고객이 고객용 제품에 AI 어시스턴트를 내장하고 싶어 하지만 반복적인 소프트웨어 전달 문제는 확인되지 않았습니다. 과정의 진행 논리에 맞는 방향은?

**정답: 3번 ✅ Codex를 억지로 적용하지 말고 API 논의로 연결한다.**

**선택지 분석:** 1번 모든 기술 요구를 개발 워크플로우로 재해석하는 건 제품 적합성을 왜곡합니다. 2번 OpenAI 대화를 전부 중단할 필요도 없습니다. 3번 앱·제품에 AI 기능을 내장하려는 요구에는 API 경로가 맞습니다. 4번 직원 생산성 문제가 아닌데 ChatGPT를 권하는 것도 맞지 않습니다.

**공식 해설 번역:** 제품·애플리케이션·시스템·고객 경험 안에 지능을 넣으려는 요구는 API를 가리킬 수 있습니다. 주된 요구가 소프트웨어 전달 개선이 아니라면 Codex를 대화에 억지로 끼워 넣지 않아야 합니다.

**핵심 암기 포인트:** 개발 업무 개선은 Codex, 기존 제품에 기능 내장은 API.

**AI 개발 실무 추가 설명:** API 제품화에서는 인증·권한·데이터 경계·지연시간·비용·관측성·장애 대응까지 함께 설계해야 합니다.

**누적 정답률:** 4/4 · 100%

## 5. Codex의 적절한 포지셔닝

**문제:** Codex를 가장 적절하게 설명한 문장은?

**정답: 1번 ✅ SDLC 전반의 범위가 정해진 다단계 소프트웨어 작업을 지원하며, 사람의 검토와 책임을 유지한다.**

**선택지 분석:** 1번은 위임 가능한 작업 범위와 인간 책임을 함께 설명합니다. 2번은 모든 조직에서 생산성 향상을 보장해 과장입니다. 3번은 Codex를 단순 자동완성으로 축소합니다. 4번은 엔지니어링 팀을 대체하는 완전 자율 시스템이라고 과장합니다.

**공식 해설 번역:** Codex는 자동완성보다 넓은 일을 지원하지만 완전 자율적인 소프트웨어 제공까지 대신하지는 않습니다. 실제 워크플로우에서 엔지니어링 작업을 위임하더라도 검토·품질·의사결정 책임은 사람에게 남습니다.

**핵심 암기 포인트:** 위임은 가능하지만 검토와 책임은 사람이 유지한다.

**AI 개발 실무 추가 설명:** 저장소 접근, 변경 범위, 테스트, 리뷰, 병합 권한을 단계별로 분리하고 성공적인 실행과 승인된 변경을 동일시하지 않습니다.

**누적 정답률:** 5/5 · 100%

## 6. 기존 IDE 보조 도구가 있을 때

**문제:** 고객이 이미 IDE 코딩 어시스턴트를 쓰고 있다고 말합니다. Codex 대화를 어떻게 이어가야 할까요?

**정답: 1번 ✅ 기존 도구를 인정하고 SDLC 전반에서 여전히 느린 부분을 묻는다.**

**선택지 분석:** 1번은 도구 교체가 아니라 아직 해결되지 않은 업무를 찾습니다. 2번 도구 전략이 없는 팀만 대상이라고 제한할 근거가 없습니다. 3번 워크플로우를 파악하기 전에 교체부터 권하면 안 됩니다. 4번 자동완성 기능 비교만으로 업무 영향 탐색을 대체할 수 없습니다.

**공식 해설 번역:** 현재 코딩 도구를 인정하되 단일 코딩 순간을 넘어 대화를 확장합니다. 테스트·리뷰·디버깅·문서화·온보딩·현대화 등 여전히 느린 워크플로우를 찾습니다.

**핵심 암기 포인트:** 기존 도구의 유무보다 남아 있는 병목이 중요하다.

**AI 개발 실무 추가 설명:** 기존 도구와 중복·차별 지점을 비교하기 전에 실제 개발자 여정과 측정 가능한 병목부터 조사합니다.

**누적 정답률:** 6/6 · 100%

## 7. CI 조사 병목에 대한 가치 설명

**문제:** 반복되는 CI 조사 때문에 릴리스가 늦어집니다. Codex의 활용을 가장 잘 설명한 선택지는?

**정답: 4번 ✅ 엔지니어가 품질 판단을 유지하면서 CI 조사·테스트 업데이트·디버깅을 지원한다.**

**선택지 분석:** 1번은 엔지니어가 조사를 모두 마친 뒤에만 Codex가 움직인다고 범위를 지나치게 좁힙니다. 2번은 테스트 통과만으로 릴리스 준비 여부를 Codex가 결정한다고 해 사람 판단을 넘깁니다. 3번 첫 수정안까지의 속도만으로 성과를 판단하면 정확성·재작업을 무시합니다. 4번 반복되는 조사와 디버깅을 지원하되 품질 책임을 사람에게 둡니다.

**공식 해설 번역:** 테스트와 디버깅은 릴리스 신뢰도에 연결된 반복적이고 증거 기반인 워크플로우입니다. Codex는 조사 부담과 문제 해결을 지원하지만 검증과 품질 결정은 엔지니어가 계속 담당합니다.

**핵심 암기 포인트:** 빠른 첫 답보다 검증 가능한 결과와 사람의 품질 판단.

**AI 개발 실무 추가 설명:** CI 로그·재현 절차·테스트 결과를 근거로 삼고, 수정 제안의 검토·테스트·승인을 분리합니다.

**누적 정답률:** 7/7 · 100%

## 8. 보안 이해관계자의 우려

**문제:** 보안 담당자가 관리되지 않는 AI 보조 개발을 우려합니다. 가장 적절한 대응은?

**정답: 2번 ✅ 사람 검토·책임·가시성을 명확히 하며 관리되는 워크플로우 지원으로 평가한다.**

**선택지 분석:** 1번 영업 단계에서 고객의 권한·배포 구조를 대신 설계하려는 것은 역할을 넘습니다. 2번 통제된 평가 범위를 설명하고 확대 전에 필요한 가시성을 확인합니다. 3번 대부분의 결과를 검토할 필요가 없다고 약속하면 위험합니다. 4번 생산성 근거가 감독 우려를 자동 해결하지 않습니다.

**공식 해설 번역:** 보안·거버넌스 담당자는 통제·감독·책임·운영 가시성을 우선합니다. Codex의 메시지는 관리된 위임과 명확한 검토 기대를 강조해야 하며, 구체 통제는 적절한 전문가와 검증해야 합니다.

**핵심 암기 포인트:** 감독·책임·가시성을 먼저 다루고 통제 세부는 검증한다.

**AI 개발 실무 추가 설명:** 권한 범위, 로그, 데이터 접근, 외부 쓰기, 승인 단계, 사고 대응을 실제 환경에서 확인합니다.

**누적 정답률:** 8/8 · 100%

## 9. Codex 가치 설명의 순서

**문제:** Codex 가치 이야기의 가장 적절한 순서는?

**정답: 2번 ✅ 고객 우선순위 → 워크플로우 압박 → SDLC 사용 사례 → 이해관계자 영향 → Codex 가치 → 결과 언어**

**선택지 분석:** 1번 기술 자산 목록은 고객 문제와 사업 결과에서 시작하지 않습니다. 2번 고객의 맥락에서 구체적인 사용 사례와 가치로 이어집니다. 3번 기능·벤치마크·경쟁사·할인부터 나열하면 제품 중심입니다. 4번 영업 단계·가격·갱신 일정은 가치 논리를 구성하지 않습니다.

**공식 해설 번역:** 고객이 중요하게 여기는 결과와 압박을 받는 워크플로우에서 출발해 적절한 SDLC 사용 사례와 이해관계자 강조점을 선택합니다. 이어 Codex가 해당 흐름을 어떻게 지원하는지, 어떤 운영 결과를 기대하는지 설명합니다.

**핵심 암기 포인트:** 고객의 문제에서 시작해 제품 가치와 결과로 좁혀 간다.

**AI 개발 실무 추가 설명:** 각 가치 주장에 측정 지표와 기준선을 대응시키고, 측정 전에는 보장된 효과처럼 표현하지 않습니다.

**누적 정답률:** 9/9 · 100%

## 10. 레거시 저장소 온보딩 반복
