## 학습 목표

- 시나리오를 보고 Opus / Sonnet / Haiku 중 무엇을 고를지 판단하기
- 모델 ID를 프로덕션에서 어떻게 고정하는지 알기
- Batches API, 프롬프트 캐시, temperature, max_tokens에 대한 시험 단골 오해를 걷어 내기

## 먼저 한 문장으로

**"요건을 만족하는 가장 싼 모델을 고른다"가 모델 선택의 원칙이고, 시험은 이 원칙을 시나리오에 적용할 수 있는지 봅니다.**

## 세 모델의 위치

| 모델 | 추론 능력 | 속도 | 비용 | 잘 맞는 일 |
|---|---|---|---|---|
| Opus | 가장 높음 | 느림 | 높음 | 복잡한 추론, 계획 수립, 오케스트레이터(허브) |
| Sonnet | 중간 | 중간 | 중간 | 일반 애플리케이션, 서브에이전트, 문서 생성 |
| Haiku | 낮음 | 가장 빠름 | 가장 낮음 | 분류, 추출, 대량 배치, 요약 |

이름은 시의 길이에서 왔습니다. Opus(장편), Sonnet(14행), Haiku(17음). 규모 순으로 외우면 됩니다.

시험에서 자주 섞는 오답: "Haiku는 Opus보다 느리지만 더 복잡한 추론을 한다." 속도와 정확도를 바꿔치기한 문장입니다. 차분히 읽으면 걸러집니다.

## 시나리오별 판단

**하루 100만 건 리뷰를 긍정/부정/중립으로 분류, 비용 최우선.**
→ Haiku. 단순 3클래스 분류에 Opus를 쓰면 수십 배 비용을 냅니다. Sonnet도 틀린 선택은 아니지만 "비용 최우선" 조건에서는 Haiku가 답입니다.

**고객 문의 10만 건, 80%는 FAQ로 답할 수 있고 20%는 복잡한 조사가 필요. 99%를 3초 안에 응답.**
→ Haiku가 먼저 "FAQ로 답할 수 있는가"를 판정하고, 되면 Haiku가 답하고, 안 되면 Opus로 넘깁니다. 이 구조를 라우팅이라고 부르고, 도메인 1의 에이전트 아키텍처에서 다시 나옵니다. 전부 Opus는 비용과 SLA 둘 다 깨지고, 전부 Haiku는 20%의 품질이 부족합니다.

**계획을 세우고 실행하는 에이전트(Plan-and-Execute).**
→ 계획은 Opus, 실행 스텝은 Sonnet/Haiku. 계획이 틀리면 뒤가 전부 헛수고라서 계획에 정확도를 씁니다.

**Hub & Spoke 멀티 에이전트.**
→ 허브(판단·통합)는 Opus, 서브(실행)는 Sonnet/Haiku. 허브는 호출 횟수가 적고 서브는 많으니 이 배치가 비용 효율이 좋습니다.

한 가지 함정: **"최신 모델 = 반드시 Opus"가 아닙니다.** 세대와 패밀리는 다른 축입니다. 최신 세대의 Haiku가 이전 세대의 Sonnet보다 똑똑한 경우도 있습니다.

## 모델 ID 고정

모델 ID는 `claude-{family}-{major}-{minor}[-{revision}]` 꼴입니다.

```
claude-haiku-4-5-20251001   # 날짜 리비전까지 붙은 형태
claude-opus-4-8             # 4.6 세대부터는 이 자체가 고정 스냅샷
```

시험 문제의 원칙은 단순합니다. **프로덕션에서는 가장 구체적으로 지정한 ID를 쓴다.** 에일리어스(짧은 이름)는 나중에 같은 패밀리의 새 버전을 가리킬 수 있어서 재현성이 깨집니다.

실제 규칙은 세대에 따라 조금 다릅니다. 4.6 이전 세대는 날짜 접미사가 붙은 것이 고정 스냅샷이고 없는 것이 에일리어스였습니다. 4.6 세대부터는 `claude-opus-4-8` 같은 날짜 없는 ID 자체가 고정 스냅샷입니다. 어느 쪽이든 "가장 구체적인 것을 고른다"는 결론은 같습니다.

고정의 대가도 알아 둡니다. 고정하면 보안 수정이나 버그 픽스를 자동으로 못 받습니다. 그래서 프로덕션은 고정, 검증 환경은 최신 추종, 그리고 정기 평가·업데이트 주기를 함께 설계합니다.

## Batches API: 동기 호출 vs 배치

`client.messages.create()`는 요청하면 그 자리에서 답이 오는 동기 API입니다. **Message Batches API**는 여러 요청을 한 덩어리로 넣고, 나중에 결과를 한꺼번에 받는 비동기 API입니다.

| 항목 | 내용 |
|---|---|
| 비용 | 동기 API의 약 50% |
| 처리 시간 | 최대 24시간 안에(보통은 훨씬 빠름) |
| 결과 대조 | 요청마다 붙인 `custom_id`로 맞춤 |
| 안 맞는 경우 | 실시간 응답, 대화, 멀티턴 툴 호출 |

판단 요령은 하나입니다. **"사람이 화면 앞에서 기다리는가?"** 기다리면 동기 API, 야간 배치처럼 기다리지 않으면 Batches API가 후보입니다.

시험 문제: "야간에 100만 건 리뷰 분류, 다음 날 아침까지만 되면 됨, 비용 최소화." → Batches API. 한 건씩 동기 호출하는 선택지, 스트리밍을 쓰는 선택지, temperature를 올리는 선택지는 전부 오답입니다.

`custom_id`가 필요한 이유도 알아 둡니다. 배치는 병렬로 처리되어 결과가 요청 순서대로 오지 않습니다. 순서로는 대조가 안 되니 ID로 맞춥니다.

## 프롬프트 캐시: 개념과 배치 순서

같은 10K 토큰짜리 시스템 프롬프트를 하루 100만 번 보내면 100억 토큰을 매번 정가로 냅니다. 프롬프트 캐시를 켜면 두 번째부터는 같은 부분을 크게 할인된 가격으로 재사용합니다.

```python
system=[{
    "type": "text",
    "text": very_long_system_prompt,
    "cache_control": {"type": "ephemeral"},
}]
```

시험에서 묻는 것은 두 가지입니다.

1. **비용 문제의 정답은 캐시다.** 시스템 프롬프트를 100 토큰으로 압축한다(품질 손실), user 메시지에 매번 넣는다(캐시 효과 없음)는 오답입니다.
2. **캐시는 앞부분부터 일치하는 접두사(prefix)에만 작동한다.** 그래서 정적인 큰 문서는 앞(system)에 두고, 날짜나 사용자 질문처럼 매번 바뀌는 부분은 뒤(user)에 둡니다. 동적인 내용을 앞에 두면 매번 캐시 미스가 납니다.

요금 숫자(첫 쓰기 1.25배, 읽기 10~20%)와 TTL(기본 5분, 1시간 옵션)은 배경 지식입니다. 시험 범위 밖이니 외우지 않아도 되지만, "정적인 문맥을 재사용해 비용을 줄인다"는 개념은 반드시 알아야 합니다.

## 파라미터에 대한 세 가지 오해

이 사이트의 [Building with the Claude API](/courses/claude-with-the-anthropic-api/02-accessing-claude-with-the-api/) 정리에 파라미터 설명이 있으니 여기서는 시험이 노리는 오해만 짚습니다.

**"max_tokens는 입력 상한이다."** 아닙니다. 출력 토큰의 상한입니다. 입력은 컨텍스트 윈도우로 제한됩니다. 크게 잡아도 실제 쓴 만큼만 과금됩니다. `stop_reason == "max_tokens"`면 출력이 잘렸다는 뜻이니 이어받기 처리를 검토합니다.

**"temperature는 0~2다."** OpenAI 감각입니다. Anthropic API는 0~1이고, 1.5를 넣으면 `invalid_request_error`가 납니다. 구조화 출력·분류·추출은 0, 창작은 0.7~1.0.

**"system은 messages 안에 role: system으로 넣는다."** 아닙니다. 최상위 `system` 필드입니다. messages 안에 넣으면 에러가 납니다. OpenAI 코드를 옮길 때 가장 흔한 실수라 시험에 자주 나옵니다.

덧붙여 messages는 첫 메시지가 user, 그 뒤로 user와 assistant가 번갈아야 합니다. user가 연속되면 에러입니다. `content`는 문자열로 써도 되고 `[{"type": "text", "text": "..."}]` 블록 리스트로 써도 됩니다. 둘은 같은 뜻입니다.

## 429가 오면

`rate_limit_error`는 "조금 기다리라"는 신호입니다. 지수 백오프(1초, 2초, 4초, 8초…)로 재시도합니다. 연속으로 10번 다시 때리기, 전부 중단하기, 다른 API 키로 바꿔서 즉시 재시도하기는 전부 오답입니다. SDK에는 `max_retries` 옵션이 있고, 직접 짤 때는 지터(랜덤 흔들림)를 더해 여러 클라이언트가 동시에 재시도하는 문제를 피합니다.

## 컨텍스트 윈도우 ≠ 성능

Opus 계열은 최대 1M 토큰까지 받습니다. 그렇다고 500K 토큰짜리 사내 문서를 통째로 넣고 질문하면 기대한 답이 안 나올 수 있습니다. 창을 넘긴 것이 아닙니다(1M 안에 들어갑니다). 중간에 있는 정보를 놓치는 **Lost in the Middle** 현상과 컨텍스트 열화 때문입니다. 대책은 RAG, 요약, 청크+랭킹이고, 레슨 6에서 다룹니다.

## RSP와 ASL, 이 정도만

Anthropic은 모델 능력이 올라갈수록 보안 대책을 강화하는 Responsible Scaling Policy를 공개하고 있고, AI Safety Level(ASL-1~4)을 정의합니다. 현재 주력 모델은 ASL-3 기준으로 배포됩니다. 시험 범위 밖이지만, "운영상의 보안 책임은 이용자 쪽에도 있다"는 문장은 알아 둡니다. API 키 관리, 외부 공개 출력의 최종 확인, 권한 관리는 이용자 몫입니다.

## 핵심 정리

- 요건을 만족하는 가장 싼 모델. 계획·허브는 Opus, 실행·서브는 Sonnet/Haiku, 대량 단순 작업은 Haiku.
- 프로덕션 모델 ID는 가장 구체적인 것으로 고정. 고정하면 업데이트 주기를 따로 설계.
- 사람이 안 기다리는 대량 처리는 Batches API(약 50%). `custom_id`로 결과 대조.
- 프롬프트 캐시는 접두사 일치. 정적인 것 앞, 동적인 것 뒤.
- max_tokens는 출력 상한, temperature는 0~1, system은 최상위 필드, 429는 지수 백오프.
- 큰 창에 다 넣는다고 잘 찾는 게 아니다(Lost in the Middle).
