## 컨텍스트 열화(Context Degradation)

컨텍스트 윈도우가 크다고 정확도가 같이 오르지 않습니다. 오히려 채울수록 중요한 정보를 놓칠 확률이 올라갑니다. 1M 토큰 창에 500K 토큰 사내 문서를 넣고 특정 정보를 물었는데 답이 안 나오면, 원인은 창 초과가 아니라(500K는 1M 안입니다) 열화입니다.

**Lost in the Middle**: 긴 입력에서 앞부분과 끝부분은 잘 기억하고 **중반의 정보를 가장 잘 놓칩니다.** 연구로 확인된 현상이고, 업계는 Needle in a Haystack 테스트로 잽니다.

대책:

- 중요 정보는 맨 앞 또는 맨 뒤에. 가운데에 두기, 무작위로 흩기, 여러 번 반복하기는 오답.
- 요약을 앞머리에 두어 전체 지도를 보여 준다.
- 청크마다 소제목을 붙인다.

## 줄이는 전략

| 전략 | 내용 |
|---|---|
| 요약 | 오래된 대화를 Haiku로 200자쯤 압축하고 최근 몇 건만 남긴다 |
| 청킹 | 크기 고정 / 장·절 구조 / 의미 단위 / 하이브리드로 나눈다 |
| 단계적 상세화 | 청크 요약만 먼저 보여 관련 청크를 고르게 하고, 그 전문만 다음 호출에 넣는다 |
| RAG | 관련 부분만 검색해서 넣는다 (아래) |

## 컴팩션

오래 도는 에이전트는 messages가 계속 불어납니다. 컴팩션은 오래된 이력을 요약해 압축하는 것입니다.

| 컨텍스트 사용률 | 액션 |
|---|---|
| 50% 초과 | 경고 로그 |
| 70% 초과 | 자동 컴팩션 |
| 90% 초과 | 강제 컴팩션 + 오래된 이력 삭제 |

Claude Code에서는 `/compact`로 수동 실행합니다. 50% 근처에서 한 번 해 주는 것이 권장됩니다. 시험 문제 "messages가 너무 커졌다" → 오래된 이력 요약 + 최근 몇 건 유지. max_tokens 올리기(출력 상한일 뿐), 전부 지우고 새 세션(문맥 손실), 스트리밍 전환(UX일 뿐)은 오답.

## RAG: 범위 밖이지만 선택지엔 나온다

RAG, 벡터 DB, 임베딩의 구현은 시험 범위 밖입니다. 그러나 "1000페이지 문서, 하루 1만 질문, 매번 다른 부분 참조" 같은 시나리오의 정답이 **RAG + 메타데이터 필터 + Sonnet**이라서 개념은 알아야 합니다.

- 매번 전량 입력 + Opus: 비용 막대, Lost in the Middle
- 전량 캐시 + Opus: 캐시는 정적 부분 재사용에는 좋지만 매번 다른 부분을 참조하면 효과 제한, 열화 그대로
- 매번 요약 + Haiku: 세부 질문에 못 답함
- RAG + Sonnet: 관련 청크만 넣어 비용·정확도 둘 다 좋음

RAG의 가장 큰 함정은 **검색 정확도**입니다. 관련 청크를 못 찾으면 모델이 아무리 좋아도 답을 못 합니다. Recall(정답 청크가 검색 결과에 있는 비율)을 계속 재고, 청크 크기 조정·메타데이터 필터·리랭킹으로 보완합니다. "큰 창이 있으니 RAG는 낡았다"는 오답입니다.

## 장기 기억 vs 단기 기억

단기 기억은 지금 대화의 messages 배열입니다. 세션이 끝나도 남아야 하는 장기 기억은 Vector DB, 파일, DB 같은 별도 저장소에 둡니다. messages에 다 남기기, 환경 변수, "Claude 내부 메모리"는 오답입니다. Claude Code의 파일 기반 메모리(레슨 7)가 이 구현의 한 예입니다.

## 대규모 탐색: scratchpad와 manifest

수천 개 파일을 하나씩 조사시키면서 결과를 전부 messages에 쌓으면 컨텍스트가 순식간에 터집니다. 대책은 중간 결과를 바깥에 쓰는 것입니다.

- **scratchpad(작업 메모)**: 중간 사고나 발견을 외부 파일에 적어 두고, 정말 필요할 때만 참조.
- **manifest(작업 대장)**: 조사 대상 목록과 각 항목의 상태(미처리/처리 중/완료)를 구조화해 기록. 무엇이 끝났고 남았는지 추적. 세션이 끊겨도 재개할 수 있고 여러 에이전트가 나눠 맡을 수도 있다.

컨텍스트에는 "다음에 처리할 몇 건"만 올립니다. 시험 문제 "수천 건 조사, 컨텍스트 비대화와 진행 상황 놓침을 둘 다 막으려면?" → scratchpad + manifest. max_tokens 늘리기, temperature 낮추기는 무관.

## claim-source mapping과 temporal grounding

여러 소스에서 정보를 모으는 조사 에이전트에서, 주장만 뽑고 출처와 날짜를 버리면 나중에 "이거 어디서 왔지, 언제 정보지"를 확인할 수 없습니다.

- **claim-to-source mapping**: 각 주장에 출처(URL, 페이지)를 붙인다. 소스끼리 모순될 때 어디가 어긋나는지 바로 보인다.
- **temporal grounding**: 각 정보에 공개일을 붙인다. 오래된 소스를 걸러내거나 우선순위를 낮출 수 있다.

"최신 모델을 쓰면 정보의 최신성은 자동 보장된다"는 오답입니다. 입력 소스 자체의 날짜는 모델이 보장하지 않습니다.

## 에스컬레이션 3트리거

| 트리거 | 예 | 대응 |
|---|---|---|
| 불확실성 | 스키마/테스트 검증에 반복 실패, 시도마다 결과가 들쭉날쭉 | HITL로 |
| 권한 | 송금, 삭제 같은 고권한 작업 | 승인 흐름으로 |
| 이상 | 툴 연속 실패, 예상 밖 상태 | 알림 + 자동 정지 |

판단은 **관찰 가능한 사실**로 합니다. 검증 실패 횟수, 연속 에러 횟수, 작업의 리스크 구분.

**모델이 스스로 보고하는 confidence는 트리거로 쓰지 않습니다.** "confidence < 0.7이면 에스컬레이션" 같은 단순 임계값이 시험의 대표 오답입니다. 자기 보고 확신도는 작업의 실제 난이도를 재는 지표로 믿을 수 없기 때문입니다. 사용자 감정(sentiment)도 마찬가지입니다.

과잉 에스컬레이션도 문제입니다. 임계값이 너무 낮으면 HITL이 병목이 되어 자동화의 이점이 사라집니다. 에스컬레이션율 5~10%가 참고 목표입니다.

## confidence 보정과 층화 추출

그래도 확신도를 쓰고 싶다면 **보정(calibration)**을 거칩니다. 정답을 아는 검증 데이터로 모델을 돌려서, "0.8이라고 했을 때 실제로 몇 % 맞았나"를 집계하고, 점수를 실제 정답률에 맞게 고칩니다. 보정된 점수라야 임계값 판단에 쓸 수 있습니다. temperature 낮추기, max_tokens 늘리기로는 이 어긋남이 해소되지 않습니다. 보정은 한 번으로 끝이 아니고, 모델이나 입력 분포가 바뀌면 다시 합니다.

품질 모니터링 샘플을 뽑을 때는 **층화 추출(stratified sampling)**을 씁니다. 전체에서 무작위로 뽑으면 건수가 많은 카테고리만 뽑히고 적은 카테고리의 품질은 놓칩니다. 카테고리·난이도 같은 층으로 나눠 각 층에서 뽑습니다.

## 에러 전략 3종

| 전략 | 뜻 | 적용 |
|---|---|---|
| Fail-fast | 에러 감지 즉시 정지 | 송금처럼 부작용 있고 정합성 필수인 작업 |
| Fail-safe | 이미 알려진 안전한 상태로 동작 | UI 표시(에러 플레이스홀더로 폴백) |
| Retry | 재시도 | 429/503/네트워크 같은 일시적 에러 |

400, 401, 404는 재시도해도 결과가 같으니 Retry 대상이 아닙니다.

## HITL 4패턴

| 패턴 | 뜻 | 예 |
|---|---|---|
| 승인 기반 | 중요 액션 전에 승인을 기다린다 | "삭제할까요? (y/n)", Claude Code plan 모드 |
| 리뷰 기반 | 완료 후 사람이 리뷰 | 생성된 자료 검토 |
| 개입 기반 | 진행 중에 끼어들 수 있다 | 채팅 UI의 중단 버튼 |
| 공동 편집 | 번갈아 편집 | 문서 협업 |

승인 워크플로 구현의 핵심: 액션을 실행하지 않고 pending으로 저장 → 사용자에게 알림 → **타임아웃을 두고** 승인 대기 → 승인이면 실행, 거부/타임아웃이면 로그. 타임아웃이 없으면 작업이 영구히 멈춘 채 리소스를 먹습니다. 알림 실패 시 폴백도 둡니다.

"HITL은 사람이 전부 수동으로 본다"는 오해입니다. 중요한 순간만 사람이 보고, 일상 작업은 자동입니다.

## 신뢰 경계와 권한 분리

에이전트는 "확률적으로 실수하는 외부 시스템"으로 취급합니다.

| 작업 | 권장 |
|---|---|
| 읽기(공개) | 자유 |
| 읽기(기밀) | 인증 + 감사 로그 |
| 쓰기(자기 데이터) | 인증 + 승인 |
| 쓰기(타인 데이터) | HITL 필수 |
| 삭제 | HITL 필수 + 로그 보관 |
| 외부 전송 | HITL 필수 + 데이터 마스킹 |

"Claude는 안전하게 훈련됐으니 권한 제한이 필요 없다"는 오답입니다. 권한 분리, 샌드박스, HITL은 설계자 책임입니다.

## 감사 로그 최소 요건

누가·언제·무엇을·어떻게 했는가. `timestamp / user_id / action / tool_name / outcome`이 기본이고, 어느 에이전트가, 왜(decision_basis)까지 있으면 좋습니다. 기밀 입력은 마스킹합니다. 인시던트 대응, 규제(GDPR, SOC2, 국내는 개인정보보호법·ISMS-P), 품질 개선에 다 쓰입니다. "규제 대응 때만 쓴다"는 오해입니다.

## SLO 지표

| 지표 | 목표 예 |
|---|---|
| 성공률 | 95% 이상 |
| 평균 레이턴시 | 10초 미만 |
| 에스컬레이션율 | 5~10% |
| 리트라이율 | 5% 미만 |
| 작업당 비용 | $0.10 미만 |

## 설계 리뷰 문제 대비

"고객 지원 에이전트, 환불·삭제 툴 포함 전부 넘김, `except: pass`" 같은 코드의 개선점 5가지:

1. 고위험 툴을 무제한 → HITL 경유 또는 별도 에이전트로 분리
2. HITL 없음 → 승인 워크플로
3. `except: pass` → 구조화 에러로 Claude에 알림
4. `max_iterations` 없음 → 상한
5. 감사 로그 없음 → user_id / action / tool / outcome 기록

## 핵심 정리

- 큰 창 ≠ 잘 찾음. 중반 정보를 놓친다(Lost in the Middle). 중요한 건 앞·뒤에.
- 이력이 커지면 컴팩션(오래된 것 요약 + 최근 유지). 대규모 탐색은 scratchpad + manifest.
- 매번 다른 부분을 참조하는 대량 질의는 RAG + Sonnet. RAG의 생명은 검색 Recall.
- 조사 결과는 출처 + 공개일을 세트로.
- 에스컬레이션은 불확실성·권한·이상, 관찰 가능한 사실로. 자기 보고 confidence 임계값은 오답, 쓰려면 보정.
- Fail-fast(송금) / Fail-safe(UI) / Retry(5xx·429). HITL은 승인·리뷰·개입·공동편집, 승인 대기엔 타임아웃.
- 최소 권한, 감사 로그(누가·언제·무엇을·어떻게), SLO로 계속 측정.
