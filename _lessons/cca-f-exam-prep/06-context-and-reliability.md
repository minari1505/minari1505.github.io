## 컨텍스트 열화(Context Degradation)

컨텍스트 윈도우가 크다고 정확도가 같이 오르지 않습니다. 오히려 채울수록 중요한 정보를 놓칠 확률이 올라갑니다. 1M 토큰 창에 500K 토큰 사내 문서를 넣고 특정 정보를 물었는데 답이 안 나오면, 원인은 창 초과가 아니라(500K는 1M 안입니다) 열화입니다.

**Lost in the Middle**: 긴 입력에서 앞부분과 끝부분은 잘 기억하고 **중반의 정보를 가장 잘 놓칩니다.** 연구로 확인된 현상이고, 업계는 Needle in a Haystack 테스트로 잽니다.

대책:

- 중요 정보는 맨 앞 또는 맨 뒤에. 가운데에 두기, 무작위로 흩기, 여러 번 반복하기는 오답.
- 요약을 앞머리에 두어 전체 지도를 보여 준다.
- 청크마다 소제목을 붙인다.

## 줄이는 전략

| 전략 | 내용 |
|---|---|
| 요약 | 오래된 대화를 Haiku로 200자쯤 압축하고 최근 몇 건만 남긴다 |
| 청킹 | 크기 고정 / 장·절 구조 / 의미 단위 / 하이브리드로 나눈다 |
| 단계적 상세화 | 청크 요약만 먼저 보여 관련 청크를 고르게 하고, 그 전문만 다음 호출에 넣는다 |
| RAG | 관련 부분만 검색해서 넣는다 (아래) |

## 컴팩션

오래 도는 에이전트는 messages가 계속 불어납니다. 컴팩션은 오래된 이력을 요약해 압축하는 것입니다.

| 컨텍스트 사용률 | 액션 |
|---|---|
| 50% 초과 | 경고 로그 |
| 70% 초과 | 자동 컴팩션 |
| 90% 초과 | 강제 컴팩션 + 오래된 이력 삭제 |

Claude Code에서는 `/compact`로 수동 실행합니다. 50% 근처에서 한 번 해 주는 것이 권장됩니다. 시험 문제 "messages가 너무 커졌다" → 오래된 이력 요약 + 최근 몇 건 유지. max_tokens 올리기(출력 상한일 뿐), 전부 지우고 새 세션(문맥 손실), 스트리밍 전환(UX일 뿐)은 오답.

## RAG: 범위 밖이지만 선택지엔 나온다

RAG, 벡터 DB, 임베딩의 구현은 시험 범위 밖입니다. 그러나 "1000페이지 문서, 하루 1만 질문, 매번 다른 부분 참조" 같은 시나리오의 정답이 **RAG + 메타데이터 필터 + Sonnet**이라서 개념은 알아야 합니다.

- 매번 전량 입력 + Opus: 비용 막대, Lost in the Middle
- 전량 캐시 + Opus: 캐시는 정적 부분 재사용에는 좋지만 매번 다른 부분을 참조하면 효과 제한, 열화 그대로
- 매번 요약 + Haiku: 세부 질문에 못 답함
- RAG + Sonnet: 관련 청크만 넣어 비용·정확도 둘 다 좋음

RAG의 가장 큰 함정은 **검색 정확도**입니다. 관련 청크를 못 찾으면 모델이 아무리 좋아도 답을 못 합니다. Recall(정답 청크가 검색 결과에 있는 비율)을 계속 재고, 청크 크기 조정·메타데이터 필터·리랭킹으로 보완합니다. "큰 창이 있으니 RAG는 낡았다"는 오답입니다.

## 장기 기억 vs 단기 기억

단기 기억은 지금 대화의 messages 배열입니다. 세션이 끝나도 남아야 하는 장기 기억은 Vector DB, 파일, DB 같은 별도 저장소에 둡니다. messages에 다 남기기, 환경 변수, "Claude 내부 메모리"는 오답입니다. Claude Code의 파일 기반 메모리(레슨 7)가 이 구현의 한 예입니다.

## 대규모 탐색: scratchpad와 manifest

수천 개 파일을 하나씩 조사시키면서 결과를 전부 messages에 쌓으면 컨텍스트가 순식간에 터집니다. 대책은 중간 결과를 바깥에 쓰는 것입니다.

- **scratchpad(작업 메모)**: 중간 사고나 발견을 외부 파일에 적어 두고, 정말 필요할 때만 참조.
- **manifest(작업 대장)**: 조사 대상 목록과 각 항목의 상태(미처리/처리 중/완료)를 구조화해 기록. 무엇이 끝났고 남았는지 추적. 세션이 끊겨도 재개할 수 있고 여러 에이전트가 나눠 맡을 수도 있다.

컨텍스트에는 "다음에 처리할 몇 건"만 올립니다. 시험 문제 "수천 건 조사, 컨텍스트 비대화와 진행 상황 놓침을 둘 다 막으려면?" → scratchpad + manifest. max_tokens 늘리기, temperature 낮추기는 무관.

## claim-source mapping과 temporal grounding

여러 소스에서 정보를 모으는 조사 에이전트에서, 주장만 뽑고 출처와 날짜를 버리면 나중에 "이거 어디서 왔지, 언제 정보지"를 확인할 수 없습니다.

- **claim-to-source mapping**: 각 주장에 출처(URL, 페이지)를 붙인다. 소스끼리 모순될 때 어디가 어긋나는지 바로 보인다.
- **temporal grounding**: 각 정보에 공개일을 붙인다. 오래된 소스를 걸러내거나 우선순위를 낮출 수 있다.

"최신 모델을 쓰면 정보의 최신성은 자동 보장된다"는 오답입니다. 입력 소스 자체의 날짜는 모델이 보장하지 않습니다.

## 에스컬레이션 3트리거

| 트리거 | 예 | 대응 |
|---|---|---|
| 불확실성 | 스키마/테스트 검증에 반복 실패, 시도마다 결과가 들쭉날쭉 | HITL로 |
| 권한 | 송금, 삭제 같은 고권한 작업 | 승인 흐름으로 |
| 이상 | 툴 연속 실패, 예상 밖 상태 | 알림 + 자동 정지 |

판단은 **관찰 가능한 사실**로 합니다. 검증 실패 횟수, 연속 에러 횟수, 작업의 리스크 구분.

**모델이 스스로 보고하는 confidence는 트리거로 쓰지 않습니다.** "confidence < 0.7이면 에스컬레이션" 같은 단순 임계값이 시험의 대표 오답입니다. 자기 보고 확신도는 작업의 실제 난이도를 재는 지표로 믿을 수 없기 때문입니다. 사용자 감정(sentiment)도 마찬가지입니다.

과잉 에스컬레이션도 문제입니다. 임계값이 너무 낮으면 HITL이 병목이 되어 자동화의 이점이 사라집니다. 에스컬레이션율 5~10%가 참고 목표입니다.

## confidence 보정과 층화 추출

그래도 확신도를 쓰고 싶다면 **보정(calibration)**을 거칩니다. 정답을 아는 검증 데이터로 모델을 돌려서, "0.8이라고 했을 때 실제로 몇 % 맞았나"를 집계하고, 점수를 실제 정답률에 맞게 고칩니다. 보정된 점수라야 임계값 판단에 쓸 수 있습니다. temperature 낮추기, max_tokens 늘리기로는 이 어긋남이 해소되지 않습니다. 보정은 한 번으로 끝이 아니고, 모델이나 입력 분포가 바뀌면 다시 합니다.

품질 모니터링 샘플을 뽑을 때는 **층화 추출(stratified sampling)**을 씁니다. 전체에서 무작위로 뽑으면 건수가 많은 카테고리만 뽑히고 적은 카테고리의 품질은 놓칩니다. 카테고리·난이도 같은 층으로 나눠 각 층에서 뽑습니다.

## 에러 전략 3종

| 전략 | 뜻 | 적용 |
|---|---|---|
| Fail-fast | 에러 감지 즉시 정지 | 송금처럼 부작용 있고 정합성 필수인 작업 |
| Fail-safe | 이미 알려진 안전한 상태로 동작 | UI 표시(에러 플레이스홀더로 폴백) |
| Retry | 재시도 | 429/503/네트워크 같은 일시적 에러 |

400, 401, 404는 재시도해도 결과가 같으니 Retry 대상이 아닙니다.

## HITL 4패턴

| 패턴 | 뜻 | 예 |
|---|---|---|
| 승인 기반 | 중요 액션 전에 승인을 기다린다 | "삭제할까요? (y/n)", Claude Code plan 모드 |
| 리뷰 기반 | 완료 후 사람이 리뷰 | 생성된 자료 검토 |
| 개입 기반 | 진행 중에 끼어들 수 있다 | 채팅 UI의 중단 버튼 |
| 공동 편집 | 번갈아 편집 | 문서 협업 |

승인 워크플로 구현의 핵심: 액션을 실행하지 않고 pending으로 저장 → 사용자에게 알림 → **타임아웃을 두고** 승인 대기 → 승인이면 실행, 거부/타임아웃이면 로그. 타임아웃이 없으면 작업이 영구히 멈춘 채 리소스를 먹습니다. 알림 실패 시 폴백도 둡니다.

"HITL은 사람이 전부 수동으로 본다"는 오해입니다. 중요한 순간만 사람이 보고, 일상 작업은 자동입니다.

## 신뢰 경계와 권한 분리

에이전트는 "확률적으로 실수하는 외부 시스템"으로 취급합니다.

| 작업 | 권장 |
|---|---|
| 읽기(공개) | 자유 |
| 읽기(기밀) | 인증 + 감사 로그 |
| 쓰기(자기 데이터) | 인증 + 승인 |
| 쓰기(타인 데이터) | HITL 필수 |
| 삭제 | HITL 필수 + 로그 보관 |
| 외부 전송 | HITL 필수 + 데이터 마스킹 |

"Claude는 안전하게 훈련됐으니 권한 제한이 필요 없다"는 오답입니다. 권한 분리, 샌드박스, HITL은 설계자 책임입니다.

## 감사 로그 최소 요건

누가·언제·무엇을·어떻게 했는가. `timestamp / user_id / action / tool_name / outcome`이 기본이고, 어느 에이전트가, 왜(decision_basis)까지 있으면 좋습니다. 기밀 입력은 마스킹합니다. 인시던트 대응, 규제(GDPR, SOC2, 국내는 개인정보보호법·ISMS-P), 품질 개선에 다 쓰입니다. "규제 대응 때만 쓴다"는 오해입니다.

  <div class="oa-card oa-card--warn"><span class="oa-card__icon">😠</span><span class="oa-card__title">기준이 아닌 것</span>고객 감정 점수, 모델이 스스로 매긴 확신도</div>
</div>

상황별로 보면 이렇습니다.

| 상황 | 올바른 행동 |
|---|---|
| "사람과 통화하고 싶어요" | 조사부터 하지 않고 **바로** 넘깁니다 |
| 고객이 화가 났지만 에이전트가 풀 수 있는 문제 | 불만을 인정하고 해결을 제안합니다. 고객이 다시 사람을 요청하면 넘깁니다 |
| "경쟁사 가격에 맞춰 주세요" (정책은 자사 사이트 가격만 다룸) | 정책이 침묵하는 영역이므로 넘깁니다. 임의로 승인하거나 거절하지 않습니다 |
| 이름으로 조회했더니 고객이 3명 나옴 | 하나를 골라 진행하지 않고 이메일이나 주문 번호를 추가로 묻습니다 |

에스컬레이션이 너무 잦거나 너무 드물면, 시스템 프롬프트에 **명시적 기준과 few-shot 예시**를 넣어 고칩니다. 감정 분석기를 붙이거나 확신도 임계값을 두는 선택지는 오답입니다.

### 3. 에러를 삼키지도, 전부 멈추지도 않는다 (5.3)

서브에이전트가 실패하면 코디네이터가 다음 행동을 정할 수 있도록 맥락을 올립니다.

```json
{
  "failure_type": "timeout",
  "attempted_query": "2026년 반도체 장비 시장 규모",
  "partial_results": [{"claim": "2025년 약 1,100억 달러", "source": "A 보고서"}],
  "alternatives": ["검색어를 좁혀 재시도", "B 데이터베이스 사용"]
}
```

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">❌ 조용한 실패</span>
    <ul>
      <li>타임아웃을 빈 결과로 돌려주고 성공 처리</li>
      <li>보고서에 빈틈이 생겨도 아무도 모릅니다.</li>
    </ul>
  </div>
  <div class="oa-vs__bad">
    <span class="oa-vs__label">❌ 전체 중단</span>
    <ul>
      <li>서브에이전트 하나가 실패하자 워크플로 전체를 종료</li>
      <li>이미 얻은 나머지 결과까지 버립니다.</li>
    </ul>
  </div>
</div>

올바른 방향은 그 사이입니다. 부분 결과를 살리고, 빠진 부분은 빠졌다고 표시합니다. "검색 불가" 같은 일반 상태만 올리면 코디네이터가 재시도할지 우회할지 판단할 수 없습니다.

### 4. 긴 탐색에서 컨텍스트 지키기 (5.4)

세션이 길어지면 답이 흐려집니다. 앞에서 찾은 `RefundPolicyValidator` 같은 구체적인 클래스 이름 대신 "일반적으로 이런 구조에서는…"이라고 말하기 시작하면 열화의 징후입니다.

<ol class="oa-flow">
  <li><strong>스크래치패드</strong>핵심 발견을 파일에 기록</li>
  <li><strong>위임</strong>장황한 탐색은 서브에이전트에게</li>
  <li><strong>단계 요약</strong>한 단계가 끝나면 요약</li>
  <li><strong>주입</strong>요약을 다음 에이전트 컨텍스트에</li>
  <li><strong>/compact</strong>탐색 출력이 컨텍스트를 채우면</li>
</ol>

위임의 예: "테스트 파일을 전부 찾아 줘", "환불 흐름의 의존성을 추적해 줘"는 서브에이전트에게 맡기고, 메인 에이전트는 전체 조율만 합니다.

**커버리지 표기**: 종합 결과에는 무엇이 잘 뒷받침되고 무엇이 비어 있는지 적습니다.

| 발견 | 근거 | 상태 |
|---|---|---|
| 결제 모듈은 재시도 로직이 있음 | 파일 3개에서 확인 | 충분 |
| 환불은 24시간 내 처리됨 | 문서 1건 | 약함 |
| 정산 배치의 동작 | 로그 저장소 접근 실패 | **확인 못 함** |

### 5. "정확도 97%"가 가리는 것 (5.5)

전체 평균이 높아도 특정 문서 유형이나 필드에서는 낮을 수 있습니다.

<div class="oa-bars">
  <div class="oa-bar"><span>전체 평균</span><span class="oa-bar__track"><span class="oa-bar__fill" style="width:97%"></span><span class="oa-bar__val">97%</span></span></div>
  <div class="oa-bar"><span>표준 송장 (8,000건)</span><span class="oa-bar__track"><span class="oa-bar__fill" style="width:99%"></span><span class="oa-bar__val">99%</span></span></div>
  <div class="oa-bar"><span>영수증 (1,600건)</span><span class="oa-bar__track"><span class="oa-bar__fill" style="width:95%"></span><span class="oa-bar__val">95%</span></span></div>
  <div class="oa-bar"><span>손글씨 견적서 (400건)</span><span class="oa-bar__track"><span class="oa-bar__fill oa-bar__fill--low" style="width:65%"></span><span class="oa-bar__val">65%</span></span></div>
  <div class="oa-bars__caption">건수로 가중 평균하면 약 97%입니다. 손글씨 견적서는 세 건 중 한 건이 틀리는데 평균에 묻힙니다. (가정한 예시)</div>
</div>

그래서 사람 검토를 줄이기 전에 이렇게 합니다.

1. 정확도를 **문서 유형별, 필드별**로 잽니다.
2. 모델이 **필드 단위 확신도**를 내게 하고, 정답이 붙은 검증 세트로 임계값을 보정합니다. "확신도 0.9 이상이면 실제로 몇 %가 맞는가"를 확인합니다.
3. 확신도가 낮거나 값이 서로 모순되는 추출을 사람에게 보냅니다. 검토 인력은 한정되어 있으니 여기에 먼저 씁니다.
4. 확신도가 높은 추출도 **층화 무작위 표본**으로 계속 검사해서 오류율과 새 오류 패턴을 봅니다.
5. 모든 구간에서 성능이 고른지 확인한 뒤에 검토를 줄입니다.

### 6. 출처가 엇갈리면 둘 다 남긴다 (5.6)

요약을 거치면서 "누가 한 말인지"가 사라지는 것이 가장 흔한 문제입니다. 서브에이전트가 주장마다 출처 URL, 문서 이름, 발췌를 붙여 내고, 종합 단계는 이 매핑을 지우지 않고 합칩니다.

믿을 만한 출처 둘이 다른 숫자를 말하면 하나를 고르지 않습니다.

| 주장 | 값 | 출처 | 기준 시점 |
|---|---|---|---|
| 국내 전기차 등록 대수 | 68만 대 | A 기관 통계 | 2025년 12월 |
| 국내 전기차 등록 대수 | 81만 대 | B 협회 보고서 | 2026년 9월 |

<div class="oa-eli">
  <span class="oa-eli__head">📅 날짜를 보면 모순이 아닐 수 있습니다</span>
  <p>위 두 값은 서로 틀린 것이 아니라 <b>시점이 다릅니다</b>. 발행일이나 수집일을 요구하지 않으면 이런 차이를 모순으로 오해합니다. 그래서 출처마다 날짜를 반드시 받습니다. (수치는 가정한 예시)</p>
</div>

보고서는 **합의된 발견과 논쟁 중인 발견을 나눠** 쓰고, 출처의 성격과 조사 방법을 같이 남깁니다. 내용 유형에 따라 형식도 다르게 합니다.

| 내용 | 형식 |
|---|---|
| 재무 수치 | 표 |
| 뉴스 | 서술형 문단 |
| 기술적 발견 | 목록 |

## 스터디 가이드로 더 채우기

여기부터는 커뮤니티 스터디 가이드(paullarionov/claude-certified-architect)의 설명과 연습 문제 가운데, 위에서 다루지 않았거나 한 줄로만 지나간 내용을 골라 채운 부분입니다. 예시 속 숫자와 이름은 이해를 돕기 위한 가정입니다.

### 7. 실패에도 종류가 있다 (5.3)

<div class="oa-eli">
  <span class="oa-eli__head">🏥 쉽게 말하면</span>
  <p>병원 접수창구에서 돌아오는 말은 여러 가지입니다. "전산이 잠깐 멈췄으니 조금 뒤에 다시 오세요", "서류의 생년월일이 틀렸으니 고쳐 오세요", "이 검사는 규정상 안 됩니다", "제 권한 밖이라 담당자를 불러 드릴게요". 넷 다 "안 됐다"이지만 다음에 할 일은 전부 다릅니다. 에이전트의 오류도 같습니다.</p>
</div>

| 범주 | 예 | 같은 요청을 재시도? | 에이전트가 할 일 |
|---|---|---|---|
| **일시적** | 타임아웃, 503, 네트워크 끊김 | 예 | 지수 백오프로 재시도 |
| **검증** | 입력 형식 오류, 필수 필드 누락 | 아니요 | 입력을 고친 다음 다시 요청 |
| **비즈니스** | 정책 위반, 한도 초과 | 아니요 | 사용자에게 설명하고 대안 제시 |
| **권한** | 접근 거부 | 아니요 | 에스컬레이션 |

위 "에러 전략 3종"의 Retry가 맞는 것은 첫 줄뿐입니다.

**"0건"과 "실패"는 다릅니다.** 검색 서브에이전트가 세 곳을 조회했다고 해 봅시다.

| 출처 | 돌아온 것 | 뜻 | 코디네이터의 대응 |
|---|---|---|---|
| 학술 데이터베이스 | 논문 15편 | 성공 | 결과 사용 |
| 산업 보고서 | `0 results` | **성공한 조회의 유효한 빈 결과** | "없음"이라는 의미 있는 결과로 받아들임 |
| 특허 데이터베이스 | `Connection timeout` | **접근 실패** | 재시도할지 결정 |

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">❌ 구분을 지우는 보고</span>
    <ul>
      <li>"출처 커버리지 67%"처럼 숫자 하나로 뭉친다</li>
      <li>타임아웃과 0건을 둘 다 "실패"로 올린다</li>
      <li>타임아웃을 빈 결과로 바꿔 올린다 (코디네이터는 "없다"고 믿습니다)</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✅ 구분을 살리는 보고</span>
    <ul>
      <li>출처별로 성공 / 유효한 빈 결과 / 접근 실패를 나눠 적습니다.</li>
      <li>코디네이터는 특허 쪽만 재시도하고 0건은 그대로 씁니다.</li>
    </ul>
  </div>
</div>

**어디서 고치나**: 오류는 해결할 수 있는 가장 낮은 곳에서 처리합니다.

<ol class="oa-flow">
  <li><strong>서브에이전트</strong>일시적 실패는 1~2회 로컬 재시도</li>
  <li><strong>그래도 실패</strong>시도한 내용과 부분 결과를 묶음</li>
  <li><strong>코디네이터</strong>재시도·우회·건너뛰기를 결정</li>
  <li><strong>종합</strong>빈틈을 표시하고 계속</li>
</ol>

양쪽 극단이 모두 오답입니다. 예외가 날 때마다 서브에이전트를 끝내고 코디네이터에게 다 떠넘기면 코디네이터가 일상적인 오류 처리에 묶입니다. 반대로 서브에이전트 안에서 끝없이 재시도하면 지연과 자원만 씁니다. 손상된 PDF처럼 다시 해도 결과가 같은 실패는 자동 재시도 대상이 아니고, 맥락을 담아 코디네이터에게 올립니다.

위 3번의 오류 객체에 스터디 가이드는 필드 두 개를 더 둡니다.

```json
{
  "status": "partial_failure",
  "failure_type": "timeout",
  "attempted_query": "AI 작곡 도구 시장 2026",
  "partial_results": [{"title": "AI 음악 생성 보고서", "relevance": 0.8}],
  "alternative_approaches": ["검색어를 좁혀 재시도", "다른 데이터 출처 사용"],
  "coverage_impact": "음악 제작 분야 미확인"
}
```

`status`는 전부 실패인지 일부만 실패인지를, `coverage_impact`는 이 실패로 보고서의 어느 부분이 비는지를 알려 줍니다. 이 정보가 있으면 코디네이터는 넷 중 하나를 고를 수 있습니다. 질의를 바꿔 재시도, 부분 결과 사용, 다른 서브에이전트에 위임, 그 부분 없이 진행하고 빈틈 표시.

### 8. 컨텍스트 예산 아끼기 (5.1, 5.4)

**API는 대화를 기억하지 않습니다.** 후속 요청마다 대화 기록을 함께 보내야 모델이 앞 내용을 압니다. 그래서 기록이 길어질수록 "무엇을 그대로 두고 무엇을 줄일지"가 설계 문제가 됩니다.

**긴 입력은 자리를 정해서 넣습니다.** 종합 에이전트가 앞부분과 끝부분은 잘 인용하는데 가운데 발견을 놓친다면 입력 배치를 바꿉니다.

```text
[핵심 발견: 맨 앞]
치명적 취약점 3건 발견 ...

[상세 결과: 가운데, 섹션 제목을 붙여서]
=== auth.ts ===
...
=== database.ts ===
...

[조치 항목: 맨 뒤]
병합 전에 auth.ts 취약점부터 수정
```

| 솔깃한 선택지 | 왜 정답이 아닌가 |
|---|---|
| 서브에이전트 출력을 전부 짧게 요약한 뒤 합친다 | 질문에 답하는 세부 내용까지 깎입니다 |
| 결과를 한 덩어리씩 순서대로 흘려 넣는다 | 가운데가 묻히는 배치는 그대로입니다 |
| 어느 결과를 앞에 둘지 매번 돌아가며 바꾼다 | 묻히는 대상만 바뀝니다 |

**부피는 만드는 쪽에서 줄입니다.** 웹 검색 에이전트가 페이지 본문을 통째로, 문서 분석 에이전트가 추론 과정을 통째로 올려 종합 에이전트가 감당할 양을 넘는 경우입니다.

<div class="oa-bars">
  <div class="oa-bar"><span>웹 검색 출력 (페이지 본문 포함)</span><span class="oa-bar__track"><span class="oa-bar__fill oa-bar__fill--low" style="width:55%"></span><span class="oa-bar__val">85K 토큰</span></span></div>
  <div class="oa-bar"><span>문서 분석 출력 (추론 과정 포함)</span><span class="oa-bar__track"><span class="oa-bar__fill oa-bar__fill--low" style="width:45%"></span><span class="oa-bar__val">70K 토큰</span></span></div>
  <div class="oa-bar"><span>종합 에이전트가 잘 다루는 입력</span><span class="oa-bar__track"><span class="oa-bar__fill" style="width:32%"></span><span class="oa-bar__val">50K 토큰 미만</span></span></div>
  <div class="oa-bars__caption">스터디 가이드 연습 문제가 가정한 수치입니다. 합치면 155K 토큰입니다.</div>
</div>

정답은 **상류 에이전트가 처음부터 구조화 데이터(핵심 사실, 인용, 관련도 점수)만 돌려주게 고치는 것**입니다. 중간에 요약 전담 에이전트를 끼우기, 종합 에이전트가 여러 묶음으로 나눠 처리하기, 벡터 DB에 넣고 검색 도구 주기는 원인(불필요한 본문과 추론 흔적)을 그대로 둔 채 단계만 늘립니다.

서브에이전트 쪽 예산을 지키는 규칙은 세 가지입니다.

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">📦</span><span class="oa-card__title">최소한만 보낸다</span>구체적인 작업과 그 작업에 필요한 데이터만 넘깁니다.</div>
  <div class="oa-card"><span class="oa-card__icon">🧾</span><span class="oa-card__title">구조화해서 받는다</span>원본 덤프가 아니라 정리된 결과를 돌려받습니다.</div>
  <div class="oa-card"><span class="oa-card__icon">🧰</span><span class="oa-card__title">도구를 줄인다</span><code>allowedTools</code>로 도구를 제한합니다. 도구가 적을수록 산만함과 컨텍스트 비용이 줄어듭니다.</div>

메인 에이전트 입장에서는 파일 15개를 읽은 탐색이 "결제 모듈은 AuthService, OrderModel, 외부 결제 게이트웨이에 의존한다" 한 줄로 돌아오는 셈입니다.

**도구 결과를 줄이는 자리**는 PostToolUse 훅입니다. 위 1번의 "필드 40개 → 5개"를 훅으로 옮기면 이렇습니다.

```python
    keep = ["order_id", "status", "total", "items", "return_eligible"]
    return {k: result[k] for k in keep}
```

**스크래치패드에는 다시 찾기 비싼 사실을 적습니다.**

컨텍스트가 흐려졌거나 새 세션을 시작했을 때 탐색을 처음부터 다시 하지 않고 이 파일부터 읽습니다. `/compact`는 공간을 되찾아 주지만 요약 과정에서 정확한 숫자와 날짜가 빠질 수 있으니, 그런 값은 압축 전에 스크래치패드나 케이스 사실 블록에 옮겨 둡니다.

### 9. 중간에 죽어도 이어 가기: 상태 파일 (5.4)

위 "scratchpad와 manifest" 절의 manifest는 조사 대상 목록의 진행 상태를 적는 대장이었습니다. 스터디 가이드는 같은 발상을 **에이전트 단위**로도 씁니다. 각 에이전트가 자기 상태를 정해진 위치에 적고, 코디네이터는 재개할 때 manifest부터 읽습니다.

`agent-state/web-search-agent.json` (에이전트 하나의 상태):

```json
{
  "status": "completed",
  "queries_executed": ["AI 음악 2026", "AI 작곡"],
  "results_count": 12,
  "coverage": ["작곡", "제작"],
  "gaps": ["유통", "저작권"]
}
```

`agent-state/manifest.json` (코디네이터가 읽는 전체 대장):

```json
{
  "web-search": "completed",
  "doc-analysis": "in_progress",
  "synthesis": "not_started"
}
```

  <li><strong>기록</strong>에이전트마다 상태 파일 갱신</li>
  <li><strong>중단</strong>프로세스가 죽음</li>
  <li><strong>재개</strong>코디네이터가 manifest 로드</li>

`gaps` 필드는 재개한 뒤 무엇을 더 조사해야 하는지도 알려 줍니다.

### 10. 엇갈린 출처는 누가 정리하나 (5.6)

위 6번은 "하나를 고르지 않는다"까지였습니다. 그다음 질문은 **누가 정리하느냐**입니다.

<ol class="oa-flow">
  <li><strong>분석 에이전트</strong>분석을 끝까지 마침</li>
  <li><strong>주석</strong>두 값을 출처와 함께 "충돌"로 표시</li>
  <li><strong>코디네이터</strong>어떻게 조정할지 결정</li>
  <li><strong>종합 단계</strong>조정된 내용으로 작성</li>
</ol>

| 분석 에이전트의 선택지 | 판정 | 이유 |
|---|---|---|
| 더 그럴듯한 값을 골라 쓰고 각주로 불일치를 언급 | ❌ | 임의로 하나를 고른 것입니다 |
| 두 값을 넣되 충돌이라고 표시하지 않음 | ❌ | 뒤 단계가 충돌인 줄 모릅니다 |
| 분석을 멈추고 코디네이터에게 어느 쪽이 맞는지 묻는다 | ❌ | 자기 일(분석)까지 멈춥니다 |
| 두 값을 출처와 함께 충돌로 명시하고 분석을 마친 뒤 코디네이터에게 넘김 | ✅ | 분석은 끝내고, 조정은 더 넓은 맥락을 가진 쪽이 합니다 |

충돌을 담는 형태는 이렇습니다.

```json
{
  "claim": "스트리밍 플랫폼의 AI 생성 음악 비중",
  "values": [
    {"value": "12%", "source": "플랫폼 연례 보고서", "date": "2024-03", "methodology": "자동 분류"},
    {"value": "8%", "source": "업계 협회 설문", "date": "2024-07", "methodology": "레이블 500곳 설문"}
  ],
  "conflict_detected": true,
  "possible_explanation": "조사 방법과 시점의 차이"
}
```

날짜뿐 아니라 **조사 방법**도 같이 남기는 점을 봅니다. 값이 다른 이유가 시점일 수도, 방법일 수도 있기 때문입니다. 위 형식 표에 하나를 더하면, **시계열 데이터는 시간순으로 정렬**해서 보여 줍니다.

### 11. 에스컬레이션, 헷갈리는 경계 (5.2)

조회할 수 있는 데이터를 다 봤는데도 판단이 애매한 상황에서, 무엇이 `escalate_to_human`을 정당화하는지 묻는 문제가 나옵니다.

| 상황 | 넘길 사유인가 |
|---|---|
| 정책은 자사 사이트의 가격 인하만 다루는데 고객이 경쟁사 가격에 맞춰 달라고 한다 | ✅ **정책 공백.** 에이전트가 정책을 지어내면 안 됩니다 |
| 고객은 못 받았다는데 추적 기록은 서명 수령으로 나온다 | ❌ 정답으로 꼽히지 않습니다. "곤란하다"는 사유가 아닙니다 |
| 한 메시지에 결제 문의와 반품이 같이 있다 | ❌ 여러 건이 섞인 것은 나눠서 처리할 일입니다(레슨 5) |
| 배송 중인 주문을 취소하고 싶다고 한다 | ❌ 고객이 마음을 바꿀지 모른다는 추측은 사유가 아닙니다 |

신뢰할 수 없는 트리거는 위 2번의 두 가지에 하나가 더 있습니다.

**한도를 넘는 금융 작업**도 에스컬레이션 대상입니다. 다만 이것은 프롬프트로 부탁하지 않고 훅으로 강제하는 편이 낫습니다(레슨 5의 차단 훅).

### 12. 값이 여러 개인 사실은 여러 칸에 담는다 (5.6)

위 6번과 10번은 **출처가 엇갈릴 때** 둘 다 남기라는 이야기였습니다. 위키는 한 걸음 더 나가, 출처가 하나여도 **시간에 따라 유효한 값이 여러 개**인 경우를 따로 다룹니다. 개정된 계약, 수정된 정책, 시계열 통계가 그렇습니다.

| 상황 | ❌ 틀린 처리 | ✅ 맞는 처리 |
|---|---|---|
| 계약이 두 번 개정됨 | 최신 조건만 남김 | 버전마다 발효일과 함께 저장 |
| 믿을 만한 두 출처의 통계가 다름 | 더 새로운 숫자를 고름 | 둘 다 + 날짜 + 맥락 |
| 정책이 연중에 바뀜 | 새 정책으로 덮어씀 | 둘 다 적용 기간과 함께 기록 |

- **"더 새롭다"와 "맞다"는 다릅니다.** 어느 값이 맞는지는 질문이 묻는 기준 시점에 달려 있습니다. 그래서 최신 값을 자동으로 고르지 않습니다.
- 개정은 덮어쓰기가 아니라 **유효한 값이 하나 더 생긴 것**입니다.
- 스키마에 값이 들어갈 칸이 하나뿐이면 모델은 어느 하나를 골라 넣을 수밖에 없습니다.

      <li>형식은 고쳐지지만, 값 칸이 하나뿐인 <b>모양이 틀린 스키마</b>는 그대로입니다.</li>

### 13. 넘길까, 물을까, 풀까 (5.2)

위 2번과 11번의 상황들을 세 가지 응답으로 묶으면 외우기 쉽습니다. 기준은 고객의 기분이 아니라 **사유**입니다.

<div class="oa-cards">
  <div class="oa-card oa-card--hl"><span class="oa-card__icon">🤝</span><span class="oa-card__title">넘긴다</span>사람을 명시적으로 요청함<br>정책이 침묵하거나 모호함<br>워크플로가 막혀 진전이 없음</div>
  <div class="oa-card"><span class="oa-card__icon">❓</span><span class="oa-card__title">묻는다</span>조회 결과가 여러 건 일치함<br><b>요구사항 자체가 모호함</b> (행동하기 전에 확인)</div>
  <div class="oa-card"><span class="oa-card__icon">🔧</span><span class="oa-card__title">푼다</span>화가 났지만 해결할 수 있는 문제<br>부정적인 감정만 있는 경우</div>
</div>

위키는 사람이 루프에 들어오는 이유를 이렇게 정리합니다. 모델이 자신 없어서가 아니라 **그 결정이 시스템의 몫이 아니기 때문**입니다. 정책이 다루지 않는 일, 사람을 직접 찾는 요청, 시스템에 주어진 권한 밖의 일이 그렇습니다. 에이전트가 할 일은 그 경계를 알아보고 넘기는 것이고, 자율을 지키려고 정책을 지어내는 것이 아닙니다.

위키는 "사람에게 넘긴다"도 좋은 패턴을 틀린 상황에 쓰는 함정이 될 수 있다고 적습니다. 넘기는 것이 **항상 즉시는 아니라는** 것입니다.

| 상황 | 위키가 적는 대응 |
|---|---|
| 맥락이 이미 충분하다 | 이관을 제안하거나 맞는 곳으로 연결 |
| 맥락이 전혀 없다 | 겨냥한 질문 **하나**를 먼저 |
| 화가 났지만 해결할 수 있다 | 인정하고 해결 |

둘째 줄은 위 2번의 "사람을 요청하면 조사부터 하지 않고 바로 넘깁니다"와 결이 다릅니다. 위키는 어떤 문제에서 이 구분이 나왔는지까지는 적지 않았습니다. 답안의 기본 축은 공식 가이드대로 **명시적 요청 → 즉시 이관**으로 두고, 문제가 "맥락이 하나도 없어 어디로 넘길지조차 정할 수 없다"는 조건을 줄 때만 질문 하나가 먼저일 수 있다고 알아 둡니다. 질문 하나를 하는 것과 문제를 직접 풀어 보려고 조사를 시작하는 것은 다릅니다.

### 14. 좋은 패턴, 틀린 상황 (5.1, 5.5)

| 패턴 | 맞는 상황 | 틀린 상황 → 대신 할 일 |
|---|---|---|
| 케이스 사실 블록 | 금액·날짜·ID 같은 **정확한 거래 사실** | 긴 이야기의 흐름을 이어 가야 할 때 → 점진적 요약 |
| 스키마 강제 | 형식이 깨진 출력 | 값의 의미가 틀렸거나 스키마 모양 자체가 틀렸을 때 (위 12번) |
| 확신도 점수 | 보정한 뒤 검토 물량을 어디로 보낼지 정하기 | 규칙 준수 보장 → 게이트 (레슨 5) |

위 1번과 Q4의 "요약 대신 케이스 사실 블록"은 정확한 값이 요약에 녹아 사라지는 상황의 답입니다. 위키는 반대 방향의 함정도 듭니다. 지켜야 할 것이 숫자가 아니라 긴 서사의 연속성이면 점진적 요약이 맞는 도구입니다. 문제가 "무엇이 사라졌는가"를 어떻게 적었는지 봅니다.

### 15. 코드베이스는 키워드 목록이 아니라 그래프로 읽는다 (5.4)

위 4번과 8번은 긴 탐색에서 컨텍스트를 **지키는** 방법이었습니다. 위키는 그 앞 단계인 **어떻게 돌아다닐지**를 따로 정리합니다. 먼저 지금 하려는 일이 셋 중 무엇인지 정합니다.

| 모드 | 문제의 모습 | 맞는 패턴 |
|---|---|---|
| 구조 이해 | "파일 800개에 걸친 인증을 파악하라" | 진입점(로그인·토큰·미들웨어)을 Grep → 그 파일을 읽음 → import와 호출을 따라가며 지도를 조금씩 넓힘 |
| 호출자 전부 찾기 | "함수가 래퍼를 거치며 다른 이름으로 불린다" | 래퍼·라이브러리 모듈을 **먼저** 읽음 → 노출된 이름과 별칭을 모두 나열 → 별칭마다 Grep |
| 장애 디버깅 | "엔드포인트가 간헐적으로 500을 낸다" | 고정 계획이나 무작정 펼치기가 아니라 증거를 따라가는 **적응형** 분해 |

<ol class="oa-flow">
  <li><strong>진입점</strong>요청이 들어오는 곳</li>
  <li><strong>인터페이스</strong>기반 클래스·공통 설계</li>
  <li><strong>import·호출자</strong>누가 쓰는가</li>
  <li><strong>구현</strong>실제 코드 경로</li>
  <li><strong>테스트</strong>기대 동작</li>
</ol>

작업 순서는 **Search → Read → Trace → Modify → Test**입니다. 전부 먼저 읽어 두기, 키워드 하나를 Grep하고 나온 조각만 믿기는 둘 다 오답입니다.

`/compact`에 대해서도 하나를 더 분명히 합니다. **`/compact`는 스크래치패드를 대신 써 주지 않습니다.** 그래서 순서가 중요합니다.

<ol class="oa-flow">
  <li><strong>탐색</strong>한 단계 조사</li>
  <li><strong>스크래치패드 기록</strong>정확한 발견을 파일에</li>
  <li><strong>단계 요약</strong>다음 단계로 넘어가기 전</li>
  <li><strong>/compact</strong>필요할 때만</li>
  <li><strong>계속</strong>압축 뒤 스크래치패드를 다시 읽음</li>
</ol>

"중요한 것이 나오면 적어 둬"처럼 모델 판단에 맡기지 않고 **"단계가 끝날 때마다 스크래치패드를 갱신한다"**로 규칙을 고정합니다. 단계마다 처음부터 다시 탐색하기, 구조화된 상태 없이 중단 뒤 재개하기도 오답으로 나옵니다.

### 16. 둘 다 맞아 보일 때의 기준

위키의 동률 깨기 규칙은 한 문장입니다. **쓸모 있는 정보를 가장 많이 남기고 맥락을 가장 적게 덜어 내는 쪽, 그리고 파이프라인에서 가장 일찍 손쓰는 쪽**을 고릅니다.

| 남기는 것 | 지켜지는 정보 |
|---|---|
| 날짜 | 시간에 따른 의미 |
| 여러 값 | 개정 이력 |
| 구조화 요약 | 낡은 도구 결과 없이 대화의 내용만 |
| 인터페이스부터 읽기 | 코드의 구조 |

이 도메인의 오답은 대개 서로 다른 두 상태를 하나로 뭉칩니다. 실패와 0건, 형식이 맞는 것과 내용이 맞는 것, 넘기기와 묻기와 풀기를 구분해 남기는 선택지가 정답 쪽입니다.

## 설계 리뷰 문제 대비

"고객 지원 에이전트, 환불·삭제 툴 포함 전부 넘김, `except: pass`" 같은 코드의 개선점 5가지:

1. 고위험 툴을 무제한 → HITL 경유 또는 별도 에이전트로 분리
2. HITL 없음 → 승인 워크플로
3. `except: pass` → 구조화 에러로 Claude에 알림
4. `max_iterations` 없음 → 상한
5. 감사 로그 없음 → user_id / action / tool / outcome 기록

## 핵심 정리

- 큰 창 ≠ 잘 찾음. 중반 정보를 놓친다(Lost in the Middle). 중요한 건 앞·뒤에.
- 이력이 커지면 컴팩션(오래된 것 요약 + 최근 유지). 대규모 탐색은 scratchpad + manifest.
- 매번 다른 부분을 참조하는 대량 질의는 RAG + Sonnet. RAG의 생명은 검색 Recall.
- 조사 결과는 출처 + 공개일을 세트로.
- 에스컬레이션은 불확실성·권한·이상, 관찰 가능한 사실로. 자기 보고 confidence 임계값은 오답, 쓰려면 보정.
- Fail-fast(송금) / Fail-safe(UI) / Retry(5xx·429). HITL은 승인·리뷰·개입·공동편집, 승인 대기엔 타임아웃.
- 최소 권한, 감사 로그(누가·언제·무엇을·어떻게), SLO로 계속 측정.
- 가이드 보완: 숫자와 날짜는 케이스 사실 블록에 따로 보존한다. 사람을 명시적으로 요청하면 바로 넘긴다. 에러는 부분 결과와 함께 올리고, 정확도는 유형별·필드별로 본다. 엇갈린 출처는 날짜와 함께 둘 다 남긴다.
- 스터디 가이드 보완: 오류는 일시적·검증·비즈니스·권한으로 나누고, "0건"과 "접근 실패"를 구분해 올린다. 일시적 실패는 서브에이전트가 1~2회 로컬 복구한 뒤 올린다. 부피는 상류 에이전트가 구조화 데이터로 줄이고, 핵심 발견은 입력 맨 앞에 둔다. 에이전트별 상태 파일과 manifest로 중단 뒤 재개한다. 충돌은 분석 에이전트가 표시하고 코디네이터가 조정한다.
- 합격자 위키 보완: 시간에 따라 값이 여러 개인 사실은 스키마에 여러 값 + 날짜로 담고 최신 값을 자동으로 고르지 않는다. 응답은 사유에 따라 넘기기·묻기·풀기로 나눈다. 코드는 진입점에서 시작해 그래프로 따라가고, `/compact` 전에 스크래치패드를 먼저 쓴다. 동률이면 정보를 가장 많이 남기는 쪽.
