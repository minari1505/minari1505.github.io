> 이 레슨은 2주(약 60시간) 공부로 843/1000점을 받은 합격자의 후기와 학습 위키를 분석한 글이에요. 출처는 Hong Chu의 [Medium 후기](https://medium.com/@yeesun.chu/how-i-passed-the-claude-certified-architect-foundations-cca-f-exam-in-2-weeks-6b967e6effb4), 같은 저자의 Reddit 글, 그리고 [CCA-F LLM Wiki](https://github.com/hong-chu/claude-certified-architect-foundations-llm-wiki)(CC BY 4.0)예요. 개인의 경험담이라 공식 자료는 아니에요. 문장을 옮기지 않고 풀어서 정리했어요.

## 학습 목표

- 2주 합격자가 **어디에서 점수가 올랐는지** 파악하기
- 후기에서 **따라 할 수 있는 공부 방법**만 골라내기
- 문제를 풀 때 쓰는 **근본 원인 의사결정 트리**와 **절대 정답이 아닌 선택지** 익히기
- 무료 모의고사 사이트의 특징을 알고 **언제 무엇을 풀지** 정하기
- 평일 2시간 · 주말 4시간 기준의 **2주 플랜 모델** 세우기

## 한눈에 보는 흐름

이 레슨을 한 문장으로 줄이면: **"정답이 뭐지?"가 아니라 "왜 이 계층에서 고치는 게 맞지?"를 묻기 시작하면 점수가 올라요.**

## 1. 2주 합격자는 무엇이 달랐나

<div class="oa-eli">
  <span class="oa-eli__head">🩺 쉽게 말하면</span>
  <p>증상마다 약 이름을 외우는 것과 <b>병의 원인을 진단하는 법</b>을 배우는 것의 차이예요. 문제마다 답을 외우던 때는 점수가 제자리였고, 원인을 찾는 법을 익히자 처음 보는 문제도 풀렸어요.</p>
</div>

합격자는 전통적인 소프트웨어 엔지니어가 아니었어요. 퀀트 트레이딩 · 데이터 과학 · 프로덕트 분석 배경이고, Claude를 매일 쓰긴 했지만 체계적으로 배운 적은 없었다고 해요. 2주 동안 약 60시간을 썼어요.

  <div class="oa-bar"><span>공부 방식을 바꾼 뒤</span><span class="oa-bar__track"><span class="oa-bar__fill" style="width:82%"></span><span class="oa-bar__val">꾸준히 820 이상</span></span></div>
  <div class="oa-bar"><span>공식 모의고사 (이틀 전)</span><span class="oa-bar__track"><span class="oa-bar__fill" style="width:95%"></span><span class="oa-bar__val">약 950</span></span></div>

  <p class="oa-bars__caption">후기에 적힌 점수예요(1,000점 만점, 합격선 720). 첫 모의고사는 쉬운 세트였는데도 76.7%였다고 해요.</p>

눈여겨볼 점은 두 가지예요.

- **문제를 더 풀어서 오른 구간은 작아요.** 720~750에서 780까지는 서서히 올랐고, 820 이상으로 뛴 것은 **공부 방식을 바꾼 뒤**예요.
- **공식 모의고사(약 950)보다 실전(843)이 낮았어요.** 후기도 공식 모의고사를 "쉬움"으로 분류해요. 공식 모의고사 점수를 실전 예상 점수로 쓰면 안 돼요.

### 무엇을 바꿨나

비슷해 보이는 두 문제의 답이 다른 이유를 설명하지 못하던 시점에, 질문을 바꿨다고 해요.

기능을 벼락치기해서 오른 게 아니라, **시험이 원하는 사고방식**을 익혀서 올랐다는 것이 후기의 결론이에요. 시나리오 문제는 고장 난 에이전트 시스템과 그럴듯한 해결책 네 개를 주고, 좋은 아키텍트가 실제로 고를 하나를 묻기 때문이에요.

## 2. 따라 할 수 있는 공부 방법

<div class="oa-eli">
  <span class="oa-eli__head">🧳 쉽게 말하면</span>
  <p>여행 가방을 쌀 때 처음엔 다 넣었다가, 떠나기 전날 <b>정말 쓸 것만 남기죠.</b> 노트도 모의고사를 볼 때마다 덜어 내서, 시험 전날에는 헷갈리는 것만 남아 있어야 해요.</p>
</div>

<ol class="oa-flow">
  <li><strong>먼저 조사</strong>다른 사람들의 후기에서 중요한 주제와 함정 파악</li>
  <li><strong>공식 가이드 정독</strong>추상적인 항목은 AI에게 예시로 풀어 달라고 하기 (약 1주)</li>
  <li><strong>모의고사 반복</strong>틀린 문제를 AI와 분석</li>
  <li><strong>노트 다이어트</strong>1~2회 풀 때마다 더 얇은 판으로</li>
  <li><strong>공식 모의고사</strong>마지막에, 준비 상태 확인용</li>
</ol>

| 단계 | 합격자가 한 일 | 내가 가져갈 것 |
|---|---|---|
| **조사** | 전체 시간의 1/3쯤을 실전 전에 조사와 이해에 씀 | 문제부터 풀지 않고 시험이 무엇을 묻는지 먼저 파악 |
| **공식 가이드** | 커뮤니티 글은 참고, **공식 시험 가이드가 기준점** | 가이드의 각 task를 "예시로 설명해 줘"라고 AI에게 물어 이해로 바꾸기 |
| **오답 분석** | 틀린 문제를 캡처해 AI에게 무엇을 놓쳤는지 분석 요청 | 정답이 맞는 이유 + **내 답이 그럴듯했지만 틀린 이유** 둘 다 적기 |
| **노트** | 모의고사 8회 동안 노트를 4번 다시 씀 | 이미 아는 것은 삭제. 비교 · 헷갈리는 개념 · 반복되는 실수만 남기기 |
| **개인 위키** | 질문할 때마다 쌓이는 LLM Wiki를 만들어 AI에게 퀴즈를 내게 함 | 정리본을 AI에 주고 "퀴즈 내 줘, 틀리면 가르쳐 줘"로 활용 |
| **마무리** | 시험 이틀 전 공식 모의고사 | 공식 모의고사는 아껴 두었다가 마지막에 |

> 후기는 **이해가 암기보다 훨씬 중요하다**고 여러 번 강조해요. 타사 문제 은행은 품질 편차가 있고 Anthropic의 실제 지침과 어긋나는 해설도 있어서, 원칙을 배우는 용도가 아니라 **기억을 다지는 용도**로 썼다고 해요.

## 3. 후기가 꼽은 원칙

<div class="oa-eli">
  <span class="oa-eli__head">🚦 쉽게 말하면</span>
  <p>"조심해서 운전하세요"라는 표지판보다 <b>과속 방지턱</b>이 확실하죠. 꼭 지켜져야 하는 것은 부탁하지 말고 구조로 막아요. 이 감각 하나가 여러 원칙의 뿌리예요.</p>
</div>

| 원칙 | 뜻 | 시험에서는 |
|---|---|---|
| **더하지 말고 제약하기** | 도구 · 에이전트 · context window를 더 키우는 것은 거의 항상 오답 | "더 많이 / 더 크게" 선택지는 먼저 지워요 |
| **프롬프트는 안내하고, 시스템은 강제한다** | 금전 · 규정 준수 · 순서처럼 반드시 지켜져야 하는 규칙은 코드나 훅으로 | "프롬프트에 강조해서 적는다"는 필수 규칙의 답이 아니에요 |
| **가장 앞단의 계층을 고치기** | 오답 대부분은 타당한 해결책을 파이프라인의 너무 늦은 단계에 적용 | 같은 문제를 더 일찍 막는 선택지를 골라요 |
| **실패 유형에 맞는 해결책** | 모호한 규칙 → 명시적 기준 / 일관성 없는 출력 → few-shot / 잘못된 JSON → 스키마 / 형식은 맞는데 내용이 틀림 → 의미 검증 | 증상에 이름을 붙이면 답이 정해져요 |
| **기준은 규칙을 설명하고, 예시는 경계를 가르친다** | 판단이 들쭉날쭉하면 추상 규칙을 하나 더 쓰는 것보다 예시가 효과적 | "지시를 더 자세히"와 "예시 추가"가 같이 나오면 증상을 봐요 |
| **상태를 뭉뚱그리지 않기** | "도구 실패"와 "아무것도 못 찾음"은 다른 상태 | 실패를 빈 결과로 돌려주는 선택지는 오답 |
| **느낌이 아니라 정책으로 넘기기** | 감정이나 모델의 확신도가 아니라 정책 · 워크플로 트리거로 에스컬레이션 | "고객이 화났으니 상담원 연결"은 오답 |
| **압축하지 말고 결정에 필요한 맥락을 보존하기** | 좋은 요약은 짧은 글이 아니라 목표 · 제약 · 사실 · 가정 · 날짜 · 출처 · 미해결 질문 · 이미 내린 결정이 남은 글 | 요약 과정에서 수치나 날짜가 사라지는 선택지를 의심해요 |
| **지시는 제자리에** | Claude Code의 설정은 종류마다 있어야 할 곳이 다름 | Rule = 정책 · Command = 버튼 · Skill = 워크플로 · CLAUDE.md = 항상 켜짐 · MCP = 외부 도구와 데이터 |

합격자가 남긴 한 줄 요약은 이래요. **모델만 믿지 말고, 모델을 둘러싼 시스템을 설계하라.** 그래서 "프롬프트를 미세 조정하자"나 "더 신중하라고 말하자"가 답인 경우는 거의 없어요.

## 4. 문제를 푸는 절차 — 근본 원인 의사결정 트리

<div class="oa-eli">
  <span class="oa-eli__head">🚰 쉽게 말하면</span>
  <p>바닥에 물이 샐 때 걸레질(뒤에서 수습)보다 <b>수도꼭지를 잠그는 것</b>(앞에서 차단)이 먼저예요. 선택지 네 개가 다 도움이 될 것 같으면, 물이 새기 시작하는 곳에 가장 가까운 것을 골라요.</p>
</div>

위키가 모의고사 오답을 분석해 만든 절차예요. 시험이 묻는 것은 "어떤 답이 도움이 될 것 같은가"가 아니라 **"어떤 수정이 가장 이르고 안전한 계층에서 근본 원인을 고치는가"**예요.

<ol class="oa-flow">
  <li><strong>실패 유형에 이름 붙이기</strong>정의 · 예시 · 스키마 · 검증 · 컨텍스트 · 도구 경계 · 분해 · 출처 · 에스컬레이션</li>
  <li><strong>표에서 고칠 곳 찾기</strong>아래 10가지</li>
  <li><strong>타이브레이커</strong>둘 다 그럴듯하면 정보를 더 많이 보존하고 더 일찍 작동하는 쪽</li>
</ol>

| # | 문제의 원인이… | 고칠 곳 | 자세히 |
|---|---|---|---|
| 1 | 도구 · 에이전트의 **경계가 불분명** | 도구 이름 변경 · 분리, 접근 범위 축소 | [레슨 4](/courses/cca-f-exam-prep/04-tool-design-and-mcp/) |
| 2 | **모호한 규칙 · 정의** | 명시적 기준 | [레슨 3](/courses/cca-f-exam-prep/03-prompts-and-structured-output/) |
| 3 | 알려진 규칙의 **일관성 없는 적용** | few-shot 예시 | 레슨 3 |
| 4 | **모호한 변환** | 입력 → 출력 예시 | 레슨 3 |
| 5 | **형식이 깨진** 구조화 출력 | `tool_use` + JSON schema | 레슨 3 |
| 6 | 구조는 맞는데 **값이 틀림** | 의미 검증 + 구체적 오류를 담은 재시도 | 레슨 3 |
| 7 | **위험하거나 필수인 순서** | 코드 게이트 · 훅. 금전 · 규정 · 되돌릴 수 없는 일은 도구 내부에서 강제 | [레슨 5](/courses/cca-f-exam-prep/05-agent-architecture/) |
| 8 | **길고 잡음 많은 컨텍스트** | 구조화된 사실 보존, 출력 다듬기, 스크래치패드 | [레슨 6](/courses/cca-f-exam-prep/06-context-and-reliability/) |
| 9 | **중복되거나 비효율적인 작업** | 작업 시작 전에 분해하고 범위를 나누기 | 레슨 5 |
| 10 | **신뢰 · 출처 누락** | 주장 · 출처 · 날짜 매핑 보존 | 레슨 6 |

### 좋은 패턴, 틀린 상황

올바른 기법도 엉뚱한 실패 유형에 쓰면 오답이에요.

| 기법 | 맞는 상황 | 틀리는 상황 |
|---|---|---|
| **스키마** | 구조가 깨질 때 | 의미가 틀릴 때, 스키마 모양 자체가 잘못됐을 때(시점별 · 다중 값) |
| **subagent** | 범위가 파악된 뒤 | 범위를 모를 때 → 진입점부터 탐색 |
| **case facts 블록** | 정확한 거래 사실 | 긴 서사의 흐름 → 점진적 요약 |
| **사람에게 넘기기** | 정책 공백, 명시적 요청 | 풀 수 있는데 고객이 답답해할 뿐일 때 → 공감하고 해결 |
| **`@import`** | 파일 정리 | 로드량 줄이기 → 경로별 규칙(`paths`) |

### 외워 둘 진단 한 줄

- 도구가 **목록에 없다** → 설정 · 등록 문제. 도구가 **있는데 안 쓰인다** → 설명(description) 문제.
- **system prompt를 바꾼 직후** 도구 선택이 틀어졌다 → system prompt 문구를 고쳐요(도구 설명이 아니라).
- 심각도 판정이 들쭉날쭉하다 → 숫자 기준만이 아니라 **등급별 구체적 예시**.
- 위 절차로도 안 갈리면 → 답은 대개 원칙을 **복원**하는 쪽이에요. 제약하고, 강제하고, 구분하고, 구조화하는 선택지.

## 5. 절대 정답이 아닌 선택지

<div class="oa-eli">
  <span class="oa-eli__head">🧹 쉽게 말하면</span>
  <p>객관식에서 정답을 찾는 것만큼 <b>오답을 먼저 지우는 것</b>이 빨라요. 아래 여섯 가지 모양이 보이면 일단 지우고 시작해요.</p>
</div>

<div class="oa-cards">
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">➕</span><span class="oa-card__title">더 추가하기</span>도구를 더, 에이전트를 더, context window를 더 크게, "신중하게"라는 문장을 더</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🙏</span><span class="oa-card__title">강제 대신 부탁</span>필수 규칙을 프롬프트에 적기, 순서를 few-shot으로 강제하기</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">😠</span><span class="oa-card__title">감정 · 확신도로 넘기기</span>고객이 화나서, 모델 확신도가 낮아서 에스컬레이션. 후보가 여럿일 때 추측하기</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🫥</span><span class="oa-card__title">오류 뭉개기</span>실패를 빈 결과로 반환, 정상적인 빈 결과를 재시도, 오류를 삼키거나 스택 트레이스를 그대로 전달</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">✅</span><span class="oa-card__title">검증 건너뛰기</span>"스키마를 통과했으니 맞다", 구체적 오류 없이 그냥 재시도</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🧩</span><span class="oa-card__title">모양이 안 맞는 도구</span>밤새 돌릴 대량 작업에 동기 API, 열린 작업에 도구 강제, 바뀐 점을 알리지 않고 세션 재개</div>
</div>

여기에 하나 더 있어요. **"모델을 fine-tuning한다"**는 이 시험에서 답이 아니에요. 아키텍처 시험이라 쓸 수 있는 수단은 프롬프트 · 도구 · 컨텍스트 · 오케스트레이션이에요.

> 예외도 기억해요. few-shot 예시 2~4개는 형식이나 판단이 일관되지 않을 때의 **올바른 추가**예요. 맞는 것을 맞는 자리에 더하는 것은 괜찮아요.

## 7. 2주 플랜 모델 (평일 2시간 · 주말 4시간)

<div class="oa-eli">
  <span class="oa-eli__head">🗺️ 쉽게 말하면</span>
  <p>등산 계획은 정상 시각에서 <b>거꾸로</b> 짜죠. 시험 이틀 전 공식 모의고사, 그 전 주말들에 시간 재는 모의고사를 먼저 박아 두고, 남은 평일에 개념과 오답 복습을 채워요.</p>

## 정리

- 2주 합격의 핵심은 문제 수가 아니라 **질문을 바꾼 것**이에요: "왜 이 계층에서 고치는 게 맞지?"
- 공부 순서는 **공식 가이드 → 모의고사 → 오답 분석 → 노트 다이어트 → 공식 모의고사**예요.
- 문제를 풀 때는 **실패 유형에 이름 붙이기 → 고칠 곳 찾기 → 정보를 더 보존하고 더 일찍 작동하는 쪽**.
- "더 추가하기", "부탁하기", "감정으로 넘기기", "오류 뭉개기", "검증 건너뛰기", "fine-tuning"은 먼저 지워요.
- 시간 재는 모의고사는 주말에, 평일에는 읽기와 오답 복습만 해요. 모의고사 시간만큼 **분석 시간**을 잡아요.
- 공식 모의고사는 마지막에 보고, 그 점수를 실전 예상 점수로 믿지 않아요.
