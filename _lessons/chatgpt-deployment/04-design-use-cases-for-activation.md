## 학습 목표

- 후보 유스케이스를 **배포 목표**에 비추어 평가하기
- **활성화 준비된(activation-ready)** 유스케이스의 특징 알아보기
- 가치·준비도·의존성 리스크로 **활성화 우선순위** 정하기
- 선택한 워크플로의 **성공 신호(success signal)** 정의하기
- 활성화 요구사항·의존성·리스크를 찾고 **Use Case Activation Plan** 만들기

## 1. 사례 고객: Northstar Home

강의 전체에서 쓰는 가상의 사례예요. 파트너 **Silverline Advisory**가 성장 중인 홈서비스 회사 **Northstar Home**을 돕고 있어요. 리더들은 성공 계획을 승인했고, 소수의 고가치 워크플로부터 켜고 싶어 해요. 그런데 각 팀이 낸 아이디어의 수준이 들쭉날쭉해요.

| 팀 | 아이디어 | 첫인상 |
|---|---|---|
| 고객 지원 매니저 | 승인된 정책으로 응대 가이드 초안 작성 | 구체적 👍 |
| 현장 운영 리더 | 기술자 노트 요약 + 후속 조치 식별 | 꽤 구체적 |
| 영업 운영 | 계정 담당자의 갱신 브리프 준비 | 가치 큼, 소스 확인 필요 |
| HR | 직원 정책 질문에 답하기 | 민감 주제 경계 필요 |
| 재무 | 월말 차이(variance) 설명 지원 | 가능성 있음 |
| 한 지역팀 | "모든 생산성 업무에" ChatGPT | 너무 넓음 ⚠️ |

Northstar Home에 필요한 건 "전부 켜기"가 아니라 **올바른 워크플로·사용자·증거로 시작하는 계획**이에요.

## 2. 유스케이스 활성화란?

<div class="oa-eli">
  <span class="oa-eli__head">🎹 쉽게 말하면</span>
  <p>학교에 새 피아노가 들어왔다고 해서 모두가 아무 곡이나 치게 두면 시끄럽기만 하죠. "<b>합창부 반주자 3명</b>이 <b>다음 달 공연곡</b>을, <b>음악 선생님 확인</b>을 받으며 연습한다"처럼 정해야 실력이 늘었는지도 알 수 있어요.</p>
  <p>활성화 = 좋은 아이디어를 <b>정해진 사용자가 시도·검토·개선할 수 있는 구체적 워크플로</b>로 바꾸는 것. 그렇지 않으면 "기능 배포"가 돼서, 사용자는 접근권만 받고 뭘 해야 할지 몰라요.</p>
</div>

| 워크스페이스 준비도가 묻는 것 | 유스케이스 활성화가 묻는 것 |
|---|---|
| 어떤 사용자·접근·소스·거버넌스를 검증? | 첫 사용자가 **어떤 워크플로**에 ChatGPT를 쓰나? |
| 어떤 소스·앱이 필요할 수 있나? | 그 워크플로에 ChatGPT가 알아야 할 **비즈니스 맥락**은? |
| 검토·에스컬레이션 기대는? | 출력을 사용 전 **어떻게 검토**하나? |
| 무엇이 Ready·Blocked·Deferred? | 어떤 워크플로가 **지금 켤 만큼** 준비됐나? |
| 준비 결정은 누가? | 워크플로 성공·피드백·이슈·다음 행동은 누가? |

### 활성화 준비된 유스케이스가 담는 것

대상 워크플로 · 사용자 그룹 · **상호작용 방식**(협업 / 위임 / 행동 수행) · 기대 산출물 · 비즈니스 결과 · 필요한 맥락·소스 · 앱·도구·신원·권한·승인·행동 경계(해당 시) · 준비도 가정 · 사람 검토 기대 · 초기 모니터링 방법 · 잘 안 될 때 후속 조치 오너.

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">❌ 약한 유스케이스</span>
    <ul>
      <li>"ChatGPT로 재무 생산성 향상."</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✅ 활성화 준비된 유스케이스</span>
    <ul>
      <li>"재무 매니저가 승인된 보고 패키지·이전 코멘터리·재무 가이드로 <b>사람이 검토하는 월간 차이 코멘터리 초안</b>을 작성해, 첫 활성화 기간에 더 일관되고 쉽게 준비한다."</li>
    </ul>
  </div>
</div>

### 기능이 아니라 "업무 순간"으로 정의

요약·초안·분석·조사는 **기능 라벨**이지 워크플로 정의가 아니에요.

| 기능 위주 | 워크플로 위주 |
|---|---|
| 요약 | 지원 리드가 승인된 티켓 내보내기로 **주간 티켓 테마**를 요약해 에스컬레이션 리뷰에 사용 |
| 초안 | HR 코디네이터가 승인된 직무 요건·매니저 노트로 **사람이 검토하는 온보딩 체크리스트** 초안 작성 |
| 분석 | 운영 분석가가 사고 로그를 비교해 **사람이 검토하는 근본 원인 요약** 초안 작성 |
| 조사 | 계정 담당자가 승인된 계정 노트·공개 자료로 **고객 미팅 브리프** 준비 |

### 협업형 vs 위임·행동형 워크플로

<div class="oa-vs">
  <div class="oa-vs__good">
    <span class="oa-vs__label">🤝 협업형 (collaborative)</span>
    <ul>
      <li>사용자가 ChatGPT와 단계별로 함께 일하고, 맥락 선택과 출력 적용에 직접 관여</li>
      <li>예: 지원 리드가 정책으로 가이드 초안 → 검토 → 직접 적용</li>
      <li>신원: 사용자 본인 계정. 워크플로·검토 오너 지정</li>
      <li>후속 행동은 사용자가 결정·수행</li>
    </ul>
  </div>
  <div class="oa-vs__bad">
    <span class="oa-vs__label">🤖 위임·행동형 (delegated / action-taking)</span>
    <ul>
      <li>여러 단계 결과를 ChatGPT Work·Workspace Agent·ChatGPT app(강의 기준)에 맡기고, 맥락 조회·행동까지 수행</li>
      <li>예: 지원 운영 에이전트가 사례·정책을 찾아 가이드를 쓰고 지원 시스템에 후속 작업 생성</li>
      <li>앱/에이전트 오너, 사용자 vs 에이전트 소유·공유 인증, 역할 접근 정의 필요</li>
      <li>허용 읽기·쓰기, 확인 지점, 사람 검토, 모니터링, 에스컬레이션을 <b>활성화 전에</b> 정의</li>
    </ul>
  </div>
</div>

연결 앱·에이전트·외부 행동이 없는 표준 워크플로라면 신원·권한·승인·행동 칸을 비워 두지 말고 **"해당 없음(Not applicable)"** 으로 적어요.

## 3. 유스케이스 품질 6기준

좋은 유스케이스는 **사용자가 할 일 · 고객이 개선하려는 결과 · 책임 있게 지원하기 위한 조건** 세 가지를 연결해요. 완벽할 필요는 없지만 **평가할 만큼 명확**해야 해요.

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">🛠️</span><span class="oa-card__title">Workflow-specific</span>업무 과정이 명확히 정의됐나?</div>
  <div class="oa-card"><span class="oa-card__icon">👥</span><span class="oa-card__title">User-specific</span>대상 그룹이 이름 있고 현실적인가?</div>
  <div class="oa-card"><span class="oa-card__icon">🎯</span><span class="oa-card__title">Outcome-aligned</span>배포 목표를 지원하나?</div>
  <div class="oa-card"><span class="oa-card__icon">📚</span><span class="oa-card__title">Context-supported</span>워크스페이스·지식 소스·맥락이 준비됐거나 가깝나?</div>
  <div class="oa-card"><span class="oa-card__icon">🔁</span><span class="oa-card__title">Repeatable</span>습관과 학습이 생길 만큼 자주 일어나나?</div>
  <div class="oa-card"><span class="oa-card__icon">📏</span><span class="oa-card__title">Measurable</span>초기 활동·품질·피드백·개선을 관찰할 수 있나?</div>
</div>

판정은 네 가지: **활성화 / 좁히기 / 보류 / no-go(당분간 안 함)**. 예: "모두를 위한 법무 Q&A"는 **좁혀서** "법무 운영 담당자가 승인 자료로 사람이 검토하는 접수 요약 초안 작성"으로. 고객 대면 응답 워크플로는 가치가 커도 검토 기대·소스 오너·고객 영향 경계가 미해결이면 **보류**.

Silverline이 Northstar 아이디어를 다듬은 결과:

| 처음 | 활성화 준비 버전 |
|---|---|
| "고객 지원에 ChatGPT" | 지원 팀 리드가 승인된 에스컬레이션 정책으로 복잡한 사례의 **사람 검토 응대 가이드** 초안 작성, 매니저·품질 검토자 피드백 |
| "현장 운영에 ChatGPT" | 지역 운영 코디네이터가 기술자 노트를 후속 조치로 요약, **배정 전 매니저 검토** |
| "직원 질문에 ChatGPT" | HR 운영이 **승인된 HR 주제**에 한해 정책 답변 초안 테스트, 민감·모호 질문은 HR 검토·에스컬레이션 |

## 4. 활성화 우선순위 정하기

<div class="oa-eli">
  <span class="oa-eli__head">🍳 쉽게 말하면</span>
  <p>요리를 처음 배울 때 "가장 멋진 요리"(코스 요리)보다 <b>재료가 다 있고, 맛을 바로 볼 수 있는</b> 계란말이부터 시작하죠. 가치가 크더라도 재료(소스)·레시피(검토 기준)가 없으면 나중으로 미뤄요.</p>
</div>

### 비즈니스 가치 — 방향성으로

최종 ROI 증명이 아니라 **초기 증거를 낼 가능성**을 봐요: **잠재 영향**(속도·일관성·품질·역량·리스크·경험), **업무 빈도**(습관·패턴이 생길 만큼 자주?), **사용자 관련성**(대상 사용자가 그 고통을 느끼나?).

### 활성화 준비도 — 지금 켤 수 있나

| 준비 영역 | 강한 상태 |
|---|---|
| 비즈니스 맥락 | 필요한 문서·가이드·시스템·보고서가 식별됨 |
| 워크스페이스 준비 | 셋업 가정·접근 경로·소스 필요가 보임 |
| 앱·에이전트·행동 준비 | 오너, 활성화, 인증 모델, 권한, 허용 행동, 승인 지점, 검토·모니터링·에스컬레이션 식별 |
| 지식 소스 | 오너 있고, 자료가 준비됐거나 거의 준비 |
| 접근 | 첫 코호트와 접근 가정이 알려졌거나 검증 오너가 있음 |
| 이해관계자 | 워크플로·비즈니스·소스·검토 오너가 지정 또는 확인 가능 |
| 출력 검토 가능성 | 적절한 오너가 볼 수 있고 구조화돼 검토 가능 |
| 모니터링·피드백 | 사용·피드백·이슈·품질 신호를 볼 경로 있음 |
| 이슈 에스컬레이션 | 접근·소스·워크플로·검토 문제 담당자 있음 |
| 거버넌스·미해결 의존성 | 검토 기대·소스 경계·허용 사용이 보이고, 열린 항목은 관리가능/블로킹/연기로 분류 |

> 가치가 중간이어도 준비도가 강한 워크플로가, 가치는 높지만 의존성이 미해결인 워크플로보다 **더 좋은 첫 활성화**일 수 있어요. 예: 고객 대면 응답 초안보다 내부 **티켓 테마 요약**이 위험이 낮고 검토도 쉬워요.

### 1–3점 간단 점수

| 요인 | 1 | 2 | 3 |
|---|---|---|---|
| 비즈니스 가치 | 낮거나 불명확 | 중간 | 배포 목표와 연결된 강한 가치 |
| 활성화 준비도 | 열린 질문 많음 | 일부 검증 필요 | 준비 또는 거의 준비 |
| 의존성 리스크 | 높거나 블로킹 | 오너 있는 관리 가능 리스크 | 낮거나 완화됨 |
| 첫 순서 적합도 | 너무 넓거나 어긋남 | 좁히면 가능 | 강한 첫 활성화 후보 |

<div class="oa-eli">
  <span class="oa-eli__head">⚠️ 블로커는 평균 내지 마세요</span>
  <p>점수는 판단을 <b>돕는</b> 도구지 대신하지 않아요. 소스 오너·검토 기대·거버넌스 승인·접근·에스컬레이션 오너가 미해결이면, 총점이 좋아 보여도 그 의존성을 <b>조건 또는 no-go 리스크</b>로 다뤄요. 시험 평균이 90점이어도 필수 과목 하나가 0점이면 통과 못 하는 것과 같아요.</p>
</div>

| **지원 응대 가이드** — 팀 리드가 승인 정책·에스컬레이션 규칙·지식베이스로 사람 검토 가이드 초안 | 3 · 3 · 2 · 3 | **먼저 시작**. 사람 검토·에스컬레이션 기대를 출시 전에 명시 |
| **현장 후속 요약** — 매니저가 기술자 노트로 사람 검토 후속 요약 | 2 · 2 · 2 · 2 | **다음 준비**. 노트 품질·사용 기대·매니저 검토 확인 후 |
| **갱신 브리프** — 매출 운영 매니저가 승인 계정 노트·서비스 이력으로 | 3 · 2 · 2 · 2 | **다음 준비**. 승인 입력 소스·검토 오너 확인 후 |
| **일반 생산성** — 전 직원, 모든 워크플로 | 1 · 1 · 1 · 1 | **보류**. 코호트·워크플로·산출물·신호가 너무 넓음 |

강한 근거 문장은 **왜 중요한지 · 왜 지금 준비됐는지 · 남은 의존성과 오너 · 첫 순서에 맞는 이유 · 무엇을 좁히거나 미룰지**를 담아요. 가장 크거나 가장 눈에 띄는 요청이 아니라 **가치·준비도·거버넌스·측정 가능성의 균형**이 첫 활성화를 정해요.

## 5. 성공 신호 정의하기

성공 신호 = 선택한 워크플로가 **의도대로 켜지고 쓰이는지** 보여 주는 실용적 증거. 장기 ROI 증명이 아니라 **계속·조정·중단·확대 준비**를 결정하도록 돕는 것.

### 결과에서 출발해 관찰 가능한 신호로

| 워크플로 | 의도한 결과 | 초기 성공 신호 |
|---|---|---|
| 법무 운영이 승인 자료로 접수 요약 초안 | 일관성↑, 접수 검토 마찰↓ | 변호사들이 1차 분류에 쓸 만큼 요약이 완성됐다고 보고 |
| 지원 리드가 주간 티켓 테마 요약 | 반복 이슈를 더 일찍 파악 | 주간 요약이 주요 테마를 찾고 올바른 오너에게 전달 |
| HR이 직무 가이드로 온보딩 체크리스트 초안 | 일관성↑, 준비 노력↓ | 샘플 체크리스트가 필수 범주를 포함하고 사용 전 검토됨 |

## 6. 선택한 유스케이스를 활성화 준비시키기

가치 있다고 준비된 게 아니에요. **대상 사용자, 필요 맥락, 검토 기대, 의존성, 리스크, 오너, 다음 행동**을 알 때 준비된 거예요.

### 출시 요구사항

대상 사용자 접근 · 소스·지식 접근 · 앱/에이전트/신원/권한/승인/행동 경계(해당 시) · 워크플로 오너·매니저 지원 · 첫 워크플로용 안내 · 모니터링·피드백·이슈 경로와 오너 · 사람 검토·허용 사용 안내 · 출력 검토 기대 · 에스컬레이션 오너. (전체 enablement 계획은 이 코스 범위 밖 — 다음 팀이 필요한 것만 식별)

### 의존성 유형

| 유형 | 예 |
|---|---|
| 워크스페이스·접근 | 대상 사용자는 정했지만 접근·프로비저닝 미확인 |
| 지식 소스·앱 | 승인 문서 접근 불가, 소스 오너 불명확 |
| 신원·권한·행동 | Work·Agent·앱을 쓰는데 오너, 인증 방식, 역할 접근, 허용 행동, 승인 지점이 불명확 |
| 승인·거버넌스 | 사람 검토 기대, 허용 사용 경계 미확인 |
| 워크플로 오너 | 출력 품질·피드백 검토·후속 조치 담당 없음 |
| 사용자 준비·지원 | 첫 사용 전 기본 안내·지원 경로 필요 |

모든 의존성이 블로커는 아니에요. 오너·행동·일정이 분명하면 관리 가능. 의존성 노트에는 **무엇 · 왜 중요 · 활성화 전 필수? · 오너 · 다음 행동 · go / 조건부 go / 당분간 no-go** 를 적어요.

결정은 절대 모호하면 안 돼요 — **조건 · 오너 · 시점 · 다음 행동**을 이름으로. 그리고 **보류는 실패가 아니라 고객 보호**예요.

### 사례: 바이오제약 규제 업무팀

워크플로: 규제 담당자가 승인된 내부 가이드·이전 서신·검토자 노트로 **사람이 검토하는 응답 요약** 초안 작성.

| 요구 | 준비 메모 |
|---|---|
| 대상 사용자 접근 | 첫 코호트는 정했지만 접근 경로 확인 필요 |
| 소스 접근 | 내부 가이드·이전 서신 사용 가능성 — 소스 오너 검증 필요 |
| 검토 기대 | 사용 전 규제 워크플로 오너가 검토 |
| 허용 사용 경계 | 포함·제외·연결 가능한 정보 확인 필요 |
| 성공 신호 | 채택, 요약 완성도, 검토 품질, 이슈 패턴 |
| 피드백 경로 | 소스 공백·불명확 출력·검토 이슈 신고처 지정 필요 |

판단: **1–2개 요구 확인 후 활성화** — 구체적·가치 있고 내부 검토용 초안이지만, 승인 소스로 제한하고 검토 기대를 먼저 확정. 반면 관련 아이디어 "**규제기관 응답 자동 발송**"은 외부 대면 행동이라 승인·거버넌스·에스컬레이션 요구가 훨씬 커서 **당분간 no-go**.

## 정리

- 활성화 = 좋은 아이디어를 **정해진 사용자가 시도·검토·개선할 구체적 워크플로**로 바꾸는 일. 기능 배포가 아니다.
- 유스케이스는 **업무 순간**으로 정의하고, 협업형인지 위임·행동형인지 구분한다(행동형은 오너·인증·허용 행동·승인 지점까지).
- 품질 6기준: 워크플로·사용자 특정, 결과 정렬, 맥락 지원, 반복성, 측정 가능성 → 활성화 / 좁히기 / 보류 / no-go.
- 우선순위는 **가치 × 준비도 × 의존성 리스크 × 첫 순서 적합도**. 점수는 판단 보조일 뿐, **블로커는 평균 내지 않는다**.
- 성공 신호는 **채택 · 산출물 · 결과 · 검토/모니터링** 네 가지를 함께, 증거 출처·오너·시점·돕는 결정까지.
- 활성화 전 요구·의존성·리스크·오너를 정리하고 **Ready / 조건부 / 좁히기 / 보류** 중 하나로 분명히 결정. 보류는 고객을 지키는 선택.
