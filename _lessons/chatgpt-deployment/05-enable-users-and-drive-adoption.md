## 학습 목표

- ChatGPT 도입을 막는 **흔한 장벽** 알아보기
- 사용자 그룹·승인된 워크플로별 **enablement(역량 지원) 요구사항** 정의하기
- 실제 워크플로 도입을 돕는 **enablement 활동** 고르기
- 목적·가치·행동 기대·지원 경로를 설명하는 **도입 커뮤니케이션** 계획하기
- 워크플로 변화를 굳히는 **챔피언·지원 구조** 만들기
- 도입 리스크와 완화책을 찾고 **User Enablement and Adoption Plan** 완성하기

## 1. 사례 고객: Rowan Retail

파트너 **Brightline Advisory**(가상)가 소매기업 **Rowan Retail**을 돕고 있어요. 활성화 계획(레슨 4)을 마치고 첫 워크플로 두 개를 골랐어요.

| 사용자 그룹 | 승인된 워크플로 |
|---|---|
| 고객 지원 리드 | 승인된 지원 노트·정책 가이드로 **사람이 검토하는 사례 해결 요약** 초안 작성 |
| 지역 운영 매니저 | 승인된 비즈니스 맥락·매니저 노트로 **주간 매장 성과 브리프** 초안 작성 |

워크스페이스 준비는 순조롭지만 **도입은 보장되지 않아요.** 누구는 신났고, 누구는 "내 업무에 어떻게 쓰지?" 하고, 매니저는 명확한 기대치를, 챔피언은 시연할 예시를, IT·리스크 담당자는 승인 소스 사용·검토·에스컬레이션 준수를 원해요.

## 2. 승인된 워크플로에서 출발하기

<div class="oa-eli">
  <span class="oa-eli__head">🚲 쉽게 말하면</span>
  <p>자전거를 선물받았다고 바로 등교길에 타지는 않아요. "<b>학교 가는 이 길</b>에서, <b>헬멧 쓰고</b>, <b>이 교차로에선 내려서 건너기</b>"를 누군가 함께 연습시켜 주고, 처음 며칠은 부모님이 확인해 줘야 습관이 돼요.</p>
  <p>enablement도 같아요. "ChatGPT 기능 소개"가 아니라 <b>특정 업무 순간</b>에 무엇을 하고, 무엇을 확인하고, 막히면 어디에 묻는지를 익히게 하는 거예요.</p>
</div>

흔한 실수는 "프롬프트 세션, ChatGPT 데모, 오피스아워가 필요해"처럼 **제품 주제**로 시작하는 것. 출발점은 활성화 계획에서 승인된 **워크플로**예요. 워크플로마다 물어볼 질문:

| 질문 | Rowan Retail 지원 워크플로 |
|---|---|
| 사용자가 ChatGPT로 완료할 일은? | 사례 해결 요약 초안 |
| 어떤 경험·상호작용 방식? (협업형 / 위임형) | 확인 안 됐으면 **가정하지 말고 열린 질문으로 기록** |
| 첫 사용자 그룹·코호트는? | 2개 파일럿 지역의 지원 리드 |
| 기댈 승인 맥락·소스는? | 승인된 사례 노트·정책 가이드 |
| 산출물은? | 요약 + 빠진 정보 + 후속 질문 |
| 사람 검토 기대는? | 고객 기록 추가·내부 공유 전 리드가 검토·수정 |
| 질문·이슈는 어디로? | 도입 지원 채널 → 워크플로 오너 |
| 매니저가 강화할 행동은? | 마감 시 체크리스트 사용, 검토 후 사용 |

## 3. 대상 그룹과 학습 요구사항

### 학습 요구사항 6(+1) 영역

| 영역 | 지원 요약 워크플로 예시 |
|---|---|
| **워크플로 목적** | 재작업을 줄이고 더 명확한 요약 준비 |
| **승인된 사용 패턴** | 승인된 노트·가이드로 초안 작성. 첫 초안을 최종으로 취급하지 않기 |
| **실무 적용 가이드** | 정책에 따라 승인·비식별 처리된 맥락만 사용. 요약 + 빠진 정보 + 후속 질문 요청 |
| **기대 행동** | 사용 전 검토·수정·검증 |
| **사람 검토·허용 사용** | 정확성·어조·완결성·고객별 결정은 리드 책임. **누가 받아도 되는지**도 확인 |
| **지원·에스컬레이션 경로** | 워크플로 질문은 도입 채널, 민감·정책 질문은 워크플로 오너 |
| **+ 승인 맥락·데이터 경계** | 어떤 소스·문서·시스템이 승인됐고 무엇을 피해야 하는지 |

> 실습을 계획했다면 해결 안 된 **접근·입력·권한·환경 의존성**도 enablement 요구사항으로 적어요. "준비됐겠지"라고 가정하지 않아요. 그리고 이 표는 기능 목록이 아니라 **한 그룹이 한 워크플로를 쓰는 방법**이에요.

## 4. Enablement 활동 설계

<div class="oa-eli">
  <span class="oa-eli__head">🏊 쉽게 말하면</span>
  <p>수영은 강당 강의 한 번으로 못 배워요. <b>왜 배우는지 듣고 → 코치 시범을 보고 → 얕은 물에서 연습하고 → 혼자 해 보다 막히면 코치에게 묻고 → 벽에 붙은 동작 그림을 보며 반복</b>해야 몸에 붙죠. 하나의 큰 이벤트보다 <b>작은 활동의 조합</b>이 효과적이에요.</p>
</div>

| 사용자 필요 | 활동 | 왜 맞나 |
|---|---|---|
| 워크플로가 왜 중요한지 이해 | 출시 브리핑·매니저 주도 킥오프 | 비즈니스 목적·팀 기대와 연결 |
| 실제 동작 보기 | **역할별 데모** | 정확한 작업·맥락·검토·지원 경로 시연 |
| 안전하게 연습 | **가이드 실습** | 승인된 예시로 실사용 전 자신감 |
| 활성화 후 도움 | 오피스아워·지원 채널 | 실제 질문이 생길 때 적시 지원 |
| 업무 순간 리마인더 | 잡 에이드·체크리스트·프롬프트 스타터·**워크플로 가이드** | 기대 행동을 쉽게 반복 |
| 매니저의 강화 | 매니저 가이드·토킹 포인트 | 공지가 아니라 코칭 |

| 활동 | 잘 맞는 곳 | 주의 |
|---|---|---|
| 워크숍 | 공통 이해 + 진행자 있는 연습 | 워크플로를 너무 많이 다루면 넓어짐 |
| 가이드 세션 | 실제 작업을 지원받으며 완료 | 승인된 예시 입력·안전 사용 가이드 필요 |
| 데모 | 빠르게 명확성·자신감 | 일반 기능 탐색 말고 역할 업무로 |
| 오피스아워 | 시도 후 실시간 도움 | 열린 제품 Q&amp;A 말고 워크플로 장애 중심 |
| 셀프서비스 자료 | 필요한 순간 반복 가이드 | 짧고 역할별로 |
| 매니저 강화 | 도입·검토 행동 코칭 | "많이 쓰라고 독려" 말고 명확한 기대 |
| 챔피언 예시 | 신뢰받는 동료의 실전 예시 | 승인된 예시 + 장애 보고 경로 필요 |

### 역할별 예시

| 대상 | 예시 | 초점 |
|---|---|---|
| 지원 리드 | 승인 노트·정책으로 요약 초안 | 요청 구조, 초안 검토, 민감 사례 에스컬레이션 |
| 지원 매니저 | 요약 품질 검토, 피드백 패턴 파악 | 행동 강화, 품질 신호 모니터링 |
| 챔피언 | **좋은 요약 1개 + 수정이 필요한 요약 1개** 시연 | 좋은 행동 모델링, 흔한 질문 응대 |
| 운영 매니저 | 승인 노트로 주간 매장 브리프 초안 | 빠진 정보는 **지어내지 말고 찾아내기**, 정확성 검토, 수신자 확인 |
| Enablement 리드 | 예시를 짧은 가이드·실습으로 패키징 | 실용적·재사용 가능하게 |

역할별 예시는 "ChatGPT가 있다는 건 알아"와 "**내 일에 어떻게 쓰는지 알아**" 사이의 거리를 좁혀요.

### 실습은 현실적으로, 하지만 안전하게

좋은 실습 = 짧은 워크플로 시나리오 + **승인됐거나 가상의 입력** + 명확한 과제 + 검토 단계 + 지원·에스컬레이션 리마인더 + "내 일상에 어떻게 적용될까?" 성찰 질문. 예: 가상 사례 노트로 요약 → 체크리스트로 검토 → 빠진 정보 찾기 → 에스컬레이션 여부 판단.

**마케팅 캠페인 실습 예시 (강의 기준)**

| 요소 | 내용 |
|---|---|
| 과제·입력 | 승인된 가상 전략 브리프·브랜드북 → 캠페인 방향 선택과 근거 설명 |
| 출력·검토 | 편집 가능한 소셜 디자인·이메일 미리보기를 브리프에 비춰 검토(일관성, 근거 없는 주장). **게시·발송은 실습 범위 밖** |
| 준비·오너 | 라이브 전 참가자의 경험·앱·입력 파일 접근 확인. 강사가 자료 공유 가능 여부 확인·리허설 |

### 4가지 목표

<ol class="oa-flow">
  <li><strong>인지 (Awareness)</strong>무엇이 출시되고, 누구 대상이며, 왜 중요한지</li>

  <li><strong>강화 (Reinforcement)</strong>예시·리마인더·FAQ·피드백 요청</li>

대상마다 필요한 목표·시점이 달라요: 임원은 간결한 가치·진척, 주 사용자는 실무 지침, 매니저는 강화 기대, 챔피언은 예시와 지원 정보.

| 워크플로가 연습할 만큼 구체적이지 않음 | 업무 순간·산출물·검토 단계로 다시 정의 |
| 대상이 너무 넓거나 불명확 | 첫 코호트를 이름으로 지정 |
| 매니저가 강화할 준비 안 됨 | 매니저 가이드·토킹 포인트 |
| 기능만 가르치고 업무 순간은 안 가르침 | 역할별 데모·가이드 실습으로 교체 |
| 승인 맥락·소스 경계 불명확 | 승인 소스 목록과 "피해야 할 것" 명시 |
| 사람 검토 강조 부족 | 체크리스트·강화 메시지 |
| 챔피언의 가이드·시간·에스컬레이션 부족 | 매니저 승인 시간, 에스컬레이션 경로 |
| 피드백은 모으지만 오너가 검토 안 함 | 피드백 리뷰 오너·주기 지정 |

다음 행동은 **목적 · 오너 · 시점 · 기대 증거/산출물**과 함께. 라이브 실습을 계획했다면 미해결 접근·셋업·승인 자료 확인도 다음 행동으로 적어요.

## 정리

- 도입은 **행동 변화** 문제. 플랫폼 접근은 문을 열 뿐, 워크플로 기반 enablement가 사용자를 그 문으로 걷게 한다.
- 출발점은 제품 기능이 아니라 **승인된 워크플로**. 경험·상호작용 방식이 미확정이면 열린 질문으로 기록.
- 대상(사용자·매니저·챔피언·L&amp;D·IT/리스크·스폰서)별로 **이해·연습·검토·에스컬레이션**할 것을 정의.
- 큰 교육 한 번보다 **역할별 데모 + 가이드 실습 + 짧은 가이드 + 매니저 강화 + 오피스아워**의 작은 조합. 실습은 현실적이되 승인·가상 데이터로.
- 커뮤니케이션은 **인지 → 이해 → 참여 → 강화**, 그리고 왜·무엇·소스·검토·어디로 다섯 가지에 답한다.
- 챔피언은 **신뢰·워크플로 근접성**으로 뽑고 과부하 금지. 피드백은 오너가 검토하고 가이드 갱신까지 이어져야 루프가 닫힌다.
- 도입 워크스트림 표로 계획이 일반 교육 달력으로 흐르지 않게 점검하고, 리스크마다 완화책·오너·시점을 둔다.
