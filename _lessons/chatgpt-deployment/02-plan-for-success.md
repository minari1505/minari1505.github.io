## 학습 목표

- ChatGPT 기회의 **출시 범위(launch scope)** 를 정하고, 고객의 AI 비전을 **구체적 우선 워크플로**에 연결하기
- **출시 팀**을 꾸리고 역할별 책임(누가 결정·검증·검토·에스컬레이션하나)을 분명히 하기
- 성공 기준을 **실용적인 KPI**와 증거 출처로 바꾸기
- **준비도·거버넌스 가정**을 워크플로 행동에 연결해 기록하기
- **30일 출시 계획**을 짜고, 워크스페이스 셋업·활성화 팀에 넘길 **핸드오프 노트**로 묶기

## 한눈에 보는 코스 흐름

<ol class="oa-flow">
  <li><strong>비전·출시 범위</strong>무엇을 먼저, 30일 동안 무엇을 증명?</li>
  <li><strong>출시 팀·운영 리듬</strong>누가 무엇을 소유하나</li>
  <li><strong>KPI·증거 지도</strong>어떤 증거로 다음 결정을?</li>
  <li><strong>준비도·거버넌스</strong>책임 있게 출시하려면 무엇이 참이어야?</li>
  <li><strong>30일 계획 → 핸드오프</strong>준비 → 활성화 → 리뷰 → 결정</li>
</ol>

레슨 1의 **Deployment Brief**가 "출발해도 되나?"였다면, 이번 코스의 결과물 **Deployment Success Plan**은 "첫 30일을 어떻게 굴릴까?"예요.

## 1. 계획 원칙 — 모든 행동을 무언가에 "연결"하기

<div class="oa-eli">
  <span class="oa-eli__head">🎒 쉽게 말하면</span>
  <p>수학여행 준비물 목록에 "수영복"이 있다면 이유가 있어야 해요 — "둘째 날 물놀이 일정"이라는 <b>일정</b>, "담임 선생님이 확인"이라는 <b>담당자</b>와 연결돼 있죠. 이유 없이 끼어든 항목은 짐만 무겁게 해요.</p>
  <p>성공 계획도 같아요. <b>모든 출시 행동</b>은 워크플로 · 오너 · KPI · 준비도 의존성 · 거버넌스 가정 · 다음 결정 중 <b>최소 하나</b>에 연결돼야 해요.</p>
</div>

체크리스트는 "어떤 일이 있나"를 알려 주지만, 성공 계획은 **왜 중요한지, 누가 맡는지, 어떤 증거를 만드는지, 다음 결정에 어떻게 도움이 되는지**를 설명해요. 행동을 추가하기 전 네 가지를 물어요.

<div class="oa-cards">
  <div class="oa-card"><span class="oa-card__icon">🛠️</span><span class="oa-card__title">어떤 워크플로를 돕나?</span></div>
  <div class="oa-card"><span class="oa-card__icon">🙋</span><span class="oa-card__title">누가 소유하나?</span></div>
  <div class="oa-card"><span class="oa-card__icon">📊</span><span class="oa-card__title">어떤 증거·결정을 돕나?</span></div>
  <div class="oa-card"><span class="oa-card__icon">🔐</span><span class="oa-card__title">준비도·거버넌스 가정을 검증하나?</span></div>
</div>

어디에도 연결되지 않으면 출시 계획 밖이거나 나중 작업이에요. 예: 법무 운영 워크플로 출시 계획에 들어간 "**일반 AI 뉴스레터 만들기**"가 가장 먼저 의심해야 할 항목이에요.

## 2. 배포 비전과 출시 범위

### 좋은 배포 비전의 6요소

**비즈니스 우선순위 · 우선 워크플로 · 첫 사용자 그룹 · 의도한 개선 · 첫 기간의 성공 증거 · 거버넌스 기대**

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">❌ 약한 비전 (그냥 접근권)</span>
    <ul>
      <li>"법무팀에 ChatGPT를 출시한다."</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✅ 강한 비전 (워크플로 연결)</span>
    <ul>
      <li>"법무 운영팀이 일상적인 <b>공급업체 계약 접수(intake)</b>에 대해 <b>사람이 검토하는 요약</b>을 준비하도록 돕고, 첫 30일 동안 요약 품질·사용자 신뢰·검토 효율에 대한 증거를 모은다."</li>
    </ul>
  </div>
</div>

### 비전 → 워크플로 다리 놓기

고객은 보통 "AI로 법무 운영을 더 빠르고 일관되게"처럼 넓게 말해요. 정상이에요. 이걸 활성화·지원·측정·통제할 수 있는 워크플로로 옮겨요.

| 질문 | 계획 답 (법무 운영 예시) |
|---|---|
| 어떤 비즈니스 우선순위? | 법무 운영 마찰 감소, 일관성 향상 |
| 먼저 켤 워크플로는? | 일상적인 공급업체 계약 접수 요약 |
| 누가 먼저 쓰나? | 정의된 법무 운영 코호트 |
| 무엇을 만들어 내나? | 사람이 검토하는 계약 접수 요약 |
| 진척의 증거는? | 요약 완성도, 검토 시간, 사용자 신뢰, 매니저 피드백 |
| 워크플로를 규정하는 거버넌스는? | 승인된 자료만 사용, 사람 검토, 민감 데이터 경계, 불확실 사례 에스컬레이션 |

### 출시 범위에 담을 것

첫 워크플로, 첫 코호트, **의도한 ChatGPT 경험과 지원 표면**(예: ChatGPT Chat / ChatGPT Work, 웹·모바일·데스크톱 — 강의 기준), 초기 부서, 고객 측 오너, 파트너 측 오너, 알려진 의존성, 첫 검증 기간, 필요한 비즈니스 맥락(승인 지식 소스·정책·시스템), 필요한 플러그인·앱·Workspace Agent·연결 도구와 접근·승인 조건, 검증할 거버넌스 기대, 측정 방식.

<div class="oa-eli">
  <span class="oa-eli__head">🎯 범위는 골디락스처럼</span>
  <p>너무 좁으면 쓸 만한 증거가 안 나오고, 너무 넓으면 오너십·측정·거버넌스를 놓쳐요. "<b>활성화할 만큼 좁고, 가치를 증명할 만큼 의미 있게.</b>"</p>
</div>

### 범위 표류(scope drift) 경고 신호

<div class="oa-cards">
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">➕</span><span class="oa-card__title">인접 워크플로 몽땅 추가</span>계약 요약에 조항 작성까지</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🏢</span><span class="oa-card__title">전 직원이 첫 그룹</span>통제된 출발 불가</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">⚙️</span><span class="oa-card__title">범위 확정 전 관리자 설정 논의</span>순서 뒤집힘</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">📢</span><span class="oa-card__title">일반 AI 교육 프로그램화</span>워크플로와 단절</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">📈</span><span class="oa-card__title">워크플로와 무관한 사용량 측정</span>로그인 수만 셈</div>
  <div class="oa-card oa-card--warn"><span class="oa-card__icon">🧾</span><span class="oa-card__title">거버넌스를 따로 떼어 놓음</span>실제 사용 방식과 분리</div>
</div>

테스트 질문: **"모든 출시 행동을 우선 워크플로·오너·KPI·준비도 의존성·거버넌스 가정·다음 결정 중 하나로 추적할 수 있나?"** 아니면 표류 중이에요.

## 3. 출시 팀과 운영 리듬

### 핵심 출시 팀

| 역할 | 소유하는 것 |
|---|---|
| **Executive sponsor** | 우선순위, 가시성, 임원 정렬 |
| **Business outcome owner** | 대상 워크플로의 성공, 첫 기간 후 출시 결정 |
| **Workflow owner / team lead** | 실무 사용자 필요, 워크플로 운영 방식 확인 |
| **Workspace owner / admin** | 접근, 설정, 워크스페이스 준비 결정 |
| **Champion (네트워크 리드)** | 동료 옹호, 초기 피드백, 실전 예시 (기술 셋업은 X) |
| **HR/L&D·enablement lead** | 사용자 준비 입력, 교육 의존성 |
| **IT·보안·법무·컴플라이언스·데이터** | 거버넌스, 소스 접근, 정책, 리스크 기대 검증 |
| **Partner deployment lead** | 출시 계획과 파트너 행동 조율 |

작은 부서 배포에서는 한 사람이 여러 역할을 맡아도 돼요. 다만 **책임은 보이게.** 흔한 실수는 **사람 이름만 적고 "결정"은 안 적는 것**. 각 역할이 무엇을 결정·검증·검토·에스컬레이션하는지 써야 해요. 핵심 질문 5가지: 워크플로는 누구? 준비도는? 거버넌스 검증은? 측정 리뷰는? 다음 결정은?

<div class="oa-vs">
  <div class="oa-vs__bad">
    <span class="oa-vs__label">❌ 약한 오너십 노트</span>
    <ul>
      <li>"고객팀과 파트너팀이 출시 활동을 협력한다."</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">✅ 강한 오너십 노트</span>
    <ul>
      <li>법무 운영 리드 = 워크플로 활성화 + 요약 품질 리뷰</li>
      <li>워크스페이스 관리자 = 접근 준비 + 승인 소스 검증</li>
      <li>컴플라이언스 = 활성화 전 민감 데이터 기대 검증</li>
      <li>파트너 배포 리드 = 30일 계획 조율 + 출시 리뷰 증거 준비</li>
    </ul>
  </div>
</div>

### 가벼운 운영 리듬

| 순간 | 목적 | 주요 참석 |
|---|---|---|
| **Kickoff** | 비전·범위·역할·첫 워크플로·결정 시점 확정 | 스폰서, 결과 오너, 워크플로 오너, 파트너 리드 |
| **셋업 준비 체크포인트** | 경험·표면, 워크스페이스·접근, 소스·제품 의존성, 요금제·지역 가용성, 관리자 활성화, 거버넌스 가정 | 워크스페이스 오너, IT·보안·법무, 파트너 리드 |
| **활성화 체크포인트** | 사용자, enablement 입력, 허용 사용 안내, 피드백·지원 경로 | 워크플로 오너, 챔피언, enablement 리드 |
| **초기 피드백 리뷰** | 실제로 써 보는지, 어떤 마찰이 있는지 | 워크플로 오너, 챔피언, 결과 오너 |
| **거버넌스·이슈 리뷰** | 소스 사용, 공유, 검토 행동, 에스컬레이션, 미해결 리스크 | 거버넌스 담당, 워크스페이스 오너 |
| **30일 리뷰** | KPI 증거로 계속·조정·확장·중단 결정 | 스폰서, 결과 오너, 워크플로 오너, 파트너 리드 |

## 4. 성공 기준을 KPI로

### 워크플로 결과에서 출발

목표는 "ChatGPT 사용량 늘리기"가 아니라 "정의된 그룹이 승인 자료로 유용하고 사람이 검토한 요약을 만들 수 있는지 시험하기"예요.

| KPI 범주 | 측정하는 것 |
|---|---|
| 채택 (Adoption) | 대상 사용자가 워크플로를 실제로 시도하나 |
| 참여 (Engagement) | 첫 노출 이후에도 계속 쓰나 |
| 워크플로 산출물 | 의도한 초안·요약·분석이 나오나 |
| 품질 | 완성도·유용성, 적절한 검토 |
| 효율 | 더 빠르거나 덜 부담스러운가 |
| 신뢰·정서 | 사용자·매니저가 계속 쓸 만큼 믿나 |
| 거버넌스 신호 | 검토·소스 사용·공유·에스컬레이션 규칙을 지키나 |

### 간단한 3단계 KPI 프로세스

<ol class="oa-flow">
  <li><strong>가치 동인 찾기</strong>고객에게 중요한 결과는?</li>
  <li><strong>기준선 세우기</strong>지금의 시간·품질·주기·만족도는?</li>
  <li><strong>개선 측정 계획</strong>30일 동안 변화를 어떻게 관찰?</li>
</ol>

기준선 데이터가 없어도 계획은 막히지 않아요. 검토자 추정, 샘플 출력 리뷰, 짧은 피드백 같은 **방향성 증거(directional evidence)** 를 모을 방법을 계획에 넣으면 돼요.

### 선행 신호 vs 후행 신호

<div class="oa-eli">
  <span class="oa-eli__head">🌱 쉽게 말하면</span>
  <p>화분에 씨를 심으면 <b>싹이 트는 것</b>(선행 신호)으로 "시작은 됐구나"를 알고, <b>열매가 열리는 것</b>(후행 신호)으로 "키울 가치가 있구나"를 알아요. 둘 다 봐야 해요.</p>
</div>

<div class="oa-vs">
  <div class="oa-vs__good">
    <span class="oa-vs__label">🌱 선행 (leading) — 출시가 움직이나?</span>
    <ul>
      <li>워크스페이스·코호트 합류</li>
      <li>enablement 완료</li>
      <li>대상 워크플로 시도</li>
      <li>매니저가 초기 행동 변화 관찰</li>
      <li>사람 검토·소스 사용 규칙 준수</li>
    </ul>
  </div>
  <div class="oa-vs__good">
    <span class="oa-vs__label">🍎 후행 (lagging) — 가치가 있나?</span>
    <ul>
      <li>작업 시간 감소</li>
      <li>일관성·품질 향상, 수정 횟수 감소</li>
      <li>이해관계자 신뢰 상승</li>
      <li>30일 동안 채택 강화</li>
      <li>계속·조정·확장·중단을 판단할 명확한 증거</li>
    </ul>
  </div>
</div>

### KPI는 "관찰 가능한 증거"에 묶기

각 KPI에는 **정의 · 데이터/피드백 출처 · 오너 · 리뷰 시점 · 한계(가정)** 가 있어야 해요. 출시 전에 고객 요금제·역할·워크플로에서 쓸 수 있는 워크스페이스 분석을 확인하고, KPI별로 필요한 증거와 연결해요.

<div class="oa-eli">
  <span class="oa-eli__head">⚖️ 소비량은 품질과 함께 봐야 해요</span>
  <p>ChatGPT Work처럼 크레딧 기반 과금(강의 기준)이라면, 사용량을 혼자 보지 말고 <b>같은 품질 기준을 통과한 결과물 1개당</b>으로 비교해요.</p>

### 거버넌스는 "보편 규칙"이 아니라 "검증할 가정"

데이터 민감도·허용 사용 경계, 사람 검토 기대, 소스·앱 승인, GPT·프로젝트·워크스페이스 공유(요약을 누가 받을 수 있나), PHI 같은 규제 데이터 제한, 첫 모션의 자동화·공유 제한, 법무·보안 리뷰, 모니터링·감사 요구, 이슈 에스컬레이션, 출력이 고객·시스템·결정에 영향 주기 전 승인… 앱·Company Knowledge·Workspace Agent·자동화가 엮이면 **가용성·관리자 활성화·권한·승인·데이터 경계를 확인할 고객 오너**를 이름으로 적어요.

### 거버넌스를 출시 계획에 연결하기

각 가정마다 **영향받는 워크플로 행동 · 검증 오너 · 시점 · 의존하는 출시 행동 · 30일 동안 볼 증거**를 적어요.

| 거버넌스 가정 | 워크플로 행동 | 오너 | 시점 | 출시 의존 | 리뷰 증거 |
|---|---|---|---|---|---|
| 승인된 계약 자료만 사용 | 접수 요약 초안 작성 | 법무 운영 오너, 컴플라이언스 | 활성화 전 | 승인 소스 안내와 함께 코호트 활성화 | 샘플 리뷰, 이슈 로그 |
| 사용 전 사람 검토 필수 | 요약을 법무 접수에 사용 | 워크플로 오너 | 활성화 전, 4주차 | 검토 가이드·체크리스트 배포 | 완료 체크리스트, 매니저 피드백 |
| 불확실·민감 사례는 에스컬레이션 | 특이 조항·민감 데이터 처리 | 법무·컴플라이언스 | 출시 전 | 에스컬레이션 경로·안내 설정 | 에스컬레이션 로그, 이슈 추세 |

### 에스컬레이션은 구체적 막힘 기준으로

막연한 불안이 아니라 **트리거 · 담당 · 기대 응답**을 적어요. 대상: 워크스페이스 관리자, IT·보안, 법무·컴플라이언스, OpenAI 계정·기술 지원, 파트너 리더십. 예: 미승인 자료 발견, 민감 데이터, 검토 기대 불명확, 앱·소스 접근 문제, 고객 결정에 영향 줄 품질 우려.

### 행동마다 붙일 7가지

**오너 · 의도한 결과 · 의존성 · 시점 · 성공 신호 · 관련 가정 · 결정/에스컬레이션 경로**

| 항목 | 예: "공급업체 계약 요약용 승인 자료 확인" |
|---|---|
| 결과 | 사용자가 첫 워크플로에 쓸 수 있는 자료를 앎 |
| 의존성 | 소스 승인, 민감 데이터 경계 가정 |
| 시점 | 1주차 또는 활성화 전 |
| 성공 신호 | 승인 소스 목록 문서화, 사용자 안내에 포함 |
| 에스컬레이션 | 승인이 불명확하면 법무·컴플라이언스로 |

### 4주차는 "결과 리뷰"가 아니라 구체적 질문으로

- 대상 코호트가 의도한 워크플로에 ChatGPT를 썼나?
- 요약이 사람 검토가 가능할 만큼 완성됐나?
- 소스 사용·사람 검토 규칙을 지켰나?
- 어떤 이슈·에스컬레이션 패턴이 보였나? (품질·가치를 **소비량·검토·재작업**과 함께)
- 계속? 조정? 확장? 중단?

## 정리

- 계획 원칙: **모든 출시 행동을 워크플로·오너·KPI·준비 의존성·거버넌스 가정·다음 결정 중 하나에 연결.**
- 비전은 6요소(우선순위·워크플로·코호트·개선·증거·거버넌스)로 구체화하고, 범위는 "활성화할 만큼 좁고 증명할 만큼 의미 있게". 범위 표류를 경계.
- 출시 팀은 이름보다 **결정**을 적고, 킥오프 → 셋업 → 활성화 → 피드백 → 거버넌스 → 30일 리뷰의 가벼운 리듬으로.
- KPI는 워크플로 결과에서 출발, **선행·후행 신호**를 함께, 각 KPI에 출처·오너·리뷰·한계. 소비량은 **합격 결과물당**으로, 분석은 채택 증거일 뿐.
- 거버넌스는 검증할 **가정**으로 적고 워크플로 행동·오너·시점·출시 행동에 연결. 접근 셋업 ≠ 컴플라이언스.
- 결과물 **Deployment Success Plan**은 다음 팀이 계획을 다시 하지 않아도 되도록 핸드오프 노트까지.
